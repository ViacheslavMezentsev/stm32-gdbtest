# Покрытие ожиданий DDTT

Уточните корень потребителя и путь подмодуля. Читайте `docs/ru/DDTT_COVERAGE.md` и
`docs/ru/PORTABLE_DDTT.md` относительно модуля; справочник API остаётся источником контрактов.

1. С автором сценария определите утверждение, проверяемую строку и смысл зелёного/красного.
   Число тестов не определяет число окрашенных строк. Составное условие не считается целиком
   проверенным только потому, что одна его часть связана с утверждением.
2. Составьте явную карту по примеру `examples/ddtt-coverage`. Якорь должен однозначно
   совпасть со строкой кода, не комментарием. Выберите среду hardware/emulator/host;
   старые карты без environment обозначают hardware. Прикладные карты оставьте потребителю.
3. Соберите ELF, выполните bind_map.py. Не меняйте исходники между сборкой и опытом.
   Для публичного отчёта до опыта создайте кампанию ddtt_provenance.py begin с картой,
   полным Git SHA и явными входами — код, сценарии, модель/конфигурация, шаблон карты.
   Владелец разрешает аппаратный запуск отдельно; сам экспорт не обращается к стенду.
4. Выполните выбранные сценарии в новой папке runs; сохраните FAIL/ERROR. Запечатайте кампанию
   seal. Не добавляйте старые результаты в новую кампанию и не исправляйте хеши ради экспорта.
5. tools/ddtt_coverage.py даёт локальную раскраску; tools/ddtt_report.py — переносимый
   комплект с источниками и ссылками на SHA. Команды — в PORTABLE_DDTT. В VS Code откройте
   корень потребителя и укажите LCOV выбранной среды. Не смешивайте hardware и emulator.
6. Проверьте не только зелёный пример: отсутствующее утверждение/ERROR должно дать UNKNOWN,
   ложное утверждение — FAILED, старый источник/карта — отказ со сбросом старого отчёта.
   Ручные результаты purpose=manual исключаются; prepare не является выполнением проверки.

UNKNOWN не превращается в ноль. Последний автоматический результат выбранной среды
определяет исход, включая отказ; не выбирайте прежний PASS. Проверяйте sidecar и исходный
сценарий: HTML не доказывает истинность задумки автора. Для публичного комплекта не копируйте
raw records/result/run и локальные пути. Публикация Pages — отдельное действие владельца;
аннотации CI не окрашивают постоянно обычный просмотр исходников GitHub.

Готовность: переносимый отчёт открывается из другой папки, ссылки ведут на проверенный SHA,
цвета объяснимы исходными утверждениями, отрицательный контроль работает. Сообщите реальные
границы среды и неподтверждённые связи; не создавайте привязки автоматически ко всем строкам.


## Условия применимости

Сверь [снимок допуска](../../docs/ru/DDTT_QUALIFICATION.md), environment, происхождение
и эпоху состояния. Исходный verdict сценария не переписывается: при нарушении или
неизвестности условия только зависимые утверждения карты получают UNKNOWN и не
экспортируются как нулевые строки LCOV. Независимые утверждения сохраняются.
При `[data]` используй квитанцию из records для связи с конкретной попыткой;
отсутствие обязательной записи — отказ анализа, не пустое измерение. Успешный
экспорт старого измерения не квалифицирует текущее состояние платы.

## Нейтральные примеры 0.5.x

Для logical-time/counter-cost/external-capture учитывай [границы примеров](../stm32-gdbtest-scenarios/references/neutral-workflows.md).
Модельные тики, время запроса GDB и временная опора fixture — разные свидетельства.
UNKNOWN анализа блокирует только зависимые утверждения; остальные сохраняются.
Не меняй исходный вердикт и не выдавай host за hardware. Прямого импорта учебных
scenario/analysis JSON в экспортёр нет: нужны согласованные связи и адаптация потребителя.
