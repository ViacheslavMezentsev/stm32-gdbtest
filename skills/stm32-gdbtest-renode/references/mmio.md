# MMIO: измерить обращения, затем проверить на цели

[English](mmio.en.md). Ресурс навыка stm32-gdbtest-renode; пути docs/tools/tests ниже
считайте от найденного корня модуля, даже если навык скопирован в другой проект.
Прочитайте docs/ru/MMIO.md и docs/ru/RENODE_PROBES.md перед опытом.

## 1. Условия и модель

Задайте один регистр/операцию, ожидаемое число чтений/записей и эффект по руководству MCU.
Фиксируйте ELF и SHA-256, сценарий, модель, версии GDB/Renode и способ подключения.
Используйте отдельный каталог результатов и собственный процесс Renode. Готовая учебная модель эффектов — `tests/mmio-renode` (внешний probe-маршрут). Примеры
`tests/renode-startup` и `tests/renode-cache` дают запуск/ELF, но не готовую универсальную
модель MMIO. Модель нужных регистров требуется подготовить и проверить отдельно.

Периферия должна журналировать callbacks без дополнительных чтений через GDB:
номер события, read/write, смещение, ширину, значение, состояние до/после. Реализуйте
независимые эффекты: WO отмечает любое чтение, W1C очищает только единичные биты,
read-to-clear возвращает старое и обнуляется, FIFO расходует элемент. Добавьте соседний
сигнальный регистр, чтобы заметить расширение доступа. Ошибка модели не равна bus fault.
Не трактуйте RAM по адресу периферии как модель устройства. Не заявляйте поддержку DMA,
если модель её не реализует. Инициализацию модели отделите от измеряемого окна.

## 2. Измерение через настоящий GDB

Работайте в основном потоке GDB с реальным ELF и действующими методами Target.
Перед каждой операцией восстановите модель, поставьте текстовые метки начала/конца
в GDB-журнал. `set debug remote 1` включает RSP-диагностику; после опыта отключите её.
Сохраните `info mem` и политику кеша. Не сбрасывайте чужую карту областей.

Сравните число обращений на трёх уровнях: метод, пакеты m/M/x/X, callbacks периферии.
Число пакетов и длина буфера не доказывают ширину транзакции. Отдельно исследуйте
nocache/cache и атрибут доступа 32; кеш может читать соседей, скрывать повторное чтение.
Проверьте также IDE watch/окна регистров: во время измерения исключите их обращения.

Минимальная матрица (только в изолированной модели):

| Случай | Что выявляет |
| --- | --- |
| read скаляра и структуры/массива | расширение обращения на соседей |
| write verify=True/False в WO | before даже при отключённой проверке |
| готовая маска и выражение reg OR mask в W1C | дополнительные чтения/RMW |
| два явных чтения RTC/FIFO | число и порядок разрушительных эффектов |
| битовое поле и изменяющийся LHS | скрытый RMW и повторное вычисление пути |
| 8/16/32, невыровненный доступ | фактические ширины callbacks; не обещание API |
| read/write в запрещённой области GDB | отказ до callback модели |
| исключение после доступа, короткий ответ | неизвестный эффект, отсутствие автоматического повтора |

Сначала проверьте саму модель на известной последовательности. В отрицательном контроле
задайте заведомо неверное ожидание числа обращений: анализ должен дать FAIL, не PASS.
Отдельно записывайте вердикт сценария и анализ журнала. Отсутствующий/неполный журнал —
UNKNOWN/ERROR анализа, не ноль обращений. Инъекцию исключения после реального эффекта
называйте инъекцией, не испытанием потери связи. Не создавайте скрытые повторы ради PASS.
После опыта проверьте cleanup и возможность нового запуска; завершайте только свои процессы.

## 3. Перенос на отладочную плату

Renode не подтверждает конкретный GDB-сервер и электрическую периферию. Предложите
минимальный аппаратный план для MCU пользователя: тот же участок сценария, документированные
регистры, независимый наблюдаемый эффект, допустимые воздействия и способ восстановления.
Уточните подключённые нагрузки и авторизацию записи до опыта; чтение RTC/FIFO тоже воздействие.
Не переносите опасные отрицательные тесты WO/невыровненных адресов на плату автоматически.
Не применяйте mass erase/option bytes или универсальный снимок всех регистров.

Сохраните разрешённую память и проверяемое исходное состояние, учитывайте DMA/RTOS и
периферию при halt. Для WO/W1C/FIFO восстановление задаётся устройством, не записью before.
Повторите минимальный положительный опыт, проверьте восстановление, сохраните FAIL/ERROR.
Не переносите результат на другой backend/версию/MCU без проверки. Если нет измерителя
транзакций, ограничьте вывод наблюдаемым эффектом, а не обещанием «ровно один доступ».
