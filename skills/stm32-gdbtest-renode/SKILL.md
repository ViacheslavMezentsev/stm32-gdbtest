# Быстрая песочница Renode

Найдите путь модуля и прочитайте `docs/ru/RENODE_PROBES.md`. Начинайте с готового примера
`tests/renode-startup`; для отложенной записи и ограниченной модели Flash — `tests/renode-cache`.
Выбери маршрут: [штатный backend](../../docs/guides/ru/RENODE.md) и `tests/renode-backend`
для обычных @case либо tools/renode_probe.py для экспертной модели. Это разные
запуски; probe не является приёмкой backend. debugpy в этот навык не входит.

1. Сформулируйте короткое утверждение и независимое ожидание: вход функции, изменение поля
   готового объекта, сохранение соседних байтов, отказ API/проверки. Запишите границу опыта.
2. Выберите готовую модель. Название MCU не означает поддержку ADC/DMA/Flash-контроллера.
   RAM по адресу регистра не воспроизводит устройство. Если свойства нет в модели, проверьте
   только логику либо предложите согласованный аппаратный опыт, не дописывайте фиктивный PASS.
3. Проверьте фактические Renode 1.17, GDB и его Python, ARM-компилятор. Не обновляйте инструменты
   автоматически. В Windows Docker исходники и сборку держите в одном volume; bind — для передачи.
4. Выполните команду нейтрального примера из руководства. Для своей задачи скопируйте минимум
   модели/ELF-сборки/сценария в согласованное место проекта. Проверьте стартовые SP/PC и Thumb,
   готовность объекта и наличие тела метода в ELF. Inline/оптимизация могут убрать вызов.
5. В штатном маршруте используй session/stand, target schema 3 и обычный runner.
   Самодостаточный REPL обязателен; внешние PythonPeripheral/includes не поддержаны
   первым backend. Для таких моделей используй tools/renode_probe.py с отдельными
   runs, явным ELF/model/scenario/map. GDB API
   вызывается только в основном потоке GDB. Произвольный call исполняет код и может зависнуть;
   его область воздействия должна быть известна, ожидания периферии в заглушке недопустимы.
6. Сначала короткий позитивный опыт, затем неверное ожидание или вход для отрицательного
   контроля. Проверяйте result.json, GDB/Renode log и cleanup; повторите запуск для проверки
   отсутствия оставшегося собственного сервера. Не подключайтесь к занятому внешнему endpoint.

Результат помечается emulator, аппаратные выводы из него не следуют. Сохраните исходный
FAIL/ERROR и входы. Для карты DDTT используйте отдельный навык coverage. При timeout сначала
разберите журнал/модель/готовность, не увеличивайте лимиты вслепую. Завершайте только собственные
процессы. Эмулятор можно пересоздать, но это не доказательство восстановления физического MCU.

Готовность: воспроизводимая команда, положительный и отрицательный исходы, сохранённые артефакты,
освобождённые ресурсы и понятный вывод, что можно перенести на плату и что ещё не проверено.

## Периферия и MMIO

Для счётчиков чтений/записей, WO/W1C/FIFO, скрытых обращений и границы backend прочитайте
[методику измерения MMIO](references/mmio.md) ([English](references/mmio.en.md)).
Она описывает журнал callbacks/RSP, отрицательный контроль и последующую проверку того же
участка на согласованной целевой плате. Эмуляция не является аппаратной приёмкой;
начиная с 0.5.0 используйте [mmio.read/write](../../docs/ru/api/mmio.md) и проверяйте обращения независимо по callbacks.

Для выбора готовой STM32-периферии или создания модели прочитайте
[ресурс периферии](references/peripherals.md) ([English](references/peripherals.en.md)):
REPL/IRQ/DMA, локальные зависимости, PythonPeripheral/C# и границы проверки.


## Исполнение API 3

В обычном def навигация и call блокируют до результата. В async def используй await
для reach/step/until/finish/reset/resume(sync=True)/call с первого вызова, включая
помощники. resume(sync=False), данные, точки, record/check и ret остаются немедленными.
wait и halt требуют await и конечного timeout; timeout wait не останавливает цель.
Доступ к цели возможен только после подтверждённой остановки. finally с await halt
не заменяет восстановление памяти/регистров и не завершает прерванный call.
Не используй execute в async и скрытые inferior calls в выражениях данных; вынеси
их в явный call. Обычный def не нужно превращать в async без живого окна.
[Контракт и миграция](../../docs/ru/LIVE_EXECUTION.md) описывают отказные пути.

## Практика состояния и порядка событий

Примени [приёмы и нейтральный пример](../stm32-gdbtest-scenarios/references/stateful-evidence.md):
следующая операция без reset, wrap и busy/complete, исходный FAIL, исправление,
повтор и полное восстановление объекта. Ресурс также задаёт границы переноса
на DMA, логическое время и внешние свидетели. Renode подтверждает модель, не плату.

## Нейтральные примеры (0.5.0 и новее)

Для гипотез о времени автомата и счётчиках используй [logical-time/counter-cost](../stm32-gdbtest-scenarios/references/neutral-workflows.md):
host сначала, затем ELF/GDB в Renode с исходными FAIL, повтором исправления и
восстановлением POD. Учебные тики не циклы MCU, время call на ПК не WCET.
External-capture из того же ресурса запускается только на host; его успешный прогон
не подтверждает Renode live-окно или реальные источники ROS/MCAP.

## Возможности 0.6.0

- Вызовы C++ (`this`, `signature`, `Pointer`/`Reference`, невиртуальные базы) и квоты журнала проверены в Renode на нейтральных ELF: `tests/renode-backend/run_cpp.py`, `run_journal.py`, `run_report_quota.py`.
- Внешний вход модели GPIO (`tests/modeled-gpio`) — единственный проверенный в 0.6.0 способ задать уровень на выводе; на плате такой вход требует внешнего источника сигнала.
- Точка останова внутри `call` проверена только в Renode.

[маршруты 0.6.0](../stm32-gdbtest-scenarios/references/release-060-routes.md) — пакеты A1–A6: команды, принимаемый исход, пары «правильно/неправильно».
