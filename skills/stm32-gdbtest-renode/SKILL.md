# Быстрая песочница Renode

Найдите путь модуля и прочитайте `docs/ru/RENODE_PROBES.md`. Начинайте с готового примера
`tests/renode-startup`; для отложенной записи и ограниченной модели Flash — `tests/renode-cache`.
Это внешний инструмент, не новый backend Target и не ручная отладка Python через debugpy.

1. Сформулируйте короткое утверждение и независимое ожидание: вход функции, изменение поля
   готового объекта, сохранение соседних байтов, отказ API/проверки. Запишите границу опыта.
2. Выберите готовую модель. Название MCU не означает поддержку ADC/DMA/Flash-контроллера.
   RAM по адресу регистра не воспроизводит устройство. Если свойства нет в модели, проверьте
   только логику либо предложите согласованный аппаратный опыт, не дописывайте фиктивный PASS.
3. Проверьте фактические Renode 1.17, GDB и его Python, ARM-компилятор. Не обновляйте инструменты
   автоматически. В Windows Docker исходники и сборку держите в одном volume; bind — для передачи.
4. Выполните команду нейтрального примера из руководства. Для своей задачи скопируйте минимум
   модели/ELF-сборки/сценария в согласованное место проекта. Проверьте стартовые SP/PC и Thumb,
   готовность объекта и наличие тела метода в ELF. Inline/оптимизация могут убрать вызов.
5. Используйте tools/renode_probe.py с отдельными runs, явным ELF/model/scenario/map. GDB API
   вызывается только в основном потоке GDB. Произвольный call исполняет код и может зависнуть;
   его область воздействия должна быть известна, ожидания периферии в заглушке недопустимы.
6. Сначала короткий позитивный опыт, затем неверное ожидание или вход для отрицательного
   контроля. Проверяйте result.json, GDB/Renode log и cleanup; повторите запуск для проверки
   отсутствия оставшегося собственного сервера. Не подключайтесь к занятому внешнему endpoint.

Результат помечается emulator, аппаратные выводы из него не следуют. Сохраните исходный
FAIL/ERROR и входы. Для карты DDTT используйте отдельный навык coverage. При timeout сначала
разберите журнал/модель/готовность, не увеличивайте лимиты вслепую. Завершайте только собственные
процессы. Эмулятор можно пересоздать, но это не доказательство восстановления физического MCU.

Готовность: воспроизводимая команда, положительный и отрицательный исходы, сохранённые артефакты,
освобождённые ресурсы и понятный вывод, что можно перенести на плату и что ещё не проверено.

## Периферия и MMIO

Для счётчиков чтений/записей, WO/W1C/FIFO, скрытых обращений и границы backend прочитайте
[методику измерения MMIO](references/mmio.md) ([English](references/mmio.en.md)).
Она описывает журнал callbacks/RSP, отрицательный контроль и последующую проверку того же
участка на согласованной целевой плате. Эмуляция не является аппаратной приёмкой;
публичный безопасный MMIO-интерфейс пока не реализован.

Для выбора готовой STM32-периферии или создания модели прочитайте
[ресурс периферии](references/peripherals.md) ([English](references/peripherals.en.md)):
REPL/IRQ/DMA, локальные зависимости, PythonPeripheral/C# и границы проверки.
