# Дорожная карта

Горизонт — конец 2026 года. Это порядок приоритетов, а не обещание дат или
разрешение на аппаратные операции/публикацию. Еженедельные действия — в TODO.

## Направление

Проверка работающей прошивки через отладчик на платах и в эмуляторах.
DDTT связывает замысел, сценарий и наблюдаемое поведение; условия пригодности
платы/сборки/стенда входят в интерпретацию свидетельств. PASS не означает
исправность всей платы, а неизвестность не превращается в нулевое покрытие.
Рабочее будущее имя — **hwlivetest**; переименование отдельно, репозиторий пока прежний.

## Выпуск 0.5.0 — принят 20.10.2026

Пакеты P1–P6 закрыты кампанией P5b на итоговом коммите `a7b0951`; ограничения — в
[итоге приёмки](docs/development/release-050-acceptance.md). Таблица ниже сохранена как план выпуска.

### План выпуска 0.5.0

| Пакет | Принято / реализовано | Осталось |
| --- | --- | --- |
| P1 | Переносимые отчёты DDTT, карта, навыки покрытия/Renode | Проверка совместимости на итоговом кандидате |
| P2 | memory/write, C++ preflight, MMIO/SVD и inspect | Общая регрессия API 3 и связей HIL |
| P3 | Async-диспетчер, resume(sync=False), await wait/halt/call и совместимый def | Финальная аппаратная матрица; прежние прогоны относятся к своим SHA |
| P4 | Нейтральный FPB/VTOR, Renode Windows/Linux, исследовательский F411 | Подтверждение публичного примера на выпускном SHA по возможностям MCU |
| DDTT | Снимок допуска, records/[data], независимый Renode-эталон, HSE-пилот и анализ сохранённых данных | Включение применимости в единую матрицу; не выдавать replay за новый HW PASS |
| P5 | Маршруты отдельных пакетов известны | Единая кампания Windows/Linux, Renode/QEMU, F030/F103/F401/F411/F429/AT32, потребители и восстановление |
| P6 | Основная документация и навыки существуют | Аудит всех навыков, устранение дублей/старых статусов, миграция/ТЗ/версии, release notes и приёмка владельцем |

[Матрица P5 и исходный кандидат](docs/development/release-050-acceptance.md) фиксируют
порядок: миграция потребителей → версия/финальный SHA (P6b-pre) → общая приёмка.

До P5 сверить незакрытые пункты старого архива с реализацией: не переносить
устаревшие флажки как новые требования и не считать их автоматически выполненными.
В частности, проверить актуальность долга по удалённому стенду, HAL F030 и Hardware CI.
В VERSIONING проверить перечень шести MCU (F103 не должен теряться или заменяться вторым F411).
Изменение кода после приёмки требует повторения затронутой части матрицы.

## Выпуск 0.6.0 — текущая цель

[План A0–A8](docs/development/release-060-plan.md): длительные сценарии и аудит,
сохранение ошибок/очистка, C++-вызовы, проверенные способы воздействий, первый реальный
внешний адаптер и пригодность DDTT. Накопленные материалы подготовки 0.5.1 сохраняются.
Сначала host/Renode Windows/Linux без плат, затем отдельная аппаратная приёмка шести
стендов по возможностям. Все расширения сопровождаются нейтральными примерами,
негативными контролями, документацией и навыками; текущие методы не меняются одним планом.

## После 0.5.0 — ориентировочно ноябрь–декабрь

1. Ручная разработка Python-сценариев/debugpy в VS Code **в паре с владельцем**:
   миграция, жизненный цикл, отсутствие внешнего таймаута во время ручной остановки,
   отличимость ручных свидетельств и их исключение из автоматической приёмки.
   Это отдельный согласуемый контракт, не обещание уже существующего API.
   Минимальный режим `run --interactive` (debugpy, без общего предела, отдельный
   `interactive-runs`) появился в кандидате 0.6.0 — [пошаговый проход](docs/ru/MANUAL_DEBUG.md);
   remote/Linux, фильтры просмотра ручных попыток и парная доводка — дальше.
2. Практика на проектах-потребителях: техники MMIO/C++, квалификация платы и DDTT;
   улучшать метод по реальной обратной связи. Различать дефект платы, прошивки,
   сценария и непригодные условия опыта.
3. Статья в научном формате об измерении/квалификации HSE по внешнему времени:
   реальные данные, модель погрешности, RTT и независимость, восстановление,
   ограничения и воспроизводимость; исходник и PDF. Образец оформления даст владелец.
4. Упорядочить документацию по разделам согласно docs/development/README.md,
   сохраняя ссылки при переносе. Уточнить границы и миграцию имени hwlivetest.

## Резерв, не условие выпуска

Renode keep/attach, SVD-кэш, универсальный FPB/VTOR-патчер, более широкая
RTOS-осведомлённость, адаптивные зависимости сценариев, дополнительные fault/snapshot
и измерительные методы. Приоритет — только после оценки практической пользы,
стоимости и отдельного принятия контракта; не добавлять всё в 0.5.0 автоматически.

в TODO, завершённые подробности — в TODO_ARCHIVE. Не дублировать исследовательские
журналы и не превращать ориентировочный месяц в критерий готовности.
