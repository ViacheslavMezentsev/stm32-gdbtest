[Выпуск v0.3.0](../../../releases/v0.3.0.md): версия пакета 0.3.0; расширенный API принят на пяти платах по шести схемам запуска; тег публикует владелец.

[План rc.2](RC2_READINESS.md): тег `v0.1.0-rc.2`, stm32-gdbtest `0.1.0rc2`; опубликован на a0d6547.

Формат — MAJOR.MINOR.PATCH по [SemVer 2.0.0](https://semver.org/spec/v2.0.0.html);
Git-теги имеют префикс `v`. Опубликован **v0.4.0** на `9c3ff2d`.
Документальный [выпуск v0.4.1](../../../releases/v0.4.1.md) сохраняет API_VERSION=2 и схемы 0.4.0.
[Выпуск 0.5.0](../../../releases/v0.5.0.md) / API_VERSION=3: приёмка P5b пройдена на итоговом коммите
`a7b0951` ([итог и ограничения](../../../development/release-050-acceptance.md)); тег ставит владелец.
Переход потребителя — [с 0.4.x на 0.5.0](../../../ru/MIGRATION_050.md).
Кандидаты v0.2.0-rc.1 и v0.3.0-rc.1 не публиковались. Предыдущий опубликованный кандидат — `v0.1.0-rc.2`.
Исходный экспорт из стендового проекта релизом не является.

До 1.0: совместимые исправления → 0.1.1; новые функции или изменения API → 0.2.0 с
явной миграцией. PATCH не ломает API. После 1.0: несовместимый API → MAJOR,
совместимые возможности → MINOR, исправления → PATCH. Версии 0.x не обещают
стабильности 1.0. Опубликованный тег не перемещается: исправление получает новую
версию. Gitlink потребителя фиксирует SHA, тег упрощает выбор этого SHA.

Источник версии — `__version__` в `stm32_gdbtest/__init__.py`. Для будущей
Python-упаковки тег `v0.1.0-rc.1` соответствует версии пакета `0.1.0rc1`, тег
`v0.1.0` — `0.1.0`. `API_VERSION` и номера схем JSON/TOML независимы от версии
релиза и меняются только при изменении соответствующего контракта.

Проект API 0.3.0 — [аудит и новый набор API](API030_PLAN.md). Состав 0.4.0 и
миграция — в [карте выпуска](RELEASE040_SCOPE.md); итоговая приёмка и публикация
отслеживаются в [TODO](../../../../TODO.md).


Версия пакета `stm32-gdbtest` — значение `__version__`; это не версия интерпретатора Python.
`API_VERSION` — номер совместимости API сценариев, а ревизии общего ТЗ и ТЗ API — версии
документов. Например, пакет выпуска 0.4.1 имеет версию 0.4.1, а `API_VERSION=2`.
Версии интерпретатора указываются отдельно для host Python и Python внутри GDB.

## Перед релизом

1. Host- и offline-проверки: CI зелёный на итоговом коммите ([проверки и CI](../../../ru/testing.md)).
2. Аппаратная проверка на итоговом SHA: F030R8, F103, F401CC, F411CE,
   F429ZI через ST-Link/OpenOCD и AT32F403A через OpenOCD/J-Link WinUSB.
   Второй backend F411 не заменяет F103. Объём, допуск и восстановление —
   в [матрице P5](../../../development/release-050-acceptance.md); другие backend и SSH
   имеют отдельные проверки и не наследуют локальный PASS.
3. Подключение потребителя настоящим Git-подмодулем; при необходимости —
   согласованные аппаратные и recovery-проверки потребителя.
4. Документация и миграция соответствуют коду; LICENSE на месте; локальных
   артефактов в коммите нет. Указаны фактическая матрица проверок и ограничения.
5. Обновлён `__version__`, открыт датированный раздел CHANGELOG (RU и EN),
   `[Unreleased]` оставлен для будущих изменений; выпущена ревизия ТЗ «к выпуску».
6. В ветке выпуска подготовлено описание `docs/releases/<тег>.md` (раздел ниже).
7. Слияние в main, затем тег на коммите слияния. Публикацию выполняет владелец;
   имя проверяется перед публикацией пакета.

## Тег и описание выпуска

Тег — аннотированный и подписанный, его сообщение — файл описания выпуска:

```powershell
git tag -s v0.1.0 -F docs/releases/v0.1.0.md --cleanup=verbatim
git push origin v0.1.0
```

`--cleanup=verbatim` сохраняет текст как есть: без него git удаляет строки,
начинающиеся с `#`. Тот же файл — текст релиза на GitHub (Releases → Draft a new
release; для `-rc` — «Set as a pre-release») или `gh release create v0.1.0 -F
docs/releases/v0.1.0.md` (`--prerelease` для кандидатов).

Описание — текст без заголовков Markdown (строки с `#` в начале исчезнут из сообщения тега при
обычной очистке и выглядят крупно на GitHub). Сначала русский текст; английский — тот же текст в
свёрнутом блоке `<details><summary>English</summary>` … `</details>` с пустой строкой после `<summary>`
и перед `</details>`, иначе GitHub не разметит содержимое. Матрицу итоговой проверки можно дать таблицей
Markdown (стенд × версия GDB). Состав: первая строка `stm32-gdbtest <версия> — <суть>`;
назначение в одном-двух предложениях; версия пакета, `API_VERSION`, ревизия ТЗ;
«Главное» — 5–8 пунктов из CHANGELOG, важных пользователю; «Итоговая проверка» —
коммит и матрица результатов; «Ограничения»; ссылки на CHANGELOG и STATUS.
GitHub превращает `@имя` в упоминание пользователя (он попадает в список участников
релиза), а `#число` — в ссылку на issue, поэтому такие фрагменты — только в обратных
кавычках: `` `@case` ``.
Пример — [v0.3.0](../../../releases/v0.3.0.md); прежний формат с `---` — [v0.1.0-rc.1](../../../releases/v0.1.0-rc.1.md).

Порядок работы с ветками и коммитами — [сопровождение](../../../ru/maintenance.md).

## Переход к 0.5.0: эмуляторы

Общий порядок перехода потребителя — [MIGRATION_050](../../../ru/MIGRATION_050.md).
Аппаратные target schema 1/2 и стенды менять не требуется. Для нового локального
эмуляторного маршрута создайте отдельные target schema 3 с environment=emulator
и stand с [emulator] и [qemu] либо [renode]. Не переносите аппаратную identity
и политику полного программирования Flash. reset пока отклоняется до команды.
Конфигурация и ограничения: [QEMU](../../../ru/QEMU.md), [Renode](../../../ru/RENODE.md).
