порядок: миграция потребителей → версия/финальный SHA (P6b-pre) → общая приёмка.

До P5 сверить незакрытые пункты старого архива с реализацией: не переносить
устаревшие флажки как новые требования и не считать их автоматически выполненными.
В частности, проверить актуальность долга по удалённому стенду, HAL F030 и Hardware CI.
В VERSIONING проверить перечень шести MCU (F103 не должен теряться или заменяться вторым F411).
Изменение кода после приёмки требует повторения затронутой части матрицы.

## Направление исследований: практика DDTT

Окружение теста определяется не только API, но и конкретной сборкой (оптимизация, LTO, `-g3`, раскладка памяти,
видимость макросов и типов в единицах трансляции), поведением инструмента (версия GDB, сервер отладчика,
аппаратные точки останова и наблюдения) и ограничениями прошивки (тайминги, прерывания, сон, сторожевые таймеры).
Общим остаётся GDB-Python. Решения ищутся для этого подхода, с проверкой на стендах, а не переносом практик
юнит-тестирования.

- [ ] **Признаки и вердикты сценариев.** Словарь признаков вместо свободных `labels`: уровень (host, prepare,
  плата, пакет), назначение (дым, соответствие требованию, робастность и внедрение отказов, измерение, регрессия),
  цена и последствия (запись Flash, сброс, разрушение состояния, длительность). Вердикт «проверка невозможна»
  (аналог `inconc` TTCN-3) отдельно от ERROR и FAIL. Обзор смежных практик: ISTQB, ISO 26262 и IEC 61508
  (методы проверки), DO-178C (нормальный диапазон и робастность), производственный контроль, NI TestStand
  (предусловия, режимы шага), pytest и Robot Framework (зависимости, теги).
- [ ] **Адаптивное дерево сценариев.** Управление группами сценариев во время прогона: отсечение ветвей после
  отказа, продолжение независимых проверок, повторная активация без повторного запуска. Имитационная модель уже
  показала механику; открыты вопросы: кто и как меняет факты (явная запись из сценария, как `record`), срок жизни
  факта после сброса, ERROR в агрегаторах, порядок обхода с учётом цены сценария, место над `run` рядом с CTest,
  отображение заблокированных узлов в отчёте. Следующий этап — тот же движок поверх `run --prepare-only` и одного стенда.
- [ ] **Зависимость от сборки и инструмента.** Каталог условий, при которых техника работает: встраивание и
  клоны функций, расположение параметров по уровню оптимизации, видимость макросов и типов CMSIS/HAL, различия
  версий GDB и серверов (события остановки, запаздывание точек наблюдения, бюджет точек). Проверка условий до
  запуска (контракты, `prepare`) и запись их в отчёт.
- [ ] **Инструменты в ОЗУ.** Загрузка на время прогона отдельно собранного тестового кода в свободную область
  SRAM и его вызов из сценария: измерения с точным временем (DWT CYCCNT), быстрые серии и проверки памяти,
  заглушки функций и перехват прерываний через копию таблицы векторов (VTOR). Прошивка не меняется, но прогон
  становится вмешивающимся. Вопросы: резерв области в скрипте компоновщика, сборка инструмента с символами
  прошивки (`--just-symbols`), стек и прерывания во время вызова, кэши и запрет исполнения из SRAM на отдельных
  семействах, восстановление памяти, отметка вмешательства в отчёте. Прецедент — алгоритмы записи Flash
  (CMSIS-Pack FLM, OpenOCD), которые выполняются из SRAM.

Ветка codex/hse-qualification-skill: отдельный навык проверки допуска частоты HSE,
методика RU/EN, интервальная погрешность и границы применимости DDTT.
Только документация; новых аппаратных прогонов нет. Skill validator PASS,
Linux docs 5/5; подписанный коммит этой ветки готовится для push владельцем.

Ветка codex/ddtt-qualification-data: снимок через [data], квитанция в records,
проверка связи до bind; сохранены исходные PASS/FAIL, result.json и records.json.
Host Windows/Linux: по 676 тестов (14/6 пропусков), Linux docs/host 6/6.
Без платы, изменения ядра и схем. Далее план аппаратного пилота с независимым
физическим эталоном и отдельным допуском на операции.

Ветка codex/ddtt-qualification-renode: реальный runner и независимый журнал приёмника.
Renode 1.17 Windows/Linux: по 6 PASS (предварительный/основной прогон × 3 условия),
применимость CONFIRMED/UNKNOWN/CONFIRMED; независимая инициализация всегда CONFIRMED.
Исходные result.json неизменны, cleanup VERIFIED. Без платы и изменений ядра.
Host Windows/Linux: по 670 тестов (14/6 пропусков); Linux docs/format/host 7/7.
Проектная интеграция продолжена следующей веткой выше; аппаратный пилот ещё не выполнен.

Влитая ветка codex/ddtt-qualification: первый пакет применимости DDTT, ТЗ 0.110,
нейтральный host-пример и снимок допуска. Без платы, runner/Target без изменений.
Host Windows/Linux: по 665 тестов (14/6 пропусков), Linux docs 5/5;
нейтральный пример — по 10 ожидаемых исходов на обеих ОС.
Renode проверен следующей веткой выше; проектная интеграция records/[data] и аппаратный
пилот ещё не приняты. Общий аудит навыков остаётся в P6.


Ветка codex/hil-inspect: публичный inspect, ТЗ 0.109, JSON schema 1;
без платы и изменений Target API. Host Windows/Linux: 645 тестов (14/6 пропусков); inspect 49/49; Linux docs 5/5.
Четыре профиля BluePill/BlackPill без ERROR, JSON Windows/Linux совпали;
push/CI/land итогового подписанного коммита выполняет владелец.
Далее квалификация платы/DDTT, P5 и общий аудит ВСЕХ навыков в P6.
Предыдущий публичный P4 влит владельцем; записи ниже сохраняют историю подготовки.


API_VERSION=3 (085f089) в main: await-диспетчер, bounded call и guard выражений;
обычный def сохраняет синхронную форму. ТЗ 0.108 / API 0.3.23.

Ветка `codex/live-observer-example`: публичный `tests/live-observer`, без изменений ядра.
Renode Windows/Linux — по 8 ожидаемых исходов, три подтверждённые привязки DDTT/LCOV.
Host Windows/Linux: 596 тестов; отдельные проверки примера: recovery 11, ownership 8,
контракт/карта 9, FPB fault matrix 191. Docs/format/host Linux: 7/7 PASS.
Изменения подготовлены в этой ветке; push/CI подписанного итогового SHA и land — владелец.

Исследовательский пилот P4 F411 на API 3: 12/12 ожидаемых исходов, Flash/SRAM и
сохранённые регистры независимо сверены. Это происхождение публичного примера,
не аппаратная приёмка его нового коммита. Новых запусков плат при переносе нет.
Границы — [пример](../ru/LIVE_OBSERVER.md) и [приёмка](../ru/API_ACCEPTANCE.md).

Далее inspect/HIL и квалификация платы/условия свидетельств DDTT; P5 на одном
кандидате (Windows/Linux, Renode/QEMU, шесть стендов по возможностям, потребители);
P6 — финальная сверка документации/навыков, миграция, версии и выпускные материалы.
Прежние P3 78/78 и MMIO 141 проверка относятся к своим ревизиям и не заменяют P5 API 3.
Debugpy — отдельно с владельцем; keep/attach, SVD-кэш, универсальный патчер и
переименование hwlivetest отложены. Выпуск 0.5.0 не объявлен готовым.

## Renode backend для 0.5.0

Ветка `codex/renode-backend`: target schema 3 и изолированный локальный Renode.
Локально: Windows host 489 (16 skips), Linux docs/host/format 7/7; Renode 1.17
Windows/Linux: prepare и шесть ожидаемых исходов, capture/cleanup. Не аппаратная
приёмка; push/CI/land — владелец.
Минимальный QEMU добавлен следующим этапом; зависимости REPL и повторное использование процесса остаются отложенными.

MMIO к 0.5.0: публичные read/write, SVD/override, прямой RSP и журнал реализованы; host и учебная Renode проверяются отдельно от аппаратной приёмки. Выбранная аппаратная матрица шести стендов завершена; её границы зафиксированы в API_ACCEPTANCE, автоматического расширения гарантий нет.
