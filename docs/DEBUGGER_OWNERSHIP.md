# Владение отладчиком между проектами

## Реализованный механизм

`probe_lock(root, serial, backend="openocd")` использует именованный Windows mutex:
`Local\stm32-gdbtest.probe.v1.<sha256>`. Ключ — тип отладчика и серийный номер
в верхнем регистре. OpenOCD и ST server отображаются в тип stlink, J-Link — в jlink.
Корень проекта, MCU и GDB-порт не входят в ключ. Серийный номер не публикуется
в имени объекта. Этот hash не является средством сокрытия секретов.

Область координации — **одна Windows-сессия**, разные процессы/проекты/копии
модуля, использующие данный протокол. Local namespace не охватывает другую
Windows-сессию/RDP/service session. Объект находится в ядре ОС, файлы вне проекта
не создаются. API Windows и семантика рекурсивного владения описаны в
[CreateMutexW](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createmutexw),
граница сессии — в [Kernel object namespaces](https://learn.microsoft.com/en-us/windows/win32/termserv/kernel-object-namespaces).

Захват выполняется без ожидания, после чтения профиля/стенда, до ELF preflight,
objcopy и запуска сервера. Занятый mutex даёт ERROR с JSON/JUnit, без аппаратного
подключения. Удержание охватывает всю execute, включая recovery и остановку
серверного дерева. Внешний инструмент должен участвовать в том же протоколе, если он использует отладчик. Внутрипроцессный guard
отклоняет повторный захват: Windows mutex сам по себе рекурсивен для одного потока.
Поддерживается один импорт пакета в Python-процессе; независимые копии проверены
в разных процессах, не как несколько alias imports в одном интерпретаторе.

Старый project-local file lock сохранён внутри named mutex для совместимости с
прежним runner в том же checkout (при одинаковой записи serial). Поэтому редкое
совпадение serial у разных типов отладчиков внутри одного checkout может дать
консервативный отказ. Старый runner в другом checkout не знает новый mutex и
не защищён им: все участвующие проекты нужно обновить. Vendor tools, VS Code и
произвольный OpenOCD/GDB Server не используют наш протокол и им не блокируются.

## Завершение и сбои

Обычный выход и Python-исключение освобождают file lock, mutex и handle в finally.
Ошибка API/прав доступа не приводит к обходу блокировки. После завершения процесса
Windows освобождает его mutex; это **не доказательство завершения дочерних серверов**.

WAIT_ABANDONED означает, что владение получено после смерти прежнего владельца.
Runner освобождает объект и отказывает до подключения, предлагая проверить
оставшиеся процессы GDB/server. Это не долговременный карантин: если все handles
закрылись, объект исчезает, и будущий запуск может не узнать о прежней аварии.
Автоматически убивать чужие процессы или сбрасывать MCU по этому признаку нельзя.
После аварийного завершения host сначала проверить/завершить его оставшиеся
серверы; отключение владельца не проверялось на реальном MCU в этом этапе.
Job Object/надзор за дочерними процессами остаётся отдельной задачей.
