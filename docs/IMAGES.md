# ELF, BIN и область проверки Flash

Runner проверяет содержимое **загружаемых секций ELF** по адресам загрузки LMA.
Это соответствует обычному `load` GDB. VMA `.data` может находиться в RAM, тогда
как её начальные значения загружаются во Flash; сравнивается именно Flash LMA.
Секции без CONTENTS/ALLOC/LOAD (например `.bss`, debug info) не сравниваются.

До сервера GNU `arm-none-eabi-objdump -h` из каталога GDB формирует список секций.
Пустой/неразбираемый список, перекрытия, загрузка за пределы profile Flash и
несовпадение длины BIN с диапазоном ELF дают ERROR до objcopy/GDB/server, кроме
проверки длины BIN, которая выполняется после objcopy. Первая загружаемая секция
должна начинаться с `profile.flash_start`; offset application и несколько банков
в этой версии не поддерживаются. После подключения также проверяется factory
Flash capacity; более вместительный MCU не расширяет допустимые границы профиля.

BIN создаётся из снимка ELF командой `objcopy -O binary --gap-fill=0xFF`.
Это определяет байты промежутков **в BIN**, но не записывает их через GDB load ELF.
На плате они могут быть стёртыми или остаться от предыдущего содержимого.
Поэтому сравнение секций пропускает промежутки, а не предполагает в них 0xFF.
Несовпадение payload вызывает load при `flash=if-different`, затем обязательный
readback тех же секций. В verify-only несовпадение даёт ERROR без записи.
Ошибка чтения не трактуется как необходимость прошивки и не скрывается.

В result.json/JUnit сохраняется `image_verification`:

- `scope: elf-load-sections`, `bin_gap_fill: 255`;
- `gaps_verified: false`, `full_region_crc_verified: false`;
- `regions`: имя, Flash address, размер, offset в BIN и после readback `matches`.

`image_verified: true` означает совпадение всех этих секций, не всей Flash и
не CRC полного образа. Чтения разбиты на блоки до 4096 байт. SHA256 BIN может
измениться относительно старого runner из-за заполнения дырок; ELF SHA не меняется.
`elf-sections.txt` и `image.bin` сохраняются рядом с run.json. API сценариев и
target/build-manifest schema не изменены; run.json — внутренний артефакт runner.
Отдельного обходного пути со сплошным сравнением старых run.json нет.

## Полный образ и CRC: явный режим

По умолчанию остаётся `elf-load-sections`. Для полного диапазона передать
`run --image-policy path/to/full-image.toml` либо абсолютный путь в
`STM32_GDBTEST_IMAGE_POLICY` (удобно для CTest). CLI имеет приоритет над environment.
Если переменная установлена, отсутствие CLI-флага НЕ отключает полный режим:
для возврата к проверке секций убрать переменную. Не редактировать run/session JSON.

```toml
[image]
schema = 1
mode = "full"
start = 0x08000000
end = 0x08004000
fill = 255
crc = "crc32-iso-hdlc"
```

Пример описывает **16 KiB**, не всю Flash MCU. `end` — исключительная верхняя
граница. Начало должно совпадать с profile.flash_start, конец помещаться в профиль
и наблюдаемый factory размер. Если ELF вырастет за пределы политики, запуск
отклоняется. Числа — целые (не bool), fill 0..255; неизвестные поля/схемы/CRC
отклоняются. MCU с другой базой требует собственного файла. Политику хранить
у потребителя, независимо от локального serial/backend.

Подготовка выполняется до сервера:

1. Проверяется исходный ELF/build manifest и его load sections.
2. Создаётся `image.bin`: байты секций сохраняются; все дырки и хвост до end
   заполняются fill. Никакое CRC-поле не вставляется в прошивку.
3. Из полного BIN создаётся `program.elf` с единственной секцией `.firmware`
   по адресу start. Проверяются её границы и побитовое совпадение обратного
   преобразования ELF → BIN. Это транспортный контейнер для GDB, не новая сборка.
4. Фиксируются SHA256 BIN, контейнера и исходной политики; GDB-agent проверяет
   неизменность BIN/контейнера и padding до подключения.

После reset/halt агент читает **весь** диапазон блоками до 4096 байт. Сравнивает
каждый байт с BIN и считает CRC исходного образа и прочитанных байтов. При
несовпадении и `if-different` выполняет `load program.elf`, восстанавливает
`symbol-file firmware.elf` и повторяет полный readback. Имена — артефакты одного
каталога запуска; исходный ELF сохранён для типов, макросов и сценариев.
`verify-only` выдаёт ERROR без записи. Ошибка чтения также ERROR, не повод
вслепую прошивать. При совпадении повторной записи нет. Далее обычный сценарий,
reset/run и правила восстановления backend.

Mass erase не добавляется. Отдельные erase-сектора/pages может стирать backend
при программировании; сохранность соседних данных вне диапазона этим режимом
не гарантируется. Для рабочего проекта выделять область firmware с учётом erase
геометрии. В проверенных F411/F103 примерах граница 16 KiB согласована с ней.
Несколько банков, смещённое приложение и политика сохранения соседних данных
пока не реализованы.

### CRC-контракт

CRC-32/ISO-HDLC: poly `0x04C11DB7`, init/xorout `0xFFFFFFFF`, refin/refout true,
проверочное значение для ASCII `123456789` — `0xCBF43926`.
[Каталог CRC RevEng](https://reveng.sourceforge.io/crc-catalogue/all.htm).
Байты подаются по возрастанию Flash-адресов, хвост нечётной длины обрабатывается
побайтно, скрытого дополнения до слова нет. Поле CRC отсутствует: учитываются
все байты диапазона без исключений. Если приложение уже хранит CRC внутри
образа, она тоже входит в расчёт; автоматического исключения/замещения нет.

Расчёт выполняется Python `binascii.crc32` на ПК, в GDB-agent, по readback через
отладчик. **Это не запуск CRC-кода на MCU и не проверка его CRC-периферии.**
Совпадение CRC не заменяет сравнение байтов: оба условия обязательны, что отдельно
проверяется host-тестом с принудительно одинаковыми CRC разных данных.

В `image_verification` полного режима: scope `full-image`, start/end/fill,
bytes_compared/bytes_match, first_mismatch (адрес либо null), gaps_verified,
full_region_crc_verified, CRC-параметры и expected/observed. При несовпадении
перед записью сохраняется также `image_before_programming`. Общий `bin_sha256`
относится к полному BIN, `elf_sha256` — к исходному ELF, `program_elf_sha256` —
к контейнеру. `image_policy.source_sha256` связывает отчёт с TOML; нормализованная
копия сохраняется в image-policy.json. CRC не является криптографической проверкой.

### Один артефакт для программирования и отладки

`image.bin` можно записывать внешним программатором **по start из политики**,
а `program.elf` — загружать под отладкой. Их payload идентичен. В подключённом
GDB с выполненным reset/halt порядок для этих артефактов:

```gdb
load /path/to/run/program.elf
symbol-file /path/to/run/firmware.elf
```

Затем reset/halt и запуск по правилам конкретного backend. Использовать оба файла
из одного завершённого snapshot, проверять manifest/SHA и readback. В VS Code
исходный ELF остаётся файлом символов; команда загрузки должна указывать контейнер.
Штатные launch.json потребителя автоматически не переписываются. Возврат к
обычному `load firmware.elf` снова оставляет gaps/tail вне явного контракта.
Команда load может затрагивать таблицы символов, поэтому их восстановление
выполняется явно: [GDB Target Commands](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Target-Commands.html).

Подготовка контейнера сейчас использует `arm-none-eabi-objcopy`, `elf32-littlearm`
и ARM backend; это не расширяет поддержку RISC-V. Протокол проверки режима —
`docs/FULL_IMAGE_CRC.md` в стендовом проекте. На ST GDB Server режим пока не проверен.
Далее: CRC-поле/исключения, другие алгоритмы, сравнение с MCU CRC и отдельная
команда экспорта артефакта без аппаратного запуска.

Причина изменения и аппаратные доказательства хранятся в
[стендовом проекте](https://github.com/ViacheslavMezentsev/stm32-hwtest-blackpill),
docs/ELF_LOAD_REGIONS.md и docs/K1921VG015_POC.md. Опыт на RISC-V мотивировал
исправление, но сам по себе не расширяет поддержку MCU/toolchain данного runner.
