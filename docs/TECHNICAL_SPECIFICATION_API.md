- Типы возврата и регистров читаются из объявленного типа: `Frame.return_type()` есть не во всех
  сборках GDB, а `sizeof(void)` в части сборок равен единице, поэтому вид типа решает код типа.
- Остановка классифицируется по виду сообщённой точки: J-Link передаёт точку наблюдения как событие
  точки останова, а часть связок не передаёт событие вовсе — тогда наблюдение подтверждается изменением
  наблюдаемого объекта и помечается `inferred`.
- Аргументами `call` принимаются числа и безопасные выражения GDB; побочные эффекты функции сохраняются.
- Инвалидация кэшей после сброса выполняется после любой попытки, включая неудачную.
- Guard-точки стенда не считаются активными точками пользователя и не блокируют сброс.
- Версия модуля поднята до `0.3.0`; `API_VERSION=1` и схемы JSON/TOML не изменены.
- Алиасы прежних имён действуют без предупреждений до 1.0, удаление запланировано в 0.4.0.
- Изменённые пункты помечены `(р.0.3.0)`. (р.0.3.0)

## 4. Функциональные требования: операции

### 4.1. Проверка check

4.1.1. `check(name, actual, expected)` ДОЛЖЕН записывать name, actual, expected,
passed в checks, печатать PASS/FAIL и при actual != expected возбуждать CheckFailed. `[R]`

4.1.2. `check_range(name, actual, low, high)` ДОЛЖЕН проходить при `low <= actual <= high`,
`check_near(name, actual, expected, tolerance)` — при `|actual - expected| <= tolerance`,
`check_in(name, actual, options)` — при равенстве actual одному из options. Запись checks ДОЛЖНА
содержать фактическое значение, expected в виде `{"low", "high"}`, `{"value", "tolerance"}` или
`{"in": [...]}` и поле kind (`range`, `near`, `in`). Нечисловое actual ДОЛЖНО давать несовпадение
CheckFailed. Неверные границы, отрицательный допуск, пустой набор или пустое имя ДОЛЖНЫ давать ApiError
операции check без записи в checks. Причина: проверка вида `check(name, low <= x <= high, True)`
оставляет в отчёте только `True`. `[N]` (р.0.3.3)

4.1.3. `check_table(rows)` ДОЛЖЕН принимать непустой список строк `(name, actual, expected)`, проверять
структуру всех строк до первой оценки, вычислять строковые actual и expected через evaluate с объявленным
типом и проверять строки по порядку через check; первое несовпадение ДОЛЖНО прекращать операцию
CheckFailed. Результат — число проверенных строк. `[N]` (р.0.3.3)

### 4.2. Чтение value

4.2.1. `value(expression)` ДОЛЖЕН вычислять gdb.parse_and_eval, отклонять optimized-out,
загружать ленивое значение и возвращать int; неизвестный символ/макрос НЕ ДОЛЖЕН
подменяться нулём. `[R]`

### 4.3. Сравнение fields

4.3.1. `fields(expression, expected)` ДОЛЖЕН по порядку expected читать
`(<expression>).<поле>` и вызывать check; строковое ожидание ДОЛЖНО вычисляться
как C-выражение через value. Первая неуспешная проверка прекращает операцию исключением. `[R]`

### 4.4. Точка breakpoint

4.4.1. `breakpoint(location, temporary=False, *, condition=None, ignore_count=0, when=None)` ДОЛЖЕН
создавать аппаратную точку; при исчерпании breakpoint_limit действующими принадлежащими Target точками
ДОЛЖЕН отказать до создания; pending-точка ДОЛЖНА удаляться с ошибкой absent from ELF;
condition (прежнее имя when) задаёт условие, temporary — временность; при заданных и различных
condition и when ДОЛЖЕН отказать с кодом conflicting_condition до создания. Успешный вызов
возвращает Point; Point ДОЛЖЕН поддерживать is_valid() и delete() прежнего gdb.Breakpoint. `[R]` (р.0.3.1)

4.4.2. Повторный вызов ДОЛЖЕН возвращать действующую постоянную точку Target только при совпадении
location, condition и ignore_count; временная точка или иные параметры ДОЛЖНЫ создавать новую точку. `[R]` (р.0.3.1)

4.4.3. `Point.disable()` ДОЛЖЕН сохранять точку и счётчик hit_count, исключая точку из остановок;
`Point.enable()` ДОЛЖЕН снова включать её и отказывать с кодом limit_exceeded, если действующие точки
Target уже исчерпали breakpoint_limit. Бюджет ДОЛЖЕН считать только активные точки, включая точки
fault handlers. Запись `Point.condition` ДОЛЖНА заменять условие живой точки (None снимает его) и
учитываться правилом повторного использования 4.4.2. Действие над удалённой точкой ДОЛЖНО давать
ApiError с кодом point_removed. `[N]` (р.0.3.3)

### 4.5. Достижение reach

4.5.1. `reach(location, condition=None, *, when=None)` ДОЛЖЕН создать собственную временную
аппаратную точку, один раз продолжить исполнение и проверить через check номер точки в последней
остановке, имя кадра и истинность условия при его наличии; созданная точка ДОЛЖНА
удаляться при любом исходе, если остаётся действующей; точки сценария в том же месте НЕ ДОЛЖНЫ
удаляться. `[R]` (р.0.3.1)

4.5.2. reach ДОЛЖЕН сравнивать имя кадра без суффикса clone, завершающих
const/volatile и списка параметров; исходное имя ДОЛЖНО сохраняться в записи остановки. `[R]`

4.5.3. Каждая остановка resume/step/until/finish/reach ДОЛЖНА нести `evidence`: `native`, если вид следует из
сообщённой GDB точки или причины, и `inferred`, если GDB причину не передал (GDB 14) и вид выведен по команде:
для step — по смене счётчика команд, для finish — по смене функции, для until — по адресу цели (иначе шаг, как у GDB 15+), для
resume/reach — по изменению наблюдаемого объекта. Первый такой вывод ДОЛЖЕН добавлять в report["warnings"]
предупреждение `inferred_stop` с версией GDB. Резервный вывод НЕ ДОЛЖЕН подменять `native_reason`. `[R]` (р.0.3.2)

4.5.4. finish ДОЛЖЕН возвращать `returned_from` (функцию до команды), `function` (кадр после неё),
`return_value` и `return_state`: `void` по объявленному типу void, `available`, если команда добавила значение в
историю значений GDB, иначе `unavailable`; значение None НЕ ДОЛЖНО означать сразу void и недоступность. `[R]` (р.0.3.2)

4.5.5. until(location) ДОЛЖЕН давать `reached` только при остановке на адресе цели, если адреса известны;
при возврате текущего кадра раньше цели — `frame_exited`; без цели — `completed`. `[R]` (р.0.3.2)

### 4.6. Запись set_value

4.6.1. `set_value(expression, value)` ДОЛЖЕН прочитать значение до записи,
выполнить set variable, прочитать значение после и добавить expression/value/before/after
в mutations. Допустимость MMIO-записи обеспечивает автор сценария. `[R]`

### 4.7. Принудительный возврат force_return

4.7.1. `force_return(expression)` ДОЛЖЕН выполнить команду GDB return с выражением
expression и записать operation=force_return, имя newest_frame и expression в mutations.
Возврат действует на выбранный кадр GDB, пропускает оставшийся код функции и НЕ ДОЛЖЕН
считаться откатом уже выполненных эффектов или выполнением finish. `[U]` (р.0.2.4)

Текущая реализация записывает имя newest_frame, хотя команда return действует
на выбранный кадр. Если сценарий сам изменил выбор кадра через GDB, имя в журнале
может не соответствовать кадру возврата; гарантия согласованности пока отсутствует.

### 4.8. Очистка clear

4.8.1. `clear()` ДОЛЖЕН удалять действующие точки Target, включая fault handlers,
и очищать список владения. `[R]`

### 4.9. Запись record

4.9.1. `record(name, data) -> None` ДОЛЖЕН после успешной проверки добавлять
глубокую независимую копию data; повторяющиеся имена допустимы. `[N]` (р.0.2.0)

4.9.2. name ДОЛЖЕН быть непустым точным встроенным str. data ДОЛЖЕН состоять
только из точных встроенных None/bool/int/конечного float/str/list/dict со строковыми
ключами; подклассы, tuple, bytes, объекты GDB и циклы ДОЛЖНЫ отклоняться.
Текст ДОЛЖЕН допускать UTF-8 без непарных суррогатов. `[N]` (р.0.2.0)

4.9.3. Запись ДОЛЖНА содержать ровно sequence/name/data; sequence начинается с 1
и растёт на 1 после успешной записи. Отказ проверки НЕ ДОЛЖЕН менять журнал,
счётчики бюджета или следующий sequence. `[N]` (р.0.2.0)

4.9.4. Журнал ДОЛЖЕН принадлежать одному вызову сценария и начинаться пустым;
continue/reset/clear внутри вызова НЕ ДОЛЖНЫ очищать его. После завершения вызова
владение журналом завершается; полученные копии остаются обычными Python-данными. `[N]` (р.0.2.0)

4.9.5. record/records НЕ ДОЛЖНЫ обращаться к MCU/GDB, продолжать исполнение,
писать файлы, автоматически экспортировать записи в report или менять исход проверки.
sequence ДОЛЖЕН означать только порядок добавления, без автоматического PC/time/image
и обещания атомарного снимка MCU. `[N]` (р.0.2.0)

### 4.10. Чтение records

4.10.1. `records(name=None) -> list[dict]` ДОЛЖЕН возвращать глубокие независимые
изменяемые копии в порядке добавления. None выбирает все записи, непустой точный
str — точное совпадение имени; отсутствие совпадений даёт []. sequence при
фильтрации НЕ ДОЛЖЕН перенумеровываться. `[N]` (р.0.2.0)

4.10.2. Изменение входа record и результата records НЕ ДОЛЖНО менять сохранённые
записи или другие результаты records. Отдельный язык запросов НЕ ДОЛЖЕН вводиться
первым пакетом: фильтры, срезы, any/all и статистика используют Python. `[N]` (р.0.2.0)

symbol_absent. `[N]` (р.0.3.3)

### 4.16. Память memory и write_memory (р.0.3.3)

4.16.1. `memory(address, size)` ДОЛЖЕН возвращать bytes блока, лежащего целиком в окне SRAM или во Flash
профиля (`flash_start`, `flash_size`). Блок вне окон ДОЛЖЕН отклоняться кодом outside_window до чтения.
Причина: чтение регистра периферии может изменить состояние устройства. `[N]` (р.0.3.3)

4.16.2. `write_memory(address, data, *, verify=True)` ДОЛЖЕН писать только в окно SRAM, при verify
читать блок обратно, записывать изменение в mutations (байты в hex) и при расхождении давать ApiError
с кодом verification_failed и effect=applied. `[N]` (р.0.3.3)

4.16.3. Неверный адрес или размер блока ДОЛЖЕН давать invalid_block; отказ GDB — read_failed или
write_failed. `[N]` (р.0.3.3)

unavailable; frame — None (внутренний кадр), глубина int или кадр GDB. locals ДОЛЖЕН обходить блоки от
внутреннего до блока функции, внутреннее имя перекрывает внешнее, аргументы в locals НЕ ДОЛЖНЫ
входить. `[N]` (р.0.3.3)

4.17.2. Оптимизированное или непреобразуемое значение ДОЛЖНО попадать в unavailable без исключения;
кадр без отладочной информации ДОЛЖЕН давать no_debug_info, отсутствующий кадр — no_frame. `[N]` (р.0.3.3)

## 5. Требования к интерфейсам

5.1. Сценарий ДОЛЖЕН пользоваться метаданными case и соглашением вызова Target,
определёнными общим ТЗ; API НЕ ДОЛЖЕН вводить второе соглашение сбора сценариев. `[R]`

5.2. Классификация CheckFailed как FAIL и остальных исключений как ERROR ДОЛЖНА
оставаться ответственностью агента по общему ТЗ. `[R]`

5.3. Ошибки входа record/records ДОЛЖНЫ давать RecordError с code из набора
invalid_name/unsupported_type/invalid_text/non_finite/cycle/limit_exceeded.
Неверный фильтр records ДОЛЖЕН давать invalid_name. При limit_exceeded поле limit
ДОЛЖНО иметь одно из значений records/nodes/depth/text_bytes/integer_bits.
Текст сообщения и приоритет при нескольких нарушениях не являются контрактом. `[N]` (р.0.2.0)

5.7. Сценарии ДОЛЖНЫ собираться из каталога по умолчанию (`tests` сессии) и дополнительных каталогов
поиска (`TEST_DIRS` в CMake, повторяемый `--tests` в CLI) в этом порядке; повтор ID сценария в любых
двух каталогах ДОЛЖЕН давать ошибку сбора. `[N]` (р.0.3.3)

5.8. Каждый каталог сценариев ДОЛЖЕН иметь свой `requirements.md`; трассировка ДОЛЖНА сверять сценарии
со всеми файлами требований вместе. Контракт ДОЛЖЕН выбираться из первого реестра `contracts.json`, где он
определён: каталог профиля, затем каталог сценария. `[N]` (р.0.3.3)

5.9. Пакет ДОЛЖЕН переносить дополнительные каталоги как `profile/tests-<n>` и восстанавливать их
список при открытии. `[N]` (р.0.3.3)

5.4. Системные исключения, включая MemoryError, НЕ ДОЛЖНЫ маскироваться под
RecordError. Необработанный RecordError ДОЛЖЕН классифицироваться агентом как
ERROR, а несовпадение check — как FAIL по п. 5.2. `[N]` (р.0.2.0)

5.5. Выбор, валидация и перенос конфигурации ДОЛЖНЫ соответствовать разделу 5.20
[общего ТЗ](TECHNICAL_SPECIFICATION.md); API НЕ ДОЛЖЕН самостоятельно повторно
читать исходные файлы или выбирать другую конфигурацию. `[N]` (р.0.2.0)

---

5.6. Публичный импорт ДОЛЖЕН иметь вид `from stm32_gdbtest import RecordError`.
RecordError ДОЛЖЕН наследовать ValueError и импортироваться на host без GDB;
импорт исключения НЕ ДОЛЖЕН требовать запуска отладчика. `[N]` (р.0.2.1)

совместимости и ссылками на проверки; добавление платы без изменения контракта
ДОЛЖНО фиксироваться в матрице поддержки без автоматического изменения runtime API. `[N]`

7.3. Начальная схема api.toml ДОЛЖНА иметь обязательное целое schema=1.

7.4. Набор известных имён и их смысл ДОЛЖНЫ определяться schema. Новый
распознаваемый параметр ДОЛЖЕН вводиться новой схемой и явным переходом;
неизвестное поле старой поддерживаемой схемы НЕ ДОЛЖНО получать новый смысл.
Для данных потребителя СЛЕДУЕТ использовать user; модуль НЕ ДОЛЖЕН интерпретировать
эту секцию или запрещать остальные неизвестные поля api.toml. `[N]` (р.0.2.0)

7.5. Перенос расширения в ядро и выпуск ДОЛЖНЫ требовать отдельного разрешения;
приёмка ДОЛЖНА проверить прежние сценарии и новую поверхность. Наличие прототипа
или новая ревизия документа НЕ ДОЛЖНЫ считаться такой приёмкой. Разрешение владельца
от 03.10.2026 на перенос первого пакета НЕ ДОЛЖНО считаться разрешением выпуска. `[U]` (р.0.2.2)

7.6. Имя МОЖЕТ удаляться без алиаса только если оно не входило в опубликованный тег; имя из
опубликованного тега ДОЛЖНО сохранять прежний контракт или получать алиас по п. 6.7. `[N]` (р.0.3.3)

## Приложение F. Расхождения и границы (информативно)

по неизменному target.py. [Справочник](ru/api/index.md) указывает версии реализации
отдельно от ревизий контракта. Новой аппаратной проверки эта правка не заявляет. (р.0.2.4)

Кандидат 0.2.0rc1 и публичные результаты — [приёмка](ru/RC020_READINESS.md).
Runtime-контракт не менялся; материалы разработки исключены из поставки по
общему ТЗ 7.7.15–7.7.17. (р.0.2.3)

Первый пакет реализован в ядре по разрешению владельца: records.py, Target,
configuration/config_transport, CMake/CLI/runner/agent/package. Host-регрессия,
offline-подготовка, пары TECH-010/011 на F030/F103/F411 и повтор затрат описаны в
[принятые результаты](ru/API_ACCEPTANCE.md). Это проверка
заданного набора, не всех MCU/backend и не выпуск. read/context/caller/finish
остаются вне пакета; RTOS и прочий аппаратный долг не возобновляются. (р.0.2.2)

clear снимает fault guards; force_return пропускает остаток функции без отката
уже исполненного кода. Их контракты первым пакетом не изменены. (р.0.2.2)
