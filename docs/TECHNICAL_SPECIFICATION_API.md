## 1. Введение

### 1.1. Назначение

1.1.1. Документ сохраняет базовый API rc.2 и фиксирует принятые требования первого
пакета расширения. Принятие требований не означает внедрение или выпуск. (р.0.2.0)

### 1.2. Область

1.2.1. В область входят восемь базовых операций Target, record/records, RecordError
и свойства config/config_props. Сбор сценариев, case, CLI/CMake, выбор/перенос файлов,
сервер, отчёт, reset/recovery и классификация результата принадлежат общему ТЗ. (р.0.2.0)

### 1.3. Источники

1.3.1. База — v0.1.0-rc.2, commit a0d6547ba83b7c911f8f3028cb064aeedd3e5a36
и контракты общего ТЗ 0.58. Дополнение — решения владельца от 03.10.2026,
принятые требования разделов 4–7 и публичные результаты приёмки.
Расхождения с кодом перечислены в приложении F и разрешаются новой ревизией. (р.0.2.3)

### 1.4. Термины

Target — объект, переданный агентом одному сценарию. CheckFailed — исключение
несовпадения проверки. Ревизия API — версия этого контракта, не версия MCU/GDB.

### 1.5. Ссылки

1.5.1. Системный жизненный цикл определён общим ТЗ, разделами 3.1, 5.10–5.12;
загрузка конфигурации — разделом 5.20. Исследовательские свидетельства не заменяют
приёмку интегрированного ядра. (р.0.2.0)

### 1.6. Соглашения

1.6.1. Разделы 1–2 и приложения — информативные; разделы 3–8 — нормативные.
ДОЛЖЕН означает требование, СЛЕДУЕТ — рекомендацию, МОЖЕТ — возможность.
Маркеры `[R]`, `[N]`, `[U]` означают восстановленное, новое и уточнённое требование.

1.6.2. Номера требований и TC-NN постоянны; номера исключённых пунктов не переиспользуются.
Ссылки различают документ: «ТЗ API 4.1.1» и «ТЗ проекта 5.10.3».

1.6.3. По решению владельца ревизия документа имеет три компонента X.Y.Z вместо
двухкомпонентной формы навыка; начальная ревизия 0.1.0. Последующие изменения
получают строку истории, блок изменений и пометки (р.X.Y.Z). Первая ревизия без пометок.
Третий компонент предназначен для небольших уточнений после проверок; конкретные
критерии изменения компонентов и несовместимости — открытый вопрос 10.2.2.
Несовместимое изменение не становится совместимым только потому, что оно небольшое.

## 2. Общее описание

2.1. Сценарий получает Target после boot; GDB находится в main. Реализация API
не содержит ожиданий о конкретной периферии платы. Такие ожидания задаёт потребитель.

2.2. Первый пакет содержит record/records, RecordError и config/config_props.
read, context/stack/caller и finish остаются экспериментами. Контракты приняты,
реализация первого пакета перенесена в ядро по разрешению владельца. Приёмка
ядра описана отдельно от исторических E1–E4 и M2–M4. (р.0.2.2)

## 3. Поверхность API и модель данных

3.1. Публичный Target API ДОЛЖЕН включать check, value, fields, reach, breakpoint,
set_value, force_return, clear; boot, close, on_stop, report, owned, stops и создание
Target НЕ ДОЛЖНЫ считаться публичными операциями сценария. `[R]`

3.2. Ревизия документа ДОЛЖНА задаваться тремя неотрицательными десятичными
компонентами X.Y.Z с начальным значением 0.1.0. `[N]`

3.3. Первый пакет ДОЛЖЕН дополнить Target операциями record/records и свойствами
config/config_props; публичное исключение RecordError ДОЛЖНО быть доступно автору
для перехвата. Старые сигнатуры и соглашение case ДОЛЖНЫ сохраняться. `[N]` (р.0.2.0)

## 4. Функциональные требования: операции

### 4.1. Проверка check

4.1.1. `check(name, actual, expected)` ДОЛЖЕН записывать name, actual, expected,
passed в checks, печатать PASS/FAIL и при actual != expected возбуждать CheckFailed. `[R]`

### 4.2. Чтение value

4.2.1. `value(expression)` ДОЛЖЕН вычислять gdb.parse_and_eval, отклонять optimized-out,
загружать ленивое значение и возвращать int; неизвестный символ/макрос НЕ ДОЛЖЕН
подменяться нулём. `[R]`

### 4.3. Сравнение fields

4.3.1. `fields(expression, expected)` ДОЛЖЕН по порядку expected читать
`(<expression>).<поле>` и вызывать check; строковое ожидание ДОЛЖНО вычисляться
как C-выражение через value. Первая неуспешная проверка прекращает операцию исключением. `[R]`

### 4.4. Точка breakpoint

4.4.1. `breakpoint(function, temporary=False, when=None)` ДОЛЖЕН создавать аппаратную
точку; при исчерпании breakpoint_limit действующими принадлежащими Target точками
ДОЛЖЕН отказать до создания; pending-точка ДОЛЖНА удаляться с ошибкой absent from ELF;
when задаёт условие, temporary — временность. Успешный вызов возвращает gdb.Breakpoint. `[R]`

### 4.5. Достижение reach

4.5.1. `reach(function, when=None)` ДОЛЖЕН создать временную аппаратную точку,
один раз продолжить исполнение и проверить через check номер точки в последней
остановке, имя кадра и истинность when при его наличии; созданная точка ДОЛЖНА
удаляться при любом исходе, если остаётся действующей. `[R]`

4.5.2. reach ДОЛЖЕН сравнивать имя кадра без суффикса clone, завершающих
const/volatile и списка параметров; исходное имя ДОЛЖНО сохраняться в записи остановки. `[R]`

### 4.6. Запись set_value

4.6.1. `set_value(expression, value)` ДОЛЖЕН прочитать значение до записи,
выполнить set variable, прочитать значение после и добавить expression/value/before/after
в mutations. Допустимость MMIO-записи обеспечивает автор сценария. `[R]`

### 4.7. Принудительный возврат force_return

4.7.1. `force_return(expression)` ДОЛЖЕН выполнить команду GDB return с выражением
expression и записать operation=force_return, имя newest_frame и expression в mutations.
Возврат действует на выбранный кадр GDB, пропускает оставшийся код функции и НЕ ДОЛЖЕН
считаться откатом уже выполненных эффектов или выполнением finish. `[U]` (р.0.2.4)

Текущая реализация записывает имя newest_frame, хотя команда return действует
на выбранный кадр. Если сценарий сам изменил выбор кадра через GDB, имя в журнале
может не соответствовать кадру возврата; гарантия согласованности пока отсутствует.

### 4.8. Очистка clear

4.8.1. `clear()` ДОЛЖЕН удалять действующие точки Target, включая fault handlers,
и очищать список владения. `[R]`

### 4.9. Запись record

4.9.1. `record(name, data) -> None` ДОЛЖЕН после успешной проверки добавлять
глубокую независимую копию data; повторяющиеся имена допустимы. `[N]` (р.0.2.0)

4.9.2. name ДОЛЖЕН быть непустым точным встроенным str. data ДОЛЖЕН состоять
только из точных встроенных None/bool/int/конечного float/str/list/dict со строковыми
ключами; подклассы, tuple, bytes, объекты GDB и циклы ДОЛЖНЫ отклоняться.
Текст ДОЛЖЕН допускать UTF-8 без непарных суррогатов. `[N]` (р.0.2.0)

4.9.3. Запись ДОЛЖНА содержать ровно sequence/name/data; sequence начинается с 1
и растёт на 1 после успешной записи. Отказ проверки НЕ ДОЛЖЕН менять журнал,
счётчики бюджета или следующий sequence. `[N]` (р.0.2.0)

4.9.4. Журнал ДОЛЖЕН принадлежать одному вызову сценария и начинаться пустым;
continue/reset/clear внутри вызова НЕ ДОЛЖНЫ очищать его. После завершения вызова
владение журналом завершается; полученные копии остаются обычными Python-данными. `[N]` (р.0.2.0)

4.9.5. record/records НЕ ДОЛЖНЫ обращаться к MCU/GDB, продолжать исполнение,
писать файлы, автоматически экспортировать записи в report или менять исход проверки.
sequence ДОЛЖЕН означать только порядок добавления, без автоматического PC/time/image
и обещания атомарного снимка MCU. `[N]` (р.0.2.0)

### 4.10. Чтение records

4.10.1. `records(name=None) -> list[dict]` ДОЛЖЕН возвращать глубокие независимые
изменяемые копии в порядке добавления. None выбирает все записи, непустой точный
str — точное совпадение имени; отсутствие совпадений даёт []. sequence при
фильтрации НЕ ДОЛЖЕН перенумеровываться. `[N]` (р.0.2.0)

4.10.2. Изменение входа record и результата records НЕ ДОЛЖНО менять сохранённые
записи или другие результаты records. Отдельный язык запросов НЕ ДОЛЖЕН вводиться
первым пакетом: фильтры, срезы, any/all и статистика используют Python. `[N]` (р.0.2.0)

### 4.11. Эффективная конфигурация config

4.11.1. `t.config` ДОЛЖЕН предоставлять глубоко неизменяемое отображение api/target/image
одного снимка запуска с применёнными defaults. Вложенность исходных документов
ДОЛЖНА сохраняться: `config['api']['records']`, `config['target']['mcu']`,
`config['image']['image']['end']` при наличии политики image. `[N]` (р.0.2.0)

4.11.2. При отсутствии файла api config ДОЛЖЕН содержать defaults API; при
отсутствии image значение image ДОЛЖНО быть None. Неизвестные поля/секции api.toml
ДОЛЖНЫ сохраняться доступными сценарию, без интерпретации модулем. `[N]` (р.0.2.0)

### 4.12. Свойства конфигурации config_props

4.12.1. `t.config_props` ДОЛЖЕН предоставлять глубоко неизменяемое отображение
api/target/image. Для выбранного файла значение ДОЛЖНО содержать data (разобранный
TOML без добавленных defaults), sha256 (исходных байтов) и reference (фактически
выбранная ссылка); для отсутствующего файла — None. Комментарии/форматирование
не входят в data; reference не обещает доступность пути на принимающем хосте. `[N]` (р.0.2.0)

4.12.2. config и config_props ДОЛЖНЫ описывать одни и те же захваченные данные;
изменение/удаление исходных файлов после захвата НЕ ДОЛЖНО менять текущий запуск.
Типы TOML ДОЛЖНЫ сохраняться, с неизменяемыми контейнерами вместо изменяемых. `[N]` (р.0.2.0)

## 5. Требования к интерфейсам

5.1. Сценарий ДОЛЖЕН пользоваться метаданными case и соглашением вызова Target,
определёнными общим ТЗ; API НЕ ДОЛЖЕН вводить второе соглашение сбора сценариев. `[R]`

5.2. Классификация CheckFailed как FAIL и остальных исключений как ERROR ДОЛЖНА
оставаться ответственностью агента по общему ТЗ. `[R]`

5.3. Ошибки входа record/records ДОЛЖНЫ давать RecordError с code из набора
invalid_name/unsupported_type/invalid_text/non_finite/cycle/limit_exceeded.
Неверный фильтр records ДОЛЖЕН давать invalid_name. При limit_exceeded поле limit
ДОЛЖНО иметь одно из значений records/nodes/depth/text_bytes/integer_bits.
Текст сообщения и приоритет при нескольких нарушениях не являются контрактом. `[N]` (р.0.2.0)

5.4. Системные исключения, включая MemoryError, НЕ ДОЛЖНЫ маскироваться под
RecordError. Необработанный RecordError ДОЛЖЕН классифицироваться агентом как
ERROR, а несовпадение check — как FAIL по п. 5.2. `[N]` (р.0.2.0)

5.5. Выбор, валидация и перенос конфигурации ДОЛЖНЫ соответствовать разделу 5.20
[общего ТЗ](TECHNICAL_SPECIFICATION.md); API НЕ ДОЛЖЕН самостоятельно повторно
читать исходные файлы или выбирать другую конфигурацию. `[N]` (р.0.2.0)

---

5.6. Публичный импорт ДОЛЖЕН иметь вид `from stm32_gdbtest import RecordError`.
RecordError ДОЛЖЕН наследовать ValueError и импортироваться на host без GDB;
импорт исключения НЕ ДОЛЖЕН требовать запуска отладчика. `[N]` (р.0.2.1)

## 6. Нефункциональные требования

6.1. Вызовы GDB API ДОЛЖНЫ выполняться в основном потоке GDB. `[R]`

6.2. Новая аппаратная проверка ДОЛЖНА фиксировать MCU, GDB, backend, ELF/manifest
и ограничения результата; PASS одной связки НЕ ДОЛЖЕН объявлять поддержку всех плат. `[N]`

6.3. Лимиты журнала ДОЛЖНЫ задаваться через api.toml, таблицу records, по таблице
ниже. Известное значение ДОЛЖНО быть целым от 1 до максимума включительно,
bool исключён; отсутствующее значение ДОЛЖНО получать default. Неверные настройки
ДОЛЖНЫ отклоняться до подключения к MCU по общему ТЗ 5.20.7. `[U]` (р.0.2.1)

6.4. max_records, max_nodes и max_text_bytes ДОЛЖНЫ ограничивать весь журнал;

служебные поля обёртки не учитываются. `[N]` (р.0.2.0)

до завершения приёмки. Логические лимиты НЕ ДОЛЖНЫ объявляться гарантией RSS/latency
или ограничением числа удерживаемых сценарием копий. `[U]` (р.0.2.3)

## 7. Совместимость и эволюция

7.1. Ревизия спецификации НЕ ДОЛЖНА автоматически менять runtime-версию.
Для принятого совместимого первого пакета целевая версия модуля ДОЛЖНА быть 0.2.0
с сохранением API_VERSION=1. Рабочая интеграция ДОЛЖНА обозначаться
__version__=0.2.0.dev0; номер выпускного prerelease определяется отдельно. `[U]` (р.0.2.2)

7.2. Изменение поведения ДОЛЖНО сопровождаться новой ревизией документа с описанием
совместимости и ссылками на проверки; добавление платы без изменения контракта
ДОЛЖНО фиксироваться в матрице поддержки без автоматического изменения runtime API. `[N]`

7.3. Начальная схема api.toml ДОЛЖНА иметь обязательное целое schema=1.
Версия схемы, ревизия API и версия пакета НЕ ДОЛЖНЫ считаться взаимозаменяемыми. `[N]` (р.0.2.0)

7.4. Набор известных имён и их смысл ДОЛЖНЫ определяться schema. Новый
распознаваемый параметр ДОЛЖЕН вводиться новой схемой и явным переходом;
неизвестное поле старой поддерживаемой схемы НЕ ДОЛЖНО получать новый смысл.
Для данных потребителя СЛЕДУЕТ использовать user; модуль НЕ ДОЛЖЕН интерпретировать
эту секцию или запрещать остальные неизвестные поля api.toml. `[N]` (р.0.2.0)

7.5. Перенос расширения в ядро и выпуск ДОЛЖНЫ требовать отдельного разрешения;
приёмка ДОЛЖНА проверить прежние сценарии и новую поверхность. Наличие прототипа
или новая ревизия документа НЕ ДОЛЖНЫ считаться такой приёмкой. Разрешение владельца
от 03.10.2026 на перенос первого пакета НЕ ДОЛЖНО считаться разрешением выпуска. `[U]` (р.0.2.2)
