# Аппаратная приёмка HAL F030

[Документация](index.md) → HAL F030 · [English](../en/F030_HAL_VALIDATION.md)

Протокол этапа: числа тестов и планы ниже относятся к указанной ревизии.
Текущий состав — [STATUS](STATUS.md), подготовка выпуска — [rc.2](RC2_READINESS.md).

Автономный [fixture](../../tests/hal-f030/README.md) прошёл аппаратную проверку
на NUCLEO-F030R8 через родной ST-Link V2J45M31, SWD 1 МГц и OpenOCD 0.12.0.
Дата: 01.10.2026 (локальная); начало отчёта: 20260930T195222.241532Z (UTC).
Хост Windows, xPack GCC 13.3.1-1.1, GDB 14.2.90.20240526-git.
База модуля cc2cf19, firmware перенесена в a3898ff; новый run_hw.py выполняет
приёмку через штатный CLI. [План и происхождение](F030_HAL_REGRESSION.md).

| Основные HAL-сценарии | 17/17 PASS |

| Зависание Python после достижения loop, timeout 5 с | Ожидаемый ERROR, TimeoutExpired, reset_run (host recovery) |
| ADC после recovery | PASS |
| Возврат исходной HAL-прошивки потребителя, boot и blink | 2/2 PASS, MCU оставлен работающим |

Первый boot записал fixture и проверил образ. Все положительные запуски имеют
image_verified и reset_run. Маркер stall-entered.txt подтверждает, что таймаут
возник внутри достигнутого сценария, а не при запуске сервера. Это искусственное
зависание Python, не аппаратный отказ MCU. Всего 27 этапов, включая ожидаемый
ERROR; формулировка «27/27 PASS» к этому протоколу неприменима.

## Повторение

Предварительно собрать fixture по его README и проверить актуальность manifest
восстанавливаемого проекта. Из корня модуля, с явно выбранным согласованным стендом:

```sh
python -B tests/hal-f030/run_hw.py --stand <private-stand.toml> --restore-session <consumer-session.json>
```

Скрипт требует OpenOCD, flash=if-different, обе сессии STM32F030R8T6;
до первого сервера проверяет оба manifest. Использует fixture build/debug,
останавливается на первом неожиданном результате и в finally пытается вернуть
исходную прошивку с проверками boot/blink. Ошибка восстановления даёт ERROR,
а не заявление об успешном возврате. Это явная аппаратная команда с записью Flash,
не часть автоматического offline CI. Не запускать одновременно другой runner/IDE.

## Границы и дальнейшая работа

Сохранены [TECH-001, TECH-003, TECH-004, TECH-007](TESTING_TECHNIQUES.md):
HAL-макросы, callbacks/IRQ, инъекции через force_return и численные векторы.
HAL Sleep-сценарии не заменяют отдельное доказательство interrupted WFI в CMSIS.
Результат не распространяется на ST server/J-Link, Linux HW, GCC14/15, Release/LTO
или другие MCU. API и firmware этим этапом не изменены.

После публикации проверить Docs и полный Offline для итогового SHA; land выполнять
по порядку fixture → CI → validation. Затем обновить gitlink потребителя.
Удаление старого HAL-профиля — отдельный шаг после интеграции, не часть этой приёмки.
