# План 0.3.0: аудит и проектирование API сценариев

[Документация](index.md) · [English](../en/API030_PLAN.md)

Решение владельца от 04.10.2026: для версии **0.3.0** провести аудит API и
спроектировать новый набор операций. Согласованы направление и имена в таблице ниже
как предмет проектирования. Сигнатуры, модели результатов, ошибки, границы поддержки
и миграция ещё требуют согласования. Это план, а не действующий справочник методов.

Текущий кандидат остаётся 0.2.0rc1; [действующий API](api/index.md) и
[ТЗ API](../TECHNICAL_SPECIFICATION_API.md) не изменяются этим документом.
Цель 0.3.0 не задаёт автоматически API_VERSION, ревизию ТЗ API, номера схем или тег
предварительного выпуска. Реализация и публикация — последующие отдельные этапы.

## Целевой набор для проектирования

Скобки обозначают операцию, а не окончательную сигнатуру. settings и sources — свойства.

| Исходный API | Возможное развитие | Рекомендация |
| --- | --- | --- |
| check(name, actual, expected) | check с валидацией и независимым снимком данных | Сохранить имя и назначение; согласовать типы, ошибки, пределы и достоверность отчёта |
| value(expression) | read(path, ...) и evaluate(expression, ...) | Заменить после проектирования; чтение объекта отделить от вычисления C/C++-выражения |
| set_value(expression, value) | write(path, value, ...) | Заменить; явно описать допустимые объекты, частичные эффекты и политику readback |
| fields(expression, expected) | read(..., fields=...) + табличная техника check | Рассмотреть перенос в технику; удалять только после проверки покрытия всех прежних применений |
| breakpoint(...) | breakpoint(...) с управляемым объектом точки | Сохранить название; переработать владение, with/remove, параметры и очистку |
| reach(function, when) | reach(location, ...) с результатом операции | Сохранить имя, изменить контракт: навигация возвращает исход, проверка ожидания выполняется явно |
| force_return(expression) | ret(value, *, frame=...) | Принудительный возврат без исполнения остатка вызова; согласовать кадр, тип значения и журнал эффекта |
| clear() | Удаление конкретной точки/группы либо выход из with | Убрать из обычного использования; управление защитными fault guards отделить |
| case(...) | @test(...) | Переименовать декоратор и добавить раннюю проверку допустимой сигнатуры сценария |
| record()/records() | Те же методы + явное преобразование новых снимков | Сохранить принятый runtime-журнал; не вводить автоматический экспорт неявно |
| config | settings | Эффективные настройки захваченного запуска с defaults; неизменяемое свойство |
| config_props | sources | Исходные данные без defaults, sha256 и reference по ролям; неизменяемое свойство |
| Нет отдельного метода | resume(...) | Аналог continue: продолжить до следующей остановки и вернуть её описание |
| Нет отдельного метода | step(...) | Ограниченное число шагов; инструкция/исходник, вход/проход поверх вызова |
| Нет отдельного метода | watch(...) | Точка на доступ к данным; явно задать чтение/запись и аппаратные ограничения |
| Нет отдельного метода | finish(*, frame=...) | Естественный возврат уже выполняющегося вызова с доступным результатом; текущий вызов по умолчанию |
| Нет отдельного метода | until(location=None, ...) | Отдельная навигация в текущем вызове; согласовать GDB-семантику вариантов с позицией и без неё |
| Нет отдельного метода | call(...) | Дополнительный вызов функции прошивки по инициативе сценария; отдельно от finish/ret |
| Прямой gdb.execute(...) | execute(command) | Явный доступ к командам GDB с журналированием и правилами инвалидации |
| Прямой доступ к кадрам GDB | context(...)/frames(...) | Общая модель снимков и ссылок на кадры для чтения, навигации и возврата |

return, break и continue — ключевые слова Python; выбраны ret, breakpoint и resume.
Имя code_point не используется. Имя run_to заменено на reach в проектируемой поверхности.
Сохранение имени reach не означает сохранения прежней семантики встроенных check.

## Различия, которые нужно сохранить в контрактах

- resume ждёт следующую остановку, reach направлен к указанной цели без ограничения
  текущим вызовом. Посторонние остановки не должны скрываться повторным продолжением.
- until имеет собственную семантику GDB: без позиции она не сводится просто к «следующей
  строке текста». При проектировании отдельно сверить адреса, строки, циклы и выход из
  кадра. Итоги target_reached/frame_exited/interrupted и их имена пока не утверждены.
- finish исполняет оставшийся код вызова; ret пропускает его; call создаёт новый вызов.
  Для finish по умолчанию предполагается самый внутренний вызов; явный старший frame
  и разные виды кадров требуют отдельной проверки.
- read не должен превращаться в неограниченный evaluator под обещанием безопасного
  чтения. RAM, MMIO, указатели, locals, регистры CPU и эффекты evaluate согласуются явно.
- Снимок — исторические данные, handle — управляемый ресурс, FrameRef — ссылка с
  ограниченным сроком актуальности. Не подменять эти сущности одной моделью объекта.
- Операции управления возвращают фактический исход; автор явно проверяет ожидание.
  Ошибка выполнения не маскируется обычным результатом. Внешний timeout может оборвать
  вызов без возвращаемого объекта; итоговый ERROR и recovery относятся к runner.

## Совместимость и критерии принятия

До 1.0 несовместимые изменения допустимы, если выгода обоснована и миграция описана.
Возможны временные адаптеры либо одновременное удаление старых имён; вариант и срок
нужно согласовать. Проверять не только исходники потребителя, но и сценарии в ранее
собранных пакетах запуска. Распаковка старого пакета не доказывает совместимости API.
Новый смысл неизвестных полей старой схемы конфигурации не вводится молча.

Критерии: однозначное назначение, удобная композиция, достоверные отчёты, явные эффекты,
управляемые ресурсы, предсказуемые ошибки, отсутствие скрытых resume/retry и достаточное
покрытие положительных/отказных случаев. Одно сокращение имени или числа строк не
является достаточным основанием замены. Потерю прежней возможности согласовывать явно.

Исследовательские планы, прототипы и сырые результаты хранятся локально по правилам
[сопровождения](maintenance.md). Публичный план фиксирует принятую цель и состав
проектирования; опубликованные контракты и итоги не должны ссылаться на локальные материалы.
