# API, CLI и подключение

[Документация](index.md) · [English](../en/API.md)

Документ описывает **0.6.x / API_VERSION=3**. Контракты операций и границы поддержки —
в [справочнике](api/index.md), изменения для пользователей — в [истории переходов](RELEASE_CHANGES.md).

## Конфигурация и исполнение

Предпочтительный вход — `SESSION_CONFIG` в CMake и `[config]` в session.toml:
`target`, `api`, `image`, `[mmio].svd` и `[data]` выбираются явно по своим контрактам.
[Структура HIL и пути](HIL_INSPECT.md), [inspect](HIL_INSPECT.md), [SVD](SVD.md).
Если SESSION_CONFIG выбран, не смешивайте его с PROFILE и отдельной image policy.
`t.profile` предоставляет неизменяемые данные и происхождение; `record`/`records` — журнал
одного сценария. Для сохранения в файл включите `[results] capture = true`.
[Результаты и экспорт](RESULTS.md) проверяются отдельно от исхода сценария.

Обычный `def` использует синхронные навигацию и `call`. В `async def` они требуют `await`;
`resume(sync=False)` запускает живое окно, `await wait()` ждёт, `await halt()` останавливает.
Данные доступны только при подтверждённой остановке. `ret` и методы данных немедленны;
`execute` в async запрещён. [Полный контракт](LIVE_EXECUTION.md).

Для периферии используйте `t.mmio.read/write` и SVD. Обычный `write` — не безопасная
замена MMIO; скрытые вызовы функций в выражениях данных запрещены. [MMIO](MMIO.md).
`memory` требует полный ответ, `write` вычисляет RHS один раз; ни один метод не откатывает
все побочные эффекты. C++ preflight не расширяет допустимые имена `call`.

## Подключение из исходного дерева

```cmake
include("${STM32_GDBTEST_SOURCE_DIR}/stm32_gdbtest/cmake/STM32GDBTest.cmake")
stm32_gdbtest_attach(firmware_target
    PROFILE_DIR "${CMAKE_CURRENT_SOURCE_DIR}/profile"
    MANIFEST_INPUTS "${CMAKE_CURRENT_SOURCE_DIR}/profile/firmware_FLASH.ld")
```

- `STM32_GDBTEST_SOURCE_DIR` — корень checkout с пакетом `stm32_gdbtest`; в примере
  потребителя это cache PATH.
- Проект обязан включить CTest (`include(CTest)` или `enable_testing()`) и создать
  firmware target до вызова `stm32_gdbtest_attach`.
- Поддерживается один firmware target верхнего каталога CMake, генератор Ninja,
  каталог сборки внутри `PROJECT_SOURCE_DIR`. Сборка, build manifest и подготовка
  и аппаратный запуск работают на Windows и Linux ([Linux-стенд](LINUX_STAND.md)).
- `PROFILE_DIR`, `PROFILE` и пути `MANIFEST_INPUTS` задаются абсолютными. В
  `PROFILE_DIR` находятся `tests/board/test_*.py`, `tests/requirements.md`, при
  использовании контрактов `tests/contracts.json` и `target.toml`. Каталог сценариев
  для новых проектов называется `tests`; прежнее имя `Tests` также поддерживается.
- `PROFILE` — описание MCU отдельным файлом вместо `PROFILE_DIR/target.toml`. Так
  несколько вариантов MCU одной прошивки используют общие сценарии, требования и
  контракты; каждый вариант — своя сборка со своим `PROFILE`:

  ```cmake
  stm32_gdbtest_attach(firmware_target
      PROFILE_DIR "${PROJECT_SOURCE_DIR}/hil"                    # общий tests/
      PROFILE "${PROJECT_SOURCE_DIR}/hil/profiles/${MCU}.toml")  # G474.toml, G431.toml
  ```
- `MANIFEST_INPUTS` добавляет файлы в снимок manifest и в зависимости перелинковки.
- `SELF_TESTS` включает host-тесты самого модуля (`host.hwtest`); потребителю не нужен.
- stm32-cmake-yml не является зависимостью API.

CMake создаёт тесты: `hw.<ID>` (аппаратный, метки `hw` и метки сценария,
`RESOURCE_LOCK stm32_swd`), `prepare.<ID>` (подготовка без оборудования, метки
`host` и `prepare`) и `host.traceability`. Цель `check-hw` запускает весь CTest
с отчётом JUnit.

Cache `STM32_GDBTEST_GDB` выбирает GDB с Python, `STM32_GDBTEST_STAND` — локальный
TOML стенда. Остальные переменные CMake с этим префиксом внутренние. Генерируемые
`session.json`, `tests.cmake` и `build-manifest.json` не редактируются вручную.
Функция `stm32_gdbtest_register` — внутренняя.

## Сценарии Python

```python
from stm32_gdbtest import case

@case("HW_GPIO", timeout_s=20, labels=("gpio",), contracts=("gpio_macros",))
def gpio(t):
    t.reach("loop")
    t.check("GPIOC clock", t.evaluate("__HAL_RCC_GPIOC_IS_CLK_ENABLED()"), 1)
```

Пример требует прошивки с функцией `loop` и объявленного контракта `gpio_macros`;
это не универсальный тест любого STM32.

- Декоратор импортируется обычным Python без модуля `gdb`. При сборе код теста не
  выполняется: ID, timeout, labels и contracts читаются из AST и должны быть литералами.
- ID — `HW_[A-Z0-9_]+`; `timeout_s` — целое 1…300 с (по умолчанию 20); labels —
  `[a-z0-9_-]+`; имена контрактов — `[a-z][a-z0-9_]+`.
- Декоратор называется `case` без псевдонима. Тест — функция верхнего уровня с одним
  параметром Target; агент вызывает её после reset и остановки в `main`.
- Вспомогательный код проекта доступен из корня потребителя. Тестовые hooks в
  прошивку не добавляются.

Публичные операции переданного Target (модуль `target` импортируется только в GDB):

| Операция | Контракт |
| --- | --- |
| [`check(name, actual, expected)`](api/check.md) | Запись результата; несовпадение вызывает `CheckFailed` → FAIL |
| [`read(path)`](api/read.md) / [`evaluate(expression)`](api/evaluate.md) | Типизированное чтение объекта / вычисление выражения GDB/C |
| [`reach(location, condition=None)`](api/reach.md) | Временная аппаратная точка, `continue`, проверка причины остановки, кадра и условия (`when=` — прежнее имя `condition`); имя кадра сравнивается без `[clone …]` и параметров (клоны LTO) |
| [`breakpoint(location, temporary=False, *, condition=None)`](api/breakpoint.md) | Аппаратная точка (`Point`) с проверкой pending и бюджета профиля; `when=` — прежнее имя `condition` |
| [`write(path, value)`](api/write.md) | Явная запись с проверкой и журналом before/after; допустимость записи в MMIO проверяет автор |
| [`ret(value=None)`](api/ret.md) | Принудительный return из текущего кадра с результатом и журналом; тело функции не выполняется |
| [`clear()`](api/clear.md) | Удалить точки останова Target, включая точки на fault handlers |

`boot`, `close`, `on_stop`, `report`, `owned`, `stops` и создание Target —
внутренний жизненный цикл агента. Вызовы GDB допустимы только в его основном
потоке. `-g3` сохраняет макросы, но не неиспользуемые функции и символы;
см. [HAL-макросы](HAL_MACRO_GUIDE.md) и [контракты](CONTRACTS.md).

## CLI

Из корня checkout модуля (из другой папки — по абсолютному пути `stm32_gdbtest/cli.py`):

```powershell
python -B -m stm32_gdbtest --version
python -B -m stm32_gdbtest collect --tests examples/minimal-consumer/profile/tests/board
python -B -m stm32_gdbtest trace --tests examples/minimal-consumer/profile/tests/board --requirements examples/minimal-consumer/profile/tests/requirements.md
python -B -m stm32_gdbtest run --session examples/minimal-consumer/build/debug/hwtest/session.json --test HW_CONSUMER_GPIO --prepare-only
python -B -m stm32_gdbtest run --session examples/minimal-consumer/build/debug/hwtest/session.json --test HW_CONSUMER_GPIO --stand path/to/stand.local.toml
python -B -m stm32_gdbtest doctor --stand path/to/stand.local.toml
```

Логическое имя CLI — `stm32-gdbtest`; отдельный исполняемый файл появится при упаковке.

| Параметр `run` | Назначение |
| --- | --- |
| `--session` или `--package`, `--test` | Сгенерированный `session.json` или пакет подготовленного запуска и ID сценария |
| `--gdb`, `--workdir` | Для `--package`: GDB стенда (иначе поиск как у `doctor`) и каталог распаковки (по умолчанию `build/ddtt-packages`) |
| `--stand` | Локальный стенд; порядок выбора: `--stand` → `STM32_GDBTEST_STAND` → `session.stand`; с таблицей `[remote]` сервер запускается на хосте стенда по SSH, в отчёте — `server_host`, журнал SSH — `tunnel.log` |
| `--timeout` | Внешний предел времени GDB, 0 < t ≤ 300 с; по умолчанию `timeout_s` сценария |
| `--identity-policy warn\|strict` | Политика DEV_ID; порядок: CLI → `STM32_GDBTEST_IDENTITY_POLICY` → `warn` |
| `--image-policy` | Политика полного образа; альтернатива — абсолютный `STM32_GDBTEST_IMAGE_POLICY` |
| `--prepare-only` | Только шаги до GDB-сервера, без оборудования |
| `--interactive` | Пошаговый проход в отладчике Python: ожидание debugpy, без предела времени, результаты в `interactive-runs` ([подробно](MANUAL_DEBUG.md)) |
| `--debug-port`, `--debugpy` | Для `--interactive`: порт на 127.0.0.1 (по умолчанию 5678) и каталог пакета debugpy (по умолчанию из расширения VS Code или `STM32_GDBTEST_DEBUGPY`) |

`--prepare-only` выполняет все шаги до GDB-сервера: стенд (если выбран), профиль,
снимок ELF, build manifest, запрошенные контракты, секции и образ, включая полный
режим. Блокировка отладчика, сервер и подключение не используются; отчёт получает
`mode: prepare` и `hardware_accessed: false`. Стенд в этом режиме необязателен,
а если выбран — проверяется целиком, включая mapping J-Link.

`--interactive` выбирает режим только для этого запуска; сценарий, его `timeout_s` и
регистрация CTest не меняются. GDB до первого обращения к MCU ждёт отладчик на
`127.0.0.1:<порт>`, общий предел времени и предел async-сценария не действуют, Ctrl+C
отменяет запуск с восстановлением платы. Результат пишется в `interactive-runs` рядом с
`runs` с полем `execution_kind: "interactive"` и в автоматические сводки не попадает.
С `--timeout` и `--prepare-only` не сочетается.

`doctor [--gdb PATH] [--stand TOML] [--json]` проверяет окружение без обращения к
отладчику: host Python, GDB-Python ≥ 3.11 и binutils рядом с ним, CMake и Ninja,
каталог блокировок, стенд (для OpenOCD — наличие `interface/stlink.cfg`) и на Linux —
ST-Link и J-Link на USB с правами доступа. Итог — строки OK/WARN/FAIL (`--json` — список
`{name, status, detail}`); код 1 при FAIL. GDB ищется так: `--gdb` → `STM32_GDBTEST_GDB` →
`arm-none-eabi-gdb-py3`/`arm-none-eabi-gdb` в `PATH` → `bin` в `ARM_TOOLCHAIN_ROOT` → на
Windows каталог xPack по умолчанию в профиле пользователя. Для стенда с `[remote]`
локальные проверки OpenOCD и USB заменяются проверками хоста стенда по SSH (`remote`,
`remote-server`, `remote-lock`, `remote-usb`, предел 40 с).

`pack --session S --output P.zip [--test ID …] [--include PATH …]` готовит сценарии без
оборудования и пишет пакет подготовленного запуска; `run --package` проверяет SHA-256
каждого файла пакета и добавляет в отчёт поле `package`
([аппаратный CI](HARDWARE_CI.md)).

`collect --cmake/--workspace` — интерфейс генерации CMake, вручную обычно не нужен.

Коды `run`: PASS — 0, FAIL — 1, ERROR — 2; ошибка аргументов также даёт 2. Отказ
до создания каталога запуска не гарантирует JSON/JUnit. Ожидаемый отказ сохраняет
ERROR и не превращается в PASS.

Стабильные схемы: target 1, реестр контрактов 1, build manifest 1, runtime
compatibility 1, политика образа 1, пакет подготовленного запуска 1. `session.json` — внутренний артефакт без
обещания стабильной схемы. Прямые вызовы `runner`, `contracts`, `processes` —
внутренний API разработки; потребители используют CMake, CLI и операции Target.
Подробности: [подключение](GETTING_STARTED.md), [manifest](MANIFESTS.md),
[identity](TARGET_IDENTITY.md), [GDB-серверы](BACKENDS.md),
[владение отладчиком](DEBUGGER_OWNERSHIP.md). `STM32_GDBTEST_LOCK_DIR` задаёт на Linux
базовый каталог блокировок: по умолчанию системный каталог временных файлов (`/tmp`
или `TMPDIR`), внутри — `stm32-gdbtest-locks`.

## Проверка образа

По умолчанию Flash сравнивается по загружаемым секциям ELF (LMA), промежутки не
проверяются. BIN формируется только из этих секций с заполнением промежутков 0xFF.
Нужны GNU `arm-none-eabi-objdump` и `arm-none-eabi-objcopy` рядом с GDB. Это не
проверка CRC всей области.

Полный образ: `run --image-policy file.toml` или `STM32_GDBTEST_IMAGE_POLICY`
(CLI приоритетнее) выбирает диапазон `[image]` schema 1. Канонический BIN,
транспортный ELF, CRC-32/ISO-HDLC по readback, поля отчёта и ограничения —
[образы и CRC](IMAGES.md). Режим не добавляет код или CRC-поле в прошивку; CRC
считается на ПК, а не периферией MCU.

## Миграция A1 к 0.6.0

API_VERSION остаётся 3. `reason` MMIO теперь можно использовать без override.
Первичная ошибка исполнения/транспорта не заменяется отказом аудита; отдельные
диагностики и подтверждение cleanup описаны в [resume](api/resume.md),
[MMIO](api/mmio.md) и [RecordError](api/record-error.md). После успешного исполнения
отказ записи execution теперь ApiError/journal_unavailable, а не голый RecordError.
Лимиты, capture и формат записей не изменены; увеличивать их для сокрытия ошибки не нужно.

## A2.1: компактный журнал (0.6.0)

В `api.toml` выберите схему 2; схема 1 сохраняет прежние значения и границы.
По умолчанию используется `full`, компактный MMIO включается явно:

```toml
schema = 2
[journal]
representation = "compact"
[records]
max_records = 65536
max_nodes = 2097152
max_text_bytes = 16777216
```

Последние три значения — максимумы для длинных серий, а не defaults.

| Параметр | Default схемы 2 | Максимум схемы 2 |
| --- | ---: | ---: |
| max_records | 4096 | 65536 |
| max_nodes | 131072 | 2097152 |
| max_text_bytes | 1048576 | 16777216 |
| max_depth | 16 | 32 |
| max_integer_bits | 256 | 1024 |

В компактном MMIO original/effective/SVD SHA-256 сохраняются один раз в таблице
описаний; события содержат ссылку и идентификатор операции. Порядок, значения,
reason, override, attempt и result сохраняются без агрегации. Отсутствующий result
не означает успех. Пользовательский `record("mmio.attempt", ...)` остаётся
пользовательской записью. Лимиты узлов/текста считают компактное хранение, включая
его ссылки и описания; логическая глубина данных не увеличивается от кодирования.
Это не лимит RSS, времени или удерживаемых сценарием копий.

`records()` возвращает прежние независимые sequence/name/data, раскрывая ссылки.
Материализация компактного журнала ограничена 2097152 узлами, 16 MiB текста,
глубиной 32 и 1024 битами целого; превышение — RecordError с
`details.scope="materialization"`, без частичного списка. Большая серия может
поместиться в компактное хранение, но не в развёрнутую выборку: выбирайте имя,
не вызывайте `records()` на каждой итерации.

При `[results] capture=true` full сохраняет `records.json` schema 1, compact —
schema 2 с таблицей definitions. Сохранение идёт частями, без полного раскрытия.
Общий читатель `stm32_gdbtest.result_capture.read(directory, report)` проверяет
обе схемы и возвращает логические записи; `materialize=False` позволяет обходить
раскрытые записи по одной. Сам JSON при этом читается в память целиком: это не
потоковый JSON-парсер и не гарантия постоянного RSS. Читатель проверяет хеш,
идентичность прогона, sequence, ссылки, пары операций и описание событий.
Лимит файла records — 64 MiB, независимо от бюджета журнала; превышение даёт
ошибку захвата, исходный вердикт сценария сохраняется. Лимиты других JSON-входов
экспортёра остаются 16 MiB. Старому потребителю schema 2 нужен обновлённый читатель.

Миграция добровольная: API_VERSION остаётся 3; схема конфигурации API, схема
records и схема капсулы — разные номера. Схема 2 переносится через runner/пакет
с проверкой соответствующего отпечатка defaults и максимумов. Исполнение,
таймауты и число обращений к MMIO не меняются; summary/truncate сюда не входят.

[замеры A2.1](../development/journal-a21-measurements.md).

## Журнал отчёта и вывод (0.6.0, A2.2)

В `api.toml` schema 2 можно независимо включить компактное хранение result и
сократить вывод. По умолчанию оба значения — `full`:

```toml
schema = 2
[report]
representation = "compact"
console = "failures"
```

`compact` сохраняет **все** checks/stops/mutations/evaluations/executions/resets,
их порядок и значения. `report_schema=2` не совпадает со схемой `records.json`:
это разные документы. Checks продолжают выполняться; перехваченный CheckFailed
остаётся отказом. `failures` скрывает строки PASS и полную копию JSON в stdout/JUnit,
оставляя ошибки, предупреждения и сводку со ссылкой на result. Это не фильтр проверок.
`execution_summary` — производная сводка, не самостоятельное свидетельство:
таймаут wait не закрывает окно и не доказывает остановку.

Общий читатель проверяет хеши блоков, ссылки, логическое число событий и полноту:

```python
from stm32_gdbtest.report_data import read
report = read("result.json")  # прежние списки после проверки схемы 1/2
report = read("result.json", materialize=False)  # последовательный обход коллекций
for check in report.get("checks", []):
    print(check["name"], check["passed"])
```

Для стороннего инструмента, который умеет только старый result:

```console
python -m stm32_gdbtest.report_data result.json result-full.json
```

Выход должен быть новым файлом. Чтение compact через обычный json.load и оценка
только status — **неправильно**: так можно пропустить коллекции или повреждение.
Штатные runner, coverage, result-index, export и stand-loop используют общий читатель.
Признаки report_storage_error/report_audit_error_count запрещают подтверждать
пригодность свидетельства; исходный результат сценария сохраняется отдельно от
ошибки артефакта и кода команды.

В compact завершённые события сохраняются блоками до 128 строк или 1 MiB
накопленных JSON-байтов во временный файл; одна большая строка допускается отдельно.
`reach` фиксирует stop после заполнения frame, `write` — после обратного чтения,
включая его отказ. Мутация возвращённого словаря не переписывает историю compact.
Буфер не вызывает дополнительных GDB/MMIO-чтений или repr при накоплении.
Нестандартные Python/GDB-объекты удерживаются до финальной сериализации с прежним
late repr; максимум 128 таких строк на коллекцию. Для предсказуемых снимков передавайте
обычные JSON-значения. Это ограничение хранения, а не гарантия чистоты пользовательского repr.

Пределы compact: 65536 строк на коллекцию, 16 MiB файла, 64 MiB раскрытых строк,
64 MiB временного потока на коллекцию; глубина проверяемого документа 40,
2097152 узла закодированного JSON. Буфер обычных событий ограничен 128 строками,
но размер строки, отложенные объекты и финальная сериализация тоже расходуют память:
постоянный RSS не обещается. Превышение бюджета, ошибка диска или повреждение —
явный отказ, не усечение. Публикация result атомарна. Первичная ошибка и ошибка
аудита сохраняются раздельно; неполная история не становится PASS.

Проверки: `tests/host/test_report_data.py`, `tests/renode-backend/run_report.py`.
Общий читатель и публикация full также ограничены 16 MiB файла.
Режим `full` остаётся совместимым по структуре; форматирование JSON не является контрактом.

## Сводки и уровни вывода (A2.3, 0.6.0)

В api.toml schema 2 `[report] console="summary"` добавляет сгруппированный итог
в терминал и JUnit. `full` и `failures` сохраняют прежний смысл; default — `full`.
Это независимо от `representation="full"/"compact"`: все проверки выполняются,
все события сохраняются. Новых методов Target и сокращения журнала нет.

Сводка `summary.json` (schema 1, derived=true) строится runner после сохранения
итогового result, через общие читатели result/records. Её можно воспроизвести без GDB:

```console
python -m stm32_gdbtest.report_summary build/run/result.json
python -m stm32_gdbtest.report_summary build/run/result.json --verify
```

Первая команда явно пересоздаёт summary.json рядом с result, вторая проверяет
схему, SHA-256 источников и совпадение с повторным расчётом. Оба режима печатают JSON.
Программные интерфейсы: `report_summary.build(path)` (без записи), `write(path)` и
`read(path)` (проверка существующей сводки). Исходные файлы офлайн-команды не изменяют.
Старый файл сводки удаляется до перестроения: неудача не оставляет старый зелёный итог.

Раздельно показаны исход сценария, захват, очистка и код команды. В коллекциях —
точные числа **сохранённых** событий, группы, ссылки на нулевой индекс коллекции;
для execution — records.sequence (с 1), операции, исходы, поколения и окна.
Отсутствующая коллекция обозначается not_recorded. Это не доказательство нулевого
числа физических операций. Пользовательские измерения автоматически не усредняются.
Группа проверок с разными ожиданиями получает different_expectations=true;
промежуточный FAIL учитывается всегда и его группа/ссылка показывается приоритетно.

analysis=complete означает, что запрошенные источники проверены и доступны для этого
представления, **не** что они достаточны для утверждения DDTT. При отсутствующем или
повреждённом records, ошибках аудита и недостаточных сведениях о поколении — partial
с причинами. runtime execution_summary не используется как доказательство сохранения
событий. Wait-timeout не закрывает окно; поколения не объединяются. Последнее состояние
closed означает зафиксированную остановку, а opened=false — отсутствие зарегистрированного
начала этого окна. Ошибка без поколения остаётся unresolved, а не относится к выдуманному.
Время MCU не вычисляется по времени хоста.

Вывод ограничен 100 группами на коллекцию и 20 ссылками на группу, 100 окнами;
числа omitted показывают скрытое представление. Счётчики вычислены по всему источнику.
Текстовые подписи/диагностика имеют preview до 256 символов, shortened и хеш полного текста;
полные ошибки доступны по ссылке на поле result и сохраняются в обычном выводе ошибок.
Предел файла сводки — 1 MiB; лимиты result/records не увеличены. Количество групп
ограничивает представление, а не память построителя: он работает в пределах бюджетов
входных читателей, постоянный RSS не обещается.

Если построитель/публикация сводки отказали, runner сохраняет summary_error отдельно,
оставляет исход сценария и события, даёт код команды 2 и JUnit infrastructure error.
В терминале/JUnit показано analysis=unavailable. Непригодный source-result в офлайн CLI
даёт ненулевой код без нового summary.json. Сводка не подтверждает DDTT и не заменяет
проверки порядка, времени или восстановления: экспортёр использует первичные события.

Правильно: открыть сводку, перейти к событию и проверить условия утверждения.
Неправильно: считать first/last полной историей, partial — полным журналом, или
подтвердить покрытие только по status/числу успешных групп в summary.json.
Проверки — `tests/host/test_report_summary.py`, `tests/renode-backend/run_report.py --summary`.

Важная граница A2.3: `mutations` не всегда содержит самостоятельный вердикт каждой
операции. Для коллекций вне checks поле failed=null означает «не классифицировано
как проверка», а не ноль отказов; причины нужно смотреть в событиях и диагностике.
Число записей воздействия не доказывает успешность записи/восстановления. Проверка
`--verify` может успешно проверить частичную сводку: код 0 подтверждает её целостность,
но для выводов обязательно читать analysis и issues. JSON-типы при сверке различаются.

Счётчики относятся к записям, а не к физическим событиям: например, одна остановка
может присутствовать в нескольких диагностических записях stops. Дедупликация по
предположению не выполняется; для числа физических событий нужен отдельный анализ.

## Полнота в строгом режиме (A3.1, 0.6.0)

Новых настроек и усечения пока нет: `on_limit` не поддерживается. API schema 1/2,
API_VERSION=3 и форматы full/compact сохраняются. В result добавлены `evidence`
(schema=1, policy=error) и `check_accounting`; это дополнительные поля строгого
режима, а не схема разрешённой потери данных A3.2.

Для checks/stops/mutations/evaluations/executions/resets и использованного журнала
records фиксируются attempted/saved/lost, state=complete/unavailable и номера
первого/последнего потерянного события. Это порядковые номера попыток записи,
не такты MCU; интервал между ними не означает потери каждого события внутри.
При отказе сериализации резервный result сохраняет число выполненных проверок,
а saved для удалённых коллекций становится 0. Отсутствие метаданных в старом
результате не является новым подтверждением полноты; исходный файл не дополняется.

`check_accounting` считает total/failed/unclassified до записи подробной строки.
Перехваченный CheckFailed остаётся FAIL даже при отказе сохранения этой строки.
Перехваченная потеря записи не позволяет нормально завершившемуся сценарию стать
PASS. Причины выполнения, capture, cleanup и command остаются раздельными;
команда с неполными свидетельствами получает код 2. SAVED означает публикацию
файла, а не наличие всех наблюдений. Ошибка входного типа/глубины — отказ валидации;
исчерпание накопительного бюджета records/nodes/text_bytes — потеря записи.
Запрос `records()` и его предел материализации не считаются новым событием журнала.

Резерв `evidence.diagnostics` независим от подробных коллекций: первые 16 ограниченных
диагностик, не более 64 KiB JSON, затем только diagnostics_total/diagnostics_omitted.
Он не хранит пользовательские значения. Старые диагностические поля A1 сохраняются
для совместимости; данный предел не является пределом всего отчёта или RSS.
Очистка не зависит от наличия места в резерве. Потеря процесса/памяти/диска не даёт
гарантии публикации даже резервного результата.

Общие читатели result/records проверяют типы счётчиков, суммы, диапазоны потерь,
согласованность saved с фактическими строками, проверки и бюджет резерва.
Сводка передаёт отдельные счётчики выполнения и сохранения; при потерях analysis=partial.
DDTT-экспорт консервативно блокирует подтверждение по неполному результату.
Правильно: проверить полноту, исходные строки, условия и cleanup.
Неправильно: считать пустые checks нулём выполненных проверок, код 2 только FAIL
прошивки или SAVED доказательством полноты.

### Где настраиваются квоты

`[records]` в api.toml задаёт max_records/max_nodes/max_text_bytes/max_depth/
max_integer_bits в пределах схемы. `[journal]` и `[report]` задают представление,
а report.console — вывод. Максимумы, пределы файлов (records 64 MiB, result 16 MiB),
коллекций/материализации, резерв и сводка пока закреплены в коде.
Пользовательский бюджет накопления и защитный предел читателя — разные ограничения.
A3.1 не увеличивает их и не вводит единую конфигурацию всех квот; это отдельное
решение перед A3.2. Произвольный подъём пределов в сценарии не является штатным API.

Поле `complete=true` внутри компактного блока коллекции подтверждает целостность
сохранённых строк, а не отсутствие потерянных наблюдений: для этого проверяется
`evidence.stores`. records.json следует анализировать вместе с result.json — в нём
находится учёт полноты и исходов. Счётчики включают служебные проверки runner.

[Журналирование](JOURNALING.md): источники, квоты, полнота, маршруты и статус schema 3 и применения квот journal.

## A3.2: квоты и усечение journal

В 0.6.0 API schema 3 исполняет `journal.on_limit="error"|"truncate"`.
Квоты `[records]` ограничивают накопление. При truncate исчерпание records/nodes/text_bytes
сохраняет только целые записи префикса; после первой потери подробности до конца сценария
не добавляются. Проверки, MMIO, живое окно и cleanup продолжаются. Полнота становится
`truncated`, но исход сценария сам по себе не меняется: возможен PASS с command=2,
SAVED и partial-анализом. DDTT-подтверждение по неполному прогону блокируется.

`records(name=None, *, require_complete=True)` отказывает с `RecordError`/`incomplete_evidence`
при неполноте всего журнала, даже при фильтре по имени. Для просмотра префикса явно укажите
`require_complete=False`; sequence сохраняется. Это разрешение чтения, а не признание
свидетельства полным. Ошибки типов, циклы, глубина, разрядность и жёсткий ресурсный предел
валидации не превращаются в усечение. Входы проверяются и после потери подробностей.

Описание и attempt MMIO сохраняются атомарно. Если result уже не поместился, attempt
не доказывает успех или отсутствие воздействия. Усечение не добавляет чтений или записей
регистра. Ошибки транспорта/хранения не подавляются. Причина первой потери и счётчики
attempted/saved/lost, first_lost/last_lost остаются в evidence; резерв диагностики ограничен.

Для политики truncate применяются evidence schema 2, result schema 3 (full/compact) и
records schema 3 с полнотой, сверяемой с result. Старые читатели отвергают новые форматы.
Используйте общие читатели модуля, а не самостоятельное раскрытие JSON.
Квоты и усечение report также применяются при исполнении; см. отдельный раздел ниже.

## A3.2: квоты и усечение report (0.6.0)

В API schema 3 `report.max_rows_per_collection` применяется отдельно к checks, stops,
mutations, evaluations, executions и resets в full и compact. Диапазон 1–65536,
default 65536. `report.on_limit="error"` — строгий отказ; `"truncate"` сохраняет
префикс каждой коллекции, не мешая другим коллекциям, journal, проверкам и cleanup.
Политики journal/report независимы; все их проверенные сочетания исполняются.

При truncate счётчик попыток продолжает расти, saved остаётся равен длине префикса,
lost и first_lost/last_lost описывают пропущенный хвост. Первая причина сохраняется
для каждой коллекции в ограниченном резерве. Независимый check_accounting считает
все проверки: FAIL нельзя убрать перехватом исключения или потерей строки. Сводка
группирует сохранённые строки, а check_accounting показывает полный учёт исходов.
PASS сценария при усечении допустим, но command=2, анализ partial, DDTT заблокирован.

Подавляется только достижение квоты строк, не ошибка временного файла, сериализации,
транспорта или восстановления. Если сохранённый префикс невозможно прочитать/записать,
состояние становится unavailable; причина усечения и независимые счётчики сохраняются.
Усечённые payload не материализуются: repr и ленивое чтение GDB ради пропущенной строки
не вызываются. Поэтому отсутствие строки не подтверждает корректность её значений.

Report truncate использует evidence schema 3 (`report-truncate`/`both-truncate`),
result schema 3 и records schema 3. Старые читатели, не знающие эту evidence schema,
отвергают результат. Journal-only truncate сохраняет evidence schema 2; прежние
строгие форматы читаются. Усечение report не делает полный journal неполным:
records() проверяет полноту journal, но анализ всего прогона учитывает все хранилища.

```toml
schema = 3
[journal]
representation = "compact"
on_limit = "error"
[report]
representation = "compact"
console = "summary"
on_limit = "truncate"
max_rows_per_collection = 1000
```

Это явный выбор частичного отчёта; для приёмки полного свидетельства оставьте error
и подберите достаточную квоту. Пример: tests/renode-backend/run_report_quota.py;
регрессии: tests/host/test_report_truncate.py. Проверки — без физических плат.

## A3.3: потребители неполных свидетельств

`results export` проверяет полноту всех хранилищ до проекции. Неполный источник
не попадает в records.csv/measurements.csv: диагностика и command=2 объясняют отказ.
Это не удаляет исходные result/records и не меняет PASS/FAIL/ERROR сценария.
Для осознанного просмотра префикса используйте общий читатель records и evidence,
а не обычную проекцию для приёмки. Полный журнал при усечённом report также не
является полным свидетельством прогона.

Индекс сохраняет вердикт, но добавляет диагностику неполноты; HTML показывает её
отдельно от integrity. Целый файл и SAVED не означают полноту. Сводка отмечает
truncated/unavailable у коллекций; группы считают сохранённые строки, независимый
check_accounting — все исходы. DDTT/LCOV оставляют UNKNOWN без DA, а не ложный ноль.

После обновления читателя пересоздайте производные summary, index и campaign по
сохранённым первичным файлам: старые сводки могут стать stale. Pack переносит
конфигурацию, а не подтверждает полноту будущего запуска. PDF-генератор навыка
получает подготовленные свидетельства, не заменяя этот допуск; автор обязан
проверить полноту перед переносом чисел в его входной документ.

Пример повторного анализа без Renode и платы:
`python tests/renode-backend/replay_consumers.py --runs <campaign>/runs --output <new-directory>`.
Host-матрица: test_partial_consumers.py (full/compact, journal/report/both, PASS/FAIL,
сохранение исходных файлов, положительный контроль полного источника).

## A4.1 — namespace/static (0.6.0)

Имя — простой идентификатор либо квалифицированное имя namespace/static, например
`demo::increment` или `Probe::twice`. В 0.6.0 квалифицированный вызов требует
единственного символа с вызываемым кодом и DWARF. Перегрузки отклоняются до исполнения
(`ambiguous_function`), нестатический метод — `unsupported_method`, отсутствующий
символ/код — `function_unavailable`. `object.method` остаётся `invalid_function`.
Для квалифицированного вызова поддержаны целые/bool и результат целое/bool/void;
проверяются число аргументов, диапазон и типы. Указатели, ссылки, float, variadic,
шаблонные имена и скрытые ABI-аргументы пока отклоняются.
Строки-выражения дают `unsupported_argument` также для обычной функции.
Preflight не доказывает безопасность исполнения. Квалифицированный вызов разрешается
при `may-call-functions off`, затем исполняется выбранный linkage-символ; его имя видно
в `expression`, а `function` сохраняет имя сценариста. Автоматического повтора нет.

Миграция: строковые аргументы замените заранее полученными числами; дополнительные вызовы выполняйте явно через call и используйте return_value. На этапе A4.1 this/signature ещё не были реализованы; текущий A4.2 описан ниже.

## A4.2 — this / signature (0.6.0)

`call(function, *args, this=None, signature=None, timeout=None)` поддерживает
явный объект и точную перегрузку в 0.6.0. В async def нужен await.
`this="&probe"` — адрес именованного объекта; `this="probe_ptr"` — именованный указатель.
Допускаются квалифицированные имена переменных. Поля, индексы, арифметика, cast и
вызовы в this пока не поддержаны. Указатель читается один раз; адрес объекта,
размер и выравнивание проверяются. Объект и память переменной-указателя должны
находиться в обычном окне SRAM 0x20000000–0x20100000 (верхняя граница исключена).
Это ограничение маршрута, не доказательство наличия/владения памятью или жизни объекта.
Сценарист обязан дойти до инициализации объекта и обеспечить безопасный контекст.

`signature="unsigned int(unsigned int) const"` задаёт результат, явные параметры
и квалификаторы метода. this в список параметров не входит; для нуля параметров — `()`.
Именованные типы/typedef разрешаются через GDB, сравниваются типы DWARF. Перегрузка
без signature остаётся ambiguous_function; несовпадение — signature_mismatch;
недопустимая грамматика — invalid_signature. Неоднозначный точный выбор тоже отклоняется.

Тип объекта должен точно совпадать либо допускать базу по A4.3b; const/volatile не отбрасываются. Методу с this
нельзя передать несовместимый объект (this_type_mismatch), отбросить квалификаторы
(this_qualifiers), передать null/MMIO/невыровненный адрес (invalid_this). this для
static/free даёт unexpected_this. Невиртуальное наследование описано в A4.3b. Полиморфные типы, ref-qualified методы,
конструкторы/деструкторы, операторы и шаблонные имена не входят в поднабор.
Скалярные аргументы и результаты A4.1 сохраняются; явные Pointer/Reference описаны в A4.3a. const-метод не гарантирует отсутствие побочных эффектов;
volatile-метод не получает транспортных гарантий MMIO.

Разрешение не исполняет код цели; затем вызывается ровно выбранный linkage-символ с
сохранённым значением this. В результате и mutations сохраняются this, this_address,
this_type, requested_signature, resolved_function и resolved_signature (по применимости).
При незавершённом dummy frame контекст не объявляется восстановленным; побочные эффекты
вызова автоматически не откатываются. Запрос в async остаётся ленивым до await.

```python
result = await t.call("Probe::choose", 2, this="&probe",
                      signature="unsigned int(int)", timeout=2)
t.check("selected overload", result["return_value"], 5)
```

## A4.3a — Pointer и Reference (0.6.0)

`from stm32_gdbtest import Pointer, Reference`. Это неизменяемые описания, не адреса
и не выражения GDB; создание не обращается к цели. Разрешение происходит при call,
а в async — только при await, на остановленном ядре.

- `Pointer("samples", count=4)` — начало именованного массива; count не превышает размер из DWARF.
- `Pointer("buffer_ptr", count=4)` — именованная переменная-указатель; одно чтение значения на аргумент.
- `Pointer("&state")` — один именованный объект; count больше 1 отклоняется.
- `Pointer.null()` — явный null только для параметра-указателя; null из обычной переменной отклоняется.
- `Reference("state")` — существующий именованный объект, без временного объекта и пользовательского преобразования.

Count задаётся в элементах, по умолчанию 1; допустимы целые 1..1048576, не bool.
Для явного null count=0. Имя — до 256 символов, допустим namespace. Поля, индексы,
арифметика, casts и вызовы в путях не поддержаны. Ошибка описания — invalid_argument.

Поддержан один уровень T*/T& для целочисленных, bool и неполиморфных class/struct с поддержкой наследования по A4.3b ниже. Проверяется точный тип или однозначная база; добавление const/volatile допустимо, снятие —
argument_qualifiers. Сигнатуры допускают эти типы и typedef; перегрузка выбирается
только явно. Для обычной C-функции описание также включает проверку DWARF.
T**, void*, function/member pointers, T&&, ссылки на массивы, объекты по значению и
указатели/ссылки в результате пока не поддержаны. Число не превращается в адрес.

До вызова проверяются размер, выравнивание и весь диапазон в обычной SRAM
0x20000000–0x20100000; память переменной-указателя проверяется перед чтением её значения.
Ошибки — argument_range, argument_type_mismatch, argument_qualifiers, unsupported_argument.
Для массива/объекта extent=known; для указателя extent=declared: это заявленная длина,
не доказательство выделения, владения или жизни памяти. Count НЕ ограничивает тело
функции и не связывается автоматически с другим аргументом длины. MMIO/Flash не допускаются.

В arguments сохраняется JSON-описание; argument_bindings содержит путь, фактический
и ожидаемый тип, адрес, count, bytes и extent. Для null — адрес/размер 0.
Модуль не добавляет снимок содержимого после вызова. Проверки изменения, соседних
данных и восстановления выполняются сценарием явно. Это не гарантия числа физических
доступов GDB-сервера; Reference передаётся выражением разыменования разрешённого адреса.
Все аргументы проверяются до единственного явного вызова; отказ не запускает функцию.

```python
from stm32_gdbtest import Pointer, Reference

result = await t.call("demo::sum", Pointer("samples", count=4), 4,
                      signature="unsigned int(const unsigned int *, unsigned int)", timeout=2)
t.check("sum", result["return_value"], 10)
await t.call("demo::bump", Reference("scalar"), signature="void(unsigned int &)", timeout=2)
```


## A4.3b — невиртуальное наследование (0.6.0)

`call("Base::step", ..., this="&derived")` явно выбирает реализацию Base::step.
Допустим точный неполиморфный тип или единственный путь от статического типа объекта
к базе: одиночное, многоуровневое и множественное невиртуальное наследование.
Автоматического поиска унаследованного имени Derived::step нет: указывайте класс,
где метод объявлен. Перегрузки по-прежнему выбираются точной signature.

Общий preflight для this, Pointer и Reference читает размещение типов из DWARF,
суммирует постоянные побайтные смещения и передаёт адрес базового подобъекта.
Для преобразования Pointer к базе count обязан быть 1, даже при нулевом смещении:
массив Derived не является массивом Base. Точные типы сохраняют правила A4.3a.
Pointer.null() не корректируется; const/volatile разрешено добавлять, но не снимать.

Проверяются весь исходный объект и итоговый подобъект: SRAM, размеры, выравнивание,
вложенность диапазонов. Обход ограничен 128 узлами и 16 типами в пути. Повторный путь
к одной базе — ambiguous_base; неизвестное, отрицательное, непобайтное смещение,
неполный тип или превышение пределов — base_layout_unavailable. Виртуальное
наследование/полиморфный исходный объект — unsupported_inheritance; ранее существующий
отказ неподдерживаемого типа параметра/метода сохраняется. Несовместимость типов,
квалификаторов и диапазонов использует прежние коды. Все отказы происходят до вызова
(stage=validation, effect=none); изменившееся сообщение не означает исполнения.

Поддержка проверена на ARM GCC/DWARF и GDB в нейтральном ELF. Динамические размещения
и vtable не читаются; downcast, cross-cast, виртуальная диспетчеризация и пользовательские
преобразования отсутствуют. public/private/protected не проверяются: это отладочный
доступ по размещению, а не проверка доступности C++-выражения компилятором. Полнота и
достоверность DWARF остаются предпосылкой; повреждённые метаданные не доказывают ABI.
Жизнь объекта, его конструирование и владение памятью остаются обязанностью сценариста.
Неподтверждённое размещение отклоняется, вычисления по содержимому объекта нет.

В результате call и журнале для this добавлены this_original_address,
this_expected_type, this_offset_bytes, this_base_path; this_address — переданный
скорректированный адрес. В argument_bindings: original_address, offset_bytes,
base_path; address и bytes описывают переданный подобъект. Путь перечисляет типы
от исходного до ожидаемого. Для явного null пути/исходного адреса нет.

```python
result = await t.call("Base::step", 3, this="&derived", timeout=2)
t.check("selected subobject", result["this_address"], expected_base_address)
await t.call("inspect_base", Reference("derived"), timeout=2)
```

В обычном def уберите await. Правильно: сравнить адрес с независимым эталоном,
проверить соседние поля и явно восстановить изменения. Неправильно: считать смещение
второй базы нулевым, передавать Derived[] как Base[] или обходить неоднозначность cast
в строке. Пример и отказы: tests/renode-backend/test_cpp.py, HW_CPP_INHERITANCE_*.


## A5.1 — применение и потребление подмены

API не расширен. Существующие write/ret проверены в [нейтральном примере](../../tests/controlled-input/README.md).
Readback SRAM и ret.applied не подтверждают потребление: продолжите до обработки,
проверьте полученное значение, ветку, пропущенные эффекты и следующий штатный вход.
Ret без await, навигация в async — с await. Обязательны отрицательные контроли и
явное восстановление. PASS модели не доказывает физический вход или периферию.

## Моделируемый вход GPIO и override (A5.2)

[Исполняемый пример](../../tests/modeled-gpio/README.md) отделяет внешний уровень
учебной модели от подмены SRAM/возврата. Проверяйте маршрут «источник → регистр →
потребление прошивкой», следующий уровень и соседний вход. `override` заменяет
описание SVD, но не превращает IDR в записываемый регистр: ACK может прийти после
игнорируемой записи. Отрицательный контроль сохраняет FAIL ложного утверждения,
а отдельный анализ проверяет ожидаемый отказ воздействия. Возвращайте состояние
прошивки **и** внешний источник. Модель не доказывает электрические/временные свойства.

## Буфер и повторное потребление (A5.3)

[Исполняемый пример](../../tests/buffer-consumption/README.md) кладёт подготовленный пакет
в буфер, принадлежащий опыту, и вызывает обработчик через `Pointer` с точной длиной.
Проверяйте возврат и состояние обработчика, порядок двух пакетов, отказный пакет и вход
после него, вложенный вызов во время штатной обработки и следующий штатный пакет.
Запись в буфер без вызова не является потреблением: такой контроль остаётся FAIL.
`Pointer` длиннее массива из DWARF отклоняется до вызова (`argument_range`). Секцию опыта
снимайте и возвращайте целиком. DMA, прерывание и приём периферией здесь не проверены.
