# MMIO: регистры периферии и границы API

[Документация](index.md) · [English](../en/MMIO.md)

**Ограничение известно: существующие методы общего доступа к памяти не являются
интерфейсом MMIO без скрытых обращений.** Отдельный контракт исследуется; публичного
метода MMIO пока нет. Этот документ предупреждает о текущем поведении, не меняя его.

## Что должен учитывать сценарист

| Путь | Поведение и риск |
| --- | --- |
| `read`, `evaluate` | Вычисление выражения и преобразование значения могут обращаться к памяти. Структура/массив могут затронуть соседние регистры; `volatile` не гарантирует одно чтение. |
| `check(rows)` | Строковые actual и expected вычисляются как выражения; обе стороны могут читать периферию. |
| `check(name, actual, expected)` | Готовые Python-значения сравниваются без чтения MCU; вычисление аргументов могло уже прочитать MCU. |
| `write`, включая `verify=False` | Сохраняется чтение before. Для MMIO outside нет подтверждающего readback, но отключение verify не убирает before. Непригодно как универсальная безопасная запись WO/read-to-clear/FIFO. |
| `write` с выражением/bitfield | Однократный RHS в кандидате 0.4.2 не устраняет before, повторное вычисление LHS и возможный read-modify-write GDB для битового поля. |
| `memory` | Доступ ограничен окнами SRAM/Flash; периферия вне окон отвергается. Не объявляйте MMIO обычной памятью профиля для обхода проверки. |

RO — только чтение, WO — только запись, W1C — очистка бита записью единицы,
read-to-clear — очистка чтением. FIFO может потреблять элемент при каждом чтении.
Обычный снимок и запись прежнего значения не являются восстановлением таких регистров.
Учитывайте также окна регистров IDE, watch и автоматическое обновление: они способны
создавать обращения независимо от сценария. Halt ядра не останавливает DMA и периферию.

Не заменяйте неизвестное состояние нулём. После ошибки обращения эффект может уже
произойти; не повторяйте операцию автоматически. Не проверяйте результат разрушительным
чтением. Выбирайте независимый безопасный признак из документации конкретного устройства.

## Где проходит гарантия

Понятное число и порядок запросов **со стороны модуля до передачи транспорту** — цель
отдельного MMIO-контракта: явная ширина/права, проверка входов до доступа, отсутствие
before/readback/RMW/retry и явный неизвестный эффект после ошибки. Это направление работы,
не обещание уже реализованного метода. До его принятия применяются ограничения таблицы.

Один вызов GDB не доказывает одну транзакцию шины. `volatile` — свойство типа для языка
и компилятора, не описание WO/W1C/FIFO и не запрет чтений в обвязке сценария.

GDB предоставляет [атрибуты областей памяти](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Memory-Region-Attributes.html):
`ro/wo/rw`, размер доступа и `nocache`. Но [RSP m](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Packets.html)
не требует от сервера определённого размера/выравнивания обращения и может не подходить
для MMIO. Сам по себе атрибут `32` не доказывает физическую 32-битную транзакцию через
Python memory API и выбранный сервер. Кеш способен скрывать чтения или расширять их
на соседние адреса. Сохраняйте и восстанавливайте исходные настройки GDB при опыте.

## Рекомендуемый маршрут: модель, затем целевая плата

Используйте [stm32-gdbtest-renode](../../skills/stm32-gdbtest-renode/SKILL.md) и его
[ресурс MMIO](../../skills/stm32-gdbtest-renode/references/mmio.md).

1. **Renode:** моделируйте эффект регистра, а не RAM по его адресу. Сопоставьте вызов
   API, запросы GDB/RSP и callbacks модели: направление, адрес, ширину, число, порядок
   и эффект. Проверьте WO, W1C, read-to-clear/FIFO, отрицательный контроль и ошибки
   после эффекта. Инъекция ошибки обвязкой не является реальным bus fault.
2. **Плата своей цели:** после согласования воздействий повторите тот же минимальный
   участок сценария с конкретными ELF, MCU, отладчиком, GDB и сервером. Заранее задайте
   безопасное наблюдение и восстановление по семантике устройства. Сохраните исходные
   FAIL/ERROR. При смене backend/версии повторите затронутую проверку.

Эти этапы дают свидетельства разных уровней; Renode PASS не заменяет аппаратную
проверку, а итоговое значение регистра на плате не доказывает число физических
транзакций. Неподдержанную периферию или неизмеренную границу отмечайте как непроверенную.
