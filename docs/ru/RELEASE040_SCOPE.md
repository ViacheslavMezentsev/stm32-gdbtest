Состав согласован 09.10.2026 и сверен с `main` на `44c795d`: изменения `codex/check-techniques`,
`codex/api040-cleanup` и `codex/api030-feedback` объединены. Это граница выпуска, а не объявление

stm32-gdbtest 0.4.0, `API_VERSION=2`. Локальная матрица ниже не заменяет CI итогового SHA.

## 1. Рекомендуемый состав

| Группа | Решение для v0.4.0 | Основание и условие |

| Исправление `reach` | Включить обработку C++-сигнатуры с внешними одинарными кавычками GDB | Есть host и аппаратная регрессия; повторить на итоговом коммите |
| Совместимые MCU и инфраструктура | Включить профиль AT32, обновлённые соглашения стендов и адаптеры архитектуры | Уже находятся в `[0.4.0]`; подтвердить доступные backend и build на итоговом коммите |
| Проверенные техники и примеры | Включить события/интервалы, ожидание watchpoint, инъекцию, пример C++ Og/O2 и TECH-019 | Используют существующий API; сохранить их как примеры, без новых методов `Target` |
| Опыт применения 0.3.0, F01–F03 | Включить; `codex/api030-feedback` объединена | F01 — ограниченное чтение символьных массивов; F02 — интерпретация кадра watchpoint; F03 — начальный SP как граница SRAM. | Очистка API | **Удалить** `value`, `fields`, `set_value`, `force_return` | Удаление обещано в 0.4.0 действующими ТЗ API 6.7, TODO и справочником; это несовместимое изменение с явной миграцией |
| st-util | Включить отдельный backend и необязательную секцию `[st-util]` target schema 2 | Согласовано 10.10.2026. Пять STM32/Windows, lifecycle и полные наборы прошли; OrangePi/SSH: полные наборы пяти STM32 также прошли. [Матрица](API_ACCEPTANCE.md) |

`API_VERSION` уже равен 2 из-за удаления публичных методов. В выпускной ветке схема
target.toml повышена до 2 для диалектов backend; остальные схемы TOML/JSON не менялись.
`@case` сохраняется как основное имя, `@test` — как алиас: ни одно из них не объявлено устаревшим.

## 2. Очистка сценариев и документации

Проверка *отслеживаемых Git-файлов* на `t.<name>(…)` и `target.<name>(…)` показала:

| Место | Что найдено | Действие |
| --- | --- | --- |
| `tests/firmware/common/tests`, `tests/firmware/profiles` | Вызовов четырёх старых методов нет | Повторить штатные сценарии на выпускном SHA |
| `tests/host` | Проверки отсутствия прежних имён и действующих `ret`/`write` находятся в main | Повторить host-регрессию на выпускном SHA |
| `docs/ru`, `docs/en` | Действующие примеры используют новый API; прежние имена сохранены в исторической миграции | Проверить `docs.public` и пары локализаций на выпускном SHA |
| `skills/stm32-gdbtest-scenarios` | Таблица «старое → новое» осталась только в миграции | Рабочие образцы используют новый API |
| Локальные `tests/dev-*` и старые результаты | Исторический код исследования использует прежние имена | Не переписывать свидетельства прежних опытов и не включать их в поставку |

Миграцию нельзя выполнить механической заменой всех строк:

- `value(expr)` возвращал `int`; для объекта подходит `read(path)`, для C/GDB-выражения — `evaluate(expr)` с проверкой ожидаемого типа.
- `fields(expr, expected)` делал последовательные сравнения и вычислял строковые ожидания. Таблица `check(rows)` должна сохранить порядок, имена проверок и оценку выражений; `read(..., fields=…)` только читает поля.
- `set_value` возвращал `None`, а `write` возвращает результат и проверяет запись. Сценарии, которые опирались на возвращаемое значение или побочный эффект чтения MMIO, требуют отдельного просмотра.
- `force_return` заменяется `ret`; проверить возвращаемый результат и тип выражения в конкретном кадре.

Противоречие старых карточек о предупреждении и алиасе устранено в ветке очистки. История версий
в ТЗ и CHANGELOG сохранена. Поиск по отслеживаемым файлам на `44c795d` находит вызовы прежних
имён только в таблице миграции навыка; это текстовые примеры старого кода, а не сценарии.

## 3. Не включать в v0.4.0

| Кандидат | Причина переноса |
| --- | --- |
| GDB-функции для битов, `bits`, `each`, `predicate` | Практические прототипы изучены; остаются решения о семантике нулевой маски, пустых массивов, лимитах, диагностике и побочных действиях. Отдельный пакет после обзора состава |
| SVD-инструменты и T6, итоговая сравнительная сводка T7 | T6 ещё не проведён; результат исследования не является условием выпуска уже работающего пакета |
| `requires`, дерево зависимостей, автоматические групповые пропуски | Для динамических фактов и жизненного цикла нужен отдельный контракт; минимальный `skip(reason)` уже работает |
| `fault`, `cycles`, `snapshot/diff`, измерение HSE | Открытые кандидаты TODO/ТЗ API без согласованной реализации и приёмки для v0.4.0 |
| RTOS-осведомлённость и внешнее оборудование | Отдельные исследования и интеграция |

## 4. Свидетельства и открытые ограничения

stm32-gdbtest 0.4.0, API_VERSION=2, target schema 2; общее ТЗ 0.94, ТЗ API 0.3.16.
Выпуск готовится в `codex/release-040` и ещё не опубликован.

Локальные свидетельства относятся к нескольким срезам:

- `b1264c1`: Docker 26/26; шесть Windows-стендов OpenOCD/J-Link, 280 сценариев,
  608 этапов; Linux-пакеты F411/F429 на Windows по 10/10; minimal-consumer
  с настоящим подмодулем — offline 3/3 и GPIO F411 PASS.
- Remote lifecycle `4cb5e0a`, сценарии до `a6b6dbd`: Windows → OrangePi/st-util 1.9.0,
  пять STM32, 233 сценария, 516 этапов с подготовкой и восстановлением;
  268 HW PASS и 5 ожидаемых timeout ERROR, OpenOCD BOOT/GPIO 10/10, стенды освобождены.
  ADC_INVALID F4 получил 120 с после сохранённого ERROR F411; изменённый F401 проверен отдельно.
- После изменений lifecycle: 426 host-тестов, Docker docs+host 6/6; итоговые документы проверяются отдельно.

Полные F411/F030 через ST-LINK GDB Server по-прежнему не приняты из-за USB ERROR.
Успех st-util не закрывает этот отказ. Также открыты диагностика USB serial в doctor,
причина прежней аномалии F429 SP/SRAM и границы принудительного cleanup.
GitHub CI последнего SHA и окончательная сверка всех схем выпуска ещё ожидаются.

Исторические протоколы и точные границы — [матрица](API_ACCEPTANCE.md).

| Остаток | Статус и следующий шаг |
| --- | --- |
| F411/F030 ST-LINK GDB Server | Граница согласована 10.10.2026; USB ERROR остаётся открытым долгом 11.2.27 |
| Последний SHA | Проверить Docker/offline и GitHub CI; при изменении runtime повторить затронутые схемы и восстановление |
| Схемы размещения и потребитель | Предыдущие проверки сохранены; сверить влияние последующих изменений helper на локальный Linux, WSL, пакеты и Hardware CI, не переносить PASS автоматически |
| Doctor/USB serial | Пустой либо бинарный serial; на Windows capture требует UTF-8, см. HOWTO; исправление представления ещё не принято |
| F429 SP/SRAM | В повторной кампании не воспроизведено, причина неизвестна |
| Принудительное завершение | Host-регрессия есть; обрыв SSH на реальном USB и безопасность аварийного cleanup не доказаны |
| Отложенные проверки | HAL F030 на железе, повтор занятого порта, практика SKIP у потребителя; остальной API-долг — раздел 3 |

## 5. Завершение подготовки

1. Сверить итоговый diff с проверенными исходниками, схемами и миграцией; новые изменения проверять по влиянию.
2. Выполнить оставшиеся выпускные проверки и записать конкретный SHA; сохранить согласованное ограничение ST-LINK.
3. Владелец пушит ветку, проверяет CI последнего SHA и выполняет land.
4. Только после приёмки — дата CHANGELOG, подписанный тег и публикация владельцем.

Эта карта не объявляет выпуск готовым и не переносит экспериментальные методы в ядро.

Внешний конечный диспетчер пакетов: [stand_loop](STAND_LOOP.md). Target API не меняется; старые команды run/pack остаются прежними.
