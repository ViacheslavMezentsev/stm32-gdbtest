# Состав кандидата v0.4.0

[Документация](index.md) · [English](../en/RELEASE040_SCOPE.md) · [Правила выпуска](VERSIONING.md) · [Дорожная карта](../../TODO.md)

Состав согласован 09.10.2026 и сверен с `main` на `44c795d`: изменения `codex/check-techniques`,
`codex/api040-cleanup` и `codex/api030-feedback` объединены. Это граница выпуска, а не объявление
v0.4.0 готовым. На этом срезе версия модуля 0.3.0, `API_VERSION=2`;
в выпускной ветке Python-версия поднята до 0.4.0. Итоговая приёмка ещё впереди.

## 1. Рекомендуемый состав

| Группа | Решение для v0.4.0 | Основание и условие |

| Журнал и результаты | Включить захват `records.json`, `results export/verify`, индекс кампании и автономный JSON/HTML-отчёт с темами и обычным/экспертным видом | Реализовано в `[Unreleased]`; проверить вместе на итоговом коммите, включая отказ сохранения |
| `skip(reason)` | Включить минимальный императивный SKIP, код 77, JUnit/CTest, явный допуск в `run_hw` | Host/docs и аппаратные опыты проведены; сохранить ограничения из [карточки](api/skip.md) |
| Исправление `reach` | Включить обработку C++-сигнатуры с внешними одинарными кавычками GDB | Есть host и аппаратная регрессия; повторить на итоговом коммите |
| Совместимые MCU и инфраструктура | Включить профиль AT32, обновлённые соглашения стендов и адаптеры архитектуры | Уже находятся в `[Unreleased]`; подтвердить доступные backend и build на итоговом коммите |
| Проверенные техники и примеры | Включить события/интервалы, ожидание watchpoint, инъекцию, пример C++ Og/O2 и TECH-019 | Используют существующий API; сохранить их как примеры, без новых методов `Target` |
| Опыт применения 0.3.0, F01–F03 | Включить; `codex/api030-feedback` объединена | F01 — ограниченное чтение символьных массивов; F02 — интерпретация кадра watchpoint; F03 — начальный SP как граница SRAM. Host/docs/offline на `44c795d` прошли; аппаратные результаты получены до объединения и требуют перепроверки на выпускном SHA |
| Очистка API | **Удалить** `value`, `fields`, `set_value`, `force_return` | Удаление обещано в 0.4.0 действующими ТЗ API 6.7, TODO и справочником; это несовместимое изменение с явной миграцией |

`API_VERSION` уже равен 2 из-за удаления публичных методов. В выпускной ветке схема
target.toml повышена до 2 для диалектов backend; остальные схемы TOML/JSON не менялись.
`@case` сохраняется как основное имя, `@test` — как алиас: ни одно из них не объявлено устаревшим.

## 2. Очистка сценариев и документации

Проверка *отслеживаемых Git-файлов* на `t.<name>(…)` и `target.<name>(…)` показала:

| Место | Что найдено | Действие |
| --- | --- | --- |
| `tests/firmware/common/tests`, `tests/firmware/profiles` | Вызовов четырёх старых методов нет | Повторить штатные сценарии на выпускном SHA |
| `tests/host` | Проверки отсутствия прежних имён и действующих `ret`/`write` находятся в main | Повторить host-регрессию на выпускном SHA |
| `docs/ru`, `docs/en` | Действующие примеры используют новый API; прежние имена сохранены в исторической миграции | Проверить `docs.public` и пары локализаций на выпускном SHA |
| `skills/stm32-gdbtest-scenarios` | Таблица «старое → новое» осталась только в миграции | Рабочие образцы используют новый API |
| Локальные `tests/dev-*` и старые результаты | Исторический код исследования использует прежние имена | Не переписывать свидетельства прежних опытов и не включать их в поставку |

Миграцию нельзя выполнить механической заменой всех строк:

- `value(expr)` возвращал `int`; для объекта подходит `read(path)`, для C/GDB-выражения — `evaluate(expr)` с проверкой ожидаемого типа.
- `fields(expr, expected)` делал последовательные сравнения и вычислял строковые ожидания. Таблица `check(rows)` должна сохранить порядок, имена проверок и оценку выражений; `read(..., fields=…)` только читает поля.
- `set_value` возвращал `None`, а `write` возвращает результат и проверяет запись. Сценарии, которые опирались на возвращаемое значение или побочный эффект чтения MMIO, требуют отдельного просмотра.
- `force_return` заменяется `ret`; проверить возвращаемый результат и тип выражения в конкретном кадре.

Противоречие старых карточек о предупреждении и алиасе устранено в ветке очистки. История версий
в ТЗ и CHANGELOG сохранена. Поиск по отслеживаемым файлам на `44c795d` находит вызовы прежних
имён только в таблице миграции навыка; это текстовые примеры старого кода, а не сценарии.

## 3. Не включать в v0.4.0

| Кандидат | Причина переноса |
| --- | --- |
| GDB-функции для битов, `bits`, `each`, `predicate` | Практические прототипы изучены; остаются решения о семантике нулевой маски, пустых массивов, лимитах, диагностике и побочных действиях. Отдельный пакет после обзора состава |
| SVD-инструменты и T6, итоговая сравнительная сводка T7 | T6 ещё не проведён; результат исследования не является условием выпуска уже работающего пакета |
| `requires`, дерево зависимостей, автоматические групповые пропуски | Для динамических фактов и жизненного цикла нужен отдельный контракт; минимальный `skip(reason)` уже работает |
| `fault`, `cycles`, `snapshot/diff`, измерение HSE | Открытые кандидаты TODO/ТЗ API без согласованной реализации и приёмки для v0.4.0 |
| RTOS-осведомлённость и внешнее оборудование | Отдельные исследования и интеграция |

## 4. Технический долг и условия выпуска

Повторная проверка 10.10.2026 уточняет приёмку: [актуальная матрица](API_ACCEPTANCE.md).
Docker 26/26 и шесть плат OpenOCD/J-Link прошли; F411/ST-LINK остаётся открытым
из-за USB ERROR полных серий. Историческая таблица ниже не заменяет этот результат.

- Практика `skip()` на сценариях потребителя: отличать неприменимость от неисправности. Прямой GDB не ограничен; уже исполненное до SKIP не отменяется. Удалённые стенды и другие версии GDB не проверены этим пакетом.
- F01–F03 объединены: TECH-013 поясняет, почему кадр остановки не всегда является писателем; TECH-017
  отделяет начальный SP на границе RAM от читаемых адресов. Аппаратные результаты на прежних SHA не заменяют
  прогон на выпускном SHA.
- Релизная матрица: Docker host/offline/docs на итоговом SHA, действительная сборка/пакет, схемы запуска из [правил версий](VERSIONING.md), аппаратный recovery, проверка потребителя с настоящим подмодулем и отсутствие публичных ссылок на исключённые исследования (`docs.public`). Локальные результаты ветки не заменяют CI итогового SHA.
- Проверить, что описание версий, `API_VERSION`, актуальные ревизии обоих ТЗ, README/STATUS, навыки, двуязычный CHANGELOG и текст релиза согласованы. Подготовить миграцию для пользователей 0.3.0.

| Свидетельство | На `44c795d` | Для выпуска |
| --- | --- | --- |
| Документация, host, offline F030 | 7/7 локально PASS | Повторить полный Docker-набор и GitHub CI на итоговом SHA |
| Сценарии и recovery на платах | На `bb74cde` шесть локальных стендов: 10/10 `run_hw` каждый, 280 сценариев, 608 этапов (602 PASS, 6 ожидаемых ERROR), BOOT/GPIO recovery 12/12 PASS | Другие схемы запуска из [правил версий](VERSIONING.md), повтор затронутого `run_hw` на последнем SHA и CI |
| Потребитель как Git-подмодуль | Не проверен на объединённом SHA | Проверить реальный gitlink и подготовку/запуск |
| Версия и выпускные документы | `__version__=0.3.0`, API_VERSION=2 | Версия 0.4.0, ТЗ, миграция и описание выпуска |

## 5. Порядок подготовки выпуска

1. Сверить объединённый состав и матрицу проверок: `main` на `44c795d` содержит три принятые ветки;
   локально на этом SHA прошли docs 5/5, host и offline F030 (всего 7/7). GitHub CI владелец проверяет отдельно.
2. В выпускной ветке `__version__` поднята до 0.4.0, обновлены оба ТЗ, README/STATUS, навыки,
   двуязычный CHANGELOG и черновик описания выпуска с миграцией 0.3.0 → 0.4.0.
   `API_VERSION=2` уже установлен; документы уточняются по итоговой приёмке.
3. На `bb74cde` выполнены локальные аппаратные сценарии и recovery шести стендов. На итоговом SHA
   выполнить Docker docs/format/host/firmware, повтор затронутого `run_hw` и оставшиеся схемы запуска,
   затем проверить потребителя с настоящим подмодулем. Записать точные версии инструментов, MCU,
   backend, ELF/manifest и ограничения; не переносить статистику с прежних SHA как итоговую.
4. Владелец публикует ветку, проверяет CI последнего SHA, делает land и после него создаёт тег.

Эта карта не переносит экспериментальные методы в ядро и не публикует выпуск.
