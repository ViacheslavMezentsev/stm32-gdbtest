# Владение отладчиком между проектами

[Документация](index.md) → Владение отладчиком · [English](../en/DEBUGGER_OWNERSHIP.md)

## Механизм

`probe_lock(root, serial, backend="openocd")` на Windows использует именованный mutex
`Local\stm32-gdbtest.probe.v1.<sha256>`, на Linux — файл с `flock` (раздел
[Linux](#linux)). Ключ — семейство отладчика и серийный номер
в верхнем регистре: OpenOCD и ST server отображаются в `stlink`, J-Link — в `jlink`.
Корень проекта, MCU и порт GDB в ключ не входят. Серийный номер не публикуется в
имени объекта, но хэш не является средством сокрытия секретов.

Область координации — **одна Windows-сессия**: разные процессы, проекты и копии
модуля, использующие этот протокол. Пространство `Local` не охватывает другую
сессию, RDP или службы. Объект живёт в ядре ОС, файлы вне проекта не создаются.
API и семантика рекурсивного владения —
[CreateMutexW](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createmutexw),
граница сессии — [Kernel object namespaces](https://learn.microsoft.com/en-us/windows/win32/termserv/kernel-object-namespaces).

Захват выполняется без ожидания — после чтения стенда и профиля, до снимка ELF,
preflight, `objcopy` и запуска сервера. Занятый mutex даёт ERROR с JSON/JUnit без
аппаратного подключения. Удержание охватывает весь запуск, включая recovery и
остановку дерева процессов сервера. Внешний инструмент, использующий отладчик,
должен участвовать в том же протоколе. Внутрипроцессная защита отклоняет повторный
захват: Windows mutex рекурсивен для одного потока. Поддерживается один импорт пакета
в Python-процессе.

`run --prepare-only` и `doctor` к отладчику не обращаются и блокировку не захватывают.

Прежняя файловая блокировка `build/probe-locks/<sha256(serial)>.lock` (только Windows)
удерживается внутри mutex для совместимости со старым runner в том же checkout. Поэтому редкое
совпадение серийных номеров у отладчиков разных семейств в одном checkout может дать
консервативный отказ. Старый runner в другом checkout нового mutex не знает — все
участвующие проекты нужно обновить. Vendor tools, VS Code и произвольный OpenOCD
или GDB Server протокол не используют и им не блокируются.

## Завершение и сбои

Обычный выход и исключение Python освобождают файловую блокировку, mutex и handle в
`finally`. Ошибка API или прав доступа не приводит к обходу блокировки. После
завершения процесса Windows освобождает его mutex — это **не доказательство
завершения дочерних серверов**.

`WAIT_ABANDONED` означает, что владение получено после смерти прежнего владельца.
Runner освобождает объект и отказывает до подключения, предлагая проверить
оставшиеся процессы GDB и сервера. Это не долговременный карантин: если все handles
закрылись, объект исчезает, и следующий запуск о прежней аварии не узнает.
Автоматически завершать чужие процессы или сбрасывать MCU по этому признаку нельзя.
После аварии host сначала проверьте и завершите оставшиеся серверы. Надзор за
дочерними процессами (Job Object) — отдельная задача ([дорожная карта](../../TODO.md)).

## Linux

Блокировка — файл `probe.v1.<sha256>.lock` с тем же хэшем в каталоге
`stm32-gdbtest-locks` внутри `STM32_GDBTEST_LOCK_DIR`, а без переменной — внутри
`/tmp`. Захват — `flock` без ожидания; занятый файл даёт тот же ERROR «another runner
on this host». Каталог создаётся с правами `1777`, файлы — `0666`, поэтому
блокировку делят все пользователи и checkout хоста.

Ядро снимает `flock`, когда процесс-владелец завершается, поэтому для обнаружения
аварии владелец пишет в файл `pid=<PID>` и очищает запись при освобождении. Если
следующий runner захватил файл и нашёл запись, прежний владелец завершился аварийно:
runner очищает запись и отказывает с «Abandoned debugger ownership», как при
`WAIT_ABANDONED`. Следующий запуск после проверки проходит.

Область координации — одно ядро и один каталог. Контейнер, виртуальная машина или
дистрибутив WSL со своим `/tmp` блокировку хоста не видят; общий каталог задаётся
`STM32_GDBTEST_LOCK_DIR`. Блокировка WSL не пересекается с mutex Windows: один
отладчик не следует одновременно использовать из Windows и WSL.

Сервер и GDB запускаются в отдельной группе процессов. Остановка посылает группе
`SIGTERM`, через 3 с — `SIGKILL`; так завершаются и потомки сервера, даже если
ведущий процесс уже вышел. Аварийное завершение самого runner группу не
останавливает — проверьте оставшиеся процессы (`pgrep -a openocd`, `pgrep -a JLink`).

## Удалённый стенд

Для стенда с `[remote]` действуют две блокировки: своя на компьютере запуска (mutex на
Windows, `flock` на Linux) и `flock` на хосте стенда с тем же хэшем. Вторую берёт
вспомогательный скрипт до запуска сервера, поэтому запуск с Windows и локальный
запуск на Orange Pi не используют один отладчик одновременно. Отказы хоста стенда
приходят как «Stand host refused the run: busy / abandoned». При закрытии или обрыве
SSH-сессии скрипт останавливает сервер и снимает блокировку
([Linux-стенд](LINUX_STAND.md#удалённый-gdb-сервер-windows-или-wsl--orange-pi)).

## Проверка механизма

Host-тесты — `Tests/host/test_probe_lock.py`: Windows-часть выполняется на Windows
(в CI — задача на `windows-2022`), Linux-часть (блокировка, брошенное владение,
остановка группы процессов) — на Linux. Аппаратные результаты и опыт конкуренции
процессов — [в стендовом проекте](https://github.com/ViacheslavMezentsev/stm32-hwtest-blackpill/blob/main/docs/DEBUGGER_OWNERSHIP.md).
