# Живое окно выполнения

[Документация](index.md) · [API](api/index.md) · [English](../en/LIVE_EXECUTION.md)


Практический пример API 3: [VTOR/FPB-наблюдатель](LIVE_OBSERVER.md), включая отрицательные исходы и восстановление.
Кандидат 0.5.0, API_VERSION=3. Обычные `def` сценарии и блокирующий `resume()`
сохраняются. Для живого окна используйте `async def`: runner возобновляет корутину
в главном потоке GDB, не в asyncio и не в рабочем потоке.

```python
from stm32_gdbtest import case


# Наблюдаем ограниченный интервал и читаем результат после остановки.
@case("HW_LIVE", timeout_s=15)
async def live(t):
    t.resume(sync=False)
    try:
        window = await t.wait(timeout=0.2)
        t.record("window", window)
    finally:
        await t.halt(timeout=2.0)
    t.check("result available", t.read("counter"), 3)
```

| Операция | Результат и границы |
| --- | --- |
| `resume()` / `resume(sync=True)` | def: синхронно; async def: await до остановки |
| `resume(sync=False)` | Только в async-сценарии: `started`, номер `generation`; не означает, что цель всё ещё работает при возврате |
| `await wait(timeout=...)` | Пассивное ожидание: `stopped`, `exited` либо `timeout`; не отправляет interrupt |
| `await halt(timeout=...)` | Interrupt при работающей цели и ожидание подтверждения; при уже остановленной цели повторный interrupt не отправляется; выход цели даёт `exited` |

Stop содержит причину; fault guard и неожиданный signal дают ApiError `fault_stop` /
`signal_stop`. SIGINT после нашего interrupt отмечается `interrupt`; breakpoint,
пришедший одновременно, сохраняет своё значение. Уже произошедшая остановка не теряется;
новый resume очищает прежний stop. Для повторного ожидания той же остановки generation
остаётся прежним. `exited` не разрешает читать память завершившейся цели.

Таймаут — обязательное конечное положительное число секунд хоста. `wait` timeout —
результат ожидания, не FAIL и не остановка MCU. `halt_timeout` — ERROR с неизвестным
эффектом. Ошибка команды не вызывает автоматический повтор. Командный таймаут GDB и
общий внешний таймаут сценария продолжают действовать: срок await не является жёстким
пределом зависшей команды GDB. После потери связи остановка и восстановление не гарантируются.

Во время выполнения или при неизвестном состоянии доступ через read/write/memory,
evaluate, MMIO, call, навигацию и execute запрещён до целевого запроса. Записи Python,
record и проверки готовых значений допустимы. Прямой `gdb` доступ остаётся ответственностью
сценариста и может обойти эти ограничения. Single inferior/thread, all-stop; non-stop,
параллельные await, произвольные asyncio-awaitables и чтение «на лету» не поддерживаются.
Существующие точки/guards сохраняются; новых точек для завершения окна не добавляется.

Runner при нормальном выходе, FAIL/ERROR/SKIP делает ограниченную попытку halt (2 с),
пишет `execution_cleanup` отдельно и только затем захват/teardown. Ошибка очистки даёт
ERROR, сохраняя предыдущий исход и ошибку тела. Это не восстановление SRAM/FPB/VTOR и
не гарантия после kill GDB. Таймаут сценария должен оставлять время для cleanup.

Не блокируйте корутину `sleep()` или CPU-циклом: это блокирует обработку событий GDB.
Время окна на хосте не является измерением времени MCU, а в Renode не равно виртуальному
времени. `wait/halt` используют цикл событий GDB; фоновой таймер вызывает только
потокобезопасный `post_event`, все команды и продолжения выполняются в главном потоке.

Пример и проверка штатного runner: [Renode fixture](../../tests/renode-backend/README.md).
Проверка на эмуляторе не означает аппаратную приёмку: P3 на платах ещё не принят.


## Исполнение в API_VERSION=3 (кандидат 0.5.0)

Обычный `def`: `reach`, `step`, `until`, `finish`, `resume()` и `reset()` возвращают
готовый результат. В `async def` эти же операции нужно ожидать с первого вызова:
`await t.reach("main")`, `await t.step()`, `await t.resume()`. Режим задаётся runner
при входе в сценарий, а не первым await. `resume(sync=False)` остаётся немедленным.
`read/write/evaluate/check/record`, создание точек и `ret()` не требуют await.
`boot()` — внутренний этап runner до запуска сценария; публичного await boot нет.

Исполняемые операции ленивы; пропущенный await обнаруживается перед следующим
доступом к цели, record или ожиданием и при нормальном завершении сценария.
Повторный await даёт `already_awaited`. Один inferior/thread, all-stop; произвольные
asyncio-awaitables и параллельные операции не поддерживаются. Исключение из помощника
не превращает незавершённую операцию в успешную.

Навигация в async принимает `timeout=` в секундах хоста; по умолчанию используется
остаток бюджета сценария с резервом 2 с. Многошаговый step использует один deadline.
Истечение даёт `operation_timeout`, не останавливая цель: нужен `finally: await t.halt(...)`.
Блокирующие команды GDB дополнительно ограничены внешним runner; срок await сам по себе
не прерывает зависший GDB. `reset` эмулятора по-прежнему отклоняется до команды.

В async используется `await t.call("function", 7, timeout=2)`. Аргументы и результат
сохраняют прежний контракт. Вызов выполняется в основном потоке GDB; это не фоновая
задача. Нужны параметры GDB `direct-call-timeout` и `unwind-on-timeout`; их значения
сохраняются и восстанавливаются. Целые секунды округляются вниз в пределах бюджета;
при остатке меньше секунды вызов отклоняется. Обычный `def` сохраняет `t.call(...)`;
явный `timeout=` включает тот же ограниченный адаптер. Без timeout действует внешний
лимит сценария, как раньше.

Ранняя остановка внутри call — ошибка, а не результат функции. Если остаётся dummy
frame, дальнейший доступ отклоняется как `call_incomplete`, execution_cleanup=ERROR;
halt не означает unwind. Автопродолжения и повтора нет. Возврат контекста не откатывает
память и эффекты вызова. `ret` подменяет возврат текущего кадра, не исполняет тело и не
является автоматическим восстановлением прерванного call.

Выражения методов данных и ret, а также вычисление условий при навигации защищаются
`may-call-functions off`. Прямой или косвенный inferior call следует вынести в явный
call и использовать готовое значение. Это намеренное ограничение совместимости:
присваивания, MMIO и Python pretty-printers этим не запрещаются. Параметры возвращаются
и при ошибке; ошибка восстановления сохраняется отдельно от первичной ошибки.
Произвольный `execute()` в async отклоняется (`unsupported_async_command`), в def
остаётся низкоуровневым выходом из гарантий API. Прямой импорт gdb также обходит защиту.

Миграция: не превращайте обычный def в async без необходимости. Для async добавьте await
к навигации и call, уберите execute, оставьте finally с halt и явно разделите результат
остановки и восстановление ресурсов. Старые аппаратные прогоны API_VERSION=2 не являются
приёмкой этой миграции. Новая аппаратная проверка выполняется отдельно.
