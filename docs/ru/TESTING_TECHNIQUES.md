# Каталог техник тестирования

[Документация](index.md) · [English](../en/TESTING_TECHNIQUES.md)

Практическое дополнение к [руководству автора](TEST_AUTHORING.md). HAL-приёмы
сохраняются здесь после перехода примеров на CMSIS: меняется реализация firmware,
но опыт работы с GDB, DWARF, callback и инъекциями остаётся полезным.
Это методические карточки, не новые требования ТЗ, API или метрики покрытия.

## Как пользоваться каталогом

ID `TECH-NNN` стабилен: не перенумеровывать и не использовать повторно. Заголовок
можно уточнить, якорь сохраняется. Устаревшую карточку пометить и связать с заменой.
Сценарий ссылается на технику в комментарии около нетривиального действия:

```python
# TECH-005: docs/ru/TESTING_TECHNIQUES.md#tech-005 (EN: docs/en/TESTING_TECHNIQUES.md#tech-005).
# Force the wait predicate false; this does not simulate a failed oscillator.
target.set_value("mask", 0)
```

Пути здесь считаются от корня модуля. Во внешнем потребителе давать GitHub URL
на закреплённый gitlink и тот же якорь. `@case` и requirements сохраняют свои ID;
TECH не заменяет ни контракт ELF, ни traceability. Нового декоратора/поля API нет.

| Группа | Техники |
| --- | --- |
| ELF, сборка и наблюдение | [001 макросы](#tech-001), [002 контекст](#tech-002) |
| Асинхронное выполнение | [003 callback/IRQ](#tech-003) |
| Управляемые отказы | [004 возврат функции](#tech-004), [005 аргумент](#tech-005), [006 MMIO](#tech-006) |
| Численные проверки | [007 векторы](#tech-007) |
| Сон и прерывания | [008 WFI-контекст](#tech-008) |

Карточки ниже основаны на выполненных примерах, но их перенос на другой MCU,
HAL, GCC или backend требует новой проверки. Ссылки ведут к коду/протоколам,
а не обещают одинаковый результат на любом окружении.

<a id="tech-001"></a>
## TECH-001 — Макросы из ELF и независимые ожидания

**Цель:** проверить конфигурацию через HAL predicates/getters и CMSIS-поля.
**Окружение:** `-g3` в нужной единице компиляции, правильные MCU defines/HAL;
контракт указывает macro context. `-g3` не сохраняет неиспользуемые функции,
а наличие определения в установленном header не доказывает его наличие в ELF.

Сначала prepare/contracts, затем reach точки с нужным контекстом и отдельные
check. Масочный результат сравнивать с маской или нормализовать; не ждать всегда 1.
Ожидаемые частоты, делители и физические номера каналов задавать независимо:
HAL TEMPSENSOR у F411 содержит служебный флаг, а аппаратный канал — 18.
Не подставлять отсутствующее определение через macro define ради PASS.

**Осторожность:** getter может читать FIFO/read-to-clear или участвовать в
последовательности SR/DR. Setter — отдельная инъекция. Clock enabled не доказывает,
что конкретный ENABLE-макрос был вызван. Для чистого наблюдения восстановление
не нужно; если чтение имеет эффект, заранее определить восстановление и границу.
[Рекомендации и проверенный объём HAL](HAL_MACRO_GUIDE.md).

<a id="tech-002"></a>
## TECH-002 — Сохранение адреса до смены DWARF-контекста

**Цель:** сравнить один MMIO-регистр до и после перехода в другую функцию.
Сохранить `&RCC->BDCR` там, где доступен RCC; затем читать по сохранённому адресу
с подходящим типом/шириной. Не заменять потерю контекста случайной константой адреса.

**Окружение:** контекст макроса и ширина типа проверены; пример относится к
32-битному STM32 и не является универсальным MMIO helper для всех архитектур.
Адрес допустим в той же сессии/карте памяти; не переносить его между ELF/таргетами.
**Граница:** это обход потери macro context, а не доказательство безопасности
чтения регистра. Инъекций техника сама не делает.
[RTC deadline: исходный ERROR и исправление](F030_RTC_DEADLINE.md),
[rtc_deadline](../../tests/firmware/profiles/f030r8/tests/board/test_rtc.py).

<a id="tech-003"></a>
## TECH-003 — Callback/IRQ → публикация результата

**Цель:** связать естественное событие с правильным экземпляром периферии и
изменением состояния приложения. HAL: остановиться в callback, проверить handle,
дождаться второго события и публикации. CMSIS: проверить exception/флаг, счётчик,
возврат в thread mode и опубликованный результат.

**Окружение:** доступные символы/параметры, действующие IRQ/DMA и корректная freeze
policy. HAL weak callback должен быть переопределён именно проверяемым кодом.
**Граница:** периферия может продолжать работу при halt; частота callback под
отладчиком не измеряет реальную производительность, software IRQ не доказывает
физический фронт. Следующий сценарий начинается из согласованного reset-состояния.
[HAL исходные ADC/TIM/RTC сценарии](https://github.com/ViacheslavMezentsev/stm32-hwtest-blackpill/blob/0c8c966f0429710e6e20472fbd9fe8898da7cfee/tests/scenarios/peripheral_runtime.py),
[CMSIS RTC](F030_CMSIS_RTC.md).

<a id="tech-004"></a>
Для проверки номера исключения Cortex-M используйте `SCB->ICSR & SCB_ICSR_VECTACTIVE_Msk`. Имена GDB `xPSR`/`xpsr` зависят от сервера. Проверяйте CMSIS-макросы preflight в нужном контексте. Чтение VECTACTIVE не очищает флаги и не доказывает физический источник IRQ.

## TECH-004 — Подмена возврата HAL и подавление callback

**Цель:** проверить реакцию вызывающего кода, пропустив тело функции.
Два разных опыта: `HAL_ADC_Start_DMA` → `force_return("(HAL_StatusTypeDef)1")`
проверяет переход в Error_Handler; `force_return("")` из void callback после
DMA подавляет публикацию и проверяет deadline. В обоих случаях нет новой sequence.

**Окружение:** реальный вызываемый frame, проверенные prototype/enum/ABI, параметры
и символы. Для пошагового пути и force_return использовать вариант без LTO;
проверить фактические compile/link flags. `-Og -g3` не гарантирует отсутствия
inline/optimized-out; prepare не заменяет проверку runtime frame/backend.

**Граница:** тело пропущенной HAL-функции не проверено, физический отказ не
воспроизведён. Для void callback DMA уже завершился — это не DMA timeout на шине.
После инъекции reset_run и отдельный положительный ADC-прогон; если recovery
неуспешен, остановить серию. [Исходные два опыта](https://github.com/ViacheslavMezentsev/stm32-hwtest-blackpill/blob/0c8c966f0429710e6e20472fbd9fe8898da7cfee/tests/scenarios/peripheral_runtime.py).
Перенос в модуль ещё [запланирован](F030_HAL_REGRESSION.md); старый PASS не новый PASS.

<a id="tech-005"></a>
## TECH-005 — Инъекция аргумента предиката ожидания

**Цель:** пройти реальную ветку deadline без повреждения конфигурации генератора.
Достичь `rtc_wait` с `error == 3`, проверить исходную mask, сохранить ticks и BDCR,
записать mask=0, дождаться rtc_fault. Проверить error3, минимум 1000 firmware ticks,
неизменный BDCR, отсутствие запуска приложения/публикации RTC.

**Окружение:** аргумент доступен и изменяем в текущем frame; функции/параметры не
устранены оптимизацией. SysTick должен работать, внешний timeout runner обязателен.
**Граница:** проверен программный deadline одной стадии, не физический отказ LSI
и не точность 1000 мс. После инъекции reset_run, положительный RTC_ALARM.
[Код](../../tests/firmware/profiles/f030r8/tests/board/test_rtc.py), [протокол](F030_RTC_DEADLINE.md).

<a id="tech-006"></a>
## TECH-006 — Управляемое состояние периферии через MMIO

**Цель:** проверить guard занятого ADC либо отсутствие IRQ-публикации.
В ADC_BUSY подтвердить idle, включить continuous conversion, подтвердить ADSTART,
затем проверить error6 и отсутствие данных. Это отличается от TECH-004.
В ADC_TIMEOUT отключается IRQ DMA, а не сам DMA.

**Окружение:** RM конкретного MCU, семантика RW/W1C/rc_w0, работа ADC при halt.
Не переносить read-modify-write на произвольный status-регистр; freeze policy
и побочные эффекты записывать в отчёте. DMA/ADC могут продолжить работу и дать OVR.
**Граница:** создано конкретное состояние, не вся совокупность отказов ADC/DMA.
Восстановление reset_run, затем нормальный ADC_DMA; failure recovery прекращает серию.
[ADC_BUSY](F030_ADC_BUSY.md), [код](../../tests/firmware/profiles/f030r8/tests/board/test_adc_faults.py),
[DMA timeout](F030_CMSIS_ADC_DMA.md).

F103: [ADC/DMA](F103_CMSIS_ADC_DMA.md) различает guard DMA EN, отключение ADC
и потерю IRQ-уведомления. Перенос названия «busy» не переносит смысл ADSTART
из F0 на F1; записывайте, какое состояние действительно создано инъекцией.

<a id="tech-007"></a>
## TECH-007 — Независимые численные векторы и невалидные входы

**Цель:** проверить арифметику через реальные аргументы/результат функции firmware.
Задать заранее рассчитанные входы и ожидаемые значения, проверить границы,
невалидные данные, затем восстановление нормального результата.
**Окружение:** доступные аргументы, размеры/знаковость C-типов, целочисленное
усечение и калибровочные данные MCU; ожидания не копировать из проверяемой функции.

**Граница:** проверяется арифметика, не точность аналогового датчика. Название m°C
не обещает точность 0.001°C. Не переносить двухточечную F4-калибровку на F030.
После подмены аргументов вернуть обычный цикл/reset и проверить quality.
[Векторы F030 и ограничения](F030_CMSIS_ADC_UNITS.md),
[adc_vectors/adc_invalid](../../tests/firmware/profiles/f030r8/tests/board/test_ci.py).

<a id="tech-008"></a>
## TECH-008 — Прерванный WFI-контекст

**Цель:** подтвердить продолжение после Sleep через выбранный IRQ.
Остановиться в handler, проверить exception, раскрутить interrupted frame и
инструкцию перед сохранённым PC. В текущем Cortex-M опыте WFI — halfword 0xBF30.
IRQ может прийти до WFI: ограниченные попытки и их контексты сохраняются в отчёте.

**Окружение:** GDB умеет unwind exception frame (возможен trampoline), нужные
символы/инструкции присутствуют; правила ISA/PC зависят от архитектуры.
**Граница:** это не измерение тока, длительности сна или проверка Stop/Standby.
Изоляция IRQ меняет среду: восстановить enable-биты в finally и завершить reset_run;
ошибка восстановления не должна скрываться.
[Код](../../tests/firmware/profiles/f030r8/tests/board/test_sleep.py), [протокол](F030_CMSIS_SLEEP.md).

## Как пополнять руководство

При новом практическом опыте сначала искать существующую карточку. Добавлять
новый ID лишь для отдельного приёма; HAL/CMSIS варианты связывать, не объявляя
эквивалентными. Записывать предусловия сборки/контекста, действие, независимый
критерий, вмешательство, восстановление, ограничения и ссылку на код/протокол
с MCU/HAL/GCC/GDB/backend. Разделять «проверено», «кандидат» и «не проверено».
Обновлять RU/EN и комментарии вместе. Первоначальные ошибки также часть опыта.
При смене HAL/оптимизации повторять затронутый preflight и HW, а не только ссылки.
Дальнейшие темы: watchpoints, временная freeze policy, sparse/full images, внешние
стимулы; добавлять карточки по мере обобщения опытов, без обещания нового API.
