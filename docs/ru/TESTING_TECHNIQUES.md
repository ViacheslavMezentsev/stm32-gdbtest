# Каталог техник тестирования

[Документация](index.md) · [English](../en/TESTING_TECHNIQUES.md)


Готовая композиция приёмов: [нейтральное живое наблюдение](LIVE_OBSERVER.md). Отдельный допуск, полный снимок, независимый эталон, records до check, проверенное снятие и повтор без reset; также разобраны ограничения миграции C++/MMIO старых сценариев.
Практическое дополнение к [руководству автора](TEST_AUTHORING.md) и [справочнику API](api/index.md).
Карточки описывают приёмы из сценариев модуля и практики потребителей: общими
(`tests/firmware/common/tests`), сценариями пяти CMSIS-профилей (`tests/firmware/profiles`)
и HAL-фикстурой F030 (`tests/hal-f030`). Это методические карточки, а не новые требования ТЗ,
операции API или метрики покрытия.

Перед прогоном используйте [шпаргалку сценариста](SCENARIO_CHECKLIST.md).

Карточки TECH-021–026 отдельно описывают рекомендации из практики потребителя;
TECH-021 дополнена нейтральным исполняемым примером; остальные остаются рекомендациями.

## Стиль штатных сценариев

Правила проверяет тест host [`tests/host/test_scenario_style.py`](../../tests/host/test_scenario_style.py);
`python tests/host/test_scenario_style.py` перечисляет все замечания по файлам.

**Оформление**

- Заголовок модуля: краткое назначение строками `RU:` и `EN:`; остальные комментарии — на английском.
- Перед каждой функцией — комментарий о назначении (не docstring), над декоратором.
  Между функциями верхнего уровня и после импортов — две пустые строки.
- Смысловые блоки внутри функции разделяются одной пустой строкой. Комментарий открывает блок:
  над ним пустая строка, если он не первая строка вложенного блока. Таблицы проверок и записей
  и нетривиальные циклы поясняются комментарием непосредственно над ними.
- Строка до 120 символов не разбивается: оператор, который помещается в строку, пишется одной строкой.
  Длинные конструкции переносятся по смыслу; продолжение выравнивается по открывающей скобке
  или, если скобка закрывает строку, сдвигается на четыре пробела.
- Необязательные завершающие запятые не используются. Запятая одноэлементного кортежа обязательна:
  `labels=("adc",)`.
- Константа модуля поясняется комментарием над ней или над группой, которую продолжает.
  Константа одного случая объявляется в этом случае, общая — в прологе модуля.

**API**

- Объект Target в сценариях и примерах называется `t`. Прежние `value`, `fields`, `set_value`,
  `force_return` не используются: их заменяют `read`/`evaluate`, `read(path, fields=…)`, `write`, `ret`.
- Три и более подряд проверок значений цели оформляются таблицей `t.check(rows)`:
  `('имя', 'выражение GDB', ожидание)`. Строковая ячейка таблицы — выражение GDB, число и
  сопоставитель — значения Python ([TECH-010](#tech-010)). Проверки значений Python — результатов
  методов API, строк, коллекций — остаются отдельными `t.check(name, actual, expected)`: строка Python
  в ячейке таблицы была бы вычислена GDB как выражение.
- Ожидания, которые следуют из устройства (биты регистров, номера IRQ, адреса), записываются
  идентификаторами прошивки; физические величины (частоты, делители, номера каналов) — именованными
  константами сценария ([TECH-001](#tech-001)).
- Ожидаемый отказ проверяется `with t.refused(code, …)`, а не `try/except ApiError` ([TECH-012](#tech-012)).
- Для периферии используйте `t.mmio.read/write` с SVD ([TECH-006](#tech-006)).
  RMW допустим только при разрешённых чтении и записи без опасных эффектов;
  обычные RAM-значения можно записывать таблицей `t.write(rows)`.
- Место остановки называется функцией (`reach`, `finish`, `until(функция)`). Адрес `файл:строка`
  ломается от любой правки исходника и допустим только в сценарии, который проверяет саму адресацию
  по строке ([TECH-016](#tech-016)).

## Как пользоваться каталогом

ID `TECH-NNN` стабилен: не перенумеровывать и не использовать повторно. Заголовок можно уточнить,
якорь сохраняется. Устаревшую карточку пометить и связать с заменой. Сценарий ссылается на технику
комментарием около нетривиального действия:

```python
# TECH-005: docs/ru/TESTING_TECHNIQUES.md#tech-005 (EN: docs/en/TESTING_TECHNIQUES.md#tech-005).
# Make the ready predicate impossible without touching the oscillator/backup domain.
t.write("mask", 0)
```

Пути считаются от корня модуля. Во внешнем потребителе давать URL закреплённой версии модуля
с тем же якорем. `@case` и requirements сохраняют свои ID; TECH не заменяет ни контракт ELF,
ни трассировку требований.

<a id="tech-001"></a>
## TECH-001 — Макросы из ELF и независимые ожидания

**Цель:** проверить конфигурацию регистрами и макросами прошивки, не повторяя её расчёт.

Остановиться в функции с нужным контекстом макросов (`t.reach("board_led_toggle")` — единица
трансляции, которая включает заголовок устройства) и проверить таблицей. Биты, маски и номера IRQ
пишутся идентификаторами — тогда ожидание следует из того же заголовка, что и прошивка:

```python
t.check([
    ("HSI enabled and ready", "RCC->CR & (RCC_CR_HSION | RCC_CR_HSIRDY)", "RCC_CR_HSION | RCC_CR_HSIRDY"),
    ("nominal core frequency", "SystemCoreClock", HSI_HZ),
    ("1 ms reload at nominal 8 MHz", "SysTick->LOAD", HSI_HZ // 1000 - 1)
])
```

Частоты, делители и физические номера каналов задаются независимыми константами сценария:
`HSI_HZ = 8_000_000` — из RM, а не из `SystemCoreClock`. Масочный результат сравнивать с маской,
а не с 1. Не подставлять отсутствующее определение ради PASS: отсутствие макроса в ELF — ошибка
сборки (`-g3` в нужной единице трансляции) или контракта.

**Окружение:** `-g3`, правильные defines MCU и HAL; контракт ELF перечисляет макросы и их контекст.
Наличие определения в установленном заголовке не доказывает его наличие в ELF.
**Граница:** getter может читать FIFO или участвовать в последовательности SR/DR; чтение с эффектом
требует заранее определённого восстановления. Clock enabled не доказывает вызов конкретного макроса.
[Рекомендации по HAL-макросам](HAL_MACRO_GUIDE.md),
[clock/gpio F030](../../tests/firmware/profiles/f030r8/tests/board/test_ci.py).

<a id="tech-002"></a>
## TECH-002 — Сохранение адреса до смены DWARF-контекста

**Цель:** сравнить регистр до и после перехода в функцию, где его макросы не видны.

Там, где контекст есть, сохранить адрес как число и маску как значение; после перехода читать
по адресу с явным типом:

```python
icsr_address = t.evaluate("&SCB->ICSR", as_type=int)
active_mask = t.read("SCB_ICSR_VECTACTIVE_Msk")
t.reach("app_loop")
t.check("thread resumes", t.read(f"*(unsigned int*){icsr_address} & {active_mask}"), 0)
```

`memory()` для этого не подходит: он читает только SRAM и Flash профиля и отказывает на адресах
периферии. Не заменять потерю контекста случайной константой адреса.
**Окружение:** 32-битная карта памяти STM32; адрес действителен в той же сессии и ELF.
**Граница:** это обход потери контекста макросов, а не доказательство безопасности чтения регистра.
[RTC deadline: исходный ERROR и исправление](../evidence/ru/F030_RTC_DEADLINE.md),
[rtc_alarm, rtc_deadline](../../tests/firmware/profiles/f030r8/tests/board/test_rtc.py).

<a id="tech-003"></a>
## TECH-003 — Callback/IRQ → публикация результата

**Цель:** связать естественное событие с правильным исключением и изменением состояния приложения.

CMSIS: `t.reach("RTC_IRQHandler")`, таблица `SCB->ICSR & SCB_ICSR_VECTACTIVE_Msk` против
`RTC_IRQn + 16`, флаги события, затем счётчик публикации и возврат в thread mode. Второе событие
подтверждает перевооружение. HAL: остановиться в callback и сравнить handle
(`t.read("timer")` с `t.read("&htim3")`), затем дождаться публикации в цикле приложения.
Номер исключения — `SCB->ICSR & SCB_ICSR_VECTACTIVE_Msk`: имена GDB `xPSR`/`xpsr` зависят от сервера.

**Окружение:** действующие IRQ/DMA, символы обработчиков; weak callback HAL переопределён проверяемым кодом.
**Граница:** периферия может работать при остановленном ядре; частота callback под отладчиком не
измеряет производительность; software IRQ не доказывает физический фронт. VECTACTIVE не очищает
флаги и не доказывает физический источник IRQ.
RTC адаптируется по семейству: F103 — counter/alarm с перевооружением в основном потоке, F4 —
masked calendar Alarm A; не переносить делители F030 (LSI 40 кГц) на F4 (32 кГц).
[CMSIS RTC](../evidence/ru/F030_CMSIS_RTC.md), [RTC/Sleep F411](../evidence/ru/F411_CMSIS_RTC_SLEEP.md),
[rtc_alarm](../../tests/firmware/profiles/f030r8/tests/board/test_rtc.py),
[HAL power](../../tests/hal-f030/hal_scenarios/power.py).

<a id="tech-004"></a>
## TECH-004 — Подмена возврата функции

**Цель:** проверить реакцию вызывающего кода, пропустив тело функции.

На входе в функцию `t.ret(value)` завершает её с типизированным значением: значение приводится
к объявленному типу возврата, идентификатор вычисляется GDB (`t.ret("HAL_ERROR")`), `t.ret()` —
возврат из void-функции. Результат называет функцию, вызывающего и применённое значение.

```python
t.reach("HAL_ADC_Start_DMA")
t.ret("HAL_ERROR")
t.reach("Error_Handler")
t.check("no sequence published", t.read("app_state.adc_sequences"), 0)
```

Опыты: HAL — `HW_RCC_ERROR`, `HW_ADC_START_ERROR`, подавление публикации из void callback
(`HW_ADC_DMA_TIMEOUT`); CMSIS — `HW_CI_RET_VALUE`, `HW_CI_RET_RECEIVER`, `HW_CI_INJECT_ZERO`:
получатель берёт подменённый 0 и уходит в ветку нулевого результата, что видно после `t.finish()`.
**Окружение:** реальный кадр вызываемой функции, проверенный прототип и ABI; вариант без LTO.
`-Og -g3` не гарантирует отсутствия встраивания.
**Граница:** тело функции не проверено, физический отказ не воспроизведён. Для void callback DMA
уже завершился — это не тайм-аут DMA на шине. После инъекции — `reset_run` и положительный прогон.
[ret](api/ret.md), [inject_zero](../../tests/firmware/common/tests/board/test_inject_zero.py),
[HAL runtime](../../tests/hal-f030/hal_scenarios/peripheral_runtime.py), [HAL-фикстура](../evidence/ru/F030_HAL_REGRESSION.md).

В [сценарии инъекции](../../tests/firmware/common/tests/board/test_event_injection.py) сравниваются два пути к нулевому результату: естественный переход счётчика через границу и `ret("0")`. Второй пропускает побочные эффекты производителя. Проверяйте и ветвь получателя, и состояние производителя; одинаковый результат не означает одинаковое исполнение.

**A5.1: применение не равно потреблению.**
[Нейтральный пример](../../tests/controlled-input/README.md) сопоставляет write в SRAM
и ret с независимыми ожиданиями получателя. Слишком ранняя запись успешно читается
обратно, но затем перезаписывается: исходный FAIL сохранён. Ret проверяется с обоими
значениями и противоположным источником, пропуском эффектов производителя и следующим
штатным входом. Полный POD восстанавливается также при FAIL и Python-исключении.
Контроль без воздействия, границы software-input и отдельный анализ кампании обязательны;
данные не превращаются в свидетельство работоспособности GPIO или физической кнопки.

<a id="tech-005"></a>
## TECH-005 — Инъекция аргумента

**Цель:** пройти реальную ветку отказа без повреждения конфигурации.

Остановиться на нужном вызове по условию, проверить исходный аргумент, сохранить свидетели и
записать аргумент в текущем кадре:

```python
t.reach("rtc_wait", condition=f"error == {RTC_ERROR_LSI_TIMEOUT}")
t.check("LSI wait mask", t.read("mask"), t.evaluate("RCC_CSR_LSIRDY"))
t.write("mask", 0)
t.reach("board_rtc_fault")
```

Затем проверить код ошибки, минимум 1000 тиков прошивки, неизменный `RCC->BDCR` и отсутствие
публикаций. HAL: NULL в указатель конфигурации (`t.write("RCC_OscInitStruct", "0")`) — только после
просмотра защиты исходника до разыменования ([TECH-009](#tech-009)).
**Окружение:** аргумент доступен и изменяем в кадре, не устранён оптимизацией; SysTick работает,
внешний тайм-аут runner обязателен.
**Граница:** проверен программный deadline одной стадии, не физический отказ LSI и не точность
1000 мс. После инъекции — `reset_run` и положительный `HW_CI_RTC_ALARM`.
[rtc_deadline](../../tests/firmware/profiles/f030r8/tests/board/test_rtc.py), [протокол](../evidence/ru/F030_RTC_DEADLINE.md).

Входные данные можно временно менять через контекстный менеджер с восстановлением в `finally`. [Пример](../../tests/firmware/common/tests/board/test_event_injection.py) восстанавливает только объявленные поля ticks/led, включая выход по исключению. Это не откат PC, периферии, времени или всего состояния программы.

<a id="tech-006"></a>
## TECH-006 — Управляемое состояние периферии через MMIO

**Цель:** создать конкретное состояние периферии и проверить защиту приложения.

Выберите точное имя регистра в SVD, допустимую ширину и семантику по reference manual.
Для обычного RW-регистра без побочных эффектов возможны явные read → вычисление Python →
write. Для командного регистра, W1C или FIFO используйте отдельно обоснованное значение
и `allow_effects=True`, когда этого требует SVD; общий RMW там небезопасен.
[Контракт MMIO](api/mmio.md): нет скрытых чтений и проверки записи, ACK не доказывает эффект.

Приём применялся к состоянию busy ADC/DMA, отключению ADC и маскированию IRQ.
Перенос названия «busy» с F0 на F1/F4 не переносит семантику ADSTART и DMA EN.
Сначала проверьте исходное состояние, выполните одно воздействие, затем независимую
проверку защиты и отсутствия публикации. Восстановление по плану завершите нормальным
повтором сбора. Неизвестное восстановление прекращает серию.

Старые сценарии ADC используют обычный write; это исторические реализации, а не образцы
MMIO-контракта API 3. Для нового кода ориентируйтесь на [MMIO/SVD](MMIO.md),
[согласованность драйвера](#tech-023) и [границы приёмки](../evidence/ru/API_ACCEPTANCE.md).

**Проверка модели перед использованием.** Установите, какие свойства периферии воспроизводятся:
доступ к регистрам, побочные эффекты, защита, завершение операции и ошибки. В ограниченной модели
Flash для Renode 1.17 наблюдались обход LOCK записью CR и EOP без записи полезных данных.
Это ограничения модели, не свойства STM32. Прямое воздействие GDB на MMIO и выполнение драйвера
CPU — разные пути; фиксируйте использованный путь. Проверяйте данные и соседние области отдельно
от флага успешности; неизвестное или неподдерживаемое свойство не получает PASS.

<a id="tech-007"></a>
## TECH-007 — Независимые численные векторы и невалидные входы

**Цель:** проверить арифметику через реальные аргументы и результат функции прошивки.

Остановиться на входе в функцию пересчёта, записать заранее рассчитанные входы, дойти до публикации
и сравнить поля таблицей. Ожидания — аналитические якоря, не скопированные из проверяемого кода;
затем невалидные входы (0, насыщение, выход за диапазон) и восстановление нормального результата.

```python
t.reach("adc_convert_f103")
for name, value in zip(("temperature", "reference"), values):
    t.write(name, value)
t.reach("board_delay_ms")
t.check([(f"board_adc_reading.{field}", f"board_adc_reading.{field}", value)
         for field, value in zip(("vdda_mv", "temperature_mdeg_c", "quality"), expected)])
```

**Окружение:** доступные аргументы, размеры и знаковость C-типов, калибровочные данные MCU.
**Граница:** проверяется арифметика, не точность датчика; m°C не обещает точности 0,001 °C.
Не переносить двухточечную калибровку F4 на F030.
[Векторы F030](../evidence/ru/F030_CMSIS_ADC_UNITS.md), [adc_vectors F030](../../tests/firmware/profiles/f030r8/tests/board/test_ci.py),
[adc F103](../../tests/firmware/profiles/f103c8/tests/board/test_adc.py).

<a id="tech-008"></a>
## TECH-008 — Прерванный WFI-контекст

**Цель:** подтвердить пробуждение из Sleep выбранным IRQ.

Изолировать источник: сохранить `NVIC->ISER`, маскировать остальные IRQ и остановить SysTick
таблицей `t.write(rows)`, восстановление — в `finally` одной таблицей. В обработчике проверить номер
исключения, раскрутить прерванный кадр через `t.frames()` (кадр с `method == "signal"` — трамплин
исключения, его пропускают) и прочитать полуслово перед сохранённым PC через `t.memory()`:

```python
chain = t.frames(FRAME_LIMIT)["frames"]
interrupted = next((frame for frame in chain[1:] if frame["method"] != "signal"), None)
instruction = int.from_bytes(t.memory(interrupted["pc"] - 2, 2), "little")
```

WFI в Thumb — `0xBF30`. IRQ может прийти до WFI: попытки ограничены, их контексты сохраняются в отчёте.
F103: RTC Alarm (IRQ41) — во втором банке NVIC; сохранять и восстанавливать оба банка. Перевооружать
RTC в thread mode, где работает SysTick.
**Граница:** это не измерение тока, длительности сна и не проверка Stop/Standby. Изоляция IRQ меняет
среду: восстановление в `finally`, затем `reset_run`; ошибка восстановления не скрывается.
[sleep F030](../../tests/firmware/profiles/f030r8/tests/board/test_sleep.py), [протокол](../evidence/ru/F030_CMSIS_SLEEP.md),
[F103](../evidence/ru/F103_CMSIS_RTC_SLEEP.md).

## TECH-009 — HAL-аргументы и проверенный вариант исходника

**Цель:** выбрать нужный вызов HAL по аргументам и проверить его входы и эффект.

Условная остановка выбирает вызов: `t.reach("HAL_GPIO_Init", condition="GPIOx == GPIOA")`. Поля
аргумента проверяются таблицей в его кадре идентификаторами HAL (`"GPIO_Init->Mode"` против

## TECH-010 — Таблицы проверок

**Цель:** проверить несколько значений цели одной конструкцией с понятным отчётом.

`t.check(rows)` принимает строки `(имя, actual)` и `(имя, actual, expected)`. Строковая ячейка —
выражение GDB, вычисляется в момент проверки строки; число, `bool` и сопоставитель (`within`,
`near`, `one_of`, `matches`) — значения Python. Строка из двух ячеек проверяет истинность.
Структура всех строк проверяется до первого вычисления, первое несовпадение останавливает таблицу,
ошибка вычисления ячейки называет строку и напоминает правило.

```python
t.check([
    ("only channels 16/17", "ADC1->CHSELR", "ADC_CHSELR_CHSEL16 | ADC_CHSELR_CHSEL17"),
    ("forward scan", "ADC1->CFGR1 & ADC_CFGR1_SCANDIR", 0),
    ("plausible VDDA", "board_adc_reading.vdda_mv", PLAUSIBLE_VDDA_MV)
])
```

Функции GDB `$_streq`, `$_strlen`, `$_memeq`, `$_regex` работают в строковых ячейках
([TECH-018](#tech-018)). Таблица для записей — `t.write(rows)`; для серии чтений таблица не нужна:
`dict(zip(paths, map(t.read, paths)))`.
**Границы:** значение Python, вычисленное при построении списка (`t.read(...)` в ячейке), читается
до первой проверки; строки — последовательные чтения, не атомарный снимок. FIFO и read-to-clear
требуют прежней осторожности. Внутрь таблицы не переносятся `reach`, записи и зависимые вычисления.
Строка Python (`result["outcome"]`, `profile.case["id"]`) в ячейку не помещается — она была бы
вычислена как выражение GDB; такие проверки остаются отдельными.
[check](api/check.md), [сопоставители](api/matchers.md), host — `tests/host/test_target_extras.py`.

### Текст и битовая маска

```python
# Scalar strings are literal text; table strings are GDB expressions.
t.check("state text", "READY", "READY")
t.check([("enabled", "(flags & 0x20) != 0", 1)])
t.check("raw mask", t.read("flags & 0x20"), 0x20)
```

Маска `0x20` не равна `1`. Нормализация нужна только для логического ожидания;
при проверке набора битов сохраняйте саму маску. Указатель может читаться как числовой адрес:
это не значение объекта по адресу, разыменование задаётся отдельно. `sizeof` сверяйте с
`gdb.lookup_type("Packet").sizeof`; преобразование ненулевого размера в `bool` даёт `True`, не размер.

### Вычислить значение один раз перед записью

В API 3 RHS вычисляется однократно, но вызов функции в выражении данных запрещён.
Если нужно получить отсчёт исполнением кода, вызовите функцию явно и проверьте результат:

```python
# next_sample — условная функция без аргументов с числовым результатом.
result = t.call("next_sample")
t.check("sample returned", result["return_state"], "available")
t.write("sample_copy", result["return_value"], verify=True)
```

Это обычный def; в async def нужен await call. Вызов и запись не атомарны.
LHS должен быть стабильным, MMIO требует специального интерфейса.

## TECH-011 — Накопление измерений и расчёт по records

**Цель:** собрать серию опубликованных результатов MCU и рассчитать статистику по завершённой серии.

1. Параметры серии — в `api.toml [user.measurement]`, сценарий читает их через
   `t.profile.user["measurement"]` и проверяет до навигации (`within(2, 20)`, `one_of(1, 2, 3)`).
2. В каждой итерации дойти до точки публикации, проверить свежесть по счётчику MCU с его разрядностью,
   прочитать значения в согласованном состоянии.
3. `t.record("measurement.sample", {...})` с исходными единицами и номером. Проверить качество
   и допустимость; при повторе, пропуске или ошибке не выпускать успешную сводку.
4. Один раз получить `t.records(...)`, проверить полноту, вычислить `mean`/`stdev` (ddof=1, N ≥ 2)
   и записать отдельную сводку.

**Границы:** номер записи не означает новый отсчёт MCU; остановка ядра не замораживает периферию.
Не заменять пропуски нулями и не скрывать их фильтрацией. Малое СКО не доказывает точность.
Лимиты records задаются в `api.toml`; повторный `records()` создаёт дополнительные копии.
[measurements](../../tests/firmware/common/tests/board/test_measurements.py),
[measurement_series](../../tests/firmware/common/tests/board/test_measurement_series.py),
[record](api/record.md), [records](api/records.md).

**События и интервалы.** [Пример](../../tests/firmware/common/tests/board/test_event_intervals.py) сохраняет источник, эпоху, ширину счётчика и номинальную частоту вместе с отсчётом. Разность по модулю допустима при совпадении метаданных и внешней гарантии интервала меньше периода; пропущенные полные обороты так не обнаружить. `board_ticks_ms` — номинальные тики прошивки, не калиброванное время. Задержка Python на остановленном ядре не измеряет время работы MCU.

### Обязательные данные и отдельный анализ

Records содержат произвольные допустимые данные, не только измерения. Название записи, поля,
единицы и ожидаемое число отсчётов задаёт потребитель. `bool` допустим в журнале, но не обязательно
допустим как измерение: проверяйте `type(value) in (int, float)`, если логические значения исключены.
`gdb.Value` и `bytes` преобразуйте явно, например `int(value)` и `data.hex()`; единицы не выводятся из типа.

Для файлового анализа сначала проверяйте принадлежность и целостность capture, затем требуемую
завершённость, наличие/число записей, поля/типы/единицы и только после этого числовые условия.
`all([])` возвращает `True`: пустая выборка не должна проходить проверку измерений.
Ошибка `record()` и отсутствие файла захвата — отказы разных этапов.

Сохраняйте вердикт анализа отдельно от исхода сценария. Для анализа можно различать нехватку
свидетельств (ERROR) и полноценные данные вне диапазона (FAIL); это политика потребителя,
не новая схема результата модуля. PASS анализа не отменяет FAIL сценария. Условие «ровно два
отсчёта» или запрет прерванной серии не универсальны: задайте их до запуска для конкретной задачи.

## TECH-013 — Кто пишет: точка наблюдения и цепочка кадров

**Цель:** найти функцию, которая изменяет объект, и её вызывающих.

```python
with t.watch("app_state.ticks"):
    stop = t.resume()["stop"]
    t.check("the stop is the watch point", stop["kind"], "watchpoint")
    names = [frame["name"] for frame in t.frames(4)["frames"]]
```

Кадры описывают место остановки, а не обязательно инструкцию записи. Проверить новое значение,
сохранить stop и frames через record(); для внешнего анализа журнал нужно явно вывести.
Сопоставить PC с symbol() и дизассемблированием конкретного ELF. HW_CI_WHO_WRITES проверяет
известный участок прошивки, а не универсальный алгоритм определения писателя.
**Окружение:** аппаратная точка наблюдения, адресуемый объект объявленного размера.
**Граница:** остановка может произойти после записи; задержка наблюдалась и на Cortex-M3,
а не только M0. Если следом выполнен вызов, писатель может оказаться в вызывающем кадре.
В эпилоге раскрутка может быть неполной. Нельзя автоматически считать писателем frames[0]
или frames[1]: нужны исходники, инструкции и корректная цепочка. При недостатке свидетельств
писатель не установлен. Не вычислять адрес записи как PC - 2: длины инструкций и пути различаются.
Признак inferred относится к классификации остановки, а не подтверждению писателя.
API не гарантирует число инструкций задержки и полноту кадров. Записи DMA и других мастеров
шины точкой наблюдения ядра не видны.
В опыте на AT32/J-Link после последней записи функция уже вернулась: её нет в цепочке кадров.
[watch](api/watch.md), [frames](api/frames.md),
[who_writes](../../tests/firmware/common/tests/board/test_who_writes.py).

## TECH-014 — Вызов функции как предиката

**Цель:** вызвать функцию прошивки на остановленном ядре как проверку, не оставив следа в состоянии.

Снять байты затрагиваемого объекта `t.memory(address, size)`, вызвать `t.call(...)`, проверить
результат и эффект, восстановить байты `t.memory(address, snapshot)` и сравнить их с исходными.

```python
state = t.symbol("app_state")
snapshot = t.memory(state["address"], state["size"])
result = t.call("app_step")  # условная функция без аргументов
t.memory(state["address"], snapshot)
```

**Граница:** восстанавливается только снятый объект; периферия, статические переменные функции и
другие побочные эффекты вызова остаются на совести автора. `memory()` пишет только в SRAM профиля.
[call](api/call.md), [memory](api/memory.md),
[call_predicate](../../tests/firmware/common/tests/board/test_call_predicate.py).

**Возврат не заменяет эффект.** До вызова задайте ожидаемое изменение и инварианты. После —
сравните возвращаемое значение, точные данные, счётчики операций и неизменность соседних областей.
Счётчик драйвера подтверждает логические операции драйвера, а не число физических транзакций.
Восстановление выполняйте и после отказа проверки; его сбой сохраняйте отдельно от исходной ошибки.
Для C++ байтовая копия не является универсальным восстановлением: учитывайте время жизни,
память по указателям и внешние ресурсы. [Отложенная запись](#tech-020) показывает отдельный случай.

## TECH-015 — Выбор нужной остановки

**Цель:** остановиться на нужном вызове, не перебирая остановки в сценарии.

`t.breakpoint(location, ignore_count=N)` пропускает N вызовов; `point.condition` меняет условие
действующей точки; `point.disable()` сохраняет точку и счётчик, но освобождает слот бюджета;
`t.reach(location, condition=...)` — разовая условная остановка (`"error == 3"`, `"GPIOx == GPIOA"`).
Бюджет `breakpoint_limit` профиля считает только активные точки, включая точки fault handlers;
точка сверх бюджета отказывает `limit_exceeded`.
**Граница:** условие вычисляет GDB при каждом попадании, ядро останавливается и продолжается —
это меняет время исполнения прошивки.
[breakpoint](api/breakpoint.md), [Point](api/point.md),
[conditional_stop](../../tests/firmware/common/tests/board/test_conditional_stop.py),
[point_budget](../../tests/firmware/common/tests/board/test_point_budget.py).

**Ожидание изменения.** [Помощник сценария](../../tests/firmware/common/tests/board/test_wait_changes.py) сначала проверяет вид остановки и ID собственной точки, затем предикат. Его исходы `matched`, `exhausted`, `unexpected-stop` — соглашение примера, не новые исходы API. Чужую остановку нельзя скрывать дополнительным resume. Лимит числа остановок не заменяет timeout сценария. `with` удаляет свою точку при обычном выходе/исключении; принудительное завершение GDB требует внешнего recovery. Источник ID может быть native или inferred: сохраняйте свидетельство вместе с результатом.

## TECH-016 — Место остановки: функция, а не номер строки

**Цель:** остановиться на нужном этапе так, чтобы сценарий не ломался от правки исходника.

Этап кода называется функцией: `reach` на входе, `finish` после выхода (результат называет
`returned_from`, текущую функцию и значение возврата), `step`/`until(функция)` внутри. Чтобы увидеть
результат работы функции, достаточно выйти из неё `finish` и проверить опубликованное состояние:

```python
t.ret("0")
t.check("the receiver returned to the loop", t.finish()["function"], "app_loop")
```

Адрес `файл:строка` ломается от любой правки исходника, в том числе от добавленного комментария.
Он допустим только там, где проверяется сама адресация по строке (`HW_CI_UNTIL_TARGET`);
тест host следит за этим.
[finish](api/finish.md), [until](api/until.md), [step](api/step.md),
[return_value](../../tests/firmware/common/tests/board/test_return_value.py),

<a id="tech-017"></a>
## TECH-017 — Профиль прогона как проверка окружения

**Цель:** убедиться, что сценарий работает на том кристалле, образе и стенде, которые заявлены.

`t.profile` объединяет `target.toml`, эффективный `api.toml`, файлы данных проекта, сведения о сборке,
case, стенд и GDB. Регистр идентификации и размер Flash читаются по адресам из профиля; таблица
векторов образа — через `t.memory(flash_start, 8)`; файл данных `board.toml` — `t.profile.data`;
сборка — `t.profile.build` (компилятор, пакеты Cube, CMSIS/HAL, defines). Значения профиля — Python,
поэтому сравниваются отдельными проверками и сопоставителями, не строками таблицы.
**Граница:** профиль описывает заявленное окружение; расхождение объёма Flash с профилем — предупреждение,
если образ помещается в оба ([TARGET_IDENTITY](TARGET_IDENTITY.md)).

Начальный SP в таблице векторов — указатель вершины стека, а не адрес байта для чтения.
Для выбранной непрерывной области RAM `[start, end)` стек, растущий вниз, может начинаться
с `end` (так определяется `_estack` в проверочных ELF). При проверке начального стека с
8-байтовым выравниванием и местом для первого сохранения используйте:

```python
# start/end describe the selected stack RAM region from the board/linker configuration.
initial_sp = int.from_bytes(t.memory(t.profile["flash_start"], 4), "little")
t.check("initial SP in stack region", start < initial_sp <= end)
t.check("initial SP aligned", initial_sp % 8, 0)
```

Для чтения непустого блока нужны другие границы: `start <= address` и `address + size <= end`.
По `end` не читать. Размеры и выбранный банк задаёт проект: широкое окно SRAM в `memory()`
не подтверждает физическую доступность всей области. Проверка SP не доказывает достаточный
запас стека или отсутствие пересечения с данными/кучей. Текущий SP после пролога может отличаться
от вектора; проверять его отдельно. На шести проверочных ELF вектор равен `_estack = end`,
последние 8 байт выбранной RAM читаются; за пределы области опыт не обращается.

[profile](api/profile.md), [profile scenario](../../tests/firmware/common/tests/board/test_profile.py).

<a id="tech-018"></a>
## TECH-018 — Строки прошивки

**Цель:** проверить C-строки прошивки.

Два равноправных способа. В таблице — функции GDB в строковой ячейке:
`("version field equals", f'$_streq(app_info.version, "{VERSION}")')`, `$_strlen`, `$_memeq`,
`$_regex`. В Python — `t.evaluate(path, as_type=str)` читает массив `char` до нуля или указатель
`char *` (не более `STRING_LIMIT`) и сравнивается обычной проверкой или `matches(pattern)`.
Литерал строки в `$_memeq` требует выделения памяти в цели; сравнивать объекты памяти.
[evaluate](api/evaluate.md), [strings](../../tests/firmware/common/tests/board/test_strings.py).

<a id="tech-019"></a>
## TECH-019 — Контекст C++ и типизированное чтение

**Цель:** исследовать объект, аргумент перегрузки и результат естественного вызова.

```python
t.reach("Converter::apply(int) const")
frame = gdb.newest_frame()
obj = frame.read_var("this").cast(gdb.lookup_type("Converter").pointer())
t.check("object bias", int(obj.dereference()["bias"]), 7)
returned = t.finish()
```

`gdb` импортируется в сценарии; вызовы выполняются в основном потоке GDB. Полная сигнатура
различает перегрузки. В API 3 reach принимает одну внешнюю пару одинарных
кавычек GDB (`t.reach("'Converter::apply(float) const'")`); прежний выпуск требовал форму без них.
Снимайте значения до смены кадра. `is_optimized_out` отличается от отсутствующего символа
и от настоящего нуля; ленивое значение может отказать при чтении. В records сохраняйте обычные
данные Python, а не живой gdb.Value. Возврат сверяйте, когда он available; дополнительно
проверяйте опубликованный результат программы.

**Проверено:** [отдельный собираемый пример](../../tests/cpp-context/README.md), шесть плат,
Og/O2, `-g3`, soft-float, без LTO. Аргументы в обеих сборках были доступны; аппаратный случай
optimized-out этим не подтверждён. RTTI, исключения, наследование и hard-float не проверялись.
[Сценарий](../../tests/cpp-context/profile/tests/board/test_cpp_context.py),
[read](api/read.md), [evaluate](api/evaluate.md), [finish](api/finish.md).

### Вызов метода живого объекта в песочнице

Остановитесь после конструктора, пока объект, адаптер и буфер аргумента ещё живы. Выберите
кадр владельца и сохраните типизированные указатели в convenience variables GDB. После выхода
из области жизни их использовать нельзя. Размеры берите из отладочной информации; произвольный
«свободный» адрес SRAM не заменяет выделенный буфер. Проверьте наличие вызываемой реализации
метода в ELF и возможные ожидания прерываний, задержек или ресурсов внутри вызова.

Пример для GDB Python после выбора кадра с `interactive` и `call_byte`:

```python
# The live object and argument storage belong to the neutral example.
gdb.execute("set $cache = &interactive")
gdb.execute("set $input = &call_byte")
assert int(gdb.parse_and_eval("$cache->write(5, $input, 1)")) == 1
assert int(gdb.parse_and_eval("$cache->dirty()")) == 1
```

Это исполнение кода CPU, а не чтение копии объекта. Дополнительно проверьте эффекты по
[TECH-020](#tech-020). Выполняйте GDB API только в основном потоке GDB.

**Граница этого опыта:** Windows, Renode 1.17, нейтральный Cortex-M4 ELF, C++17, `-O0`, без LTO,
GDB 14.2.90 с Python 3.11.4. Использовался `gdb.parse_and_eval`, не штатный `Target.call()`.
PC/SP до и после серии совпали; предупреждение GDB о предположении MSP сохранилось.
Это не проверка всех регистров, PSP, ISR, RTOS, оптимизированных сборок или реальной платы.
Данная граница относится к принудительным вызовам в песочнице, а не к аппаратному примеру выше.

Публикуемый нейтральный [пример C++/GDB/Renode](../../tests/renode-cache/README.md) содержит
команды, host-проверки и отдельный сценарий; он не подключён к аппаратной матрице CI.

### Проверка вызова и полноты восстановления

`Target.call()` принимает простое имя функции и численные аргументы; свободная C++-функция
может ему соответствовать. `Object::method` и `object.method` не становятся допустимыми именами
из-за PASS [ELF-контракта](CONTRACTS.md). Прямой `gdb.parse_and_eval` — отдельный путь,
его эффекты и свидетельства фиксируются сценарием. Наличие inline-объявления не гарантирует
отдельного вызываемого тела. У скрытого `this` возможен тип `Object * const`, отличный от
`Object *` и `const Object *`; не удаляйте квалификаторы ради прохождения preflight.
API 3 (0.5.0) принимает `Object * const` в явном контракте this; пример
`tests/renode-startup/run_cpp.py` разделяет offline-проверку и реальный вызов в Renode.

Для снимка обычной памяти до вмешательства сверьте независимо известную разметку с DWARF,
затем длину полученных байтов с размером. Равенство двух одинаково коротких снимков ничего
не доказывает. В нейтральном примере полезны защитные байты до и после объекта: проверяйте
их сразу после изменения и после восстановления. API 3 (0.5.0) проверяет длину ответа в `memory()`, но правильность запрошенного размера задаёт сценарий.

После исключения тела выполняйте восстановление в `finally`, затем чтение и сравнение всей
согласованной области. Сохраняйте исходную ошибку тела и ошибку восстановления отдельно;
неподтверждённое восстановление запрещает дальнейшие изменения. Успешное восстановление
не отменяет исходный отказ. `finally` не гарантирует восстановление при аварии процесса или
потере связи; копия байтов не восстанавливает внешние ресурсы и произвольные инварианты C++.

Эти границы дополнительно проверены на нейтральном ELF в Windows/Renode 1.17, GDB 14.2.90,
`-O0 -g3`: типы/вызовы и восстановление простой RAM-области. Отказы транспорта внедрялись
в host-модели; короткий ответ настоящего GDB и восстановление DMA этим не подтверждены.


<a id="tech-020"></a>
## TECH-020 — Отложенная запись и идемпотентность

**Цель:** отличить изменение кэша от сохранения и обнаружить лишнюю либо отсутствующую запись.

Предусловия: известный исходный образ, принадлежащие примеру объект и буферы, отдельное чтение
хранилища, наблюдаемый счётчик логических сохранений. Ожидания задаются независимо от реализации.

| Действие | Проверка |
| --- | --- |
| Записать изменённый байт в кэш | Успех, dirty установлен, хранилище и счётчик сохранений прежние |
| Сохранить изменённый кэш | Точный образ совпал, dirty снят, счётчик вырос на один, соседи прежние |
| Сохранить чистый кэш повторно | Успех без изменения данных и счётчика |
| Передать выходящий за границу диапазон | Отказ без изменения кэша, хранилища и счётчика |
| Смоделировать отказ или неверное обратное чтение | Ошибка обнаружена, dirty сохранён, повторная попытка проверяется отдельно |

Сначала используйте host fake для отказов и частичных изменений. Затем проверяйте вызовы через
GDB и образ памяти в эмуляторе. Каждому независимому случаю задавайте известное исходное состояние;
после опыта проверьте восстановление либо завершите принадлежащий опыту экземпляр эмулятора.
Политику dirty при возврате байта к прежнему значению определяет контракт: она не обязана
автоматически становиться false.

**Проверено:** 39 host-проверок нейтральной обёртки; два независимых цикла Renode подтвердили
вызовы C++ и эффекты сохранения. Отказы и повреждение обратного чтения проверены host fake,
не моделью отказов Renode. Стирание отдельных граничных страниц проверено в модели; защита,
физическое программирование, износ и потеря питания не подтверждены. Это техника сценария,
не новый API хранения данных и не аппаратная приёмка EEPROM/Flash.

<a id="tech-021"></a>
## TECH-021 — Порядок событий и следующая операция

[Исполняемый пример host/Renode](../../tests/stateful-buffer/README.md): два дефекта,
исправление, повтор и восстановление; периферия не моделируется.

**Цель:** обнаружить остаточное состояние и ошибки взаимодействия обработчиков.
Используйте принадлежащие опыту объект и буферы, известные head/tail и завершённую
инициализацию; сохраните состояние по [TECH-019](#tech-019).

| Воздействие | Независимое ожидание |
| --- | --- |
| Частичный пакет, затем завершение или таймаут | Публикация только полного допустимого пакета; после таймаута заданное состояние |
| Следующий пакет другой длины и содержания | Его точные байты и длина, без хвоста предыдущего; независимый CRC |
| Ошибка RX при занятом TX | Нет отмены, повторной отправки или изменения текущего TX, если это задано контрактом |
| Завершение TX до/после проверки очереди | Нет потери/дублирования, tail сдвинут ровно на переданные данные |
| Переход кольца через конец буфера | Следующий сегмент передан в правильном порядке, защитные области целы |

Проверяйте промежуточные состояния и следующий цикл без reset. Независимые случаи
начинайте с одинаковых предусловий; после серии восстановите объект, буферы и ресурсы.
Явный вызов callback проверяет выбранную последовательность, а не все гонки и не доставку
реального IRQ/DMA. Восстановление байтов не отменяет уже переданные UART-данные.

<a id="tech-022"></a>
## TECH-022 — Логическое время автомата

**Цель:** быстро проверить debounce, backoff, повтор и предельное время состояния.
Сначала задайте таблицу переходов: состояние, вход, длительность, ожидаемое состояние
и допустимое действие. Проверяйте порог −1, порог и порог +1, повтор входа и переход
через переполнение счётчика с учётом его разрядности и максимального интервала.

Меняйте только контролируемый источник времени и входы, затем выполняйте один шаг.
Для нейтрального примера используйте изолированный автомат без физических выходов.
На плате запись системного tick влияет на другие задачи; снимка объекта недостаточно:
нужны согласованная изоляция, учёт всех затронутых часов/аргументов/выходов и восстановление.
Задержки, ожидание IRQ и захваченные блокировки могут сделать GDB-вызов непригодным.

**Граница:** виртуальное время доказывает логику переходов, но не фактическую задержку,
работу планировщика, watchdog или безопасность нагрузки. Их проверяют живым окном
и отдельным временным свидетелем. Остановка CPU не замораживает всю периферию.

**Исполняемый пример:** [logical-time](../../tests/logical-time/README.md): пороги,
переполнение uint32_t, повтор после отказа без reset, отказ start без изменения POD.
Три независимых дефекта; тот же сценарий на исправленном варианте и повтор.
`call` возвращает словарь операции: сравнивайте `return_value` после проверки
`outcome`/`return_state`, а не весь словарь. Время передаётся числом, без скрытых
вызовов в read и без sleep ПК. Отказ функции start (0) проверяется check, не refused.

<a id="tech-023"></a>
## TECH-023 — Согласованность драйвера и периферии

**Цель:** проверить восстановление после ошибки по состоянию обеих сторон.
Задайте допустимые сочетания программного состояния драйвера, счётчиков, флагов
и состояния DMA по документации конкретного MCU/HAL. Например, READY при ещё активном
приёмном DMA может быть противоречием; это не универсальное правило всех драйверов.

Сверьте Instance/канал и SVD с целью до доступа. Сохраните RAM отдельно от регистров;
[MMIO](api/mmio.md) используйте с правами и эффектами конкретного регистра. Перед
изменением буфера/счётчика остановите принадлежащий опыту поток и подтвердите остановку.
После инъекции ошибки проверьте согласованное состояние, сохранность другого направления,
повторный запуск и приём следующего блока. Восстанавливайте в порядке из reference manual,
не записывая общий снимок в W1C/FIFO. Ошибка восстановления прекращает серию.

**Граница:** SVD и ответ сервера не доказывают физический эффект. Инъекция состояния
не подтверждает механизм возникновения аппаратной ошибки; Renode проверяет только модель.

<a id="tech-024"></a>
## TECH-024 — Стоимость диагностики и переполнение счётчика

**Цель:** убедиться, что сама диагностика не создаёт неприемлемую нагрузку и что
счётчики продолжают работать после переполнения. Зафиксируйте частоту, разрядность,
режим счёта в halt/sleep и границы измеряемого участка; DWT доступен не на всех Cortex-M.
Проверьте накладные расходы измерителя отдельным контролем. Запишите все выборки,
правило исключения прогрева, медиану и максимум; порог задайте до опыта.

Для n-битного счётчика используйте разность по модулю 2**n, только если прирост между
чтениями строго меньше 2**n (это подтверждено верхней границей скорости счётчика). Проведите серию через границу переполнения,
сравните приращения с независимой временной опорой; пропуск выборок делает вывод неизвестным.
Сохраните и восстановите настройки счётчика и разрешения отладки, если меняли их.

**Граница:** измеренное время GDB-вызова не является WCET или временем свободного
исполнения под IRQ/RTOS. Часы хоста включают транспорт; сравнение двух производных
одних MCU-часов не подтверждает их абсолютную частоту.

**Исполняемый пример:** [counter-cost](../../tests/counter-cost/README.md): независимая
граница прироста, достоверный ноль/UNKNOWN, пустой контроль и полные расходы наблюдения.
Модельные тики и измеренные длительности запросов GDB по часам ПК записываются отдельно.
Три дефекта проверяются теми же сценариями, что исправление; физический WCET не заявляется.

<a id="tech-025"></a>
## TECH-025 — Неравномерные выборки и качество фильтра

**Цель:** отделить ошибку расчёта от шума, выбросов и переходного процесса.
Для частоты событий задайте одинаковую интенсивность при разных интервалах, нулевой
прирост, переполнение и недопустимый dt. Ожидание вычисляйте независимо; например,
для согласованного экспоненциального фильтра alpha = 1 − exp(−dt/tau), а не копией кода MCU.

Для измерительного фильтра нужны отдельные опыты: стационарный шум, скачок входа,
одиночные выбросы и сходимость. Сохраняйте сырые и обработанные значения, единицы,
время публикации и номер выборки. Новый системный tick не означает новое измерение.
Проверяйте число уникальных выборок до анализа; не смешивайте переходный участок
со стационарной дисперсией. Восстановите входной источник и состояние фильтра.

**Граница:** уменьшение разброса не доказывает точность. Нужен независимый эталон входа;
физический источник, допустимые уровни и восстановление согласуются отдельно.

<a id="tech-026"></a>
## TECH-026 — Живое окно и внешний свидетель

**Цель:** связать внутреннее состояние с наблюдением другого участника стенда.
Радиоимитатор mcu_gcs_board выступает управляемым источником для mcu_power_board;
инженерный инструмент hwlivetest-android может записывать MCAP. Это роли стенда,
а не автоматически поддерживаемые backend или импортёры модуля.

До resume подготовьте захват и очистку всех собственных процессов; подтвердите готовность
приёмника. Используйте ограниченное [живое окно API 3](LIVE_EXECUTION.md), не блокируя
GDB-поток синхронным ожиданием внешнего процесса. После окна остановите цель, завершите
и выгрузите захват, проверьте восстановление. Обрабатывайте таймаут и частичный запуск;
смерть процесса не покрывается одним finally, а удалённый процесс требует отдельного владения.

Связывайте записи по идентификатору прогона, ревизии/ELF, источнику, единицам, номерам
сообщений и временной шкале с известной погрешностью. Обнаруживайте пропуски и дубликаты.
MCAP/rosbag — контейнеры: заранее определите обязательные каналы и поля; отсутствие
данных не заменяйте нулём. Сохраняйте исходы сценария, захвата, анализа и восстановления
раздельно ([TECH-011](#tech-011)).

**Граница:** чтение одного значения через GDB и телеметрию проверяет доставку/согласованность,
но не независимую точность датчика. PASS процесса не равен валидному журналу.

**Исполняемый host-пример:** [external-capture](../../tests/external-capture/README.md):
READY до окна, drain до EOF, номера/каналы/идентичность, модельные временные опоры
и отдельный вердикт анализа. Полная противоречащая запись даёт FAIL, непригодная —
UNKNOWN; исходный сценарий неизменен. Это host-fixture, не GDB/аппаратная проверка.

## Как пополнять каталог

При новом опыте сначала искать существующую карточку; новый ID — только для отдельного приёма.
HAL- и CMSIS-варианты связывать, не объявляя эквивалентными. Записывать предусловия сборки и
контекста, действие, независимый критерий, вмешательство, восстановление, ограничения и ссылку
на код или протокол с MCU, HAL, GCC, GDB и backend. Разделять «проверено», «кандидат»,
«не проверено»; первоначальные ошибки — тоже часть опыта. RU и EN, комментарии сценариев и
тест стиля обновлять вместе. При смене HAL или оптимизации повторять затронутый preflight и HW,
а не только ссылки.

В API 3 (0.5.0) повторное вычисление RHS устранено: см. [контракт write](api/write.md). Явное предварительное вычисление остаётся полезным для старых версий.

## Исследование обращений к периферии

Перед применением техник к MMIO используйте [ограничения API](MMIO.md) и
[ресурс навыка Renode](../../skills/stm32-gdbtest-renode/references/mmio.md).
Сопоставляйте три уровня: вызов метода → запрос GDB/RSP → callback модели.
Ожидание задавайте по семантике регистра до запуска, отдельно от результата модели.
Сначала проверяйте положительный и отрицательный случаи в Renode, затем повторяйте
минимальный участок на своей цели с конкретным сервером и безопасным восстановлением.
Это рекомендация исследования, не новое правило синтаксиса сценария и не доказательство
точного числа физических транзакций. WO/W1C/FIFO нельзя обрабатывать общим снимком RAM.


Живое окно 0.5.0: обычные сценарии сохраняются; `async def`, `resume(sync=False)`,
`await wait()` и `await halt()` — [контракт и миграция](LIVE_EXECUTION.md).


В API_VERSION=3 обычные def сохраняют синхронную навигацию. В async def используйте await для reach/step/until/finish/resume()/reset/call; resume(sync=False), ret и методы данных остаются немедленными. Не помещайте inferior calls в выражения методов данных. Ограничения и миграция: [LIVE_EXECUTION](LIVE_EXECUTION.md).

## Моделируемый вход GPIO и override (A5.2)

[Исполняемый пример](../../tests/modeled-gpio/README.md) отделяет внешний уровень
учебной модели от подмены SRAM/возврата. Проверяйте маршрут «источник → регистр →
потребление прошивкой», следующий уровень и соседний вход. `override` заменяет
описание SVD, но не превращает IDR в записываемый регистр: ACK может прийти после
игнорируемой записи. Отрицательный контроль сохраняет FAIL ложного утверждения,
а отдельный анализ проверяет ожидаемый отказ воздействия. Возвращайте состояние
прошивки **и** внешний источник. Модель не доказывает электрические/временные свойства.

## Буфер и повторное потребление (A5.3)

[Исполняемый пример](../../tests/buffer-consumption/README.md) кладёт подготовленный пакет
в буфер, принадлежащий опыту, и вызывает обработчик через `Pointer` с точной длиной.
Проверяйте возврат и состояние обработчика, порядок двух пакетов, отказный пакет и вход
после него, вложенный вызов во время штатной обработки и следующий штатный пакет.
Запись в буфер без вызова не является потреблением: такой контроль остаётся FAIL.
`Pointer` длиннее массива из DWARF отклоняется до вызова (`argument_range`). Секцию опыта
снимайте и возвращайте целиком. DMA, прерывание и приём периферией здесь не проверены.

## Офлайн-импорт внешней записи (A6)

[Исполняемый пример](../../tests/rosbag-import/README.md) читает сохранённую ROS1 bag v2
строго по индексу и переводит топики в каналы с объявленными единицами. Время записи —
время приёма хостом записи, а не часы МК и не момент чтения GDB. Анализ отдельный и не
меняет исход сценария. Связь со снимком отладчика требует опор счётчика МК (переходы
до и после момента чтения в одном сегменте) и измеренной границы задержки доставки;
иначе итог UNKNOWN. Обрыв, неполный индекс, чужой тип, другие единицы или NaN дают
UNKNOWN, а не нулевое измерение. ROS и GDB читают одно состояние прошивки — это не
независимые датчики; последовательные выборки rostopic не считаются одновременными.
MCAP и радиоимитатор — следующие источники того же нейтрального формата.

## Журнал, квоты и полнота (A1–A3)

Ошибка журнала не скрывает исходную: исполнение, транспорт и аудит записываются раздельно,
у лимита видны имя записи, путь и used/maximum/attempted. Строгий режим по умолчанию;
`truncate` допустим, только если объём известен заранее и частичный журнал годится для
конкретного утверждения, — тогда `records(require_complete=False)` с явной пометкой.
Неполный прогон завершается command 2, исход сценария проверяется отдельно; CSV отклоняет
неполный источник, HTML и сводки показывают неполноту, DDTT остаётся UNKNOWN.
Уровень вывода (`failures`, `summary`) не меняет коллекции проверок; сводку проверяют повторным
расчётом, а не сравнением первой и последней строки. Неправильно: поднять лимит или включить
`truncate`, чтобы получить PASS; ловить RecordError; подавать сводку как вход DDTT.
Примеры: `tests/renode-backend/run.py`, `run_report.py --summary`, `run_journal.py`,
`run_report_quota.py`; [руководство журналирования](JOURNALING.md).

## Вызовы C++ (A4)

Один явный `call`: квалифицированное имя, `this=` — именованный объект или указатель в SRAM,
`signature=` — точная перегрузка, буферы — `Pointer`/`Reference`. Проверяйте `outcome`,
`return_state`, затем `return_value`; отказ до исполнения подтверждайте счётчиком вызовов цели.
Публичный метод вместо ручной записи private-полей. Неправильно: вызов внутри `read`/`evaluate`/`write`
(`expression_call_forbidden`), перегрузка без `signature` (`ambiguous_function`), поле или выражение
в `this`, виртуальный метод, обработчик, вызванный как метод, под видом аппаратного IRQ.
Пример: `tests/renode-backend/run_cpp.py`; контракт — [call](api/call.md).
