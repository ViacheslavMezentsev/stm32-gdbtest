# Переход потребителя с 0.4.x на 0.5.0

[Документация](index.md) → [Версии](VERSIONING.md) → Переход на 0.5.0 · [English](../en/MIGRATION_050.md)

0.5.0 — выпуск с `API_VERSION=3`. Обычные сценарии `def` сохраняют синхронную форму, аппаратные
target schema 1/2 и стенды менять не нужно. Переход обязателен там, где сценарий вычисляет скрытые
вызовы функций в выражениях, использует `execute()` в `async def` или читает и пишет регистры
периферии выражениями GDB. Порядок ниже повторяет миграцию демонстрационных потребителей
[stm32-hwtest-bluepill](https://github.com/ViacheslavMezentsev/stm32-hwtest-bluepill) и
[stm32-hwtest-blackpill](https://github.com/ViacheslavMezentsev/stm32-hwtest-blackpill).

## Что изменилось для потребителя

| Область | 0.4.x | 0.5.0 | Что сделать |
| --- | --- | --- | --- |
| Совместимость API | `API_VERSION=2` | `API_VERSION=3` | Проверить сценарии по таблице ниже; `def` в `async` без необходимости не переводить |
| Выражения | Могли неявно вызывать функции цели | `may-call-functions off` для методов данных, `ret` и условий навигации | Вынести вызов в явный `t.call(...)` и использовать готовое значение |
| `async def` | — | Навигация и `call` ожидаются через `await`; `execute()` отклоняется | Добавить `await`, убрать `execute`, оставить `finally` с `halt` ([контракт](LIVE_EXECUTION.md)) |
| Регистры периферии | Выражения GDB по адресам и макросам | `t.mmio.read/write` по снимку SVD с правами и эффектами ([mmio](api/mmio.md)) | `[mmio] svd` в `session.toml`, замена обращений, явные `allow_effects` |
| Пакет | Капсула конфигурации schema 1 | Schema 2, если задан SVD (без SVD — schema 1) | Получатель пакета должен поддерживать schema 2 |
| Конфигурация | Проверялась при запуске | Офлайн-команда `inspect` ([руководство](HIL_INSPECT.md)) | Проверить каждый профиль до prepare |
| Эмуляторы | — | target schema 3 для Renode/QEMU ([Renode](../guides/ru/RENODE.md), [QEMU](../guides/ru/QEMU.md)) | Только для нового маршрута; аппаратные target не переносить |
| Навыки | Прежний заголовок | Формат Agent Skills, `metadata.version` 0.5.0 ([навыки](../../skills/README.md)) | Обновить копии `.claude/skills` вместе с gitlink |

## Порядок перехода

1. **Ветка и gitlink.** Отдельная ветка потребителя; gitlink — на тег `v0.5.0` (до выпуска — на принятый
   кандидат), затем `git submodule update --init`. Прочитать раздел CHANGELOG модуля и этот документ.
2. **Навыки.** Скопировать `modules/stm32-gdbtest/skills/stm32-gdbtest-*` в `.claude/skills/` заново, а не
   править старые копии.
3. **Сборка.** Если сценарии или сверка SVD/ELF опираются на типы CMSIS, которые код не использует, добавить
   `-fno-eliminate-unused-debug-types`: иначе GDB не увидит структуры регистров.
4. **SVD.** Указать `[mmio] svd = "<путь от session.toml>"` в каждом профиле. Допустимо проверенное подмножество
   (BlackPill — 40 регистров общего F4-описания) с указанием источника: RM/PM, лицензия, хеш. Регистры ядра
   могут отсутствовать в vendor SVD: дополнить проверенным описанием или ограниченным override с причиной.
5. **Сценарии.** Сначала инвентаризация всех `read`, `evaluate`, `write`, `check(rows)`, `memory` и динамических
   выражений, касающихся периферии, а не только совпадений по имени регистра. Затем замена на `t.mmio`:
   - флаги W1C — явной маской, сначала проверка ошибки, потом очистка;
   - регистры с эффектом чтения (SysTick `CTRL.COUNTFLAG`, FIFO) и командные биты (`SCB.ICSR`, NVIC
     `ICER`/`ISER`) — без общего снимка и RMW, с `allow_effects=True` только для известного эффекта;
   - write-only — без контрольного чтения; `NDTR` DMA — только при выключенном потоке;
   - инъекции `ret`, аргументы, поля приложения и RAM остаются в общем API.
   Каждое новое ожидание берётся из требования или RM, а не из ответа платы.
6. **Записи.** Каждая операция MMIO добавляет две записи журнала; при `[results] capture = true` проверить
   лимит records (`max_records` в `api.toml`).
7. **Проверка без платы.** `inspect` каждого профиля → сборка → `ctest --preset <профиль>-host` (prepare,
   трассировка, host-регрессии миграции). prepare не исполняет тела сценариев и миграцию не доказывает.
8. **Плата.** Один сценарий, затем полный набор `ctest --preset <профиль>-hw` на каждом профиле.
   Прежние аппаратные прогоны 0.4.x приёмкой новой версии не являются.
9. **DDTT.** После изменения сценариев перепривязать карты и anchors; сохранить контроль неверного допуска и
   отсутствующей записи ([раскраска](DDTT_COVERAGE.md), [применимость](DDTT_QUALIFICATION.md)).

Если операцию перенести нельзя, зафиксируйте узкое исключение и его влияние, а не объявляйте весь проект
мигрированным.

## Чего делать не нужно

- Менять аппаратные target schema 1/2, файлы стендов и политику программирования Flash.
- Переводить рабочие `def`-сценарии в `async def`.
- Заменять на MMIO обращения к памяти приложения и инъекции.
- Переносить результаты 0.4.x на новую версию: свидетельства относятся к своей ревизии модуля.
