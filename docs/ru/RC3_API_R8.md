Перенос в ядро требует утверждения владельца.

## Измерение и практические техники

[Два сценария](../../tests/api-experiments/profile/tests/board/test_code_limits.py)
работают на F411CE/ST-Link/OpenOCD0.12.0. Четыре fault guard остаются включёнными;
сравниваются их номера и адреса до и после очистки собственных точек.

| Опыт | Проверенное поведение |
| --- | --- |
| CAPACITY | Четыре guard + одна/две точки на различных адресах устанавливаются. Третья дополнительная точка приводит к отказу вставки. Общий измеренный бюджет6, доступно сценарию2 |
| FINISH | Четыре guard + две неисполняемые точки заполняют бюджет. Вставка внутреннего FinishBreakpoint отклоняется. После удаления одной собственной точки та же FinishBreakpoint срабатывает, возвращает773; вызывающий код получает ожидаемый checksum |

CAPACITY намеренно создаёт сырые `gdb.Breakpoint` вне предварительного ограничения
экспериментального адаптера, чтобы измерить физическую вставку. Guard при этом
не отключаются. Адреса точек различны и не совпадают с guard. Это не разрешение
обходить ограничения в обычных сценариях.

После отказа удаляются только собственные точки. Продолжение проверено без reset:
в CAPACITY достигается process_sample, в FINISH остаётся исходный sum_bytes,
затем завершается его естественный вызов. В конце всей серии firmware restore
по-прежнему обязателен. Такое восстановление подтверждено именно для отказа вставки;
его нельзя переносить на произвольный ERROR или нарушенное состояние inferior.

Для проверенного finish нужно резервировать один слот: при четырёх guard
остаётся одна постоянная пользовательская точка и один слот операции finish.
Не все команды next/step/until/advance проверены этой оценкой; они могут иметь
собственные временные точки. Бюджет DWT из R7 относится к точкам на данные и
не складывается с этим количеством как с единым ресурсом.

## Время жизни FinishBreakpoint

Первая серия успела измерить бюджет и выполнить finish после освобождения слота,
но получила ERROR при чтении `finish.number`: объект уже недействителен.
Ошибка была в сценарии; исходный протокол сохранён, прошивка восстановлена.

Номер теперь сохраняется до continue и сопоставляется со снимком события.
После срабатывания отдельно проверяются `is_valid() == False` и сохранённый
`return_value == 773`. Возможность читать return_value не означает доступность
остальных свойств недействительного объекта. Такая техника нужна и для
корректной регистрации событий временных точек.

## Результаты и воспроизведение

| Интерфейс | GDB14 | GDB16 |
| --- | --- | --- |
| HLA | 8/8 PASS | 8/8 PASS |
| native DAP/SWD | Не проверялся | 8/8 PASS |

В каждой ячейке два сценария, первый проход и три заданных повтора.
Исходная серия дополнительно содержит один CAPACITY PASS и один FINISH ERROR;
они не включены в положительную матрицу. Ожидаемые отказы вставки фиксируются
по конкретной диагностике GDB, а не только по тексту `Command aborted.`.

После всех трёх серий — restore HW_BOOT/HW_GPIO PASS. Windows/Linux build и
host/prepare:42/42 PASS (40 prepare, traceability и20 host-тестов одной группой).
Документация3/3. Новый C-код не добавлялся; старый общий format FAIL не исправлялся.
Linux HW и другие платы не проверялись. Успех R8 на native DAP не отменяет
ограничение повторного stepi в бесконечном цикле из R4.

К [команде R1](RC3_API_R1.md#воспроизведение) добавить `--suite r8`; для отдельного
сравнения native — `--native-stlink` и один GDB16. Без `--execute` только prepare.
[Обезличенный протокол](../research/rc3-r8-results.json) содержит версии, хэши,
отказы и восстановление; raw-журналы остаются в `tests/api-experiments/build/evidence/`.
