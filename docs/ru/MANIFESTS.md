# Метаданные совместимости и происхождения сборки

[Документация](index.md) → Manifest · [English](../en/MANIFESTS.md)

Наличие GDB API проверяется до подключения клиента, ELF-контракты — до сервера.
Оба механизма проверяют выбранные предпосылки, а не всю совместимость MCU и HAL.

## Runtime manifest (schema 1)

Блок `compatibility` добавляется в `result.json` и system-out JUnit для PASS, FAIL
и ERROR, включая отказ до запуска сервера. Прежние поля `gdb_version` и
`python_version` верхнего уровня сохранены. Источник каждого значения указан в
`evidence`; недоступное значение — `null` с причиной, а не предполагаемая версия.
Из `server.log` извлекаются только токены версии сервера, прошивки и API отладчика:
строки целиком, пути и серийные номера в этот блок не копируются. Остальные
диагностические журналы от локальных данных не очищаются.

`scope: runtime-only` относится к блоку `compatibility`; сведения о сборке — в
отдельном `build_manifest`. `compatibility.build.provenance` показывает, прошёл ли
manifest проверку привязки к ELF и `target.toml`. `session.json` без пути manifest
поддерживается с явным `unavailable`; сессии, сгенерированные CMake, manifest
содержат. Нераспознанный баннер оставляет метаданные недоступными и не меняет
результат сценария; отсутствие обязательного GDB API — инфраструктурный ERROR.

## Build manifest (schema 1)

При линковке firmware target создаётся `build/<preset>/hwtest/build-manifest.json`.
Реализация рассчитана на Ninja и один firmware target, работает на Windows и Linux
(команды компилятора разбираются по правилам ОС). CMake включает
`compile_commands.json`; шаг POST_BUILD читает `ninja -t deps`, требует состояния
VALID и проверяет, что входы не менялись после компиляции объекта. Для простого
`.s` без зависимостей учитывается сам файл; `.include`, `.incbin` и `#include` в
ассемблере пока отклоняются. Изменение скрипта manifest, `target.toml` или
отслеживаемых входов вызывает перелинковку.

Содержимое:

- SHA-256 ELF и `target.toml`; хэши объектов и использованных исходников и
  заголовков C/C++, startup, IOC, YAML и скрипта компоновщика профиля;
- имя, хэш и версия компилятора; выбранные флаги define, ABI, оптимизации и
  отладки; хэш полной команды без публикации личных путей;
- имя пакета STM32Cube отдельно от числовых деклараций версий HAL и CMSIS с
  файлом-источником и его хэшем — это чтение литералов, а не препроцессор. Если
  HAL и CMSIS не из пакета `STM32Cube_FW_*` (например, Arduino Core STM32), список
  пакетов пуст, а версии — только найденные литералы; это не ошибка.

Runner копирует ELF и сверяет его SHA-256 и текущий `target.toml` с manifest.
Несовпадение, отсутствующий файл или неподдержанная схема дают ERROR до `objcopy`,
GDB и сервера. Принятый manifest копируется в каталог запуска, `result.json` и
JUnit. Исходники и STM32Cube во время запуска не перечитываются: отчёт описывает
сохранённую сборку. Для новых сессий сначала выполните configure и build.

Границы доказательства: это снимок после линковки, а не аттестация происхождения
бинарника. Нужны надёжные метки времени, отсутствие параллельного редактирования и
неизменная установка компилятора между компиляцией и снимком; после замены
компилятора — чистая пересборка. Не сохраняются все флаги компоновщика и содержимое
предсобранных библиотек. Не вычисляются действующие условные макросы HAL. Хэш IOC
не доказывает соответствия генерации CubeMX. Проверка SHA не является цифровой
подписью. Личные пути в manifest не пишутся, но другие журналы могут их содержать.

## Размещение образа

Список загружаемых секций извлекается из проверенного снимка ELF до сервера,
передаётся агенту и отражается в `image_verification`; схема build manifest при этом
не меняется. Полный режим дополнительно фиксирует `image_policy.source_sha256`,
`bin_sha256` и `program_elf_sha256`. Политика образа — отдельный вход, не часть
build manifest; исходный ELF не модифицируется. Подробнее — [образы и CRC](IMAGES.md).
