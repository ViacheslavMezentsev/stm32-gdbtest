# Журналирование

[Документация](index.md) · [API](API.md) · [Результаты](RESULTS.md) · [English](../en/JOURNALING.md)

## 1. Статус возможностей

Это руководство описывает рабочую ветку кандидата 0.6.0. Выпуск 0.5.0 не содержит
всех перечисленных расширений. A2 и A3.1 реализованы; A3.2 сейчас реализован **только
на уровне конфигурации и её передачи**. Schema 3 проверяется через inspect/prepare
и переносится в pack. Исполнение schema 3 пока отклоняется до захвата отладчика и
запуска сервера с `api_execution_unsupported`, даже если on_limit=error.
Это не реализация truncate. Для исполнения пока используйте schema 1/2.

## 2. Что и где хранится

| Источник | Содержимое | Назначение |
| --- | --- | --- |
| records.json | Именованные данные сценария, аудит MMIO и execution | Первичные свидетельства |
| result.json | Вердикт, checks/stops/mutations/evaluations/executions/resets, полнота, cleanup | Исход опыта и подробные события |
| summary.json | Производные группы, ссылки, хеши источников | Навигация, не замена исходных данных |
| stdout / JUnit | Выбранный уровень представления и ошибки | Просмотр результата, не полный журнал |

`[results] capture=true` задаётся в session.toml и сохраняет records.json.
Без capture журнал доступен внутри сценария, но его сохранение не обещается.
Чтение records.json требует соответствующего result.json: он связывает хеш,
идентичность прогона и полноту. print не заменяет record.

## 3. Рабочая настройка без потери данных

```toml
schema = 2
[records]
max_records = 16384
max_nodes = 524288
max_text_bytes = 4194304
[journal]
representation = "compact"
[report]
representation = "compact"
console = "summary"
```

Full и compact сохраняют одинаковые логические события; compact уменьшает повтор
описаний. Full/failures/summary изменяют вывод, не число выполняемых проверок.
Повторный records() создаёт копию; полный журнал на каждой итерации читать не нужно.

## 4. Кандидат schema 3: конфигурация, пока без исполнения

```toml
schema = 3
[records]
max_records = 16384
max_nodes = 524288
max_text_bytes = 4194304
max_depth = 16
max_integer_bits = 256
[journal]
representation = "compact"
on_limit = "truncate"
[report]
representation = "compact"
console = "summary"
on_limit = "error"
max_rows_per_collection = 16384
```

| Квота | Default schema 3 | Максимум |
| --- | ---: | ---: |
| max_records | 4096 | 65536 |
| max_nodes | 131072 | 2097152 |
| max_text_bytes | 1048576 | 16777216 |
| max_depth | 16 | 32 |
| max_integer_bits | 256 | 1024 |
| report.max_rows_per_collection | 65536 | 65536 |

Минимум — 1. Bool/float/строка, 0, отрицательное число и превышение максимума
отклоняются. Значения unlimited нет. В schema 3 неизвестные ключи в records/journal/
report — ошибка. Прочие прикладные разделы api.toml сохраняются как данные, как раньше;
их наличие не превращает их в поддержанные настройки журналирования.
Defaults: representation=full, console=full, on_limit=error. Политики journal/report
независимы. Schema 1/2 не принимают новые ключи; их defaults и отпечатки сохранены.

Runner помещает применённые schema/records/journal/report в api_policy результата.
Capsule переносит исходные TOML с хешами; принимающая сторона повторно проверяет
значения и отпечаток defaults/максимумов/политик. Pack сохраняет эту capsule; исходные
пути на принимающей стороне не открываются. Номера API schema, capsule и форматов
result/records независимы. API_VERSION остаётся 3.

## 5. Защитные пределы

Настраиваемый бюджет накопления не равен пределу читателя и не ограничивает RSS.
Фиксированы: records-файл 64 MiB, result-файл 16 MiB, раскрытие result 64 MiB,
размеры блоков, ограничения материализации и отложенных значений. Сводка: 1 MiB,
100 групп, 20 ссылок на группу. Резерв evidence.diagnostics: 16 деталей/64 KiB JSON.
Поднятие max_records не отменяет остальные пределы. Не меняйте константы из сценария.

## 6. Поведение на маршрутах

| Маршрут | Что происходит | Что нельзя заключать |
| --- | --- | --- |
| inspect / prepare | Валидация и подготовка, без исполнения сценария | Prepare PASS не является свидетельством поведения MCU |
| pack / открытие пакета | Перенос и повторная проверка снимка конфигурации | Успешное открытие не означает поддержку исполнения schema 3 |
| def, check/reach/write | Проверки и завершённые события учитываются; строгий отказ хранения | Пустые checks не означают, что проверки не выполнялись |
| async def, resume/wait/halt | Журналируются события живого окна, ошибка аудита отделяется от исполнения | Timeout wait не означает остановку цели |
| MMIO | Аудит attempt/result, исход операции и ошибка аудита различаются | Attempt без result не доказывает успех или отсутствие записи |
| caught CheckFailed | Независимый счётчик сохраняет FAIL | Перехват исключения не делает проверку успешной |
| Исключение / cleanup | Первичная ошибка, аудит и очистка фиксируются раздельно | Вызов cleanup не равен подтверждённому восстановлению |
| Offline-анализ | Общие читатели проверяют метаданные и сохранённые строки | SAVED и целый файл не означают полное свидетельство |

## 7. Строгая полнота A3.1

Evidence хранит attempted/saved/lost и границы потерь по хранилищам; check_accounting —
выполненные проверки и отказы независимо от строк. После потери записи строгий
режим не допускает успешного завершения за счёт перехвата ошибки. Первичный FAIL
не скрывается; неполнота даёт command=2. Сводка становится partial, DDTT-подтверждение
блокируется. Поле complete компактной коллекции относится к сохранённым строкам;
проверяйте также evidence.stores. Старый файл без этих метаданных читается, но не
получает новую гарантию полноты автоматически.

Резерв содержит ограниченные причины без копирования пользовательского payload.
После исчерпания сохраняется число пропущенных диагностик; старые поля A1 также
сохраняются для совместимости. Это не предел всего отчёта. Потеря процесса, памяти
или диска не позволяет обещать безусловное сохранение даже резервного результата.

## 8. Согласованное усечение — следующий пакет

Планируемый truncate сохраняет префикс, прекращает приём подробностей затронутого
хранилища, но не выполнение проверок и cleanup. Неполный прогон сохранит command=2.
Ошибки типов, транспорта, диска и восстановления он подавлять не будет. Планируется
явное разрешение частичного чтения records; сейчас такого параметра нет.
Не используйте schema 3 для исполнения до реализации и приёмки этого пакета.

## 9. Проверка перед применением

Проверьте конфигурацию без платы, выберите бюджеты по ожидаемому объёму, включите
capture для нужных измерений. После прогона оцените отдельно scenario, command,
capture, evidence и cleanup; затем применимость данных к конкретному утверждению.
Примеры отказов: tests/renode-backend/run_report.py; host: test_evidence.py,
test_policy_config.py. Намеренный ERROR проверяет контракт инструмента, а не MCU.
