# Журналирование

[Документация](index.md) · [API](API.md) · [Результаты](RESULTS.md) · [English](../en/JOURNALING.md)

## 1. Статус возможностей

Это руководство описывает выпуск 0.6.0; в 0.5.0 перечисленных расширений нет.
A2, A3.1 и применение квот journal A3.2 реализованы.
Schema 3 допускает независимые error/truncate и квоты journal/report при исполнении.

## 2. Что и где хранится

| Источник | Содержимое | Назначение |
| --- | --- | --- |
| records.json | Именованные данные сценария, аудит MMIO и execution | Первичные свидетельства |
| result.json | Вердикт, checks/stops/mutations/evaluations/executions/resets, полнота, cleanup | Исход опыта и подробные события |
| summary.json | Производные группы, ссылки, хеши источников | Навигация, не замена исходных данных |
| stdout / JUnit | Выбранный уровень представления и ошибки | Просмотр результата, не полный журнал |

`[results] capture=true` задаётся в session.toml и сохраняет records.json.
Без capture журнал доступен внутри сценария, но его сохранение не обещается.
Чтение records.json требует соответствующего result.json: он связывает хеш,
идентичность прогона и полноту. print не заменяет record.

## 3. Рабочая настройка без потери данных

```toml
schema = 2
[records]
max_records = 16384
max_nodes = 524288
max_text_bytes = 4194304
[journal]
representation = "compact"
[report]
representation = "compact"
console = "summary"
```

Full и compact сохраняют одинаковые логические события; compact уменьшает повтор
описаний. Full/failures/summary изменяют вывод, не число выполняемых проверок.
Повторный records() создаёт копию; полный журнал на каждой итерации читать не нужно.

## 4. Schema 3: исполняемая настройка journal

```toml
schema = 3
[records]
max_records = 16384
max_nodes = 524288
max_text_bytes = 4194304
max_depth = 16
max_integer_bits = 256
[journal]
representation = "compact"
on_limit = "truncate"
[report]
representation = "compact"
console = "summary"
on_limit = "error"
max_rows_per_collection = 65536
```

| Квота | Default schema 3 | Максимум |
| --- | ---: | ---: |
| max_records | 4096 | 65536 |
| max_nodes | 131072 | 2097152 |
| max_text_bytes | 1048576 | 16777216 |
| max_depth | 16 | 32 |
| max_integer_bits | 256 | 1024 |
| report.max_rows_per_collection | 65536 | 65536 |

Минимум — 1. Bool/float/строка, 0, отрицательное число и превышение максимума
отклоняются. Значения unlimited нет. В schema 3 неизвестные ключи в records/journal/
report — ошибка. Прочие прикладные разделы api.toml сохраняются как данные, как раньше;
их наличие не превращает их в поддержанные настройки журналирования.
Defaults: representation=full, console=full, on_limit=error. Политики journal/report
независимы. Schema 1/2 не принимают новые ключи; их defaults и отпечатки сохранены.

Runner помещает применённые schema/records/journal/report в api_policy результата.
Capsule переносит исходные TOML с хешами; принимающая сторона повторно проверяет
значения и отпечаток defaults/максимумов/политик. Pack сохраняет эту capsule; исходные
пути на принимающей стороне не открываются. Номера API schema, capsule и форматов
result/records независимы. API_VERSION остаётся 3.

## 5. Защитные пределы

Настраиваемый бюджет накопления не равен пределу читателя и не ограничивает RSS.
Фиксированы: records-файл 64 MiB, result-файл 16 MiB, раскрытие result 64 MiB,
размеры блоков, ограничения материализации и отложенных значений. Сводка: 1 MiB,
100 групп, 20 ссылок на группу. Резерв evidence.diagnostics: 16 деталей/64 KiB JSON.
Поднятие max_records не отменяет остальные пределы. Не меняйте константы из сценария.

## 6. Поведение на маршрутах

| Маршрут | Что происходит | Что нельзя заключать |
| --- | --- | --- |
| inspect / prepare | Валидация и подготовка, без исполнения сценария | Prepare PASS не является свидетельством поведения MCU |
| pack / открытие пакета | Перенос и повторная проверка снимка конфигурации | Поддержку выбранной политики проверяют перед исполнением |
| def, check/reach/write | Проверки и завершённые события учитываются; строгий отказ хранения | Пустые checks не означают, что проверки не выполнялись |
| async def, resume/wait/halt | Журналируются события живого окна, ошибка аудита отделяется от исполнения | Timeout wait не означает остановку цели |
| MMIO | Аудит attempt/result, исход операции и ошибка аудита различаются | Attempt без result не доказывает успех или отсутствие записи |
| caught CheckFailed | Независимый счётчик сохраняет FAIL | Перехват исключения не делает проверку успешной |
| Исключение / cleanup | Первичная ошибка, аудит и очистка фиксируются раздельно | Вызов cleanup не равен подтверждённому восстановлению |
| Offline-анализ | Общие читатели проверяют метаданные и сохранённые строки | SAVED и целый файл не означают полное свидетельство |

## 7. Строгая полнота A3.1

Evidence хранит attempted/saved/lost и границы потерь по хранилищам; check_accounting —
выполненные проверки и отказы независимо от строк. После потери записи строгий
режим не допускает успешного завершения за счёт перехвата ошибки. Первичный FAIL
не скрывается; неполнота даёт command=2. Сводка становится partial, DDTT-подтверждение
блокируется. Поле complete компактной коллекции относится к сохранённым строкам;
проверяйте также evidence.stores. Старый файл без этих метаданных читается, но не
получает новую гарантию полноты автоматически.

Резерв содержит ограниченные причины без копирования пользовательского payload.
После исчерпания сохраняется число пропущенных диагностик; старые поля A1 также
сохраняются для совместимости. Это не предел всего отчёта. Потеря процесса, памяти
или диска не позволяет обещать безусловное сохранение даже резервного результата.

## 8. Явное усечение journal

В 0.6.0 API schema 3 исполняет `journal.on_limit="error"|"truncate"`.
Квоты `[records]` ограничивают накопление. При truncate исчерпание records/nodes/text_bytes
сохраняет только целые записи префикса; после первой потери подробности до конца сценария
не добавляются. Проверки, MMIO, живое окно и cleanup продолжаются. Полнота становится
`truncated`, но исход сценария сам по себе не меняется: возможен PASS с command=2,
SAVED и partial-анализом. DDTT-подтверждение по неполному прогону блокируется.

`records(name=None, *, require_complete=True)` отказывает с `RecordError`/`incomplete_evidence`
при неполноте всего журнала, даже при фильтре по имени. Для просмотра префикса явно укажите
`require_complete=False`; sequence сохраняется. Это разрешение чтения, а не признание
свидетельства полным. Ошибки типов, циклы, глубина, разрядность и жёсткий ресурсный предел
валидации не превращаются в усечение. Входы проверяются и после потери подробностей.

Описание и attempt MMIO сохраняются атомарно. Если result уже не поместился, attempt
не доказывает успех или отсутствие воздействия. Усечение не добавляет чтений или записей
регистра. Ошибки транспорта/хранения не подавляются. Причина первой потери и счётчики
attempted/saved/lost, first_lost/last_lost остаются в evidence; резерв диагностики ограничен.

Для политики truncate применяются evidence schema 2, result schema 3 (full/compact) и
records schema 3 с полнотой, сверяемой с result. Старые читатели отвергают новые форматы.
Используйте общие читатели модуля, а не самостоятельное раскрытие JSON.
Квоты и усечение report также применяются при исполнении; см. отдельный раздел ниже.

## 9. Проверка перед применением

Проверьте конфигурацию без платы, выберите бюджеты по ожидаемому объёму, включите
capture для нужных измерений. После прогона оцените отдельно scenario, command,
capture, evidence и cleanup; затем применимость данных к конкретному утверждению.
Примеры отказов: tests/renode-backend/run_report.py; host: test_evidence.py,
test_policy_config.py; tests/renode-backend/run_journal.py и test_journal_truncate.py. Намеренный ERROR проверяет контракт инструмента, а не MCU.

## A3.2: квоты и усечение report (0.6.0)

В API schema 3 `report.max_rows_per_collection` применяется отдельно к checks, stops,
mutations, evaluations, executions и resets в full и compact. Диапазон 1–65536,
default 65536. `report.on_limit="error"` — строгий отказ; `"truncate"` сохраняет
префикс каждой коллекции, не мешая другим коллекциям, journal, проверкам и cleanup.
Политики journal/report независимы; все их проверенные сочетания исполняются.

При truncate счётчик попыток продолжает расти, saved остаётся равен длине префикса,
lost и first_lost/last_lost описывают пропущенный хвост. Первая причина сохраняется
для каждой коллекции в ограниченном резерве. Независимый check_accounting считает
все проверки: FAIL нельзя убрать перехватом исключения или потерей строки. Сводка
группирует сохранённые строки, а check_accounting показывает полный учёт исходов.
PASS сценария при усечении допустим, но command=2, анализ partial, DDTT заблокирован.

Подавляется только достижение квоты строк, не ошибка временного файла, сериализации,
транспорта или восстановления. Если сохранённый префикс невозможно прочитать/записать,
состояние становится unavailable; причина усечения и независимые счётчики сохраняются.
Усечённые payload не материализуются: repr и ленивое чтение GDB ради пропущенной строки
не вызываются. Поэтому отсутствие строки не подтверждает корректность её значений.

Report truncate использует evidence schema 3 (`report-truncate`/`both-truncate`),
result schema 3 и records schema 3. Старые читатели, не знающие эту evidence schema,
отвергают результат. Journal-only truncate сохраняет evidence schema 2; прежние
строгие форматы читаются. Усечение report не делает полный journal неполным:
records() проверяет полноту journal, но анализ всего прогона учитывает все хранилища.

```toml
schema = 3
[journal]
representation = "compact"
on_limit = "error"
[report]
representation = "compact"
console = "summary"
on_limit = "truncate"
max_rows_per_collection = 1000
```

Это явный выбор частичного отчёта; для приёмки полного свидетельства оставьте error
и подберите достаточную квоту. Пример: tests/renode-backend/run_report_quota.py;
регрессии: tests/host/test_report_truncate.py. Проверки — без физических плат.

## A3.3: потребители неполных свидетельств

`results export` проверяет полноту всех хранилищ до проекции. Неполный источник
не попадает в records.csv/measurements.csv: диагностика и command=2 объясняют отказ.
Это не удаляет исходные result/records и не меняет PASS/FAIL/ERROR сценария.
Для осознанного просмотра префикса используйте общий читатель records и evidence,
а не обычную проекцию для приёмки. Полный журнал при усечённом report также не
является полным свидетельством прогона.

Индекс сохраняет вердикт, но добавляет диагностику неполноты; HTML показывает её
отдельно от integrity. Целый файл и SAVED не означают полноту. Сводка отмечает
truncated/unavailable у коллекций; группы считают сохранённые строки, независимый
check_accounting — все исходы. DDTT/LCOV оставляют UNKNOWN без DA, а не ложный ноль.

После обновления читателя пересоздайте производные summary, index и campaign по
сохранённым первичным файлам: старые сводки могут стать stale. Pack переносит
конфигурацию, а не подтверждает полноту будущего запуска. PDF-генератор навыка
получает подготовленные свидетельства, не заменяя этот допуск; автор обязан
проверить полноту перед переносом чисел в его входной документ.

Пример повторного анализа без Renode и платы:
`python tests/renode-backend/replay_consumers.py --runs <campaign>/runs --output <new-directory>`.
Host-матрица: test_partial_consumers.py (full/compact, journal/report/both, PASS/FAIL,
сохранение исходных файлов, положительный контроль полного источника).
