# Автономные циклы на стенде

[Документация](index.md) · [English](../en/STAND_LOOP.md)

`tools/stand_loop.py` — внешний инструмент кандидата 0.4.0. Он исполняет согласованный конечный
план через штатный CLI, без изменения Target, прошивки или ожиданий сценария. Репозиторий
приложения на стенде не нужен: нужны checkout этой версии модуля, ZIP-пакеты, GDB-Python/binutils,
сервер и локальный TOML стенда. Сборка на стенде не выполняется.

## Комплект и план

Подготовьте пакеты через [pack](HARDWARE_CI.md); до упаковки включите в session.toml
`[results] capture = true`. Для анализа кода прошивки при необходимости добавьте исходники через
`--include`; сценарии, требования и контракты уже входят в пакет. Они не означают полный исходный
репозиторий. Конфигурация пакета неизменяема; новый набор параметров требует нового пакета.

[Пример плана](../../examples/stand-loop/plan.example.toml) использует наши сценарии 0.4.0.
У потребителя замените ID и ZIP на свои. Пути относительно плана; выход задаётся отдельно.

| Поле | Значение |
| --- | --- |
| schema | 1 |
| stand | файл с локальным [probe]; [remote] в первом варианте запрещён |
| cycles | 1..10000, по умолчанию 1; бесконечного режима нет |
| interval_s | пауза между циклами 0..86400, по умолчанию 0 |
| on_fail | stop (по умолчанию) или continue; только для достоверного FAIL сценария |
| min_free_mib | нижняя граница свободного места 1..1048576, по умолчанию 256 MiB |
| cases | упорядоченный список из 1..64 элементов |
| cases.package / id | ZIP и ID из его manifest |
| cases.allow_skip | bool, по умолчанию false; разрешает SKIP, но не требует его |
| cases.timeout_s | 1..3600, по умолчанию 60; передаётся runner как timeout GDB, не всей кампании |

Неизвестные поля/неверные типы отвергаются. Версия пакета должна совпадать с версией модуля;
все пакеты должны включать capture. Сохраняются копии пакетов/стенда/плана, хеши входов и Python-кода
модуля/диспетчера. Входы и код проверяются между операциями; параллельно изменять их нельзя.
Это проверка воспроизводимости, не защита от недоверенного Python-кода сценария.

## Запуск на OrangePi

```sh
. "$HOME/.local/stm32-gdbtest/env.sh"
cd "$HOME/stm32-gdbtest"
python3 -B tools/stand_loop.py --plan "$HOME/stand/plan.toml" --output "$HOME/stand/runs/run-001"
```

Каталог output должен быть новым: повтор никогда не перезаписывает предыдущую кампанию.
Сначала doctor, затем prepare всех выбранных сценариев и только затем MCU. Любая ошибка этой
подготовки запрещает аппаратную часть. Для каждого запуска проверяются ID/пакет/код/status,
проверенный образ, reset_run, capture/records/JUnit; для st-util — shutdown_wait.ready.
Ожидания прикладных checks остаются в сценарии. Наличие PASS не доказывает полноту checks.

| Исход | Продолжение и код диспетчера |
| --- | --- |
| PASS, разрешённый SKIP | следующий сценарий; при завершении плана 0 |
| FAIL | stop: остановка с 1; continue: дальнейшие сценарии, но общий код остаётся 1 |
| ERROR, неожиданный SKIP, несогласованные/отсутствующие артефакты | остановка с 2 |
| Цикл только из SKIP | nothing tested, остановка с 2 |
| Ошибка export/verify/report или изменение входов | остановка с 2; прежние статусы сохранены |
| STOP или SIGINT/SIGTERM | завершение текущей команды и обработки, затем остановка с 130 |

Все статусы сценариев считаются отдельно. COMPLETED означает выполнение плана, а не новый вид PASS
и не приёмку всего устройства. UNKNOWN/код2 обработки не маскируются удачной генерацией HTML.
Новых повторов после ERROR и самостоятельного восстановления диспетчер не делает; штатный cleanup
остаётся в runner. Сбой USB может потребовать ручного вмешательства.

Создайте пустой файл `<output>/STOP` для штатной остановки. Он не прерывает работающую команду;
не удаляйте lock и не убивайте сервер вместо ожидания cleanup. Отдельный lock диспетчера по
семейству/серийнику в temp не даёт двум stand_loop работать на одном отладчике. После аварии lock
сохраняется: сначала подтвердите завершение владельца и дочерних процессов. Штатный runner lock
действует на каждый запуск; между запусками другие ручные инструменты не блокируются диспетчером.

## Артефакты и агент

```text
run-001/
  plan.toml, inputs.json, inputs/   снимок входов и хеши (стенд содержит личные настройки)
  doctor.log, prepare/             окружение и preflight без MCU
  summary.json                    состояние кампании, независимые счётчики, код
  c00001/
    t000/, t001/                  отдельные распаковки пакета и первичные результаты
    selection.json, summary.json  точная выборка и состояние цикла
    export/, integrity.json       журнал и проверка файлов
    report/                       campaign.json/html
    review.json                   публикуется последним, цикл готов к анализу
```

Агент читает только циклы с review.json; у незавершённого цикла его нет. В частичном цикле
сохраняются все доступные результаты, ошибки обработки и причина остановки. Исходники выбранных
сценариев доступны в распакованном пакете внутри tNNN. Корень selection — каталог cNNNNN.
Навык [stm32-gdbtest-results](../../skills/stm32-gdbtest-results/SKILL.md) объясняет интерпретацию.
Для управления этим инструментом — [stm32-gdbtest-stand-loop](../../skills/stm32-gdbtest-stand-loop/SKILL.md).

Диспетчер не вызывает pi/Qwen и не исполняет команды из их ответов. Внешний агент может наблюдать
за новыми review.json, сохранять отдельное заключение и предложения. Автоматически менять план,
ожидания, пакеты или возобновлять ошибочную кампанию он не должен. Полный снимок исходников прошивки
для причинного анализа добавляется отдельно; при его отсутствии агент явно ограничивает вывод.

## Фоновая служба и границы первого варианта

[Шаблон user systemd unit](../../examples/stand-loop/stand-loop@.service) запускает один конечный план.
Перед установкой проверьте пути checkout, env.sh, plan и доступ к USB. Пример после проверки:

```sh
mkdir -p "$HOME/.config/systemd/user"
cp examples/stand-loop/stand-loop@.service "$HOME/.config/systemd/user/"
systemctl --user daemon-reload
systemctl --user start stand-loop@run-001
journalctl --user -u stand-loop@run-001
```

Новому запуску — новый instance/output. Restart=no исключает автоматический повтор после ERROR.
`systemctl --user stop` запрашивает остановку диспетчера после текущей команды; unit не посылает
SIGKILL его детям. Для работы после выхода пользователя нужен настроенный user manager/linger;
это отдельная настройка администратора, автоматически инструмент её не меняет.

Первый вариант не обещает 24/7, аварийное питание, очистку диска, дедлайн всего процесса,
авторемонт USB, автоматический деплой новых пакетов или защищённую песочницу LLM. При зависании
самого host CLI штатный STOP также ждёт; автоматический внешний watchdog пока не реализован.
Место проверяется до шагов, но проверка свободного места не резервирует его и не заменяет квоты.
Системную службу и модель не считайте проверенными одним ручным аппаратным прогоном.

## Проверка первого варианта — 10.10.2026

Host-регрессия StandLoopTests: 20 проверок, включая doctor/prepare gate, FAIL stop/continue,
неожиданный и разрешённый SKIP, только SKIP, повреждение records/JUnit, неверный package/mode/code,
cleanup/capture, изменение входов, занятость lock, STOP, недостаток места и ошибку обработки.

Аппаратно: F411CE/ST-Link, локальный OrangePi 5/Ubuntu 20.04 aarch64, Python 3.11.16,
xPack 13.3.1-1.1/GDB 14.2.90 и st-util 1.9.0. Использованы неизменные пакеты сценариев 0.4.0:

| План | Фактический результат |
| --- | --- |
| 2 цикла RECORDS + разрешённый SKIP | COMPLETED/code0, 2 PASS + 2 SKIP, два отдельных review |
| 3 цикла, STOP после первого review | STOPPED/code130, 1 PASS + 1 SKIP; второй цикл не создан |
| 2 цикла без разрешения SKIP | ERROR/code2 после первого SKIP; повтор не начат |

Всего 7 аппаратных запусков: 3 PASS + 4 SKIP, 20 записей. В последнем плане SKIP остаётся
исходом сценария, ERROR — решением диспетчера. Все 7 образов/teardown/shutdown_wait подтверждены;
4 цикла export/verify/report успешны, свежая проверка скопированных свидетельств — 4/4.
Хеши входов и runtime совпали; процессов st-util и lock диспетчера после завершения нет.
Предупреждение inferred_stop для finish сохранено. Принудительных аппаратных отказов не создавали.

Первая SSH shell-обёртка после успешного завершения Python получила лишний CR и вернула ошибку;

pi/Qwen не вызывались; их работу, длительный прогон и другие платы этим этапом не принимаем.
