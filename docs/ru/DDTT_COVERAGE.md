# Раскраска DDTT в VS Code

[Документация](index.md) · [English](../en/DDTT_COVERAGE.md)

Внешний инструмент `tools/ddtt_coverage.py` переводит сохранённые результаты проверок в LCOV.
Это пакет примеров для 0.5.0 и новее; ядро, Target API и формат result.json не меняются.
Связь задаёт разработчик: **сценарий → имя проверки → строка исходника**.

## Значение цвета

| Отметка | Значение DDTT |
| :--- | :--- |
| Зелёная, DA=1 | Указанная проверка выполнена и подтвердила ожидание |
| Красная, DA=0 | Указанная проверка выполнена и не подтвердила ожидание |
| Без отметки | Нет привязки либо достоверного результата; причина в JSON |

DA здесь — булев исход проверки, а не число исполнений инструкции. Процент читателя LCOV относится
только к экспортированным строкам. Для полноты смотрите также UNKNOWN в `ddtt-evidence.json`.
Одно подтверждение не раскрашивает автоматически всё тело функции. Если на строке есть несколько
проверок, любой FAILED делает её красной; UNKNOWN остаётся в сводке, даже если другая проверка зелёная.
Общий FAIL сценария не отменяет уже выполненную успешную проверку; ERROR/SKIP не дают отметок.

## Почему строк меньше, чем тестов

В первом аппаратном примере было семь привязок в пяти сценариях. Наличие файлов `test_app.py`,
`test_board.py`, `test_boot.py`, `test_ddtt_feedback.py`, `test_injection.py` не задаёт номера строк C++.
Часть проверок относится к конфигурации стенда, идентичности MCU или самому сценарию — у них может
вообще не быть подходящей строки прошивки.

В [шаблоне BluePill](../../examples/ddtt-coverage/bluepill.template.json) добавлены привязки завершения
setup и авторов записи времени; [BlackPill](../../examples/ddtt-coverage/blackpill.template.json) показывает
GPIO, отказ ADC и публикацию IRQ. Дополнительные привязки становятся цветными только после запуска
соответствующих сценариев. Расширяйте карту по конкретным проверкам, не по числу файлов.

## Повторяемый маршрут

Python 3.11+, собранный ELF, исходники этого ELF и отдельная папка результатов выбранной кампании.
Команды выполняются из корня stm32-gdbtest; замените примерные пути. PowerShell:

```powershell
$project = 'D:/work/stm32-hwtest-bluepill'
$elf = "$project/build/debug/firmware.elf"
$campaign = "$project/build/ddtt-campaign"
python examples/ddtt-coverage/bind_map.py --project $project --elf $elf --template examples/ddtt-coverage/bluepill.template.json --out "$campaign/map.json"
# Выполните выбранные сценарии обычным runner/CTest в отдельную папку $campaign/runs.
# Перед запуском очистите прежнюю раскраску в выделенной папке визуализации:
New-Item -ItemType Directory -Force "$campaign/view" | Out-Null
Set-Content -LiteralPath "$campaign/view/lcov.info" -Value ''
# После завершения runner, включая FAIL/ERROR, сформируйте отчёт:
python tools/ddtt_coverage.py --project $project --map "$campaign/map.json" --runs "$campaign/runs" --out "$campaign/view"
```

`--runs` читает только непосредственные `*/result.json`. Не выбирайте весь многолетний архив.
`--out` — отдельная папка только для представления; не помещайте туда входную карту или исходники.
Не регенерируйте карту ради обхода несовпадения хеша: сначала пересоберите и повторите сценарии.
Сборку, запуск и снятие оборудования выполняет существующий runner; экспортёр к плате не подключается.
На Linux те же команды Python работают с обычными путями оболочки.

Утилита примера `bind_map.py` проверяет уникальность строк и записывает SHA-256 ELF/исходников.
Она не доказывает, что исходники вошли в ELF: это дополнительно проверяется по build_manifest результата.
`anchor` сопоставляется с полной строкой после удаления крайних пробелов; внутренние пробелы значимы.
`check` — точное имя из `result.json`, включая динамически подставленные значения. Повторённое имя
подтверждено только если все его выполненные проверки успешны. `source` — путь относительно проекта с `/`.

## VS Code

Установите [Coverage Gutters](https://github.com/ryanluker/vscode-coverage-gutters).
В настройках workspace укажите **абсолютный путь** к созданному файлу:

```json
{
  "coverage-gutters.manualCoverageFilePaths": ["D:/work/stm32-hwtest-bluepill/build/ddtt-campaign/view/lcov.info"],
  "coverage-gutters.showLineCoverage": true,
  "coverage-gutters.watchOnActivate": true
}
```

Откройте C++-файл проекта и вызовите `Coverage Gutters: Display Coverage` или `Watch` из палитры команд.
После экспорта расширение перечитывает LCOV. SF содержит абсолютные пути этой машины: после переноса
на другой хост экспортируйте снова с его `--project`. Это же LCOV можно отдавать другим читателям,
но автоматическая интеграция GitHub/GitLab и их интерпретация процентов здесь не проверены.

## Защита от устаревшего зелёного результата

Для каждого сценария выбирается последняя аппаратная попытка по `started_utc` с часовым поясом.
При одинаковом времени нескольких попыток результат UNKNOWN. Более новый ERROR или другой ELF
не заменяется старым PASS. Prepare не участвует. ELF, исходник и запись build_manifest должны совпадать.
Нет проверки, неподходящий статус или manifest — UNKNOWN с причиной, без DA=0.
Ошибочная карта, изменённый исходник, неоднозначный anchor или повреждённый JSON дают код команды 2,
пустой LCOV и sidecar ERROR, чтобы прежняя раскраска не сохранилась. Успешный экспорт возвращает 0,
даже если есть FAILED/UNKNOWN: это исход обработки, не приёмка сценариев.

Выходы: `lcov.info` и `ddtt-evidence.json` (schema 1). JSON сохраняет все точки, причины UNKNOWN,
путь и SHA-256 result.json, run_id, статус сценария, исходы проверок и счётчики состояний.
Хеши связывают артефакты, но не являются криптографической подписью результатов.

## Проверенная основа и границы

15.10.2026 исходный маршрут проверен на BluePill/F103CB и BlackPill/F411 через OpenOCD:
пять выбранных сценариев PASS в двух свежих сериях, семь подтверждённых строк; просмотр VS Code
подтверждён владельцем. Публичный экспортёр дополнен host-регрессиями устаревания, ошибок и конфликтов.
Новые привязки не считаются аппаратно проверенными только потому, что шаблон принят.
Это представление свидетельств DDTT; наблюдатели FPB, трассировка функций и ручная debugpy-отладка
не входят в этот инструмент.

## Совместимость новых инструментов

Старые карты без `environment` сохраняют аппаратную трактовку. Для отдельной эмуляторной карты укажите `environment: "emulator"`. Отсутствующий `purpose` означает automated; manual исключается. Строка с CONFIRMED и UNKNOWN теперь исключается из LCOV, если на ней нет FAILED. Перепривяжите карту, если якорь указывает на комментарий. Подробности: [переносимый отчёт](PORTABLE_DDTT.md).
