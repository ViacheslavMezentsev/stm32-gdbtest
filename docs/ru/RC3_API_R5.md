# rc3 R5: типы возврата и ARM ABI

[Документация](index.md) · [English](../en/RC3_API_R5.md)

02.10.2026. Продолжение [R4](RC3_API_R4.md) после `2c6c8a6` в
`codex/rc3-api-r1`. Все изменения только в consumer; публичный API, ТЗ и версия
пакета прежние. Перенос в ядро требует утверждения владельца.

## Что сравнивается

Обычный обработчик вызывает три функции из отдельной единицы трансляции и
сохраняет полученные значения. Межмодульная оптимизация отключена. Сценарии
сверяют значение GDB, результат вызывающего кода и следующий естественный вызов.

| Тип | Обычный результат | Принудительная подмена |
| --- | --- | --- |
| `uint64_t` | `0x123456789abcdef9` | `0xfedcba9876543210` |
| `float` | `4.75` | `-2.5` |
| `struct ReturnPair` (8 байт) | `{code:-8,count:20}` | `{code:-7,count:19}` |

Операции: `FinishBreakpoint.return_value`, CLI `return <value>` и прямой вызов
через `gdb.parse_and_eval`. Для прямого вызова дополнительно проверены PC/SP и
неизменность объекта sample. Значения float точно представимы; NaN/Inf, округление,
double, hard-float, void и C++ не проверялись.

[Основные сценарии](../../tests/api-experiments/profile/tests/board/test_return_types.py),
[обычные функции](../../tests/api-experiments/src/returns.c).

## Почему нельзя доверять только успешному return

На обеих версиях `return pair_input` выбрал вызывающий кадр без исключения GDB,
но вызывающий код получил `{-8,20}`, а не ожидаемые `{-7,19}`. Оба исходных FAIL
сохранены; runner остановил серии и восстановил прошивку. Нельзя считать команду
успешной подменой по одному отсутствию исключения. Старые байты возвратного буфера
не следует интерпретировать как доказательство исполнения тела функции.

В проверенном ELF `process_returns` передаёт адрес временного результата через
`r0` и затем читает результат из этого буфера через сохранённый `r4`.
`transform_pair` записывает два поля по `r0`. Это соответствует возврату составного
типа размером больше4 байт через память в [ARM AAPCS32](https://github.com/ARM-software/abi-aa/blob/main/aapcs32/aapcs32.rst#result-return).
Результат опыта не устанавливает внутреннюю причину поведения конкретной сборки GDB.

## Альтернативная техника: возвратный буфер

[Отдельный сценарий](../../tests/api-experiments/profile/tests/board/test_sret.py)
останавливается строго перед прологом, проверяет SHA256 ELF, вызывающую функцию,
размер структуры8, совпадение `r0` и `sp`, выравнивание и границы SRAM. После
фиксации намерения он записывает восемь байт, проверяет соседние четыре байта
с каждой стороны, выполняет `return` без значения и проверяет результат вызывающего.
Следующий естественный вызов должен снова дать `{-8,20}`.

Это приём для конкретного разобранного ELF, не универсальный `return_struct`.
Адрес буфера не обязан совпадать с SP в другом коде; после пролога `r0` уже может
быть изменён. Нельзя переносить эти предположения на другую структуру, ABI или
оптимизацию. Не откатывать буфер до того, как вызывающий код его прочитал.
Сценарий намеренно отклоняет другой ELF до записи памяти.

## Результаты

| Операция | uint64_t | float, soft-float | Структура8 байт |
| --- | --- | --- | --- |
| FinishBreakpoint | 8/8 PASS | 8/8 PASS | 8/8 PASS |
| return значения | 8/8 PASS | 8/8 PASS | FAIL на GDB14 и GDB16 |
| Прямой вызов | 8/8 PASS | 8/8 PASS | 8/8 PASS |
| Буфер + bare return | — | — | 8/8 PASS |

Каждая положительная ячейка — первый проход и три заранее заданных повтора на
каждой из двух версий GDB. Итого64/64 основной положительной матрицы и8/8 SRET.
В исходной прерванной серии дополнительно прошли семь сценариев GDB14; они не
включены в64/64. Два исходных FAIL не заменены положительными результатами.

Windows/Linux build/host/prepare: **34/34 PASS**, включая32 prepare, traceability
и20 host-регрессий одним тестом; формат затронутого C PASS. Старый общий format
FAIL остаётся. Изменение прошивки дополнительно проверено на GDB16/native DAP:
R4 —16/16, R3 DEADLINE/SAMEVALUE —8/8. Это выбранная регрессия, не полный R1–R4.
Все шесть серий завершили restore HW_BOOT/HW_GPIO PASS. R5 выполнялся на HLA;
Linux HW и другие платы не проверялись.

## Воспроизведение и свидетельства

F411CE/ST-Link/OpenOCD0.12.0 HLA, Windows; GCC13 `-Og -g3 -fno-lto`, soft-float.
ELF `db27a41c0115eb83d0a7a808b6f68d59098ec20be91f98b1a9a48ae10e6abe0e`.
В локальном стенде запрошен SWD1000кГц, но reset-журналы сообщают запрос2000 и
подбор1800кГц; постоянная фактическая частота1000 здесь не утверждается.

К [команде R1](RC3_API_R1.md#воспроизведение) добавить `--suite r5`.
Полный набор намеренно содержит диагностический STRUCT_RETURN, который даёт FAIL.
Для положительной матрицы перечислить восемь `--test HW_R5_<TYPE>_<MODE>`, исключив
STRUCT_RETURN; SRET запускать отдельно `--test HW_R5_STRUCT_SRET`.
Без `--execute` выполняется только prepare.

[Обезличенный протокол](../research/rc3-r5-results.json) хранит исходные FAIL,
положительные серии, версии, SHA256 источников и результаты восстановления.
Полные журналы остаются в `tests/api-experiments/build/evidence/`.
Добавление SRET меняет инвентарь сценариев, но не ELF; исходные протоколы не заменены.
Предыдущие результаты относятся к своим ELF и не объявляются автоматически
перепроверенными для новой прошивки.
