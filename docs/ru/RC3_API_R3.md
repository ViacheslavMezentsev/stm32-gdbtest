# rc3 R3: действия при остановке и счётчики прогресса

[Документация](index.md) · [English](../en/RC3_API_R3.md)

02.10.2026. Продолжение [R2](RC3_API_R2.md) в `codex/rc3-api-r1` после
`33938d2`. Только экспериментальный consumer; перенос в ядро требует явного
утверждения владельца. Публичный API, ТЗ и версия пакета не изменены.

## Проверенные техники

Исходная идея — пользовательские `test_runner.cmd` и `.gdbinit.txt` проекта
buck-boost-course. Они изучены как примеры, без запуска. Их `cmds` делит строку
по `;`, а `break ...; continue; finish` ожидает естественный вызов функции.
Это отличается от непосредственного вызова через GDB evaluator.

| Сценарий | Результат и применение |
| --- | --- |
| COMMANDS | Условная аппаратная точка на `sum_bytes` исполняет `return 100; continue` как список команд GDB. Остановка на отдельном sentinel подтверждает изменённый checksum вызывающего кода. Следующий вызов после удаления перехвата вычисляется обычно. Так можно подавать выбранный результат в существующую ветвь обработки без firmware hook |
| DEADLINE | Hardware watchpoint на `(unsigned int)(cycles - $start) >= 3` останавливает после трёх завершённых циклов приложения. Проверены старт0 и `0xfffffffe`, включая переход через ноль. Можно ограничить ожидание числом выполненных операций |
| SAMEVALUE | Повторное вычисление с аргументом0 записывает прежний checksum. `watch` не сообщает остановку; sentinel доказывает завершение цикла. `awatch` сообщает доступ до инкремента cycles. Это позволяет отличать изменение значения от факта обращения к данным |
| LANGUAGE | `macro define`, `sizeof(input->bytes)` в текущем C-кадре и параметризованная команда `define` с `if/else` проверены. Список полных Python-строк сохраняет `;` внутри `printf`; ошибка команды прекращает последовательность до следующего действия |

Код: [сценарии](../../tests/api-experiments/profile/tests/board/test_automation.py),
[композиция команд](../../tests/api-experiments/lab/commands.py).

## Уточнения к техникам

- Список команд точки прекращается после возобновления: команда после `continue`
  не исполняется. Это проверено отдельным `$after_continue`, оставшимся0.
  Поэтому проверка результата выполняется после возвращения управления Python
  на подтверждённой sentinel-точке. Это список CLI-команд точки, а не изменение
  состояния inferior из `Breakpoint.stop()`.
- `return` отбрасывает текущий кадр; последующий `finish` относится уже к вызывающему.
  Перехват инициализатора watchdog может предотвратить его обычную инициализацию,
  но не доказывает отключение уже запущенного watchdog. Сам watchdog в R3 не проверялся.
- Счётчик прогресса не заменяет внешний timeout: при зависании без изменения
  `cycles` watchpoint не сработает. Для `uwTick` необходимо отдельно доказать
  источник тика, единицы, работу IRQ и поведение при halt. Модульная разность
  выдерживает проверенное однократное переполнение; произвольное число полных
  оборотов счётчика по ней восстановить нельзя.
- RSP показывает шесть `T05watch` для двух опытов по три инкремента: GDB
  скрывает промежуточные аппаратные остановки, пока predicate ложен. При записи
  прежнего checksum сервер также сообщает `T05watch`, но GDB продолжает до sentinel.
  Фильтрация не устраняет остановки ядра и влияние отладчика на время исполнения.
- `awatch` ловит чтения и записи. Для доказательства именно записи нужны контекст
  инструкции и контрольные точки. Здесь прошивка присваивает checksum и не читает
  его в исследуемом участке; наблюдение относится к CPU, не к DMA.
- `execute_sequence` исполняет доверенные команды последовательно и передаёт ошибку
  наружу. Это не транзакция: предыдущие эффекты остаются. Он не проверяет причину
  остановки автоматически; после `continue` нужна отдельная проверка ожидаемой точки.
  В отличие от `split(';')`, команды задаются списком целых строк.
- Макрос задан самим сценарием GDB. Это не проверка импорта всех макросов заголовков
  из DWARF и не полноценный компилятор C; выражения зависят от выбранного кадра.

Семантика: [списки команд точек GDB](https://www.sourceware.org/gdb/current/onlinedocs/gdb.html/Break-Commands.html),
[watchpoints](https://www.sourceware.org/gdb/current/onlinedocs/gdb.html/Set-Watchpoints.html),
[принудительный возврат](https://www.sourceware.org/gdb/current/onlinedocs/gdb.html/Returning.html).

## Стенд, протокол и воспроизведение

F411CE, ST-Link V2J43M28, SWD1МГц, OpenOCD0.12.0 native DAP/SWD, Windows.
Один прежний GCC13 ELF (`-Og -g3 -fno-lto`, soft-float):
`38375f4f7d58cdb637c69ae099b47c03061230a9df4eecd530475cbc96a2fd19`.
Новых hooks и кода прошивки нет.

К [команде R1](RC3_API_R1.md#воспроизведение) добавить
`--suite r3 --native-stlink`; два `--gdb` задают GDB14 и GDB16.
Без `--execute` выполняется только prepare. Набор — четыре сценария,
первый проход и три заранее заданных повтора на каждом GDB.

Результаты: **32/32 HW PASS** (16 на GDB14/Python3.11,16 на GDB16/Python3.13).
Baseline и последующее восстановление: HW_BOOT/HW_GPIO PASS, reset_run;
restore ELF `1ff37ae10a007401de5e0eaf826764f60a2849c8b7821c123f12caa28c2e79c3`.
[Обезличенная сводка](../research/rc3-r3-results.json) содержит версии, хэши,
проверки и события. Полные журналы остаются в локальном
`tests/api-experiments/build/evidence/20261002T003408.255257Z/`.

Windows/Linux build и CTest host: **20/20 PASS** (18 prepare, traceability,
20 host-регрессий одним тестом). Общий прежний format FAIL из R1 не исправлялся.
Linux HW, другие платы/серверы и HLA для R3 не проверялись.

Далее: ширина/выравнивание и бюджет DWT; фильтрация по стеку при рекурсии;
выходные буферы, ABI возвратов, прерывание прямого вызова. Наличие этих пунктов
не означает аппаратную проверку или утверждение нового публичного API.
