# Нейтральный пример VTOR/FPB

[Документация](index.md) · [Живое исполнение](LIVE_EXECUTION.md) · [English](../en/LIVE_OBSERVER.md)

[Исходники и запуск](../../tests/live-observer/README.md) показывают применение API 3
без новых методов Target. Для первого опыта достаточно Renode, платы не нужны.
Пример поставляется как исходники; бинарники, журналы, снимки и личные стенды остаются в build.

## Что проверяется

Нейтральный ELF выполняет `original_work(x) = x * 3 + 1`, считает вызовы и подтверждённые
IRQ0. Python независимо вычисляет сумму: при семи вызовах это 70. Pending-бит не очередь:
следующий программный IRQ подаётся только после подтверждения предыдущего.

Линкер выделяет 4096 байт по 0x20008000; стек ниже 0x20007000. Первые 1024 байта
отведены коду и remap-таблице (+0x300), счётчики находятся на +0x400, 512-байтная
таблица векторов — на +0x800. Между областями — проверяемые защитные байты.
Размеры и адреса сверяются с ELF, состояние сохраняется полностью до изменения.

| Случай | Ожидание |
| --- | --- |
| BASELINE | Семь исходных вызовов/IRQ, сумма 70 без наблюдателя |
| SEVEN / ZERO | Семь наблюдаемых входов / валидный ноль в завершённом окне |
| EXCEPTION | Намеренный ERROR до resume; очистка VERIFIED |
| HALT | Пассивный timeout, затем явный halt и проверка |
| ACTIVE | Намеренный ERROR внутри известного ISR; ограниченный выход и очистка |
| NEGATIVE | Намеренный FAIL: ожидаются восемь при фактических семи |
| TRAMPOLINE | Прямой SRAM-вызов с воспроизведением вытесненного пролога |
| FPB_ZERO / FPB_SEVEN / COMBINED / FPB_EXCEPTION | Только квалифицированный F411: remap, совместный VTOR, отказ после установки |

После успешного снятия выполняются ещё три исходных вызова без reset. Сценарий,
очистка наблюдателя и внешнее восстановление имеют отдельные свидетельства.
Отсутствующий журнал не считается нулём или успешной очисткой.

## Границы механизма

VTOR-обёртка сохраняет аргументы и EXC_RETURN, передавая управление исходному ISR.
FPB использует code COMP5 и literal COMP7 при проверенной геометрии F411. Trampoline
воспроизводит только `push {r7}; sub sp,#12`, затем переходит на entry+4. Изменение
пролога/ABI/расположения требует нового решения, а не отключения проверки.

Renode не реализует remap в используемой платформе: четыре случая перечислены как
NOT_SUPPORTED. Прямой вызов trampoline проверяет инструкции и результат, но не FPB.
Это Cortex-M3-модель для общего набора инструкций Cortex-M4 soft ABI, не эмуляция
всей периферии F411. RTOS, DMA, физический таймер, вложенные IRQ и временная прозрачность
не входят в доказанное. Обёртка меняет длительность исполнения и флаги; это не
универсальная подмена произвольной инструкции или функции.

Низкоуровневые helper-файлы используют GDB-Python из основного потока и прямые
обращения к выбранным системным регистрам. Это отдельно проверенная процедура,
**не гарантия транспорта Target.mmio**. Для новой периферии используйте SVD/MMIO и
[проверку в модели и на целевой плате](MMIO.md). Raw GDB нельзя считать общим способом
обхода запретов async API. Обычные чтения данных остаются синхронными; навигация в
async-функциях требует await, ожидание остановки не останавливает цель само.

## Аппаратный маршрут — только отдельный допуск

В этом переносе плата не запускается. Исследовательский F411-пилот на API 3 дал
12/12 ожидаемых исходов, независимая сверка Flash/SRAM и сохранённых регистров успешна.
Это происхождение примера, а не новая аппаратная приёмка опубликованного коммита.

1. Подтвердить конкретный свободный F411CE/ST-Link/OpenOCD, отключённые нагрузки,
   watchdog и допустимость reset/resume. Проверить reset-halt состояние до backup.
2. `prepare.py --toolchain <root> --out <new-build-directory>` собирает пакет;
   `campaign.py --package <directory> --stand <local.toml> --serial <serial>` печатает план.
3. После фактического допуска записать локальный admission JSON: `serial`, `elf_sha256`,
   `stand_free`, `watchdog_inactive`, `loads_disconnected`, `reset_resume_allowed`.
   Последние четыре значения должны быть true; файл фиксирует решение оператора,
   а не автоматически доказывает электрические условия.
4. Добавить `--allow-hardware f411ce --admission <file>`. Проверяются identity, размер
   Flash и геометрия стирания; свежие Flash/SRAM читаются дважды. Backup не делает
   повторный reset между снимками. Пишется только выбранный ELF в первом секторе.
5. Сценарии работают verify-only. При отказе прекратить кампанию; внешний recovery
   выполняется в finally. Собственный FPB снимается только при доказанном владении
   по журналу и текущему состоянию. Неоднозначность блокирует дальнейшую запись.
6. Восстановить первый сектор, проверить всю Flash, затем вернуть и проверить SRAM.
   Подтвердить reset-состояние CPU и отдельно, новым подключением без reset/resume,
   сравнить сохранённые FPB/VTOR/NVIC. Автоматический recovery проверяет память и
   PC/SP/xPSR/PRIMASK; независимая сверка системных регистров остаётся обязательной
   операторской проверкой. Все периферийные регистры и прежний живой контекст не восстанавливаются.

При потере GDB: тот же `campaign.py` с `--recover <fresh-backup>` и
`--events <same-attempt/fpb-events.jsonl>`, прежними package/stand/serial/admission
и явным allow-hardware. Не смешивать попытки. При непригодных снимках, USB-отказе или
неоднозначном владении остановиться; восстановление не обещается при недоступном устройстве.
Плата остаётся halted, исходная прошивка сама не возобновляется. Не использовать mass erase.

## Приёмы из прикладных сценариев и миграция

Обобщены приёмы работы с протоколом, питанием, измерениями и телеметрией; прикладная
логика моста и управление лабораторным питанием в пример не копируются.

| Приём | Применение в API 3 |
| --- | --- |
| Отдельная пригодность rig до поведения | Проверить владение памятью/IRQ, полный снимок и layout; несовпадение прерывает опыт до мутации |
| Контекст C++ `this` и DWARF | Дойти `await t.reach(...)`, получить тип/размер/адрес в остановленном кадре; не сохранять ленивый gdb.Value для чтения после resume |
| Независимый эталон | Вычислять ожидаемые байты/сумму на хосте; сопоставлять с исходными и наблюдаемыми счётчиками |
| Снимок объекта отдельно от периферии | RAM восстанавливается побайтно; регистры требуют своего порядка, прав и побочных эффектов |
| Наблюдение → records → проверки | Сохранить JSON-совместимые факты до check, который может прервать сценарий; полнота ряда обязательна |
| Порядок событий и свежесть отсчётов | Условные точки, счётчик публикаций/тик прошивки, ограничение числа остановок и общего времени; время хоста не равно времени MCU |
| Повтор после cleanup | Повторить исходный путь без reset; не скрывать ошибки восстановления успешным основным вердиктом |

Старое `execute("call ...")` в async не переносится. Для **простого имени функции
с числовыми аргументами** применяется `await t.call(...)`. Интерфейс call не принимает
`this->method`, `Class::method`, строковые указатели или произвольные выражения.
Успешный C++ preflight это не меняет. Для методов используйте штатный путь прошивки
и навигацию; отдельный raw-GDB опыт имеет собственные ограничения и не выдаётся за API.
Скрытый `HAL_GetTick()`/`getData()` внутри read/evaluate заменяется чтением доступных
данных либо отдельным допустимым call, после которого используется сохранённый результат.
Старые записи MMIO через execute заменяются явной операцией SVD/MMIO, без механической
read-modify-write для W1C/read-clear. Таблица check оценивает выражения; одиночный check
сравнивает уже полученные Python-значения. Готовые строки в records не вычисляются.

## DDTT

Счётчик входа — свидетельство события; сумма — свидетельство результата; восстановление —
свидетельство пригодности опыта. Автор карты отдельно утверждает, какие ожидания связаны
с какими строками. Для отображения используйте [экспортёр DDTT](DDTT_COVERAGE.md),
сохраняя environment и ревизию источников. Не объединяйте аппаратные и эмуляторные
наблюдения в один неподписанный счётчик. Пример не генерирует вымышленное построчное покрытие.

Готовый запуск также создаёт `map.json`, `build-manifest.json`, `view/lcov.info` и
`view/ddtt-evidence.json`. Три утверждённые привязки в `map.template.json`: `calls++`
к числу исходных вызовов, `return x * 3 + 1` к независимой сумме, `delivered++` к числу
подтверждённых IRQ. Это проверка ожиданий на строках, не трасса инструкций. Отрицательный
сценарий проверяет механизм отказа и намеренно не включён в карту поведения прошивки.
Для Coverage Gutters выберите абсолютный путь к `view/lcov.info` этого прогона.
Манифест описывает явную компиляцию одного исходника; не заявляет Ninja-граф зависимостей
и не хеширует все заголовки/бинарники установленного тулчейна.
