# ELF, BIN и область проверки Flash

[Документация](index.md) → Образы и CRC · [English](../en/IMAGES.md)

Runner проверяет содержимое **загружаемых секций ELF** по адресам загрузки (LMA).
Это соответствует обычному `load` GDB: VMA `.data` находится в RAM, а её начальные
значения загружаются во Flash — сравнивается именно Flash LMA. Секции без флагов
CONTENTS, ALLOC, LOAD (например, `.bss`, отладочная информация) и пустые секции не
сравниваются.

## Режим загружаемых секций (по умолчанию)

До сервера GNU `arm-none-eabi-objdump -h` из каталога GDB формирует список секций.
ERROR до `objcopy`, GDB и сервера дают: пустой или нераспознанный список, перекрытия,
неупорядоченные секции, загрузка за пределы Flash профиля и первая секция не с
`flash_start`. Смещённое приложение и несколько банков не поддерживаются. После
подключения проверяется заводской размер Flash; более вместительный MCU не
расширяет границы профиля ([identity](TARGET_IDENTITY.md)).

BIN создаётся командой `objcopy -O binary --gap-fill=0xFF` **только из выбранных
секций** (`-j` для каждой); длина BIN должна совпадать с протяжённостью секций.
Раньше пустая секция с адресом в RAM (например, пустая `.data`) растягивала BIN до
сотен мегабайт — теперь она в него не попадает.

Заполнение 0xFF определяет байты промежутков **в BIN**, но GDB `load` ELF их не
записывает: на плате они могут быть стёртыми или остаться от прежней прошивки.
Поэтому сравнение секций пропускает промежутки. Несовпадение вызывает запись при
`flash = if-different`, затем обязательное повторное чтение тех же секций; в
`verify-only` несовпадение даёт ERROR без записи. Ошибка чтения не считается
поводом для записи и не скрывается. Чтения идут блоками до 4096 байт.

В `result.json` и JUnit сохраняется `image_verification`:

- `scope: elf-load-sections`, `bin_gap_fill: 255`;
- `gaps_verified: false`, `full_region_crc_verified: false`;
- `regions`: имя, адрес во Flash, размер, смещение в BIN и после чтения `matches`.

`image_verified: true` означает совпадение всех этих секций, а не всей Flash и не
CRC полного образа. `elf-sections.txt` и `image.bin` сохраняются в каталоге запуска.

## Полный образ и CRC (явный режим)

Для полного диапазона передайте `run --image-policy path/to/full-image.toml` или
абсолютный путь в `STM32_GDBTEST_IMAGE_POLICY` (удобно для CTest); CLI приоритетнее.
Если переменная установлена, отсутствие флага **не** отключает полный режим — для
возврата к проверке секций уберите переменную.

```toml
[image]
schema = 1
mode = "full"
start = 0x08000000
end = 0x08004000
fill = 255
crc = "crc32-iso-hdlc"
```

Пример описывает **16 KiB**, а не всю Flash MCU; `end` — исключительная граница.
Начало должно совпадать с `flash_start` профиля, конец — помещаться в профиль и в
прочитанный заводской размер. Если ELF вырастет за пределы политики, запуск
отклоняется. Числа — целые (не bool), `fill` 0…255; неизвестные поля, схемы и
алгоритмы CRC отклоняются. MCU с другой базой требует своего файла; политика хранится
у потребителя независимо от стенда.

Подготовка до сервера:

1. Проверяются исходный ELF, build manifest и загружаемые секции.
2. Создаётся `image.bin`: байты секций сохраняются, промежутки и хвост до `end`
   заполняются `fill`. CRC-поле в прошивку не вставляется.
3. Из BIN создаётся `program.elf` с единственной секцией `.firmware` по адресу
   `start`; проверяются её границы и побайтное совпадение обратного преобразования
   в BIN. Это транспортный контейнер для GDB, а не новая сборка.
4. Фиксируются SHA-256 BIN, контейнера и исходной политики; агент проверяет их и
   заполнение до подключения.

`run --prepare-only` с политикой выполняет эти шаги без оборудования и оставляет
`image.bin` и `program.elf` в каталоге запуска.

После reset/halt агент читает **весь** диапазон блоками до 4096 байт, сравнивает
каждый байт с BIN и считает CRC ожидаемого и прочитанного образа. При несовпадении
и `if-different` выполняет `load program.elf`, восстанавливает `symbol-file
firmware.elf` и повторяет полное чтение. `verify-only` даёт ERROR без записи; ошибка
чтения — тоже ERROR, а не повод прошивать вслепую. При совпадении записи нет. Далее
обычный сценарий, reset/run и правила восстановления backend.

Mass erase не выполняется. Сектора или страницы при записи может стирать backend;
сохранность соседних данных вне диапазона не гарантируется. В рабочем проекте
выделяйте область прошивки с учётом геометрии стирания; в проверенных примерах
F030/F103/F411 граница 16 KiB с ней согласована. Несколько банков, смещённое
приложение и сохранение соседних данных не реализованы.

### CRC-контракт

CRC-32/ISO-HDLC: полином `0x04C11DB7`, init/xorout `0xFFFFFFFF`, refin/refout —
да; для ASCII `123456789` — `0xCBF43926`
([каталог CRC RevEng](https://reveng.sourceforge.io/crc-catalogue/all.htm)).
Байты подаются по возрастанию адресов, хвост нечётной длины — побайтно, без
скрытого дополнения до слова. Поля CRC нет: учитываются все байты диапазона. Если
приложение хранит CRC внутри образа, он тоже входит в расчёт.

Расчёт выполняется `binascii.crc32` на ПК, в агенте GDB, по данным, прочитанным
через отладчик. **Это не запуск CRC-кода на MCU и не проверка его CRC-периферии.**
Совпадение CRC не заменяет сравнения байтов: обязательны оба условия.

`image_verification` полного режима: `scope: full-image`, `start`, `end`, `fill`,
`bytes_compared`, `bytes_match`, `first_mismatch` (адрес или `null`),
`gaps_verified`, `full_region_crc_verified`, параметры CRC и `expected`/`observed`.
Перед записью сохраняется `image_before_programming`. `bin_sha256` относится к
полному BIN, `elf_sha256` — к исходному ELF, `program_elf_sha256` — к контейнеру;
`image_policy.source_sha256` связывает отчёт с TOML, нормализованная копия —
`image-policy.json`. CRC не является криптографической проверкой.

### Один артефакт для программирования и отладки

`image.bin` можно записать внешним программатором **по адресу `start`**, а
`program.elf` — загрузить под отладкой: их payload идентичен. В подключённом GDB
после reset/halt:

```gdb
load /path/to/run/program.elf
symbol-file /path/to/run/firmware.elf
```

Затем reset/halt и запуск по правилам backend. Используйте оба файла из одного
каталога запуска и проверяйте manifest, SHA и readback. В VS Code исходный ELF
остаётся файлом символов, а команда загрузки указывает контейнер; `launch.json`
потребителя автоматически не меняется. Обычный `load firmware.elf` снова оставляет
промежутки и хвост вне явного контракта. `load` может затронуть таблицы символов,
поэтому они восстанавливаются явно ([GDB Target Commands](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Target-Commands.html)).

## Проверенный объём и ограничения

Полный режим проверен на оборудовании через OpenOCD, J-Link GDB Server и ST-LINK
GDB Server ([текущее состояние](STATUS.md)). Контейнер строится `objcopy` для
`elf32-littlearm`; поддержку RISC-V это не расширяет. Дальнейшие темы: CRC-поле и
исключения, другие алгоритмы, сравнение с CRC-периферией MCU.

Причины изменений и аппаратные доказательства — в
[стендовом проекте](https://github.com/ViacheslavMezentsev/stm32-hwtest-blackpill):
docs/ELF_LOAD_REGIONS.md, docs/FULL_IMAGE_CRC.md, docs/K1921VG015_POC.md. Опыт на
RISC-V мотивировал проверку по секциям, но не расширяет поддержку MCU и toolchain.
