# rc3 R4: выходные буферы и подмена результата

[Документация](index.md) · [English](../en/RC3_API_R4.md)

02.10.2026. Продолжение [R3](RC3_API_R3.md) после `8ec9978` в
`codex/rc3-api-r1`. Только consumer; перенос в ядро — после утверждения владельца.

## Техника

Обычная функция `read_packet(output, capacity)` копирует восемь байт и возвращает
их количество либо отрицательную ошибку. `process_packet()` сохраняет статус и
вычисляет сумму только для полного пакета. Вокруг массива лежат метаданные пакета.
Эти функции исполняются в обычном цикле приложения; отладочных hooks нет.

[Сценарий](../../tests/api-experiments/profile/tests/board/test_outputs.py):

1. Дождаться естественного входа в функцию; подтвердить вызывающий кадр.
2. Получить указатель и ёмкость из аргументов, сверить с известным объектом RAM.
3. Зафиксировать намерение изменения; записать данные строго в выходной массив.
4. Выполнить `return <status>`, убедиться, что выбран вызывающий кадр.
5. Дождаться следующего входа в обработчик; проверить статус, вычисленный результат,
   байты буфера и неизменность соседних метаданных.
6. Пропустить ещё один естественный вызов и подтвердить обычный результат.

| Опыт | Данные и статус | Проверка вызывающего кода |
| --- | --- | --- |
| NATURAL | Обычные восемь байт,8; естественный `finish` | Сумма770 |
| OUTPUT | Байты1…8, принудительный статус8 | Сумма36 |
| ERROR | Восемь байт0xa5, статус−5 | Статус−5 сохранён, сумма остаётся исходной0 |
| SHORT | Байты10,20,30 и хвост0xa5, статус3 | Неполный пакет отвергнут, сумма остаётся0 |

После каждого опыта следующий естественный вызов даёт статус8 и сумму770.
Смежные поля `format` и `destination` сохраняются во всех случаях.

## Границы применимости

Так можно моделировать отказ, неполный ответ или выбранные данные устройства,
не меняя вызывающий код. Здесь нет реального SPI/I2C/DMA: опыт доказывает управление
потоком обработки в обычной C-программе, а не корректность драйвера периферии.

`return` не откатывает действия, выполненные до точки останова. Для реального
драйвера нужно изучить пролог, блокировки, ресурсы и побочные эффекты. Наш
остановленный вызов ещё не заполнил буфер; проверяется конкретный ELF с `-Og`.
Подмена живёт до чтения вызывающим кодом: ранний rollback сделал бы опыт неверным.
Указатель из аргумента сам по себе не даёт права писать произвольную память;
здесь проверены точное совпадение адреса, ёмкость8 и границы известного объекта.

SHORT моделирует статус неполного ответа и непригодный хвост, записывая весь буфер.
Это не доказательство частичной записи самим драйвером. ERROR проверяет отказ от
приёма данных после старта; сохранение предыдущего ненулевого результата отдельно
не проверялось. Возврат только `int32_t`; другие ABI, структуры и float — далее.

## Результаты и выявленное ограничение

R4: **32/32 HW PASS**, по16 на GDB14/Python3.11 и GDB16/Python3.13.
ELF SHA256: `893444194ffab90c1977d13d5aef1a47e50adcb33261c20f85090fe17095f2ae`.
Windows/Linux build/host/prepare: **24/24 PASS** (22 prepare, traceability,
20 host-регрессий одним CTest); формат затронутого C PASS. Старый общий format
FAIL остаётся отдельным ограничением.

Регрессия на новом ELF, только GDB16:

| Набор | Интерфейс | Фактический результат |
| --- | --- | --- |
| R1 | native DAP | 24/24 PASS |
| R2 | native DAP | 7 PASS первого прохода; ASM ERROR, серия остановлена |
| R2 ASM отдельно | HLA | 4/4 PASS |
| R3 | native DAP | 16/16 PASS |

В native DAP `jump` достиг Default_Handler; распознавание `b` на себя и первый
`stepi` прошли. На следующем `stepi` OpenOCD сообщил `target not halted`, после
чего сработал внешний20с timeout. Исходный ERROR сохранён, восстановление прошло.
На том же ELF HLA выполнил все три шага в каждом из четырёх запусков.
Это наблюдаемое различие интерфейсов, а не доказательство первопричины внутри
OpenOCD или ST-Link. Native DAP не объявляется универсальной заменой HLA.
Все пять серий завершили restore HW_BOOT/HW_GPIO PASS; программные Z0-вставки
после включения RSP-трассы не обнаружены. Повтор всей R1–R3 на GDB14 не выполнялся.

## Проверки и воспроизведение

Прежний F411CE/ST-Link/OpenOCD0.12.0, native DAP/SWD1МГц, Windows; GDB14 и GDB16,
одна новая прошивка GCC13, soft-float, `-Og -g3 -fno-lto`.
К [команде R1](RC3_API_R1.md#воспроизведение) добавить `--suite r4 --native-stlink`.
Четыре сценария × первый проход и три повтора × две версии GDB.

Фактические версии, ELF SHA256, исходники и результаты:
[обезличенная сводка](../research/rc3-r4-results.json). Raw-журналы находятся
в локальном `tests/api-experiments/build/evidence/`; имена серий перечислены в сводке.
После каждой серии восстанавливается согласованная прошивка, проверяются
HW_BOOT/HW_GPIO и reset_run. Предыдущие протоколы R1–R3 сохраняют свои исходные ELF.

Публичный API, ТЗ и версия пакета не менялись. Следующий этап — типы возврата,
включая 64-битные числа, float и структуры, с раздельной оценкой естественного
возврата, принудительного возврата и прямого вызова.
