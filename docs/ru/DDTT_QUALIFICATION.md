# Квалификация условий DDTT

[Документация](index.md) · [English](../en/DDTT_QUALIFICATION.md)

Первый пакет 0.5.0: внешний экспортёр проверяет применимость выбранного утверждения.
Он не определяет исправность всей платы и не переписывает result.json. Нейтральный
[пример](../../examples/ddtt-qualification/README.md) включает **синтетические host-данные**
и отдельный маршрут Renode с журналом модельного приёмника. Аппаратных измерений нет.

## Три независимых результата

- `raw_state`: прежняя проекция проверки CONFIRMED/FAILED/UNKNOWN; исходный verdict
  сценария сохранён в evidence.status и result.json.
- `applicability`: APPLICABLE, VIOLATED, UNKNOWN, NOT_APPLICABLE или NOT_REQUIRED.
- `state`: итоговая раскраска. Без применимости — UNKNOWN даже при сыром FAILED.

В LCOV/Cobertura UNKNOWN не превращается в DA=0. При допустимых условиях сырая
FAILED остаётся красной. На общей строке применимый FAIL имеет приоритет, затем
UNKNOWN, затем CONFIRMED. Отсутствующий допуск новой попытки не возвращает старый зелёный.
Пустой набор обязательных утверждений не считается принятой кампанией.

## Карта schema 2

Schema 1 сохраняет прежнее поведение, но отвергает поля квалификации вместо их
молчаливого игнорирования. В schema 2 каждая точка явно задаёт `requires: ["clock"]`
или `requires: []` для независимой проверки; `required` — boolean, по умолчанию true.
Верхний `qualification` содержит ровно context и conditions:

```json
{
  "context": {
    "instance": "local-board-alias",
    "environment": "hardware",
    "elf_sha256": "<64 hex>",
    "inputs_sha256": "<64 hex>"
  },
  "conditions": {
    "clock": {"unit": "Hz", "min": 24900000, "max": 25100000, "max_age_s": 60}
  }
}
```

Environment и ELF должны совпасть с картой. `inputs_sha256` вычисляет организатор
по каноническому инвентарю входов: ревизии платы, сценария, профиля, SVD, стенда,
инструментов, проводки и измерительной цепочки. Его фактическое наполнение — обязанность
проекта; экспортёр проверяет равенство отпечатков, не угадывает серийник или кварц.
Изменяемые условия, например питание, должны быть проверены непосредственно перед
зависимым действием и контролироваться на нужном интервале. Срок действия — обещание
измерительной процедуры, не доказательство непрерывного наблюдения.

Условия — конечные числовые интервалы с явной единицей и положительным max_age_s.
Опциональный `kind: "capability"` требует unit=present, min=max=1; измерение — 0/1
с нулевой неопределённостью. Подтверждённое отсутствие даёт NOT_APPLICABLE только
для точки required=false; для обязательной — VIOLATED. Неизвестность не SKIP.
Другие виды предикатов и зависимости сценариев пока не вводятся.

## Снимок и привязка к попытке

Снимок JSON schema=1: ровно `schema`, `context`, `measurements`. Контекст точно
соответствует карте. Каждый элемент measurements содержит:

| Поле | Значение |
|---|---|
| condition | ID из conditions |
| value, uncertainty | конечные числа, uncertainty >= 0 |
| unit | точное совпадение с правилом, автоматической конверсии нет |
| observed_utc, valid_until | ISO timestamp с часовым поясом |
| invalidated_utc | timestamp либо null: обнаруженное событие утраты пригодности |
| method | measured для допуска; declared не подтверждает условие |
| evidence_sha256 | хеш исходной записи измерения, 64 hex |

На требуемый ID должна быть ровно одна запись: ноль/две — UNKNOWN. Интервал
value ± uncertainty целиком внутри нормы — APPLICABLE; целиком снаружи — VIOLATED;
пересечение границы — UNKNOWN. Нужен допуск на весь интервал started_utc + duration_s
результата; отсутствие длительности, будущее измерение, истечение max_age/valid_until
или invalidated_utc до конца опыта блокируют утверждение. Сравнение проводится
относительно времени опыта, а не времени повторного экспорта исторического отчёта.

Внешний организатор вызывает `tools.ddtt_qualification.bind(result_path, snapshot)`:
создаётся новый admission.json рядом с результатом (существующий не перезаписывается).
Формат: schema=1, result_sha256, snapshot_sha256, snapshot. Хеш снимка — SHA-256 JSON
с sort_keys=True, separators=(',', ':'), allow_nan=False, стандартным ensure_ascii=True,
затем UTF-8. Хеш результата — точные байты файла. Связь создаётся после попытки,
используя снимок условий, полученный до неё; хеш не доказывает время создания снимка.

`ddtt_provenance seal` сохраняет хеш admission.json, включая его отсутствие.
Переносимый экспорт проверяет его неизменность; добавление/удаление/замена после seal
вызывает ERROR и очистку прежнего вывода. Обычный экспорт без запечатанной кампании
даёт проверку внутренней согласованности, не защиту от намеренной подделки всех входов.
Исходные записи измерений не открываются по хешу автоматически: проект хранит их локально.

## Отчёт и пределы первого пакета

ddtt-evidence.json/public-data.json schema=2 добавляют raw_state, applicability и
acceptance: required (число обязательных точек), blocked, accepted. Accepted=true
только при непустом обязательном наборе и CONFIRMED каждой его точки. Это приёмка
выбранных утверждений, не автоматический общий вердикт прошивки. Exit 0 по-прежнему
означает успешный экспорт: CI отдельно проверяет acceptance.accepted.

Панель строки HTML показывает сырой исход, применимость и причины. Переносимый
отчёт не публикует context, сырые измерения, actual/expected или персональные пути;
только статусы, ID условий, коды причин и хеш снимка. Имена условий должны быть публичными.

Runner и Target не изменены. Нет автоматического запуска квалификации, skip/scheduler
или передачи JSON в [data]. Для сценария проект может подготовить соответствующий TOML
снимок и подключить существующим [data]; этот маршрут показан в нейтральном примере.
Следующие этапы — аппаратный пилот и измерительная
цепочка. reach(main), HSE_VALUE и виртуальная кнопка не доказывают физические параметры.

## Проверка в Renode

[Исполняемый пример](../../examples/ddtt-qualification/README.md#renode-независимый-журнал-приёмника)
использует отдельный журнал периферии как эталон доставки. Один ELF и один сценарий:
норма, потеря слова, повторная норма; raw PASS сохранён, зависимая точка блокируется
только при нарушении условия. Это проверка детерминированной модели, не физических
параметров MCU. Контракт и схемы первого пакета не изменены.

Проектный маршрут примера передаёт JSON-снимок строкой в TOML, записывает квитанцию
qualification_input в records и сверяет её до bind. Это соглашение проекта поверх
существующих API; исходные PASS/FAIL и журналы сохраняются без редактирования.

## Повторный анализ сохранённого измерения HSE

Проверку интерпретации выполняйте отдельно от исходного аппаратного результата:
сверьте SHA исходных записей, создайте производную host-проекцию и изменяйте
ожидание карты, а не измерение. Для интервала 24.987985–25.015135 MHz ожидание
25 MHz ±1% даёт APPLICABLE; 16 MHz ±1% — VIOLATED и итог UNKNOWN только для
зависимого утверждения. Независимая сверка памяти остаётся CONFIRMED. Интервал,
пересекающий границу, и завершённая epoch дают UNKNOWN; LCOV не должен рисовать
такую точку красной или возвращать прежний зелёный.

Если первоначальный аппаратный протокол не является runner result.json, не
подменяйте его этим форматом. Сохраняйте его отдельно; новая запись анализа
помечается mode=host и содержит хеш исходника. Времена host-анализа относятся
к импорту, не выдумывают время прежнего измерения. Такая проекция проверяет
экспортёр, но не открывает аппаратный допуск после восстановления/смены ELF.
Для реального последующего сценария снимок нужен до него в действующей эпохе.
