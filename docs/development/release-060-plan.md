# План 0.6.0: длительные сценарии, C++ и управляемые воздействия

[Памятка](../../TODO.md) · [Дорожная карта](../../ROADMAP.md) · [Предыдущий пакет](release-051-plan.md)

Согласованное направление от 27.10.2026. Это план, а не описание реализованного API.
Текущая выпущенная версия — 0.5.0; номера API и схем заранее не повышаются.
Накопленные примеры, навыки и отчёты подготовки 0.5.1 сохраняются и входят в состав
приёмки 0.6.0. Выпуск 0.5.1 отдельно сейчас не готовим; история его проверок сохраняется.
Реальные внешние адаптеры временно отложены, но включены отдельным этапом этого плана.

## Цель и правила работы

Сценарист должен выполнять длинные серии воздействий, вызывать C++ и понимать,
что именно проверено, не обходя API и не теряя исходную причину ошибки.
Для каждого изменения нужен нейтральный пример «ограничение/дефект → точный исход →
изменение → повтор → соседние случаи», с независимыми ожиданиями и явной средой опыта.
Ожидаемый ERROR/FAIL не подменяется успешной проверкой прошивки.

Пакеты идут по зависимостям ниже. Не дробить согласованный пакет на отдельные разрешения
для каждой host-проверки. Перед изменением публичного контракта показать окончательную
семантику, совместимость, ошибки и миграцию. Аппаратные операции согласуются отдельно.
Каждый пакет заканчивается результатом, ограничениями, документацией и подписанным
коммитом; push, land и выпуск выполняет владелец. Новые ветки — после принятия текущей.

Дополнительные находки классифицировать: блокер корректности/очистки устраняется до
следующего этапа; связанное улучшение включается с проверками; независимое расширение
уходит в резерв. Не расширять выпуск молча и не ослаблять ожидания ради PASS.

### A0 — воспроизведение и измерение

- Разделить report.checks, report.mutations, report.stops и Journal; измерить рост каждого.
- Считать resume, wait (включая повторные timeout), halt и async-навигацию отдельно:
  окно не равно одной записи execution. Сравнить capture=true/false при одинаковых лимитах.
- Проверить max_records/nodes/depth/text, большой единичный record и длинную серию;
  отказ должен быть атомарным, уже принятые записи остаются доступны.
- Отдельно измерить reach против постоянной точки при одинаковом числе остановок;
  время хоста, число запросов и расход журнала — разные метрики. Не обещать ускорения async.
- Сохранить нейтральные исходные ошибки и проверяемый подсчёт бюджета. Отсутствующие
  сырые записи потребителя не считать самостоятельно подтверждёнными измерениями.

Выход: воспроизводимая матрица и baseline для A1–A3; без изменения ядра на этапе измерений.

Промежуточно, 27.10.2026: host Windows/Linux — восемь наблюдений; Renode Windows/Linux —
по семь запусков (четыре PASS и три воспроизведённых ERROR). Десять окон дают 30 записей,
400 узлов; при max_nodes=4096 отказ на halt 103-го окна. Capture=false не устраняет отказ.
При полном журнале перед resume остановка в cleanup подтверждена событием и диагностикой,
но её журналирование даёт execution_cleanup=ERROR; завершение сервера отдельно VERIFIED.
На host подтверждено замещение fault_stop ошибкой записи. Это дефекты до исправления,
не новая аппаратная приёмка. A0 остаётся в работе: контролируемые замеры циклов/роста
отчёта и дополнительные отказные случаи Renode; время startup не считать ценой breakpoint.

Итог A0, 27.10.2026: вторая кампания Renode Windows/Linux — по пять PASS и два
ожидаемых ERROR. 1000 reach дают 2002 checks и 1001 stops, 1000 write — 1000 mutations;
лимит Journal эти списки не ограничивает. Пять wait в одном окне дают семь execution
вместе с resume/halt. При полном журнале fault guard даёт RecordError вместо fault_stop,
хотя stop.kind=fault остаётся в отчёте. Это обычная функция с guard, не аппаратный IRQ.
Host MMIO выявил оба отказа аудита: до транспорта и после записи, с разными effect.
Циклы измерены внутри сценария с тремя повторами; это стоимость маршрутов, не одного
breakpoint и не время MCU. A0 завершён как диагностическая база; heap-профилирование
нового представления относится к A2. Ни один дефект пока не исправлен.

### A1 — диагностика и ошибки

- RecordError: имя записи, путь, предел, использованный бюджет и место превышения;
  ограниченные по размеру сведения, без копирования всего отклонённого объекта.
- Ошибка журналирования не заменяет исходную ошибку исполнения/транспорта. Обе причины,
  состояние цели, подтверждённые эффекты и результат очистки доступны в результате.
- Проверить отказ записи после continue, при wait/halt, fault/disconnect, таймауте,
  завершении сценария и восстановлении. Cleanup не зависит от свободного места в журнале.
- Разрешить reason без override; тип/пустоту валидировать, права не менять;
  обязательное обоснование override и остальные проверки MMIO сохраняются.

Выход: host-регрессии, Renode Windows/Linux, ТЗ и API RU/EN; ошибки не скрываются.

Проверено локально 27.10.2026 (host и Renode Windows/Linux, без плат): первичный fault/transport сохраняется; ошибки аудита имеют
отдельные ограниченные сведения, первые 16 execution-диагностик и общий счётчик.
Подтверждённый halt не становится cleanup ERROR из-за полного Journal; общий исход
при отказе аудита остаётся ERROR. Лимиты показывают имя/путь и used/maximum/attempted;
reason не меняет права. Регрессии: tests/host/test_records.py, test_mmio.py,
test_live_execution.py; Renode — tests/renode-backend и tests/mmio-renode.
Агрегация, truncate и изменение численных лимитов не входят в A1. Далее A2:
сначала согласовать компактное представление и уровни детализации, затем менять код.


### A2 — компактное представление без потери смысла

- Согласовать уровни детализации, область настройки и совместимость до реализации.
- Сначала сокращать без потерь: дескрипторы MMIO один раз, ссылки на описание,
  идентификаторы операций и соответствие attempt/result; сохранить порядок и значения.
- Затем явная агрегация успешных повторов execution: число операций по виду,
  поколения, первая/последняя операция, причины остановок и открытое окно.
- Не агрегировать пользовательские измерения и значимые промежуточные события молча.
- Сокращение reach касается представления; чужой breakpoint, неверное условие и кадр
  по-прежнему дают отказ. Оценить также рост mutations/stops/checks и вывода терминала.
- Пример: длинная серия, неожиданная остановка посередине, повтор после отказа;
  сравнение полного и компактного режимов по смыслу результатов и расходу памяти.

Выход: согласованный контракт, ограниченный рост, совместимые читатели/экспортёры.

### A3 — исчерпание бюджета и полнота

- Рассмотреть явную политику error/truncate, строгий режим по умолчанию. Место настройки
  выбрать по смыслу накопления, а не смешивать с сохранением capture.
- Отдельный ограниченный резерв диагностики/незавершённой операции; определить поведение
  при исчерпании и этого резерва. Не обещать безусловной сохранности при потере процесса.
- Признаки полноты, причина, счётчики пропусков, затронутые виды записей и интервалы;
  различать сохранённый, полный и пригодный для конкретного утверждения журнал.
- Исход сценария, состояние захвата, cleanup и анализ DDTT остаются раздельными.
  Нельзя получать зелёное подтверждение из отсутствующих обязательных данных.
- Проверить читатели records, отчёт, coverage, pack и повторный анализ; старые полные
  записи читаются, новая схема при необходимости получает явную версию и миграцию.

Выход: потеря данных видна, исходные FAIL/ERROR сохранены, зависимые утверждения блокируются.

### A4 — C++ без скрытого исполнения

- Сначала namespace и static; затем явный объект/this и выбор перегрузки.
- Проверить const/volatile и квалификаторы методов, наследование/корректировку this,
  неоднозначность, оптимизированный/inline-код, отсутствующий символ, типы аргументов
  и возврата. Для неподдержанного случая — ранний объяснимый отказ.
- Согласовать допустимый поднабор, включая указатели/ссылки; не превращать имя функции
  в произвольное выражение GDB. Виртуальную диспетчеризацию принять либо явно исключить.
- Одинаковая семантика def/async def, lazy await, deadline, breakpoint внутри call,
  исключение/ошибка, незавершённый dummy frame и восстановление контекста.
- Пример объекта после конструктора: публичный метод вместо ручной записи private-полей;
  обработчик как обычный метод не объявляется аппаратным IRQ.
- write/read не получают allowed_calls: время вычисляется явным call, используется
  return_value, затем конкретное значение записывается отдельно.

Выход: поддержанный поднабор C++ с примерами успеха и отказа, миграция потребителей.

### A5 — управляемые воздействия

- Различать модель периферии, подмену значения для кода, изменение объекта/буфера,
  физический сигнал. В отчёте фиксировать способ, место воздействия и непроверенные слои.
- Сначала проверить спорный механизм: override SVD сам по себе не делает IDR записываемым.
  Нужны наблюдаемый эффект, фактическое чтение кодом и отрицательный контроль.
- На Renode показать моделируемый вход; на нейтральном ELF — программную подмену
  с владением памятью, восстановлением и проверкой соседнего пути.
- Если нужен публичный helper, сначала определить возможности backend и явный отказ
  неподдержанного способа. Не вводить универсальный inject как обход read-only.
- Широкие MMIO-окна memory не включать; конкретный буфер периферии рассматривается
  только с контрактом ширины, порядка, побочных эффектов и восстановления.

Выход: исполняемые техники и честные границы DDTT; новый метод только при доказанной необходимости.

### A6 — возврат отложенного адаптера

Первый кандидат — сохранённая ROS1 bag v2 записи телеметрии F411 от 23.10.2026,
с метаданными захвата и парой result/records. Исходные пути и данные — локально.

- Импорт офлайн в нейтральный формат примера: каналы/типы/единицы, хеши, происхождение,
  временные метки с явным источником часов, отдельный analysis и неизменный результат.
- Не считать последовательные rostopic-выборки одновременными или совпадающими с bag;
  без опор связь с моментом чтения GDB неизвестна. ROS и GDB не независимые датчики.
- Повреждение/усечение, неверная идентичность, тип, хеш, канал, нечисловое значение,
  сдвиг часов и нехватка опор; повторяющееся постоянное значение не является дублем само по себе.
- Приватные метаданные исключить из публичных fixtures; добавить синтетический файл
  того же формата для CI, реальный импорт подтвердить локально на Windows/Linux.
- MCAP Android и радиоимитатор сохраняются следующими источниками, не обещать их
  реализацию как часть первого адаптера. Общий формат должен допускать их подключение.

Выход: реальный офлайн-импорт и пример ограничений, рекомендации results/DDTT/Pages.

### A7 — объяснение причин изменений

Каждый пакет содержит пример «неправильно/правильно» с проверяемым ожидаемым исходом,
а не только новый параметр. Обновить техники, шпаргалку, DDTT и навыки scenarios/develop/
results/renode/coverage/report, при необходимости периферийный навык; проверить ресурсы
в отдельной копии. API, карточки и миграция — RU/EN; изменения поведения — с ревизией ТЗ.
Pages обновлять содержательно, дизайн сохранять. PDF обеих форм строить на новых
пригодных свидетельствах, с происхождением и границами полноты.
Потребители BluePill/BlackPill и выбранные сценарии практического проекта: сначала
inspect/prepare/сборка, затем согласованные аппаратные проверки. Не менять соседние проекты молча.

### A8 — кандидат 0.6.0

- Аудит diff от v0.5.0, включая накопленные материалы подготовки 0.5.1;

## Что можно завершить без плат

A0–A4 полностью разрабатываются и проверяются на host/Renode; аппаратная переносимость
подтверждается позже. A5 — модель и программная подмена; электрический эффект без платы
не подтверждается. A6 полностью офлайн по сохранённым данным. A7 — документы, навыки,
сборки потребителей, Pages/PDF. A8 — вся offline-часть. Ни один из этих PASS не HW PASS.
До согласования стендов работа не блокируется: сначала закрываем весь этот объём.

## Вне обязательного состава

Debugpy/ручная отладка в VS Code — отдельно в паре с владельцем; keep/attach, SVD-кэш,
универсальный FPB/VTOR-патчер, переименование hwlivetest и научная статья HSE сохраняются

механизма фиксируется вместе с работающей альтернативой, а не как реализованная возможность.
