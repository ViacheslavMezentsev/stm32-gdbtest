## Зафиксированная база

19.10.2026: технический кандидат **0.5.0-p5-baseline-01** — полный SHA
`f751fd1dee3c66959d2ec02620bf8439c343dabf`. Это исходная база приёмки, не тег
и не опубликованная версия. Родительский ddtt-roadmap принят владельцем;
CI ветки api3-skills-audit ещё выполняется по сообщению владельца.

В этой базе API_VERSION=3, target schema 3 (аппаратные 1/2 совместимы),
капсула конфигурации 1 без SVD / 2 с SVD, ТЗ 0.112 / API 0.3.23.
`__version__` пока 0.4.1: результат нельзя идентифицировать только строкой версии.
Паспорт — документ планирования, runner его не читает; schema здесь не новая схема API.
Хеш lock-файла записан для LF-представления в Git (не зависит от Windows checkout).

Правила фиксации:

1. Проверять чистый checkout указанного SHA, сохранять SHA модуля и отдельно
   проекта-потребителя, ELF, SVD, сценариев, модели, инструменты и выбранный стенд локально.
2. Сейчас не менять ядро и не запускать платы. Перенос навыков/архива уже входит в базу.
   Файл паспорта и матрица находятся в дочерней документальной ветке.
3. До финальной P5b закрыть миграцию потребителей и подготовить P6b-pre:
   версию 0.5.0, миграцию и выпускные документы. Зафиксировать **новый полный SHA**
   как финального кандидата, подтвердить CI. Поле final_candidate_commit пока null.
   Не объявлять базу с версией 0.4.1 финальным выпускным кандидатом.
4. При изменении кода/сценариев/SVD не переписывать прежнюю кампанию. Новый кандидат
   получает новую кампанию; повторить затронутые проверки и зафиксировать решение
   по остальным. Полная итоговая матрица относится к одному финальному SHA модуля.
5. После приёмки исправление метаданных тоже меняет SHA: проверить diff, повторить
   docs/host/pack и пересмотреть матрицу. Старые свидетельства указывать как прежние,
   не приписывать их новому SHA. Подписанный тег и публикация — владелец.

| MCU | Локальный маршрут | Объём |
| --- | --- | --- |
| F030R8 | ST-Link / OpenOCD | H1/H2/H4; Cortex-M0, не требовать VTOR/FPB-remap M3/M4 |
| F103 | ST-Link / OpenOCD | H1/H2; точный суффикс и объём Flash подтвердить перед опытом |
| F401CC | ST-Link / OpenOCD | H1/H2; C3 после согласования совпадения платы/профиля |
| F411CE | ST-Link / OpenOCD | H1/H2/H3; C3 по выбранному профилю |
| F429ZI | ST-Link / OpenOCD | H1/H2 |
| AT32F403A | J-Link WinUSB / vendor OpenOCD | H1/H2; штатный shutdown, exit=0 и отсутствие forced termination |

F103 не заменяется вторым F411. ST-LINK GDB Server, SEGGER GDB Server и st-util —
дополнительные backend с собственной прежней матрицей; новые результаты OpenOCD
не расширяют их приёмку. Если выпуск заявляет свежую регрессию этих backend,
нужны отдельные строки/запуски или явное ограничение в release notes.
GCC 13/14/15 — offline-матрица из ci/dependencies.lock.json. Для аппаратных API 3
сначала закрепить GCC 14.2.1/GDB-Python и его функции direct-call-timeout,
unwind-on-timeout, send_packet; другие GDB проверять отдельными строками.

Перед каждым аппаратным блоком: подтвердить свободный стенд/нагрузки и разрешённые
операции, сохранить свежие проверенные снимки затрагиваемой Flash/SRAM и безопасных
регистров. Не читать WO/FIFO ради снимка, не восстанавливать RO/W1C общим дампом.
После опыта, включая FAIL: halt, снять observer, восстановить память/конфигурацию
в согласованном порядке, независимо сверить; final halt/run задать заранее.
Reset-halt baseline не выдавать за восстановленный живой контекст. При неизвестном
состоянии остановить кампанию, сохранить ERROR. Разрешения прошлых пилотов здесь
не превращаются в разрешение нового запуска. Mass erase/option bytes запрещены.

## Миграция потребителей на MMIO

Исходные ревизии и gitlink перечислены в паспорте; пользовательские рабочие деревья
не менять в ходе P5a. Каждому потребителю нужна отдельная ветка и свой принятый SHA.
Обычные def сохраняются; async добавлять только там, где действительно нужно живое окно.

| Группа | Где смотреть | Решение и независимая проверка |
| --- | --- | --- |
| SVD | hil/<MCU>/session.toml | [mmio] svd от session; происхождение/лицензия/хеш, inspect и снимок в pack; проверить каждый профиль |
| GPIO / RCC | test_board, test_boot, test_startup | Имена SVD вместо выражений; маски по RM, без обещания напряжения по ODR; RCC readiness не измеряет кварц |
| ADC / DMA | BluePill test_dma/test_dma_error; BlackPill test_adc/test_adc_faults | NDTR только при выключенном потоке; flags W1C явной маской, сначала ошибка, потом очистка; без readback write-only |
| NVIC | BlackPill test_sleep/test_ddtt_feedback/test_adc_faults | ICER/ISER W1C/W1S: сохранить разрешённое состояние, отдельные маски записи и чтение читаемого статуса |
| SysTick / SCB | BlackPill test_sleep/test_timers | CTRL COUNTFLAG имеет эффект чтения, ICSR — командные биты; не делать общий RMW/снимок; явно определить допустимое воздействие |
| Инъекции / RAM | Оба проекта | ret, аргументы, поля приложения и память оставить общим API; не заменять на MMIO механически |
| DDTT | Карты, anchors, records | Перепривязать после изменения сценария; сохранить контроль неверного допуска и отсутствующей записи |

Нужна инвентаризация всех read/evaluate/write/check(rows)/memory и динамических
выражений, а не только совпадений по имени регистра. Core-регистры могут отсутствовать
в vendor SVD: проверенное дополнение либо ограниченный MMIORegister override с причиной;
не выдумывать имена и не снимать проверки через safety=False. Отдельно сверять поля,
access, readAction, modifiedWriteValues; SVD не заменяет RM/модель/плату.
mmio.write принимает готовое int; allow_effects=True — согласие на известный эффект,
не на неизвестную операцию. При потере ACK эффект неизвестен, автоматического повтора нет.
Не добавлять скрытое чтение только ради проверки, что write прошёл.

Порядок: инвентаризация → SVD/контракты → host/inspect/prepare/pack на Windows/Linux →
отрицательные модели Renode → согласованный минимальный аппаратный опыт → полный
набор → DDTT. Новый check требует независимого ожидаемого значения. При невозможности
перенести операцию зафиксировать узкое исключение и влияние на выпуск, не объявлять
весь потребитель мигрированным. Тела сценариев prepare не исполняет.

## Следующий шаг

Миграция потребителей и P6b-pre выполнены (см. выше). После land P6b-pre и зелёного CI —
коммиты приёмки потребителей с gitlink на финальный SHA; затем запуск O/E/D,
аппаратный допуск и H/C/R. P6b после P5 оформляет фактические результаты и ограничения.
При недоступности SSH/CI/прибора не молча исключать строку: вынести решение владельцу.
Новые измерения HSE не обязательны для проверки логики DDTT; повтор сохранённого
набора явно помечается host replay, а физическая квалификация — отдельный опыт.
