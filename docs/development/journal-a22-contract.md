# A2.2: коллекции отчёта и вывод — кандидат контракта

Статус: подготовка, не реализованный публичный API. Продолжение A2.1 к 0.6.0.
Ядро пока не меняется. Решение требуется для формата result и границы сводок.

## Что обнаружено

| Данные | Где живут | Кто зависит от полной истории |
| --- | --- | --- |
| execution | records; LiveExecution.audit | records(), capture, анализ живых окон и cleanup |
| checks | result.json; Target._verdict | scenario.reject_failed_checks, DDTT coverage, stand_loop |
| stops | result.json; навигация и LiveExecution | анализ причин остановки, порядка и контекста |
| mutations | result.json; write/call/ret/write_memory | анализ воздействий и восстановления |
| evaluations/executions/resets | result.json | чтения, произвольные команды, сбросы; тоже растут |

`Target.stops` — рабочий буфер событий GDB, не та же коллекция, что
`report['stops']`. Его нельзя заменять сжатой историей. `reach()` сначала добавляет
stop в отчёт и только затем дописывает frame; мгновенная заморозка при append теряет
поле. Возвращаемые методы словари также требуют проверки владения/поздних изменений.

`checks` содержит actual/expected произвольных типов; agent сейчас использует
`json.dumps(..., default=repr)` в конце. Ранний вызов repr во время накопления может
изменить момент чтения GDB-значения или вызвать пользовательский код. Новый буфер
не должен молча добавлять такие вычисления, особенно при MMIO.

Наконец, agent печатает весь JSON отчёта в stdout, а JUnit включает его в system-out.
Уменьшение сообщений PASS само по себе не устраняет эти повторные копии.

## Проверенные отрицательные контроли

1. checks `[PASS, FAIL, PASS]` с одним именем: текущий экспортёр правильно даёт FAILED.
   Если оставить только первую/последнюю проверки, он даёт CONFIRMED даже при
   status=FAIL всего сценария. Это ожидаемое поведение привязки отдельного утверждения,
   которое становится опасным при потере средней записи. Lossless-раскрытие сохраняет FAILED.
2. Сценарий перехватил CheckFailed: reject_failed_checks всё равно находит отказ в
   раскрытой коллекции из 1000/10000 проверок. Сводка не должна обходить эту защиту.
3. Последнее событие resume без halt остаётся незавершённым окном; повторяющиеся wait
   не создают фиктивной остановки и не смешивают поколения.
4. Фиксация stop после завершения его формирования сохраняет frame; фиксация сразу
   при append — нет. Нельзя внедрять универсальный сжимающий list без аудита писателей.
5. Повреждённые ссылки, длины, дубликаты ключей формы и чрезмерное раскрытие отклоняются.
   Литеральные массивы/словари, похожие на ссылки, остаются данными; 0/false/null/1/1.0 различаются.

## Офлайн-прототип

Проверено кодирование уже сериализованных JSON-строк: общая форма ключей, таблица
повторяющихся значений, ссылки и повтор одинаковых соседних строк. Это пример
lossless-кодирования, не утверждение о лучшем формате или runtime-экономии памяти.
Декодер имеет отдельный предел раскрытия. Он не является готовым валидатором
публичного отчёта: предел байтов/глубины, атомарность потока и полный набор
недоверенных входов должны быть реализованы перед переносом.

Повторно проанализированы 76 коллекций (13970 строк) из сохранённых A0-результатов
Renode Windows/Linux. Новые запуски эмулятора и плат не выполнялись. Для каждой
коллекции совпал SHA-256 канонического JSON до/после раскрытия; исходные ERROR сохранены.
Host-контроли: 6/6 на Windows и Linux, включая серии 1000/10000 и действующие
reject_failed_checks/экспортёр DDTT. Документы: локальный CI 5/5.
Размеры ниже сравнивают JSON без отступов с JSON без отступов:

| Коллекция | Строк | Исходно, байт | Прототип, байт | Изменение |
| --- | ---: | ---: | ---: | ---: |
| checks (1000 reach) | 2002 | 151152 | 118263 | −21,8% |
| stops (1000 reach) | 1001 | 207105 | 167230 | −19,3% |
| mutations (1000 write) | 1000 | 61669 | 55764 | −9,6% |
| execution (длинная серия) | 308 | 33959 | 31220 | −8,1% |

Маленькая или неповторяющаяся коллекция может увеличиться. Ротация breakpoint-номеров
и меняющиеся actual/значения записи ограничивают экономию. RLE одинаковых timeout
не решает размер всех stop. Постоянную память при сохранении всех уникальных значений
получить сжатием нельзя — нужен перенос завершённых блоков на диск или явный отказ.

## Предлагаемая граница публичного контракта

Сохраняем различие: **compact — без потерь; summary — производное представление**.

Предложение для api.toml schema 2 (ещё не настройка модуля):

```toml
schema = 2
[journal]
representation = "compact"   # Уже реализованный MMIO A2.1.
[report]
representation = "compact"   # Новое, явное; default full.
console = "failures"         # Новое; full или failures, default full.
```

- `report.representation=full` сохраняет нынешний формат и поведение.
- `compact` сохраняет каждую запись, её порядок и значение. Введение явного
  `report_schema=2` и общего читателя result обязательно; это отдельно от records schema 2.
  Таблицы описаний/форм, ссылки и повторы относятся только к хранению. Значимые
  изменения причины остановки, поколения, ошибки и неоднозначный результат не исчезают.
- Логические checks/stops/mutations доступны общему читателю как прежние записи;
  есть последовательный обход и отдельно ограниченная материализация. Количество
  логических записей и полнота каждого потока проверяются до использования свидетельства.
- Сводка execution (вид, количество, поколения, первая/последняя операция, причины
  остановки, открытое окно) дополняет полную историю. Она не становится источником
  подтверждения DDTT и не подменяет результат wait/halt. Summary-only относится к A2.3/A3.
- `console=failures` убирает отдельные строки PASS, но сохраняет FAIL/ERROR, предупреждения,
  диагностику cleanup и итоговые счётчики. Checks продолжают исполняться и сохраняться.
  Полный JSON не дублируется в stdout; JUnit получает итог и ссылку на result вместо
  второй полной копии. В full сохраняется прежний вывод.
- Событие фиксируется в буфер только после завершения формирования. Состояния ошибок
  и рабочих буферов GDB не зависят от успешности компрессии. Резерв диагностики A1 сохраняется.
- Нельзя добавлять repr/str или чтения GDB/MMIO для сжатия. Для непереносимых объектов
  нужна явно определённая совместимость с текущим поздним default=repr; это отдельный
  пункт приёмки, а не неявное изменение check().
- Размер файла, объём runtime-буфера и предел раскрытия — отдельные бюджеты. Предлагаю
  сначала блоковое хранение завершённых событий с переносом на диск; численные пределы
  фиксировать по замерам runtime-прототипа. Потери/усечение не входят в A2.2.

Старые сторонние читатели, читающие result напрямую, не считаются совместимыми с
compact. Default full позволяет мигрировать добровольно. Нельзя обещать, что любой
старый инструмент заметит неизвестную схему: наши читатели должны отвергать её до
оценки status/пригодности, а для сторонних нужен явный экспорт полного совместимого JSON.

## Порядок реализации после принятия

1. Единый интерфейс записи завершённых событий, аудит поздних мутаций; защитить
   check/cleanup от влияния сохранения. Зафиксировать поведение нестандартных actual/expected.
2. Блоковый lossless-буфер и общий reader result; атомарный артефакт, хеши, порядок,
   пределы, повреждённые ссылки и незавершённая запись. Полный совместимый экспорт.
3. Мигрировать agent → runner → result_export/stand_loop/coverage → отчёты/JUnit.
   Сохранить исходные вердикты, число проверок и все ошибки; проверить старые result.
4. Добавить управление выводом и производные сводки, не меняя выполнения проверок.
5. Host и новые Renode Windows/Linux: 1000/10000 событий, ошибочная остановка в середине,
   перехваченный CheckFailed, незавершённое окно, ошибка записи/раскрытия и повтор после отказа.
   Измерить runtime-память и время; сохранённые A0 не заменяют эту приёмку. Платы пока не нужны.
