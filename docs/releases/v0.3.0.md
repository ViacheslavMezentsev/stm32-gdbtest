stm32-gdbtest 0.3.0 — расширенный API сценариев

stm32-gdbtest реализует DDTT: Python-сценарии управляют GDB и проверяют работающую прошивку на реальной
плате через SWD-отладчик, без тестового кода в прошивке. Подключение — закреплённый Git-подмодуль.
Python 0.3.0; API_VERSION 1; ТЗ API 0.3.7; общее ТЗ 0.69.

Главное:
- Навигация и наблюдение: `reach` с условием, `resume`, `step`, `until`, `finish`, объект `Point` (включение,
  выключение, условие, бюджет точек) и точка наблюдения `watch`.
- Вызовы и инъекции: `ret` с типизированным значением, `call` функций прошивки, `reset` и `execute` команд отладчика.
- Чтение и запись: `read`/`write` объектов, выражение в значении и таблица записей `write(rows)`, `evaluate`
  (в том числе C-строк), `memory`, `symbol`, `registers`, `frames`, `locals`/`arguments`.
- Одна `check` для всех проверок: сопоставители `within`, `near`, `one_of`, `matches`, проверка истинности
  и таблица `check(rows)`, где строковая ячейка — выражение GDB; ожидаемый отказ `refused`.
- Профиль прогона `profile`: `target.toml`, эффективный `api.toml`, файлы данных проекта, сведения о сборке,
  case, стенд и GDB. Заменяет `config`/`config_props`.
- Общий каталог сценариев для всех профилей и девять сценариев-примеров API; каталог техник TECH-001…018
  и тест стиля сценариев.
- Удалённый стенд: порт сервера вне эфемерного диапазона Linux и повтор при занятом порте.
- Миграция: `value`, `fields`, `set_value`, `force_return` работают с предупреждением и удаляются в 0.4.0;
  `config`, `config_props`, `settings`, `sources` удалены (в опубликованные теги не входили).

Итоговая проверка:
Код принят на main `782798f` (выпускной коммит меняет только документацию). Пять плат: F030R8, F401CC,
F411CE, F429ZI — ST-Link/OpenOCD, F103C8 — J-Link. Полный набор — 42 сценария F030R8 и по 44 у остальных.

Windows, прошивка собрана GCC 13.3.1, набор выполнен GDB из трёх выпусков xPack:

| Стенд | GDB 13.3.1 | GDB 14.2.1 | GDB 15.2.1 |
| --- | --- | --- | --- |
| F030R8, OpenOCD | PASS 48 | PASS 48 | PASS 48 |
| F103C8, J-Link | PASS 50 | PASS 50 | PASS 50 |
| F401CC, OpenOCD | PASS 50 | PASS 50 | PASS 50 |
| F411CE, OpenOCD | PASS 50 | PASS 50 | PASS 50 |
| F429ZI, OpenOCD | PASS 50 | PASS 50 | PASS 50 |

Число — выполненные этапы набора, включая повторы после инъекций; единственный не-PASS каждого набора —
намеренная проверка `timeout` с ожидаемым ERROR. Через Orange Pi 5: полный набор 5/5 локально на стенде,
5/5 с удалённым сервером с Windows и 5/5 из WSL2; жизненный цикл `run_hw.py` 10/10 на всех пяти платах из
пакета и в аппаратном CI GitHub. Docs, Offline и Hardware на main зелёные; HAL-фикстура F030 без платы — PASS.

Ограничения:
HAL-фикстура F030 после перевода сценариев на 0.3.0 на плате не запускалась. Повтор порта удалённого сервера
проверен host-тестом, в аппаратной кампании он не понадобился. Точка наблюдения на Cortex-M0 останавливает
ядро на одну-две инструкции позже записи. Hardware workflow проверяет жизненный цикл, а не полный набор.
Результаты MCU не являются метрологической калибровкой или процентом покрытия.

stm32-gdbtest 0.3.0 — extended scenario API

stm32-gdbtest implements DDTT: Python scenarios drive GDB and verify a running firmware on a real board through
an SWD debugger, with no test code in the firmware. Delivered as a pinned Git submodule.
Python 0.3.0; API_VERSION 1; API specification 0.3.7; general specification 0.69.

Highlights:
- Navigation and observation: `reach` with a condition, `resume`, `step`, `until`, `finish`, the `Point` object
  (enable, disable, condition, point budget) and the `watch` point.
- Calls and injections: `ret` with a typed value, `call` of firmware functions, `reset` and `execute` of debugger commands.
- Reading and writing: `read`/`write` of objects, an expression as the value and a `write(rows)` table, `evaluate`
  (C strings included), `memory`, `symbol`, `registers`, `frames`, `locals`/`arguments`.
- One `check` for every check: the matchers `within`, `near`, `one_of`, `matches`, a truth check and the
  `check(rows)` table, where a string cell is a GDB expression; an expected refusal with `refused`.
- The run `profile`: `target.toml`, the effective `api.toml`, project data files, build facts, case, stand and GDB.
  It replaces `config`/`config_props`.
- A shared scenario directory for all profiles and nine API showcase scenarios; the TECH-001…018 techniques
  catalogue and a scenario style test.
- Remote stand: the server port lies above the Linux ephemeral range, and a busy port is retried.
- Migration: `value`, `fields`, `set_value`, `force_return` work with a warning and are removed in 0.4.0;
  `config`, `config_props`, `settings`, `sources` are removed (they were not part of any published tag).

Final verification:
The code was accepted on main `782798f` (the release commit changes documentation only). Five boards: F030R8,
F401CC, F411CE, F429ZI — ST-Link/OpenOCD, F103C8 — J-Link. The full suite is 42 scenarios for F030R8 and 44 for
each of the others.

Windows, firmware built with GCC 13.3.1, the suite run with the GDB of three xPack releases:

| Stand | GDB 13.3.1 | GDB 14.2.1 | GDB 15.2.1 |
| --- | --- | --- | --- |
| F030R8, OpenOCD | PASS 48 | PASS 48 | PASS 48 |
| F103C8, J-Link | PASS 50 | PASS 50 | PASS 50 |
| F401CC, OpenOCD | PASS 50 | PASS 50 | PASS 50 |
| F411CE, OpenOCD | PASS 50 | PASS 50 | PASS 50 |
| F429ZI, OpenOCD | PASS 50 | PASS 50 | PASS 50 |

The number counts the executed suite stages, repeats after injections included; the only non-PASS of every suite
is the intended `timeout` check with its expected ERROR. Through the Orange Pi 5: full suite 5/5 locally on the
stand, 5/5 with the remote server from Windows and 5/5 from WSL2; the `run_hw.py` lifecycle 10/10 on all five
boards from packages and in the GitHub hardware CI. Docs, Offline and Hardware on main are green; the F030 HAL
fixture without a board passes.

Limitations:
The F030 HAL fixture has not run on a board after its scenarios moved to 0.3.0. The remote server port retry is
covered by a host test; the hardware campaign did not need it. A Cortex-M0 watch point halts the core one or two
instructions after the store. The Hardware workflow checks the lifecycle, not the full suite. MCU results are not
a metrological calibration or a coverage percentage.
