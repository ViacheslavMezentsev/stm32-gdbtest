stm32-gdbtest 0.1.0-rc.1 — первый кандидат выпуска

Реализация DDTT для STM32: проверки работающей прошивки на реальной плате через GDB
и SWD-отладчик сценариями на Python в репозитории проекта. Тестового кода в прошивке нет.

Версия stm32-gdbtest 0.1.0rc1, API_VERSION = 1, ТЗ ревизии 0.21. Поставка — Git-подмодуль.

Главное
- Сценарии с декоратором `@case` и Target API: reach, breakpoint, value, fields, set_value,
  force_return; CMake/CTest (stm32_gdbtest_attach), отчёты JSON/JUnit.
- GDB-серверы OpenOCD, ST-LINK GDB Server и J-Link GDB Server; Windows и Linux
  (glibc >= 2.31); сервер рядом с runner или на хосте стенда по SSH (только ключи,
  удалённая блокировка, сигнал присутствия).
- Проверка и запись образа по секциям ELF или полным образом с CRC-32 на ПК;
  DEV_ID и размер Flash в режимах warn/strict.
- Проверки без оборудования: build manifest, ELF/HAL-контракты, run --prepare-only,
  трассировка требований; CI на GitHub Actions в закреплённом Docker-образе.
- Пакеты подготовленного запуска (pack, run --package), workflow Hardware на
  self-hosted раннере, run_hw.py --repeat для прогонов в цикле.
- Окружение Linux-стенда без root (tools/linux_stand.py), команда doctor.
- Общие сценарии для нескольких вариантов MCU одной прошивки (PROFILE),
  переменные окружения в путях стенда.

stm32-gdbtest 0.1.0-rc.1 — first release candidate

A DDTT implementation for STM32: checks of running firmware on a real board through GDB
and an SWD debugger, written as Python scenarios in the project repository. No test code
in the firmware.

package version 0.1.0rc1, API_VERSION = 1, specification revision 0.21. Delivered as a
Git submodule.

Highlights
- Scenarios with the `@case` decorator and the Target API: reach, breakpoint, value, fields, set_value,
  force_return; CMake/CTest (stm32_gdbtest_attach), JSON/JUnit reports.
- OpenOCD, ST-LINK GDB Server and J-Link GDB Server; Windows and Linux (glibc >= 2.31);
  the server next to the runner or on the stand host over SSH (keys only, remote lock,
  heartbeat).
- Image verification and programming by ELF sections or as a full image with CRC-32
  on the PC; DEV_ID and Flash size in warn/strict modes.
- Checks without hardware: build manifest, ELF/HAL contracts, run --prepare-only,
  requirement traceability; CI on GitHub Actions in a pinned Docker image.
- Prepared run packages (pack, run --package), the Hardware workflow on a self-hosted
  runner, run_hw.py --repeat for soak runs.
- Rootless Linux stand environment (tools/linux_stand.py), the doctor command.
- Shared scenarios for several MCU variants of one firmware (PROFILE), environment
  variables in stand paths.

Final check (commit 2143665, the tagged code is identical)
- CI: Docs, Offline — green.
- Windows, run_hw.py: F030R8 / J-Link STLink, F103C8 / J-Link CE, F411CE / OpenOCD,
  F411CE / ST-LINK GDB Server — 4 x 10/10.
- Windows -> Orange Pi 5 over SSH: F030R8, F103C8, F411CE — 3 x 10/10.
- Hardware workflow on the Orange Pi 5 runner — 3 x 10/10.
- STM32G474 consumer project (Arduino Core STM32, OpenOCD on Orange Pi 5) — host 5/5,
  on the board 4/4.

Limits
- J-Link GDB Server only for STM32F103C8T6 and STM32F030R8T6; no ST-LINK GDB Server on
  Linux aarch64; H503 is not supported.
- Not verified on hardware: local Linux x86_64 with a debugger, WSL2 with usbipd-win.
- No power or instrument control, no pip package or separate executable yet.
