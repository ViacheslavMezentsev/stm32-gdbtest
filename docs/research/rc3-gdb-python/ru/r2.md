# rc3 R2: навигация, вызовы и распознавание остановок

[Документация](index.md) · [English](../en/r2.md)

02.10.2026. Эксперименты продолжаются в `codex/rc3-api-r1`, после R1-коммита
`0d0db6a`. **Перенос в ядро запрещён до явного утверждения владельца.**
Ни публичный API, ни ТЗ0.58, ни версия пакета не изменены.
Код находится только в [consumer](../../../../tests/api-experiments/profile/tests/board/test_navigation.py).

## Подтверждённые результаты

Та же WeAct BlackPill F411CE, STM32F411CEU6, ST-Link V2J43M28, SWD1МГц,
OpenOCD0.12.0, Windows. Один ELF GCC13.3.1 (`-Og -g3 -fno-lto`, soft-float),
тот же, что в [R1](r1.md):
`38375f4f7d58cdb637c69ae099b47c03061230a9df4eecd530475cbc96a2fd19`.

| Интерфейс OpenOCD | Сценарии | GDB14.2/Python3.11 | GDB16.3/Python3.13 |
| --- | --- | --- | --- |
| `interface/stlink.cfg`, HLA | CONDITION, HITCOUNT, RETURN, FINISH, STEP, CALL, ASM | 28/28 PASS | 28/28 PASS |
| `interface/stlink.cfg`, HLA | WATCH | FAIL: нет идентификатора watchpoint | FAIL: то же ограничение |
| `interface/stlink-dap.cfg`, `dapdirect_swd` | WATCH: write/read/access | 4/4 PASS | 4/4 PASS |

Это **56/56** навигационных запусков и **8/8** watchpoint-запусков на разных
вариантах интерфейса. Каждый успешный набор — первый проход плюс три заранее
заданных повтора. Это не заявление, что все восемь сценариев прошли на каждом
интерфейсе. Запуск WATCH проверяет три типа доступа последовательно.

После каждой серии — restore ELF
`1ff37ae10a007401de5e0eaf826764f60a2849c8b7821c123f12caa28c2e79c3`,
HW_BOOT/HW_GPIO PASS, reset_run. Проверка GPIO наблюдает регистр PC13, не свет.
Платы F030/F103/F401, другие серверы, Linux HW и другие варианты ABI не проверялись.

## Техники, подтверждённые на этом стенде

| Техника | Опыт и полезное поведение |
| --- | --- |
| Остановка на выбранном входе | Временный hardware BP с `sequence == 3 && input->mode == MODE_ACTIVE`; после остановки условие проверяется снова, точка удалена. Можно выбирать состояние без firmware hook |
| Пропуск прогрева | `ignore_count=2`: остановка на третьем естественном вызове, `sequence=2`, hit_count=3. Удобно отделять стартовый режим от установившегося |
| Отпечаток места остановки | Текущая функция + вызывающий на глубине1/2 + аргументы. `$_caller_is("process_sample")` реально доступен на обеих версиях и совпал с обходом кадров; неверное имя/глубина отвергнуты |
| C-контекст внутри Python | `sequence + (uint32_t) input->mode`, `sizeof(input->bytes)` вычисляются в кадре по выражениям исходника; `$result` связывает Python-проверку с GDB. Это доверенный evaluator, не безопасное read-only выражение |
| Подмена результата естественного вызова | `return 100` из sum_bytes; продолжение вызывающего кода даёт checksum по независимой Python-формуле с100 вместо773. Можно исследовать ветви обработки кодов результата без изменения прошивки |
| Наблюдение настоящего результата | FinishBreakpoint завершает естественный sum_bytes, `return_value=773`, выбран process_sample; затем проверено следствие в checksum. Это отличается от принудительного return |
| Навигация по уровню абстракции | stepi изменяет PC, bounded step входит в sum_bytes, CLI finish возвращает в caller, next проходит вызов без выбора дочернего кадра |
| Проверка функции как вычислителя | Прямой `sum_bytes(sample.bytes, 8, 5)` даёт775; PC/SP и входная RAM совпадают до/после. Это доказательство только для этой чистой uint32-функции в thread mode |
| Поиск места публикации данных | На native DAP write-watchpoint cycles останавливает первое увеличение до1, read/access-watchpoints массива — sum_bytes. Получены номера точек и причины stop |
| Распознавание тупикового обработчика | jump в существующий Default_Handler; инструкция b.n на собственный адрес, байты0xE7FE и три stepi с неизменным PC. После намеренного изменения потока обязателен reset до main |

Для распознавания перехода адрес сравнивается **численно**, а не через равенство
строк `hex(pc)`. [Чистый helper](../../../../tests/api-experiments/lab/navigation.py)
проверяет безусловную мнемонику b/b.n/b.w и числовую цель. Host-тесты отвергают
условный bne, bl, другую цель, отсутствие адреса и неправильную глубину caller.
Проверка0xE7FE относится только к конкретному 16-битному Thumb b-to-self; это
не обобщённый детектор бесконечных циклов или зависания всей системы.

Полезная композиция для следующих опытов: выбрать вызов по аргументу/стеку →
снять входы → подменить код возврата → продолжить до публикации результата →
сравнить с независимым оракулом. Здесь проверены составляющие, но не универсальный
диспетчер перехватов или произвольная подмена управления.

## Почему watchpoint не прошёл через HLA

В первой серии GDB14 успешно выполнил пять сценариев, затем WATCH дал FAIL.
OpenOCD зарегистрировал DWT0 write-watchpoint на cycles, но stop reply оказался
`T05` без `watch:<address>`. Python-событие не содержало нужного номера BP.
Отдельный запуск GDB16 воспроизвёл это. Оба исходных FAIL и успешные restore сохранены.
Подменять проверку «номер ожидаемой точки» на «процесс просто остановился» нельзя.

Контролируемое сравнение изменило только драйвер ST-Link в OpenOCD:
`stlink-dap.cfg` и явно `transport select dapdirect_swd`. На том же MCU, отладчике,
скорости и ELF сервер вернул `T05watch:...`, `T05rwatch:...`, `T05awatch:...`;
GDB сформировал ожидаемые breakpoint events. Журналы содержат Z2/Z3/Z4.

Флаг `--native-stlink` существует **только у экспериментального runner**.
[Локальный transform](../../../../tests/api-experiments/lab/openocd_native.py) временно
заменяет построение команды в текущем Python-процессе, сохраняя serial/target/скорость;
ни ядро, ни TOML-схема, ни установленный OpenOCD не менялись. Host-тест проверяет
сохранение аргументов и отказ при неожиданной исходной команде. Для штатного
backend поддержка native DAP пока не заявляется.

## Внутренние точки next/finish/call

Перед опытом задано `monitor gdb_breakpoint_override hard`, включён auto-hw и
выключен displaced stepping. Диагностика GDB/OpenOCD включается после загрузки ELF.
Для успешной серии навигации сводка сохраняет число Z0/Z1 и сообщений добавления
hardware/software BP. В измеряемой части **нет Z0 и добавленных software BP**;
FINISH/STEP/CALL используют Z1 и подтверждённые аппаратные установки.
Это более сильное свидетельство, чем просто неизменившаяся Flash.

Основание настройки: [GDB auto-hw](https://www.sourceware.org/gdb/current/onlinedocs/gdb.html/Set-Breaks.html)
выбирает аппаратные точки для read-only адресов; [OpenOCD override](https://openocd.org/doc-release/html/Server-Configuration.html)
принудительно задаёт hardware-тип. Такой протокол нельзя автоматически переносить
на другой сервер. Исчерпание FPB должно оставаться ошибкой, не разрешением software fallback.

## Воспроизведение и свидетельства

[Обезличенная сводка](../results/rc3-r2-results.json) содержит stages, версии,
хэши источников, события, результаты и счётчики протокола. Полные журналы —
`tests/api-experiments/build/evidence/`:

- `20261001T235131.910896Z`: исходная серия HLA, WATCH FAIL на GDB14;
- `20261001T235327.668203Z`: отдельный WATCH FAIL на GDB16;
- `20261001T235455.208709Z`: семь навигационных сценариев,56/56;
- `20261001T235712.923348Z`: native DAP WATCH,8/8.

Это UTC-имена; местная дата02.10.2026. Отчёты первых серий не перезаписывались.
Runner помечает общий протокол ERROR при неожиданном FAIL сценария — исходный
result.json остаётся FAIL. Во всех четырёх summary `restored=true`.

К команде [R1](r1.md#воспроизведение) добавить `--suite r2`.
Для навигации перечислить семь `--test HW_R2_...` из таблицы, исключив WATCH;
для сравнения данных — `--test HW_R2_WATCH --native-stlink`. `--execute` по-прежнему
нужен для HW, без него только prepare. Один GDB задаётся одним `--gdb`; второй
добавляется повторением аргумента. Смена физического стенда согласуется отдельно.

Windows и Linux build/host/prepare: **16/16 PASS** (14 prepare, traceability,
17 host-регрессий в одном CTest). Новый C-код не добавлялся. Старый общий format
FAIL из R1 не исправлялся и не превращён в PASS.

## Что ещё не доказано

Same-value store: различие watch/awatch пока не проверено; также не проверены DMA,
ширина/выравнивание/исчерпание DWT, ошибки C-условий, рекурсия, IRQ и RTOS.
Нет матрицы void/float/struct/64-bit return, out_of_scope и вызовов с побочными
эффектами. Прямой вызов без сбоев не доказывает надёжность зависшего dummy frame.
Не проверялись nexti/until/advance, произвольный безопасный jump внутри C-функции,
макросы новых consumer и live-code patching. Все GDB API вызваны из главного потока.

Следующие эксперименты: same-value writes и границы watchpoints; фильтрация вызовов
по стеку/аргументам; ветви возврата и выходные буферы; разные ABI и прерванный call.
Результаты расширяют экспериментальный набор, **не дают разрешения на перенос в ядро**.
