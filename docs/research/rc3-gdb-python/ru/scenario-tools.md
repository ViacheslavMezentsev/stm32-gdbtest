# Инструменты сценариев: API, техники, шаблоны

[Документация](index.md) · [English](../en/scenario-tools.md)

Проект классификации по [R1–R18](summary.md), 02.10.2026. Названия кандидатов
ниже описывают смысл, а не утверждённые имена новых методов.
Действующий [API](../../../ru/API.md) остаётся прежним.

## Три слоя

| Слой | Что входит | Пример и ответственность |
| --- | --- | --- |
| API | Одна операция с явными входами, результатом, эффектами и отказами | Прочитать значение, установить точку, получить снимок; ядро отвечает за контракт и владение ресурсом |
| Техника | Воспроизводимая композиция операций с предусловиями, проверками и очисткой | Дождаться естественного входа, заменить out-buffer/status, проверить caller и следующий естественный вызов |
| Шаблон сценария | Организация нескольких техник вокруг проверяемого поведения | Подать последовательность отказов/успеха и проверить сохранение принятого состояния |

«Парадигма» — более широкий подход (например, DDTT); для этого каталога точнее
«шаблон сценария». Не каждый шаблон должен стать методом ядра. Техники могут
жить в библиотеке потребителя, шаблоны — в примерах с явными ожиданиями приложения.
Сначала отделяем механизм от политики: работа с кадром универсальнее правила
«эта функция должна вызываться только из такого обработчика».

## Области применения

| Область | Проверенные инструменты | Техники → шаблоны | Ограничение |
| --- | --- | --- | --- |
| C: выражения, структуры, массивы, макросы | parse/eval, sizeof, поля/индексы, типизированные снимки (R1–R5) | Снять аргументы и выходы → проверка контракта функции | value текущего API возвращает int; произвольное C-выражение может иметь побочные эффекты |
| C: циклы, ветвления, прогресс | Условия точек, счётчик, until/advance, forced return (R2–R4, R16) | Ограниченное ожидание; подмена status для выбора ветви → проверка обработки ошибок | Число итераций не wall-clock timeout; принудительный выход пропускает тело |
| Функции, стек, рекурсия | finish/call, caller walk, кадры, scalar ABI (R5–R6, R9, R17) | Выбор конкретного вызова, наблюдение естественного результата → контракт caller/callee | call исполняет прошивку и меняет состояние; dummy call отличается от естественного вызова |
| C++: методы и объекты | this, const-перегрузки, полная сигнатура, агрегаты/HFA (R18) | Выбрать перегрузку и проверить объект/приёмник → контракт метода | Это не покрытие классов вообще: virtual/lifetime/exceptions не проверены |
| Оптимизированный код | INLINE_FRAME, locations, scope, optimized_out (R15–R16) | Сопоставить символы, инструкции и конечный sink → проверка результата независимо от доступности local | Строка/имя/PC по отдельности неоднозначны |
| Ассемблер и ABI | disassemble, stepi/nexti, регистры, стековые аргументы (R2, R4, R16–R18) | Распознать self-branch; проверить границу BL/возврата → машинный контракт | Синтаксис asm и ABI зависят от сборки; native stepping regression остаётся открытой |
| RAM и доступы CPU | Ограниченный patch/restore, watch/rwatch/awatch, разбиение диапазона (R1, R3–R4, R7) | Проверить доступ вместо изменения; подать входные байты → проверка обработки данных | Restore RAM не отменяет уже совершённые внешние эффекты |
| MCU: IRQ, DMA, таймеры, Sleep | Регистры/флаги, IRQ sentinel, hardware frame, WFI (R10–R13) | Наблюдать завершение DMA до CPU-чтения; отделить wakeup от ticks → контракт обмена/пробуждения | Нужны профиль и обычная прошивка; нет универсального снимка всей периферии |
| Управление экспериментом | Stop identity, ownership, FPB/DWT budget, evidence, timeout/recovery (R1, R7–R10, R14) | Контрольная остановка, очистка и естественный контроль → воспроизводимый ограниченный сценарий | Внешний kill требует host recovery; надёжность всех сочетаний ещё не доказана |

## Кандидаты и их место

Метки: **есть** — публичный API; **кандидат** — предлагаемый примитив;
**техника** — композиция; **шаблон** — цель сценария. GDB-примитив сам по себе
не становится API stm32_gdbtest только потому, что доступен через Python.

| Средство | Категория и рекомендуемое размещение | Основание |
| --- | --- | --- |
| check, value, fields, reach, breakpoint, set_value, force_return, clear | Есть; сохранять задокументированный контракт | Текущий API; новые возможности не должны молча менять старые результаты |
| Типизированное чтение и снимок контекста/остановки | Кандидат API наблюдения | R1, R11, R15–R18; [проект контекста](execution-context.md) |
| Разрешение location, owned breakpoint/watchpoint, ресурсный бюджет | Кандидаты API управления ресурсами | R2, R7–R8, R15, R18; pending/multiple locations и отказ установки должны быть явными |
| Продолжение до события, шаг инструкции, естественный finish | Кандидаты API исполнения с результатом остановки | R2, R9, R16; не выдавать ранний выход кадра/чужую точку за достижение цели |
| Вызов функции и типизированный результат | Условный кандидат API вмешательства | R5, R9–R10, R17–R18; нужны ABI/capability и состояния interrupted/fault/timeout |
| Ограниченное чтение RAM, запись/восстановление | Примитивы — кандидаты API; patch/restore — техника | R1/R4; не распространять rollback на MMIO и произвольное исполнение |
| Caller predicate, выбор рекурсивного кадра, self-branch | Техники поверх кадров/инструкций; возможные библиотечные helpers | R2/R6; ограничение глубины, вид кадра, архитектура |
| Счётчик прогресса, range split, резерв finish | Техники поверх выражений и ресурсов | R3/R7/R8; формула переполнения, покрытие диапазона, физические слоты |
| Out-buffer + status; конечная последовательность перехватов | Техники; шаблоны «ветви ошибок» и «сохранить принятое состояние» | R4/R14; потребитель задаёт данные, порядок и ожидаемые sinks |
| Hidden-sret запись по закреплённому ELF | Узкая ABI-техника, не общий API возврата структуры | R5/R18; known FAIL не исправлять скрытой догадкой о раскладке |
| IRQ/DMA/WFI диагностика | Техники профиля; шаблоны периферийных контрактов | R11–R13; обычная прошивка, MCU-регистры и контрольные точки |
| Команды GDB, macro/define, Python if/else | Низкоуровневые средства композиции; helper в consumer | R3; C-выражения берут значения из прошивки, логика сценария остаётся Python/GDB |
| Fault sidecar, восстановление после timeout | Техника orchestration на host, не синхронный GDB helper | R10; отчёт об исходном ERROR сохраняется |

## Свойства будущего API и критерии приёмки

| Свойство | Проверяемое правило |
| --- | --- |
| Простота | Одна операция — один смысл; обычный сценарий не требует raw GDB, внутренних полей Target или знания формата CLI-вывода |
| Преемственность | Старый сценарий работает на новой версии в прежней поддержанной конфигурации; обязательная регрессия старого API. Новая функция на старой версии явно недоступна, не имитируется |
| Однозначность | Natural finish, forced return и direct call различны; результат содержит достигнутую причину/место, а не только boolean; несколько locations не выбираются случайно |
| Параметризуемость | Явные location/frame/condition, лимиты времени/шагов/байт/глубины, политика неожиданных остановок; значения валидируются до вмешательства, где возможно |
| Типизация и доступность | Тип/ширина/знаковость сохраняются; missing, optimized_out и unreadable не превращаются в 0/False |
| Композиционность | Результат одной операции пригоден для техники; управление ресурсом отделено от ожиданий приложения; нет неявного continue |
| Ограниченность | Каждое ожидание имеет предел; бюджеты учитывают физические locations и служебные точки; внешний watchdog остаётся последней границей |
| Владение и восстановление | Удаляются только собственные ресурсы; настройки восстанавливаются; исходная и cleanup-ошибка сохраняются обе. Не обещать транзакционный откат исполнения |
| Наблюдаемость | Снимок привязан к остановке/образу; отчёт различает ожидаемый отказ, FAIL и ERROR и сохраняет before/after для вмешательства |
| Честная переносимость | Поддержка определяется операцией, MCU, backend, GDB и ABI/сборкой; неизвестная комбинация не получает статус verified по одному номеру версии |
| Расширяемость | Аддитивные необязательные поля и версия схемы; изменение смысла требует миграции. MCU-политика остаётся у потребителя; raw GDB доступ документируется как отдельный выход за гарантии оболочки |
| Поток и жизненный цикл | Только главный поток GDB; живые handles не переходят через resume/reset; immutable evidence можно хранить и читать позже |

Предлагаемый порядок обсуждения: наблюдение/контекст и причины остановки →
ресурсы и навигация → вмешательство с явными ABI-границами → библиотека техник
и примеры шаблонов. Реализация начинается только после утверждения объёма;
непроверенные сочетания остаются в [долге](technical-debt.md).
