# rc3 R6: контекст вызова и рекурсивные кадры

[Документация](index.md) · [English](../en/r6.md)

02.10.2026. Продолжение [R5](r5.md) после `191244d` в
`codex/rc3-api-r1`. Только consumer; публичный API, ТЗ и версия пакета прежние.
Перенос в ядро требует отдельного утверждения владельца.

## Задача и техники

Два обычных обработчика вызывают одну рекурсивную функцию `walk_route(depth,seed)`.
На каждом уровне seed увеличивается на10, при возврате прибавляется depth.
`route_alpha` начинает с(2,1), затем прибавляет100; `route_beta` — с(3,2),
затем прибавляет200. Обычные результаты124 и238 вычисляются независимо в сценарии.
Новых hooks нет; код выполняется в основном цикле приложения.

| Опыт | Подтверждаемое поведение |
| --- | --- |
| CONTEXT | Python `Breakpoint.stop()` читает кадры и аргументы; выбирает depth1 только при наличии `route_beta` на глубине3. В alpha при depth1 seed11, в beta seed22. `$_caller_is` подтверждает выбранный стек; неверная глубина отвергается |
| FINISH | На beta/depth2 `FinishBreakpoint` переживает вложенные вызовы с повторяющимися адресами возврата и получает35. Затем проверяются имя, depth3, seed2, PC и SP вызывающего кадра |
| RETURN | Из beta/depth1 выполняется `return 100`; оставшиеся уровни дают305. Alpha остаётся124, следующий естественный цикл снова даёт beta238 |

[Сценарии](../../../../tests/api-experiments/profile/tests/board/test_recursion.py),
[обычные функции](../../../../tests/api-experiments/src/routes.c).

## Исправленное предположение

Первая версия сочетала `bp.condition = 'depth == 1'` и Python `stop()`, ожидая
только два вызова callback. В действительности callback увидел шесть входов с
seed1,11,21,2,12,22. Нужный контекст был выбран, но проверка числа посещений дала
FAIL на GDB14. Исходный результат сохранён, серия остановлена, прошивка восстановлена.
Это ошибка предположения сценария, а не установленный дефект GDB.

Теперь все условия отбора находятся внутри одного Python-предиката. Проверяется
полная последовательность depth2,1,0,3,2,1, пять отказов и один выбор. Отдельно
FINISH/RETURN используют только CLI-условие с `$_caller_is`, без Python callback.
Не полагаться на то, что выражение condition предварительно отфильтрует все
вызовы пользовательского `stop()`; для этого сочетания порядок отдельно не обобщается.

## Практическое применение и ограничения

- Можно перехватывать общую функцию только из нужного обработчика, отделять
  рекурсивные уровни и подавать результат выбранному вызывающему коду.
- Имя функции или один адрес возврата не идентифицируют рекурсивный кадр.
  В опыте использованы ancestry, аргументы и PC/SP; FinishBreakpoint проверен
  по событию собственной точки и независимому значению35.
- В callback только чтение GDB и сбор Python-данных: нет continue, удаления точек,
  смены кадра или записи памяти. Изменения выполняются после возврата управления сценарию.
- Отказ Python-предиката не делает проверку невидимой для MCU: отладочные остановки
  влияют на время исполнения. Опыт не измеряет real-time характеристики.
- Проверены небольшая глубина, обычный стек C и GCC13 `-Og -fno-lto`.
  IRQ, RTOS, inline/tail-call, повреждённый стек и исключения callback не проверялись.

## Воспроизведение и результаты

F411CE/ST-Link/OpenOCD0.12.0 HLA, Windows; GDB14 и GDB16. ELF GCC13 soft-float:
`7842e8ee9471ec777001a1fcc5be6e4a9625af3883eee7c8a1b15ebbcd6c5552`.
Частота SWD не считается постоянной: reset-журналы могут переопределять настройку
стенда, как отмечено в R5.

**Результат исправленной R6:24/24 HW PASS**, по12 на каждой версии GDB.
Первый FAIL относится к прежнему предположению callback и не заменён повтором.
Windows/Linux build/host/prepare:37/37 PASS (35 prepare, traceability и20 host-тестов
одной группой); формат затронутого C PASS. Старый общий format FAIL остаётся.

Выбранная регрессия на новом ELF/GDB16/HLA: восемь положительных ABI-сценариев R5,
32/32 PASS. Отдельный запуск старого SRET дал ожидаемый FAIL на проверке SHA256
до записи возвратного буфера; guard не отключался и pin не менялся. Это не
регрессия поддерживаемого SRET: новый ELF не входит в область его применимости.
Все четыре серии завершили restore HW_BOOT/HW_GPIO PASS. Полная R1–R5,
Linux HW, native DAP для R6 и другие платы не проверялись.

К [команде R1](r1.md#воспроизведение) добавить `--suite r6`.
Три сценария × первый проход и три заданных повтора × два GDB.
Без `--execute` — только prepare. [Обезличенный протокол](../results/rc3-r6-results.json)
сохраняет первый FAIL, исправленную серию, выбранную регрессию и восстановление.
Raw-журналы остаются в `tests/api-experiments/build/evidence/`.

Новый ELF намеренно не соответствует старому SHA256 в R5 SRET. Этот прототип
нельзя автоматически перепривязывать: сначала нужна новая проверка дизассемблера
и размещения возвратного буфера. Исторический R5 PASS относится к прежнему ELF.
