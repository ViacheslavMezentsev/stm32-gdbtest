# Эволюция API: проект соглашений и порядка спецификации

[Документация](index.md) · [English](../en/api-evolution.md)

02.10.2026. **Предложение для согласования**, не новая нормативная редакция ТЗ.
Текущий цикл исследования R1–R18 завершён с [техническим долгом](technical-debt.md).
Далее обсуждаются правила и небольшое расширение; HW остаётся на паузе.
Состав кандидатов — в [api-proposal](api-proposal.md). Этот документ определяет,
как предлагается принимать и проверять изменения, а не утверждает эти кандидаты.

## 1. Разделение документов

Рекомендация — отдельное подчинённое ТЗ Target API с независимыми ревизиями,
но единым владельцем каждого требования. Не создавать два конкурирующих ТЗ.

| Документ | Ответственность |
| --- | --- |
| [Общее ТЗ](../../../TECHNICAL_SPECIFICATION.md) | Система: host/agent lifecycle, backend, стенд, таймаут процесса, отчёты PASS/FAIL/ERROR, CMake/CLI, интеграция и системная приёмка |
| Будущее `docs/TECHNICAL_SPECIFICATION_API.md` | Подсистема Target API: публичные операции и модели данных, предусловия/постусловия, ошибки, ресурсы, совместимость и проверка контрактов |
| Будущие `docs/ru/API_EVOLUTION.md` и EN-пара | Практические соглашения и процесс изменения; ссылка на нормативные пункты ТЗ без второй копии требований |
| [Текущий API](../../../ru/API.md) и EN-пара | Руководство по реализованным и выпущенным операциям, примеры и миграция |
| Исследование и предложение API | Свидетельства, альтернативы и ограничения; не источник утверждённых контрактов |

Имена будущих файлов — предложение, этих документов ещё нет. Пока соглашения
обсуждаются здесь. Оба ТЗ вести только на русском по
[embedded-tech-spec](https://github.com/ViacheslavMezentsev/demo-stm32-skills/tree/main/embedded-tech-spec),
как требует [maintenance](../../../ru/maintenance.md). Их ревизии независимы;
редакция документа, API_VERSION, схема данных и версия пакета — разные величины.

В общем ТЗ сейчас есть §5.10. Не копировать его целиком в новое ТЗ: boot/import/
итог сценария относятся к системе, публичные контракты — к API. При разделении
подготовить таблицу «старый пункт → документ-владелец → новый пункт/ссылка».
Старые номера сохранить как делегирующие ссылки либо явно исключённые пункты с
историей, без переиспользования. Системный документ ссылается на API-контракт;
ТЗ API ссылается на системные ограничения. Спорный пункт имеет одного владельца.

Ссылки из кода/тестов квалифицировать документом: например,
`ТЗ API <пункт>` / `ТЗ проекта <пункт>`; TC-01 в разных документах не один тест-кейс.
В междокументной матрице использовать `(документ, пункт/TC, ревизия)`, а не голый
номер. Поддержку таких ссылок текущим check_spec нельзя считать доказанной:
CI сейчас проверяет только общее ТЗ. До принятия второго ТЗ добавить strict-проверку
обоих документов и отдельную проверку перекрёстных ссылок/покрытия.

## 2. Предлагаемые соглашения

| ID | Правило для согласования | Как оценивать соблюдение |
| --- | --- | --- |
| E1 | Один примитив — одно действие; чтение, продолжение и вмешательство различимы по контракту | Для каждого метода явно указаны эффекты и запрещённые неявные действия |
| E2 | Имена Python в snake_case; необязательные политики/лимиты — keyword-only; единицы отражены в имени, например timeout_s | Проверка публичных сигнатур, типов, единиц, диапазонов и defaults |
| E3 | Старый сценарий сохраняет поведение на новой версии в ранее поддержанной конфигурации; никаких скрытых смен типов/ошибок/defaults | Регрессия старого API и матрица изменений: additive / behavioral / breaking |
| E4 | Новые функции не объявляются доступными на старых версиях; deprecated и removal разделены | Явная диагностика отсутствия возможности, план миграции и согласованный срок удаления; срок не придумывать автоматически |
| E5 | Результаты типизированы, материализованы и имеют provenance/availability; снимок не является живым handle | Проверки сериализации, неизменяемости, границ, lifetime и недоступных значений |
| E6 | Ошибочные входы, неподдержанная конфигурация и несовпадение ожиданий — разные случаи | Таблица исходов, типы ошибок и отображение в системные FAIL/ERROR |
| E7 | Нет скрытого resume, software fallback, выбора первой location или retry после call | Негативные проверки и наблюдение фактических событий/эффектов |
| E8 | Каждый ресурс имеет владельца, предел и порядок cleanup; каждый wait ограничен бюджетом case | Исчерпание, чужие ресурсы, interruption и cleanup failure; primary error не теряется |
| E9 | GDB API вызывается только из главного потока; snapshot и frame reference имеют разные сроки жизни | Host-модель invalidation плюс интеграционные проверки GDB; MCU-контракт отдельно |
| E10 | Поддержка задаётся комбинацией операции/сборки/ABI/MCU/backend/GDB, не одной версией | Раздельные статусы mechanism available, verified, known failure, untested и ссылки на доказательства |
| E11 | Каждый новый контракт получает пункт, положительные/отказные TC и матрицу прослеживаемости до реализации | Нет нормативного требования без метода A/T/I/D и критерия приёмки |
| E12 | Сначала утверждается контракт, затем отдельно разрешается реализация; доказательства старого прототипа не принимают автоматически новый код | Реализация и итоговые проверки привязаны к коммиту и заявленному набору конфигураций |

Не переопределять [политику версий](../../../ru/VERSIONING.md) молча. Сейчас она
относит новые функции до 1.0 к 0.2.0, а исследование называлось rc3. До выбора
релизной цели нужно явно решить, уточняем ли политику для кандидатов ещё не
выпущенного 0.1.0 или планируем расширение на 0.2.0. Название исследования не
является разрешением сменить это правило. API_VERSION также не обязан совпадать
с номером пакета или ревизией любого из ТЗ.

## 3. Паспорт каждой операции

До реализации заполнять один паспорт: назначение и исключения из области;
сигнатура/типы/defaults/единицы; допустимое состояние MCU/GDB; входные ограничения;
успешный результат; все альтернативные исходы; эффекты и инвалидируемые объекты;
владение/cleanup; время/память/слоты; совместимость; ссылки на пункты ТЗ и TC.
Обязательные общие модели (Context, StackSnapshot, FrameRef, StopResult) описывать
один раз, а из операций ссылаться на них. Не начинать с большого списка методов.

| Случай | Ожидаемое поведение операции | Оценка сценария/проверки |
| --- | --- | --- |
| Корректный вход, поддержанная конфигурация | Заявленный результат, точная причина остановки и только заявленные эффекты | PASS после независимой проверки результата, не по факту отсутствия exception |
| Неверный тип/диапазон/устаревшая ссылка | Заданная диагностическая ошибка до вмешательства, где это возможно | Негативный host-тест проходит, если проверил отказ и отсутствие нежелательных эффектов; необработанная ошибка сценария остаётся ERROR |
| Значение optimized_out/out_of_scope/unreadable | Заданный availability либо ошибка, без подстановки нуля | Совпадение с ожидаемым статусом; недоступность не маскируется успешным значением |
| Неполный stack/unexpected stop | Явная неполнота/interrupted, а не ложное достижение цели/отсутствие caller | По согласованному контракту результата и проверке ожидания сценария |
| Проверяемое значение не равно ожидаемому | Корректно полученный результат, check фиксирует несовпадение | FAIL, а не инфраструктурная ERROR |
| Fault/потеря связи/внешний timeout | Диагностика ERROR; возможен частичный отчёт, возвращаемое значение метода не гарантируется | Проверка fault/recovery отдельна от исходного ERROR; его статус не переписывается |
| Ошибка cleanup после исходной ошибки | Сохраняются обе причины и фактически восстановленные/невосстановленные ресурсы | Нельзя получить PASS только потому, что исходная ошибка была ожидаемой |

Пример малого изменения: сначала `frames`/StackSnapshot и caller-helpers. Это ещё
не выбранный состав релиза, но у него ограниченные эффекты и опора R1/R2/R6/R15.
Первый набор TC: порядок/точная глубина; ближайший предок; конец стека;
depth_limit/unwind_error; недоступное имя; recursive/inline; неизменяемость;
устаревший FrameRef; отсутствие изменения selected frame и неявного continue.
Нужны независимые ожидаемые значения и отрицательные контроли, а не тесты,
повторяющие алгоритм реализации. Host PASS не заменяет GDB/HW доказательство.

## 4. Порядок перехода

1. Завершить текущий цикл исследования с сохранением отчётов и незакрытого долга.
2. Согласовать E1–E12, границы документов и политику версий; решения записать явно.
3. Подготовить ТЗ API по шаблону навыка: первая ревизия 1.0 «черновик для согласования»;
   отдельно baseline существующего API и предлагаемые расширения/открытые вопросы.
   Структура: область, модели/жизненный цикл, операции, ошибки, интерфейсы,
   нефункциональные ограничения, эволюция, верификация, матрица, вопросы, приложения.
4. В согласованном переходе обновить общее ТЗ следующей ревизией (сейчас 0.58):
   делегирование API, междокументные ссылки, правила и системная приёмка. Оба
   документа и CI согласовать одним набором изменений, без периода двух истин.
5. Выбрать одно небольшое расширение и заполнить его паспорта/TC; утвердить контракт.
6. После отдельного разрешения реализовать, выполнить host/GDB проверки и только
   после отдельного возобновления HW — требуемую аппаратную приёмку. До неё не
   объявлять непроверенные аппаратные гарантии поддержанными.

Текущий результат — завершение исследовательского цикла и этот проект соглашений.
Следующий предмет обсуждения: **разделение двух ТЗ, E1–E12 и выбор версии**.
Сами нормативные документы сейчас не переписаны: варианты ещё обсуждаются,
действующие требования §5.10 остаются источником текущего контракта.
