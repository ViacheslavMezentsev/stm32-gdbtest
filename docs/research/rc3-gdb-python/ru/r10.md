# rc3 R10: fault и timeout незавершённого вызова

[Документация](index.md) · [English](../en/r10.md)

02.10.2026, после `67066e2`, ветка `codex/rc3-api-r1`. Только consumer-сценарии,
проверка доказательств на host и выбор серии runner. Ядро, API, ТЗ и прошивка
прежние. Перенос в ядро отдельно утверждает владелец.

## Что выполнено

F411CE/ST-Link/OpenOCD0.12.0 HLA, Windows, GDB14/16. Вызовы из остановленного
thread mode; четыре fault guard включены. [Сценарии](../../../../tests/api-experiments/profile/tests/board/test_call_failures.py)
имеют намеренные отрицательные исходы: запускать их через `run_matrix.py --suite r10`,
а не считать ERROR отдельного сценария успешным обычным CTest.

| Сценарий | Доказательство | Завершение |
| --- | --- | --- |
| FAULT | CPU выполняет sum_bytes с указателем0x20020000 — первым байтом за128KiB SRAM этого профиля. Guard HardFault, exception=3, CFSR=0x8200, HFSR=0x40000000, BFAR=0x20020000 и один DUMMY_FRAME | Исходное исключение GDB повторно выбрасывается; ERROR, teardown reset_run |
| TIMEOUT | Call Default_Handler сначала остановлен собственной точкой. Подтверждены thread mode, один DUMMY_FRAME и инструкция Thumb0xe7fe. Точка удалена, снимок записан отдельно, continue возобновляет незавершающийся вызов | Внешний лимит8с завершает GDB; ERROR TimeoutExpired и reset_run через host recovery |
| CONTROL | Новый запуск после каждого отрицательного опыта: thread mode, CFSR=0, вызов sum_bytes даёт775, естественный checksum правильный | PASS |

TIMEOUT проверяет **продолжение прерванного dummy-call**. Первоначальный
parse_and_eval уже выдал исключение на входной точке; зависает последующий continue.
Это не испытание direct-call-timeout GDB и не доказательство async interrupt.
Внешний лимит относится к процессу GDB, а duration отчёта включает дополнительные
действия; он не является измерением времени исполнения функции на MCU.

## Приёмы и границы

1. **Классифицировать fault по совокупности признаков.** Здесь событие —
   BreakpointEvent с номером HardFault guard, не SignalEvent. В стеке есть
   обработчик, кадр исключения, sum_bytes и dummy. CFSR содержит PRECISERR и
   BFARVALID, HFSR — FORCED. Один текст ошибки call не отличает этот случай от R9.
   Маски сверены с [CMSIS core_cm4.h](https://github.com/ARM-software/CMSIS_5/blob/develop/CMSIS/Core/Include/core_cm4.h).
2. **Не продолжать повреждённый вызов автоматически.** После фиксации fault
   использован reset, затем отдельный положительный сценарий. Возврат к прежнему
   PC без reset, очистка fault-регистров и продолжение той же операции не проверялись.
3. **Сохранять доказательство до потенциального зависания.** При принудительном
   завершении GDB его finally не создаёт обычный полный отчёт агента. Sidecar
   entered-call.json хранит подтверждённый вход, кадры, инструкцию и версию GDB.
   Host требует одновременно этот снимок, TimeoutExpired и успешный recovery;
   отсутствие снимка либо посторонний ERROR останавливает серию.
4. **Не превращать отрицательный исход в PASS.** Сами16 отрицательных result.json
   имеют ERROR. PASS общей серии означает, что ожидаемые ошибки проверены,
   контроль после каждой прошёл и HAL восстановлен. Host-валидатор имеет отказные
   регрессии для неверного статуса, причины, кадра, адреса, инструкции и восстановления.

Общие свойства прерванных calls описаны в [руководстве GDB](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Calling.html).
Поддержка unwind-on-signal сама по себе не доказывает восстановление Cortex-M
после HardFault, остановленного breakpoint. Эту настройку в R10 не меняли.

## Результаты и воспроизведение

На каждой версии GDB четыре прохода:4 ожидаемых FAULT ERROR,4 ожидаемых TIMEOUT
ERROR и8 CONTROL PASS. Итого **8 fault ERROR +8 timeout ERROR +16/16 CONTROL PASS**.
Baseline и итоговый restore HW_BOOT/HW_GPIO PASS. После серии оставшихся процессов
GDB/OpenOCD не обнаружено.

Первоначальная серия сохранила отдельный неожиданный ERROR: read_register('xpsr')
дал ValueError: Bad register. Guard уже остановил HardFault, диагностика ядра
сохранила CFSR/HFSR, но consumer не собрал полный снимок. Host отверг такой ERROR,
серия остановилась, HAL восстановлен. Исправлено имя на xPSR, как в профиле;
полная исправленная серия выполнена отдельно. Первый ERROR не включён в16 ожидаемых.

GCC13.3.1, `-Og -g3 -fno-lto -mfloat-abi=soft`; ELF:
`7842e8ee9471ec777001a1fcc5be6e4a9625af3883eee7c8a1b15ebbcd6c5552`.
Restore ELF: `1ff37ae10a007401de5e0eaf826764f60a2849c8b7821c123f12caa28c2e79c3`.
Включён hardware override; журналы всех research HW-запусков содержат Z1,
не содержат Z0, server logs подтверждают аппаратные точки. Запрошено1000кГц;
reset-конфигурация запрашивает2000, фактически1800кГц, как раньше.

Windows/Linux build и host/prepare47/47 на каждой ОС (45 prepare, traceability,
23 host-теста одной группой). После исправления регистра затронутые4/4 повторены
на обеих ОС. Документация3/3. Полная HW-регрессия старых серий, native DAP,
другие платы, Linux HW и прочие причины fault здесь не проверялись.

[JSON двух серий](../results/rc3-r10-results.json) сохраняет исходный ERROR,
ожидаемые ошибки, кадры/регистры, маркеры, контрольные исходы и хэши исходников/логов.
Raw-файлы остаются в consumer build/evidence, каталоги20261002T074407.099377Z
и20261002T074529.477991Z. Персональные пути из traceback в JSON заменены краткой
причиной; полный traceback остаётся в локальных raw-отчётах.

Воспроизведение: [команда R1](r1.md#воспроизведение) с `--suite r10 --execute`,
