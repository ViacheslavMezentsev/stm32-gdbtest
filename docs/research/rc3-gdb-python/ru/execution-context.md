# Предложение: именованный контекст исполнения

[Документация](index.md) · [English](../en/execution-context.md)

02.10.2026. **Проект контракта для обсуждения, не реализованный API.** Да,
разработчику можно предоставлять `context['PC']`: в Python это именованное
отображение (mapping), а не C-массив. Предлагается неизменяемый снимок одной
остановки с явными происхождением и доступностью данных.

## Предлагаемая форма

Ниже только чтение уже полученного предлагаемого объекта; метода его получения
в текущем Target нет. Имя метода и окончательная схема ещё не утверждены.

```python
pc = context['PC']                       # int, physical stopped core PC
sp = context['SP']                       # int, active physical stack pointer
stop_id = context['meta']['stop_id']
frames = context['frames']               # immutable bounded sequence
if context['availability']['MSP'] == 'available':
    msp = context['MSP']
```

| Поле/группа | Предлагаемая семантика | Основание и ограничение |
| --- | --- | --- |
| PC, SP | Обязательные целые адреса физически остановленного ядра; не выбранного старшего кадра | R1/R11/R16; чтение не должно зависеть от ранее выполненного select-frame |
| LR, xPSR, MSP, PSP, CONTROL | Запрошенные именованные регистры Cortex-M; имена/ширины описаны профилем возможностей | xPSR и basic MSP использованы в R10/R11; общий контракт всех полей ещё не проверен |
| registers | Дополнительные регистры по явному списку, с типом/шириной; без автоматического чтения всего FP-состояния | Scalar ABI R17/R18 не доказывает сохранность полного FPU-контекста |
| stop | Вид события GDB, все связанные номера точек, signal, классификация ожидаемости относительно операции | R1/R2/R16; один PC не объясняет причину остановки; несколько причин нельзя сводить к случайной одной |
| frames | Ограниченный список снимков: index, kind, function, pc, source, availability; selected_index отдельно | R6/R15: recursion и inline; одинаковые PC допустимы, имя не является ID кадра |
| interrupted | Отдельный запрошенный снимок прерванного контекста с источником декодирования hardware frame | R11 только basic MSP; не заменяет верхнеуровневый PC обработчика, PSP/RTOS остаются долгом |
| values | Явно запрошенные locals/аргументы/this с типом, шириной и кадром происхождения | R1/R15/R18; scope, optimized_out и unreadable различаются |
| memory | Только явно запрошенные ограниченные диапазоны RAM, адрес/размер/байты | R1; SP сам по себе не является дампом или границей стека; пределы даёт профиль потребителя |
| meta | Версия схемы, run/image ID, stop_id, state_revision, идентификаторы inferior/thread/core, архитектура и набор возможностей | Это предлагаемая схема; GDB thread не объявляется RTOS task |
| availability | Статус каждого предусмотренного схемой поля и каждого запрошенного элемента | available / not_captured / unsupported / optimized_out / out_of_scope / unreadable; причина отказа отдельно |

Прямой доступ возвращает значение только при `available`. Неизвестный ключ —
`KeyError`; известное недоступное поле — отдельная ошибка доступности с кодом и
причиной (имя класса ещё не выбрано). Нет подстановки `0`, `False` или `None` вместо
ошибки. Если обязательные PC/SP недоступны, создание базового контекста завершается
явной ошибкой; частичная диагностика сохраняется отдельно от успешного контекста.
Необязательные группы запрашиваются явно; отсутствие запроса — `not_captured`.

## Актуальность и согласованность

1. Сбор выполняется в главном потоке GDB, только при подтверждённой остановке
   выбранного ядра. Операция не продолжает программу и не вызывает функции MCU.
   Чтение C-выражений с потенциальной записью/call не входит в базовый снимок.
2. `stop_id` идентифицирует остановку внутри run; `state_revision` меняется и при
   вмешательстве без continue: запись регистров/RAM, forced return и подобные
   операции также делают прежний снимок историческим. Reset/reconnect/load
   инвалидируют живой контекст независимо от совпадения PC. Это расширяет опыт
   R1: его epoch увеличивается на continue и сам по себе недостаточен для общего API.
3. Исторический снимок остаётся доступным для сравнения/отчёта. Перед использованием
   его как предусловия вмешательства операция сверяет run/stop/revision; устаревший
   снимок отклоняет. Само чтение сохранённого `context['PC']` не обращается к MCU.
4. Снимок не содержит живых `gdb.Frame`/`gdb.Value` или ленивых чтений. Вложенные
   отображения и последовательности тоже неизменяемы; экспорт в JSON создаёт копию.
   Сериализация сохраняет ширины, большие целые и специальные float без потери
   точности и неоднозначных JSON NaN; точное кодирование предстоит утвердить.
5. CPU-регистры и память читаются последовательно. Halt не гарантирует остановку
   DMA/периферии/других ядер; «атомарного состояния всего MCU» не обещаем.
   MMIO по умолчанию исключено: чтение может сбрасывать флаги. Расширение профиля
   должно указывать адреса, эффекты чтения, порядок и пределы, сохраняя эту оговорку.
6. Для raw GDB выход за оболочку требует явной инвалидации/повторного снимка:
   события continue не обнаруживают любую запись через консоль. Не объявлять
   автоматическое отслеживание всех внешних изменений уже решённым.

## Объём для первого обсуждения и приёмка

Предлагаемый минимальный набор: PC/SP, stop, bounded frames, meta/availability.
Типизированные values и выбранные регистры — следующий согласуемый слой.
RAM/MMIO/декодирование IRQ/RTOS не должны быть неявной стоимостью каждого снимка.
Параметры запроса ограничивают число кадров, значений, байт и размер отчёта.

Перед реализацией согласовать ключи/регистр имён, обязательность полей, исключения,
схему сериализации и связь с результатами операций навигации. До объявления API
готовым проверить: PC не зависит от selected frame; inline/recursion не теряют
идентичность; недоступные значения дают разные статусы; resume и запись без resume
делают контекст устаревшим; reset/reconnect не повторно используют идентичность;
снимок не меняется после публикации и не читает MMIO неявно; бюджеты и ошибки
не скрываются. Host-проверки модели недостаточны для подтверждения чтения MCU.
Эти проверки записаны в [D4](technical-debt.md), сейчас не запускаются.

Опора: [consumer Research](../../../../tests/api-experiments/lab/session.py)
уже материализует значения, ограничивает кадры и отслеживает continue; R11/R15/R18
дают аппаратные примеры. Полного предложенного объекта `context` пока нет.

Группа кадров уточнена в [предложении API](api-proposal.md): frames/frame,
arguments/locals и caller-helpers. context['frames'] и отдельный StackSnapshot
используют одинаковые записи и порядок от внутреннего кадра к внешнему;
метаданные стека включают complete и termination_reason (stack_end, depth_limit,
unwind_error). Неполный стек не доказывает отсутствие caller. Это текущая цепочка,
не история вызовов; граф всех вызовов не входит в снимок.
