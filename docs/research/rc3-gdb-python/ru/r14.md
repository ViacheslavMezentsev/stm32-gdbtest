## Проверенные сценарии

[Сценарии](../../../../tests/api-experiments/profile/tests/board/test_sequences.py)
следят одновременно за process_packet и read_packet двумя hardware breakpoints.
Каждая остановка проверяется по номеру точки и точному PC, затем передаётся
[CallOrder](../../../../tests/api-experiments/lab/sequence.py). Проверяется
чередование этих двух функций, номер итерации cycles, caller, указатель и capacity.
Контроль действует на выбранные функции; это не полная трасса всех вызовов.

| Сценарий | Результаты read_packet по итерациям | Проверка вызывающего кода |
| --- | --- | --- |
| SEQUENCE | -5, -5, 8, естественный8 | После ошибок total=0, после подменённого успеха52, после естественного770 |
| RETAIN | 8, -5, 3, естественный8 | Первый total=36 сохраняется после ошибки и короткого ответа; затем770 |
| ORDER | Естественный8 | На реальном входе read_packet намеренное ожидание process_packet отклоняется; выполнение продолжается без подмены |

При подмене сначала записываются восемь байт в проверенный выходной буфер, затем
GDB return передаёт signed status вызывающему коду. Следующий вход process_packet
служит границей: предыдущее значение уже потреблено, следующее ещё не получено.
Проверяются сохранённый status, байты и последний принятый total. Поля format и
destination сохраняются. Для SEQUENCE/RETAIN наблюдаются ровно9 выбранных событий
за4 итерации, для ORDER —3 за1. После удаления точек ещё один естественный проход
подтверждает status8 и total770.

**24/24 HW PASS:** три сценария × четыре прохода × GDB14/16, BlackPill F411CE,
ST-Link/OpenOCD0.12.0 HLA/SWD, Windows. Неожиданных FAIL/ERROR нет. Ожидаемая ошибка
ORDER сохранена отдельно в JSON; это проверка отказа наблюдателя, а не нарушение
порядка самой прошивкой. Baseline и итоговое восстановление HAL HW_BOOT/HW_GPIO
PASS. Оставшихся GDB/OpenOCD процессов нет.

## Приёмы и границы

- Конечный список действий позволяет задавать разные ответы одной функции без
  hooks и dummy-call. Здесь повторные обращения выполняет основной цикл;
  внутренний retry-алгоритм, backoff и прекращение повторов по успеху не проверялись.
- Две одновременно активные точки обнаруживают неожиданный порядок выбранных
  вызовов. Последовательное run_until только к ожидаемому имени могло бы пропустить
  лишний вызов другого имени. Ошибка CallOrder не потребляет ожидание; недостающие
  и лишние события отдельно отклоняются в host-регрессии.
- После ошибки важно проверять сохранение ранее принятого результата, а не всегда
  ожидать ноль. В этой прошивке буфер и signed status меняются, total сохраняется.
- Две точки плюс четыре fault guard занимают шесть code-слотов. Здесь не нужен
  FinishBreakpoint; добавлять его без освобождения слота нельзя считать проверенным.
  Логи подтверждают Z1 без Z0. Ожидание ограничено внешним timeout и конечным планом.
- RAM-подмена намеренно остаётся видна вызывающему коду; это не транзакционный
  rollback. После снятия перехвата read_packet заново заполняет буфер естественно.
  Другие ABI, IRQ/RTOS-конкуренция, Linux HW и другие платы не проверены.
