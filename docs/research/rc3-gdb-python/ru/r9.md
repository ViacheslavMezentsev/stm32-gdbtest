## Проверенные техники

[Два сценария](../../../../tests/api-experiments/profile/tests/board/test_interrupted_calls.py)
проверяют вызовы из остановленного thread mode на F411CE/ST-Link/OpenOCD0.12.0 HLA.

| Опыт | Действия и независимая проверка |
| --- | --- |
| RESUME | Вызвать `sum_bytes(sample.bytes, 8, 5)` через `parse_and_eval`, остановить собственной hardware-точкой. Проверить номер события, аргумент seed=5 и один DUMMY_FRAME. Удалить точку, продолжить; проверить PC/SP/LR/r0–r12, исчезновение dummy и исходный кадр process_sample. RAM sample прежняя; новый непрерванный вызов возвращает775, естественное выполнение даёт ожидаемый checksum |
| INTERCEPT | Вызвать `process_packet()`, остановиться в его read_packet. После остановки выполнить `return -7`, затем continue. Восстановлены проверенные регистры, но packet_status=-7 сохраняется в RAM; packet и packet_total не изменились. Нормальный вызов затем даёт status=8 и total=770; естественный checksum также правильный |

Это способ проверить ветку ошибки в вызывающем коде по запросу, без ожидания
естественного события и без изменения прошивки. Подмена происходит после выхода
из GDB callback, в основном потоке. Условия выбора вызова, известное начальное
состояние и постусловие вызывающего обязательны: один успешный `return` их не заменяет.

## Как распознать остановку

При прерывании `parse_and_eval` выдаёт `gdb.error`: вычисление выражения прекращено.
Сценарий сохраняет полный текст как ожидаемое наблюдение и дополнительно проверяет
номер своей точки, имя остановленной функции и `frame.type() == gdb.DUMMY_FRAME`.
Произвольное исключение не считается доказательством успешного перехвата.

В этих опытах `name()` служебного кадра возвращает **Reset_Handler**.
Поэтому имя само по себе не означает ни reset, ни обычный вызов Reset_Handler;
для классификации нужен тип кадра. После continue приходит обычный StopEvent
без номера пользовательской точки. Завершение распознаётся по исчезновению dummy,
возврату в исходный кадр и совпадению сохранённых регистров.

Python-выражение уже завершилось исключением и не возобновляется вместе с MCU.
Эта техника не возвращает потерянный результат исходного `parse_and_eval`.
RESUME получает775 отдельным новым вызовом; его нельзя приписывать прерванному.
INTERCEPT проверяет результат через независимый RAM-приёмник вызывающего кода.

Восстановление регистров **не откатывает RAM**. Состояние packet_status=-7 после
возврата dummy — намеренно проверяемый побочный эффект. Сравнение PC/SP/LR/r0–r12
не доказывает сохранность всей RAM, стека, xPSR, FPU, периферии или состояния IRQ.

## Результаты и ограничения

GDB14 и GDB16: по8/8 PASS, всего16/16 — два сценария, первый проход и три заранее
заданных повтора на каждой версии. В этой серии нет неожиданных FAIL/ERROR;
ожидаемые сообщения о прерывании сохранены в [JSON](../results/rc3-r9-results.json).
Baseline и итоговое восстановление HAL: HW_BOOT/HW_GPIO PASS, reset_run.

GCC13.3.1, `-Og -g3 -fno-lto -mfloat-abi=soft`; прежний ELF R6–R8:
`7842e8ee9471ec777001a1fcc5be6e4a9625af3883eee7c8a1b15ebbcd6c5552`.
Restore ELF: `1ff37ae10a007401de5e0eaf826764f60a2849c8b7821c123f12caa28c2e79c3`.
Локальные raw-журналы: consumer `build/evidence/20261002T070117.121647Z/`.
JSON содержит фактические версии GDB/Python, хэши исходников, снимки и утверждения.

Четыре fault guard не отключались. Включён OpenOCD hardware override;
RSP содержит Z1 и ни одного Z0 во всех16 сценариях, server logs подтверждают
аппаратную вставку. Внутренняя точка dummy также требует бюджета: здесь есть
одна пользовательская точка плюс внутренний механизм вызова, без дополнительных
постоянных точек. Исчерпание бюджета именно dummy-call отдельно не проверялось.
Запрошено1000кГц; reset-конфигурация OpenOCD запрашивает2000, фактически1800кГц,
как в предыдущих сериях.

Windows/Linux build и host/prepare44/44 на каждой ОС (42 prepare, traceability,
20 host-регрессий одной группой); документация3/3. Linux HW, native DAP, другие
платы, signal/fault/timeout во время call, async и RTOS здесь не проверялись.
Полная HW-регрессия R1–R8 не выполнялась; старые ограничения остаются.

Воспроизведение: [команда R1](r1.md#воспроизведение) с `--suite r9 --execute`,
без `--native-stlink`; оба GDB задаются явно. Без execute — только prepare.
Основание для опыта: [GDB Calling Program Functions](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Calling.html),
раздел о прерывании вызова и dummy frame. Следующие отдельные опыты — fault/timeout
во время вызова с сохранением причины и recovery, затем IRQ-контекст.
