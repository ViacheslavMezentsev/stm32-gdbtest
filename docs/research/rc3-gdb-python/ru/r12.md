# rc3 R12: запись DMA и наблюдение через watchpoints

[Документация](index.md) · [English](../en/r12.md)

02.10.2026, после `2bd17d2`, ветка codex/rc3-api-r1. Использована прежняя
CMSIS-прошивка F411 из tests/firmware: ADC CH18/17 → DMA2 stream0/channel0 →
board_adc_buffer[2]. Исходники прошивки, ядро, API и ТЗ не изменены.

## Проверка на плате

[WRITE и ACCESS](../../../../tests/api-experiments/profile/tests/board/test_dma_watch.py)
выполнены на BlackPill F411CE/ST-Link/OpenOCD0.12.0, native DAP/SWD, Windows,
GDB14/16. Выбран уже испытанный native backend: ограничение HLA по идентификации
watchpoints из [R2](r2.md) остаётся. Это флаг consumer runner, не правка ядра.

До первого board_adc_sample устанавливается hardware write-watch либо access-watch
на весь4-байтовый DMA-буфер. Независимая аппаратная точка — **точный вход**
DMA2_Stream0_IRQHandler, до исполнения чтений буфера процессором. Продолжение
ограничено этим sentinel и внешним timeout; бесконечно ждать watchpoint не требуется.

| Наблюдение | WRITE | ACCESS |
| --- | --- | --- |
| Первая сообщённая остановка | Вход DMA IRQ, не buffer watch | Вход DMA IRQ, не buffer watch |
| Доказательство передачи до CPU-чтений | Буфер изменён с00000000, NDTR=0, TCIF0 установлен, stream EN=0, sequences=0 | То же |
| Положительный CPU-контроль | Новый write-watch на board_adc_sequences останавливает CPU при записи1 | **Тот же** access-watch на буфере останавливает CPU при чтении внутри DMA handler |
| Результат вызывающего кода | Оба raw-приёмника равны буферу, sequences=1, adc_error=0, достигнута задержка500мс | То же |

Также проверяется exception72, диапазон обоих ADC-значений1…4095 и точный PC
sentinel. Значения ADC не заданы константами: в каждом запуске приёмники сравниваются
с его собственным снимком буфера. Это не метрологическая проверка ADC.

**Итог:16/16 HW PASS** — два сценария, первый проход и три заданных повтора на
каждом GDB; по8/8. Неожиданных FAIL/ERROR в R12 не было. Baseline и итоговый
restore HW_BOOT/HW_GPIO PASS; оставшихся GDB/OpenOCD процессов не обнаружено.

## Что даёт сценариям

- Отсутствие watchpoint stop не означает отсутствие записи RAM. На этой комбинации
  DMA завершил запись без сообщённого buffer-watch события. Это измеренная граница,
  не универсальное утверждение обо всех MCU, шинах и отладчиках.
- Проверять DMA можно через совместное условие: состояние передачи + изменение
  буфера + вход IRQ до потребления + проверка конечных приёмников.
- Access-watch полезен для следующей фазы: определить, где **CPU потребляет** уже
  заполненный DMA-буфер. Сначала sentinel отделяет запись DMA от чтения CPU.
- Write-контроль использует другой объект — счётчик. Он подтверждает работу
  CPU write-watch механизма, но не является CPU-записью по адресу DMA-буфера.
  Контроль того же адреса выполнен только для ACCESS.

Сценарии не записывают MMIO или RAM; четыре fault guard сохранены. Задействован
hardware override, логи подтверждают Z1 без Z0, Z2 для WRITE и Z4 для ACCESS.
Наблюдение через остановки меняет временное поведение; непрерывный/circular DMA,
гонка CPU/DMA, overrun, cache coherency, Linux HW, другие платы и HLA не проверялись.
Успех native DAP здесь не отменяет прежнее ограничение stepi из [R4](r4.md).
