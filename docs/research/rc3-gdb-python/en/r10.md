TIMEOUT tests **continuation of an interrupted dummy call**. The original
parse_and_eval has already raised at the entry point; the subsequent continue
hangs. This does not test GDB direct-call-timeout or prove async interrupt support.
The external deadline applies to the GDB process; reported duration includes
additional operations and does not measure function execution time on the MCU.

## Techniques and boundaries

1. **Classify faults using combined evidence.** The event here is BreakpointEvent
   with the HardFault guard number, not SignalEvent. The stack contains the handler,
   exception frame, sum_bytes and dummy. CFSR has PRECISERR and BFARVALID, HFSR has
   FORCED. The call error text alone cannot distinguish this case from R9.
   Masks were checked against [CMSIS core_cm4.h](https://github.com/ARM-software/CMSIS_5/blob/develop/CMSIS/Core/Include/core_cm4.h).
2. **Do not automatically resume the damaged call.** After recording the fault,
   reset was followed by a separate positive scenario. Returning to the old PC
   without reset, clearing fault registers and resuming the same operation were
   not tested.
3. **Persist evidence before a possible hang.** Forced GDB termination prevents
   its finally block from producing the normal complete agent report. The
   entered-call.json sidecar stores verified entry, frames, instruction and GDB
   version. Host requires that snapshot, TimeoutExpired and successful recovery;
   missing evidence or an unrelated ERROR stops the series.
4. **Keep negative outcomes as ERROR.** All16 negative result.json files retain
   ERROR. Overall series PASS means expected errors were validated, every subsequent
   control passed and HAL was restored. Host rejection regressions cover incorrect
   status, cause, frame, address, instruction and recovery evidence.

General interrupted-call behavior is described in the [GDB manual](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Calling.html).
Availability of unwind-on-signal does not itself prove Cortex-M recovery after a
HardFault intercepted by a breakpoint. R10 did not change this setting.

## Results and reproduction

Four passes per GDB:4 expected FAULT ERRORs,4 expected TIMEOUT ERRORs and8 CONTROL
PASSes. Total: **8 fault ERRORs +8 timeout ERRORs +16/16 CONTROL PASS**.
Baseline and final restore HW_BOOT/HW_GPIO PASS. No remaining GDB/OpenOCD processes
were found after the series.

The initial series retained a separate unexpected ERROR: read_register('xpsr')
raised ValueError: Bad register. The guard had reached HardFault and core
diagnostics retained CFSR/HFSR, but the consumer failed to capture the full snapshot.
Host rejected this ERROR, stopped the series and restored HAL. The name was fixed
to xPSR, matching the profile; the full corrected series ran separately. This first
ERROR is not included in the16 expected errors.
