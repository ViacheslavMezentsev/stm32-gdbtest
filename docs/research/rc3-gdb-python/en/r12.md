## Board experiments

[WRITE and ACCESS](../../../../tests/api-experiments/profile/tests/board/test_dma_watch.py)
ran on BlackPill F411CE/ST-Link/OpenOCD0.12.0, native DAP/SWD, Windows, GDB14/16.
The already tested native backend was selected; the HLA watchpoint-identification
limitation from [R2](r2.md) remains. This is a consumer runner flag, not a core edit.

Before the first board_adc_sample, install a hardware write or access watch over
the entire4-byte DMA buffer. An independent hardware point targets the **exact entry**
of DMA2_Stream0_IRQHandler, before any CPU buffer reads. Continuation is bounded by
that sentinel and the external timeout; the test never waits indefinitely for a watch.

| Observation | WRITE | ACCESS |
| --- | --- | --- |
| First reported stop | DMA IRQ entry, not the buffer watch | DMA IRQ entry, not the buffer watch |
| Transfer evidence before CPU reads | Buffer changed from00000000, NDTR=0, TCIF0 set, stream EN=0, sequences=0 | Same |
| Positive CPU control | A new write-watch on board_adc_sequences stops the CPU writing1 | The **same** buffer access-watch stops the CPU reading inside the DMA handler |
| Caller outcome | Both raw sinks equal the buffer, sequences=1, adc_error=0,500ms delay reached | Same |

The tests also check exception72, both ADC values within1…4095 and exact sentinel
PC. ADC samples are not fixed constants: each run compares its sinks with its own
buffer snapshot. This is not a metrological ADC validation.

**Result:16/16 HW PASS** — two scenarios, initial pass and three predetermined
repeats per GDB;8/8 each. R12 had no unexpected FAIL/ERROR. Baseline and final
restore HW_BOOT/HW_GPIO PASS; no remaining GDB/OpenOCD processes were found.

## Techniques for scenarios

- No watchpoint stop does not imply no RAM write. On this combination DMA completed
  its write without a reported buffer-watch event. This is a measured boundary,
  not a universal claim about every MCU, bus and debugger.
- Verify DMA through combined evidence: transfer state, buffer mutation, IRQ entry
  before consumption and final consumer sinks.
- An access watch is useful for the next phase: identify where **CPU consumes** the
  filled DMA buffer. The initial sentinel separates DMA writes from CPU reads.
- The write control uses a different object, the sequence counter. It verifies the
  CPU write-watch mechanism, not a CPU write at the DMA buffer address. Same-address
  control was performed only for ACCESS.

Scenarios write neither MMIO nor RAM; four fault guards stay enabled. Hardware
override is enabled; logs confirm Z1 without Z0, Z2 for WRITE and Z4 for ACCESS.
Debug stops affect timing; continuous/circular DMA, CPU/DMA races, overrun, cache
coherency, Linux HW, other boards and HLA were not tested. Native DAP success here
does not remove the previous stepi limitation from [R4](r4.md).
