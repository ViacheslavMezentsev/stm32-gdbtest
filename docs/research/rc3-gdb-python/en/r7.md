## Measurements and techniques

Stand: F411CE/ST-Link/OpenOCD0.12.0 native DAP/SWD, Windows, GDB14 and GDB16.
These are limits of the tested combination, not universal properties of all STM32s.
Scenarios use ordinary CPU accesses to the sample object only.

| Trial | Observation |
| --- | --- |
| WIDTH | Aligned1/2/4/8-byte ranges produce hardware read-watchpoint events in sum_bytes. Unaligned2/4-byte ranges are rejected on continue |
| CAPACITY | One through four separate aligned word write-watchpoints insert successfully; the fifth is rejected. Application code does not modify these static words; a sentinel proves execution |
| SPLIT | An unaligned2-byte range is split into1+1; four bytes into1+2+1. Exact coverage without extra bytes, hardware types, access order and exit from sum_bytes are checked |

[Measurements](../../../../tests/api-experiments/profile/tests/board/test_watch_limits.py),
[decomposition](../../../../tests/api-experiments/profile/tests/board/test_watch_split.py).

The array address comes from ELF: sample is40 bytes; bytes starts at offset29.
Array alignment cannot be inferred from whole-structure alignment. For WIDTH,
an aligned range may include adjacent sample fields; it still lies entirely within
the object and overlaps the array actually read by the CPU.

SPLIT observes only the requested bytes and checks each access: part sequence0,1
for two bytes and0,1,1,2 for four. A process_packet sentinel stops before that
function reads the array again. This consumes two or three points instead of one.
It is not presented as a general range decomposition algorithm. The budget was
measured for separate word points; arbitrary expressions, overlaps or larger ranges
may consume different resources. FPB, DMA and MMIO were not investigated.

## Rejections and recovery

The first FAIL was an incorrect array-alignment assumption, before watchpoint
installation. Addresses now follow the actual ELF layout. In the second series,
aligned ranges passed, but the first unaligned range caused ERROR: Python received
only `Command aborted.`, while GDB output contained the cause. Both original
results are retained; both series completed firmware restoration.

Each continue now has a separate local GDB log. Only a specific
`Could not insert hardware watchpoint N.` line permits classification as
`insertion_rejected`; other errors propagate. `Command aborted.` alone is
insufficient. After deleting points, each WIDTH/CAPACITY performs a reset and a
positive control: a hardware cycles watchpoint, expected stop identity and value1.
This verifies cleanup plus reset, not continuation of the previous frame after failure.

Successful Python object creation and a hardware type do not prove MCU insertion:
the limit appears on continue. Scenario PASS means observations and recovery
controls succeeded, not that rejected ranges are supported. Full diagnostic logs
remain local; the summary excludes personal paths.

## Reproduction

Add `--suite r7 --native-stlink` to the [R1 command](r1.md#reproduction).
Select `--test HW_R7_WIDTH --test HW_R7_CAPACITY` or `--test HW_R7_SPLIT` for
individual series; without `--execute`, preparation only.
The [sanitized summary](../results/rc3-r7-results.json) retains all attempts,
source variants, specific rejections, events and firmware restoration.
Logs remain in `tests/api-experiments/build/evidence/`.
