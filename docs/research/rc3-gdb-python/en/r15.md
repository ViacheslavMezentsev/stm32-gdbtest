# rc3 R15: O2/Os, inline frames and value availability

[Documentation](index.md) · [Русский](../ru/r15.md)

2026-10-02, after `77b6c4e`, branch codex/rc3-api-r1. Core, public API and specification
unchanged. Added consumer build variants and a separate ordinary
[dual-channel calculation application](../../../../tests/api-experiments/src/optimized.c):
two volatile inputs, a shared multiplier, inline scale_channel and two outputs. No hooks.

## Preliminary observations

Building the previous application with O2 produced undefined memcpy/memset from
Reset_Handler: optimization converted startup loops to library calls.
Optimized variants now apply -fno-tree-loop-distribute-patterns to startup only;
other units retain O2/Os and startup source is unchanged. The initial failure is
retained in [JSON](../results/rc3-r15-results.json). The first Linux command also
failed before configuration because PowerShell expanded bash variables; quoting was corrected.

In the previous O2 application, walk_route no longer resolves to a breakpoint:
route_alpha becomes movs r0,124; bx lr. Os retains walk_route. This is an offline
GDB14 observation, not hardware verification of these two previous variants.
Inline research uses a new application with variable inputs rather than disabling
optimization.

## Hardware results

[LOCATIONS and VALUES](../../../../tests/api-experiments/profile/tests/board/test_optimized.py)
ran on BlackPill F411CE/ST-Link/OpenOCD0.12.0 HLA/SWD, Windows,
GCC13.3.1, soft-float, -g3, without LTO. Two optimizations × two GDBs × two scenarios ×
four runs: **32/32 HW PASS**,16/16 each for O2 and Os. No unexpected HW FAIL/ERROR.
Baseline and HAL restore HW_BOOT/HW_GPIO PASS after each matrix;
no remaining GDB/OpenOCD processes.

| Observation | O2 | Os |
| --- | --- | --- |
| scale_channel: two locations | 0x080000c2,0x080000ce | 0x0800009e,0x080000a8 |
| First instruction | mul.w,4bytes | muls,2bytes |
| Frames | INLINE_FRAME scale_channel → NORMAL_FRAME main, same PC | Same |
| Before multiplication | input=11, multiplier=3, product=33 | Same |
| After one stepi | input=optimized_out, multiplier=3, product=33 | Same |
| Outputs after one iteration | output_a=40, output_b=76, iterations=1 | Same |

LOCATIONS verifies A→B→A stops by PC and one breakpoint identity, arguments11/23
and3, inline frames and final results. First Research.breakpoint rejects the name
with two locations and deletes its point. A raw GDB breakpoint with two addresses
then uses two physical slots, six together with four guards. Logs confirm Z1 without
Z0. This is an experiment outside the core, not an extension of the adapter contract.

VALUES resolves addresses, removes the multiple-location point, reaches the first
address using an individual point and executes one stepi. It checks the next address
against disassembly, INLINE_FRAME and changing local availability; Research.freeze
explicitly rejects optimized_out. Continuing through exact addresses verifies ordinary
caller consumption. No manual RAM/register substitution is performed.

## Implications for scenarios

- Budget locations rather than breakpoint objects. The event number identifies
  the object; here PC identifies the instance. Resolve addresses from the current
  ELF instead of carrying them between O2 and Os.
- An inline frame exposes source arguments without a separate machine call.
  Check its type before attempting return/finish. Inline return/finish was not tested.
- product=33 is available before multiplication executes. Debug information values
  alone do not prove execution; instruction/PC and final volatile outputs were checked.
- Availability depends on the exact PC: input disappears after register overwrite.
  Do not substitute zero for unavailable data or treat an earlier snapshot as a
  current value. Specifically is_optimized_out was tested; other unavailability
  states remain uncovered.
- Function disappearance is a valid optimization outcome. A pending breakpoint
  is not a working point. LTO, tail-call frames, other compilers/ABIs/boards,
  Linux HW and native DAP were not tested; the earlier native stepi limitation remains.

RC3_OPTIMIZED_FIXTURE=ON (default OFF). For R15 use separate build directories with
ON and O2/Os, then pass their hwtest/session.json to the [runner](../../../../tests/api-experiments/run_matrix.py)
with --suite r15 --execute, both previous GDBs and the agreed restore session,
