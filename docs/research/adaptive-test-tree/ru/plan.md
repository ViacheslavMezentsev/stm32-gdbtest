# План S1: динамическое отсечение и реактивация

[Документация](index.md) · [English](../en/plan.md)

Цель: проверить предложенную модель без оборудования, сравнивая состояние всего
дерева после каждого теста с заранее заданным результатом. Это исследовательский
контракт модели, не утверждённое расширение stm32_gdbtest.

## Структура и вычисления

Каждая папка содержит `node.json`: id, enabled, activation, output, упорядоченные
tests и children. Имена children — прямые подпапки, порядок задан явно, а не порядком
файловой системы. ID узлов и сценариев уникальны в своих пространствах. Выход за
корневую папку, повторная папка, неизвестное поле/факт и неоднозначный JSON отклоняются.

Вход узла — **полный выход непосредственного родителя**; вход корня пуст.
Выход — именованные трёхзначные поля, вычисляемые из входа, общих фактов и результатов
собственных тестов. Потомки в вычислении родительского выхода не участвуют, чтобы
не создавать циклическое ожидание. Глобальные факты передают наблюдения между ветками.

Язык выражений: true/false/null, `{"fact":"name"}`, `{"input":"name"}`,
`{"results":"all"}`, `{"results":"any"}`, `{"all":[...]}`, `{"any":[...]}`.
Нет eval, Python callbacks и аппаратных чтений. Имена проверяются до первого шага.
Условие активации не может ссылаться на собственный results.

| Значения | All | Any |
| --- | --- | --- |
| Пусто | UNKNOWN | UNKNOWN |
| TRUE, UNKNOWN | UNKNOWN | TRUE |
| FALSE, UNKNOWN | FALSE | UNKNOWN |
| TRUE, FALSE | FALSE | TRUE |
| TRUE, TRUE | TRUE | TRUE |
| FALSE, FALSE | FALSE | FALSE |

Для агрегации PASS → TRUE, FAIL → FALSE, ERROR и невыполненное → UNKNOWN.
Первоначальный ERROR сохраняется как ERROR в results. Политика ERROR здесь выбрана
как недостаток доказательства, а не универсальное правило будущего API.

Активность = enabled AND активность всех предков AND собственное условие равно TRUE.
UNKNOWN не разрешает запуск. Узел без тестов complete=true, но All/Any пустого
набора остаётся UNKNOWN. Активность, завершённость и успешность независимы.
Выходы пересчитываются даже у неактивных узлов, но их потомки всё равно блокируются
по цепочке предков. Вычисление идёт сверху вниз, без поиска неподвижной точки.

## Один шаг

1. Пересчитать все входы/выходы и активности; сохранить начальный snapshot.
2. Выбрать первый ещё не выполненный активный тест: preorder дерева, порядок tests.
3. Атомарно записать заранее заданные outcome/reason и effects (изменения фактов).
4. Пересчитать всё дерево и записать snapshot после шага; повторить выбор.
5. Остановиться, когда доступных тестов нет. Это terminal, не «всё прошло».

Статусы невыполненных тестов: PENDING, BLOCKED, DISABLED. Они вычисляются заново;
результаты выполненных PASS/FAIL/ERROR не меняются. Реактивация не повторяет тест.
Обход всегда начинается с корня, поэтому после восстановления сначала выполняется
ранее заблокированный оставшийся тест ранней ветки. Число исполнений ограничено
числом тестов и max_steps; превышение бюджета — ошибка модели.

Снимок содержит schema/step, все facts с provenance (step/source), результаты,
весь список узлов с parent/input/output/condition/active/reason/complete/tests,
упорядоченную очередь eligible, next и terminal. Возвращается глубокая копия;
её можно редактировать вне движка без изменения сохранённой истории.
Атомарность здесь относится к имитационному шагу Python, не к состоянию реального MCU.

## Проверки и границы

S1: защёлка → ключи; связь → протокол; независимая температура; независимое
восстановление; отключённая ветка. Эталон задаёт каждый снимок полностью, включая
неактивные и завершённые узлы. Дополнительно проверить All/Any, непрерывность
активации по предкам, ERROR, invalidation до UNKNOWN, реактивацию, неверные входы,
конечную остановку без доступных тестов и обнаружение намеренно испорченного движка.

Не реализуются реальные тесты, reset, retries, параллелизм, внешние события между
шагами, автоматические диагностические вставки, TTL, persist/resume, CTest/JUnit
и интерпретатор произвольных условий. Reset моделируется явным effects=null.
Граф зависимостей по произвольным узлам, статический анализ конфликтов facts и
масштабирование на большие деревья — возможные следующие исследования, не обещания.

## Представление workflow и следующий шаг с YAML

Проигрыватель S1 использует прямоугольные карточки, неподвижные связи и состояния
из snapshots.json. Это расширение представления; семантика движка не меняется.
Каркас сейчас берётся из первого снимка, определение сценариев остаётся в node.json.

Предлагается отдельное статическое описание workflow в YAML и адаптер в текущую
модель. YAML-парсер пока не реализован. Формат не объявляется совместимым с GitHub
Actions: сходство представления не задаёт правила исполнения. Следует разделить:

- вложенность групп (`parent`/`children`) и передачу входа от предка;
- зависимости порядка выполнения (`needs`, если они появятся), включая проверку циклов;
- условия активации по текущим facts/input с UNKNOWN и пересчётом после каждого теста;
- упорядоченные сценарии узла и выражения для его выхода (All/Any и прочие);
- результаты конкретного запуска, хранимые отдельно от каркаса.

Текущие линии показывают только родительскую связь. Произвольный граф needs ещё
не поддерживается. Готовый viewer можно подключить через адаптер представления,
если он сохраняет отдельные состояния доступности и результата, реактивацию и
просмотр шагов. Выбор библиотеки, YAML-схема и валидация — отдельный следующий этап.
Проверка такого этапа: один каркас в JSON и YAML должен дать одинаковые полные
снимки на независимом эталоне; неверные ссылки и циклы должны быть отклонены.
