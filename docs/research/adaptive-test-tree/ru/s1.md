# S1: моделирование отказов, отсечения и восстановления

[Документация](index.md) · [English](../en/s1.md)

02.10.2026. Только имитация. Измерений MCU нет, серверы отладчиков не запускались.
Модель находится вне пакета stm32_gdbtest; это не утверждённый API/runner.

## Пример и ожидаемые переходы

```text
board
├── latch: release
│   └── keys: key1, key2
├── comm: handshake
│   └── protocol: exchange
├── temperature: sample
├── recovery: recover
└── disabled: never
```

Ветка keys требует input.keys=true, protocol — input.link=true. Latch/comm передают
текущие факты из общего контекста своим детям. Их поле ok отдельно агрегирует
результаты собственных тестов; FAIL handshake не стирается восстановлением link.
Корень и промежуточные узлы не зависят от результатов своих детей.

| Шаг | Выполнен | Факты keys/link | Что должно происходить дальше |
| --- | --- | --- | --- |
| 0 | — | UNKNOWN / UNKNOWN | keys/protocol BLOCKED, следующий release |
| 1 | release PASS | TRUE / UNKNOWN | keys активен, следующий key1 |
| 2 | key1 FAIL | FALSE / UNKNOWN | key2 BLOCKED, перейти к handshake |
| 3 | handshake FAIL | FALSE / FALSE | protocol BLOCKED, перейти к sample |
| 4 | sample PASS | FALSE / FALSE | Независимая температура проверена, следующий recover |
| 5 | recover PASS | TRUE / TRUE | keys/protocol снова активны, следующий key2; key1 остаётся FAIL |
| 6 | key2 PASS | TRUE / TRUE | Следующий exchange; первый ключ повторно не запускать |
| 7 | exchange PASS | TRUE / TRUE | Нет доступных тестов; never остаётся DISABLED |

Итого: семь имитированных исполнений, пять PASS и два **намеренно заданных FAIL**;
один DISABLED. Это результаты фиктивных сценариев, не отказ тестов движка.
Положительный результат проверки модели означает точное воспроизведение этой
истории, включая отказ и временную блокировку. На шаге5 keys active=true, но
output.ok=false — наглядное различие доступности оборудования и успешности тестов.

## Эталон и проверки

[expected.json](../../../../tools/research/adaptive_tree/fixtures/bringup/expected.json)
подготовлен независимо от Engine по приведённой таблице: восемь полных состояний,
включая значения полей каждого узла, очередь, историю и происхождение facts.
Он не обновляется командой run. Исполнитель сохраняет фактические snapshots и
сравнивает типы, ключи, значения и порядок списков; первая разница содержит JSON-путь.
Порядок ключей объектов незначим, порядок eligible и массивов значим.

**14 поведенческих проверок модели проходят на Windows:** полный эталон; таблица
All/Any; недоступный предок при истинном условии листа; активация Any после FAIL/PASS;
ERROR → UNKNOWN и независимая ветка; reset-инвалидация/диагностика; terminal с
BLOCKED; DISABLED с потомком; отделённые снимки; неверные входы и бюджет;
неверные пути/JSON; испорченный snapshot; намеренно испорченный движок, игнорирующий
входные условия; встраивание JSON в HTML и экранирование окончания script.

Контроль с испорченным движком действительно запускает key2 сразу после key1,
вопреки блокировке, и эталон выявляет отличие. Это отрицательный контроль средства
проверки, а не замена основного прогона. Полный Windows host-набор:112 тестов,
8 платформенных skips, без неожиданных FAIL/ERROR.

## Просмотр

[player.html](../results/player.html) — автономный файл без CDN и сетевых запросов,
его можно открыть непосредственно в браузере. Все данные встроены из фактического
[snapshots.json](../results/snapshots.json), логики движка в HTML нет.
Слайдер и кнопки First/Previous/Next, Play/Pause, интервал воспроизведения;
клик по карточке показывает весь JSON узла. Статический каркас расположен слева
направо: прямоугольные карточки соединены линиями родительского входа. Положение
узлов не меняется между шагами. ACTIVE отмечен зелёным, неактивная карточка серая;
результаты PASS/FAIL/ERROR показаны отдельными метками. После восстановления
карточка может быть ACTIVE с сохранённым FAIL. Золотая обводка отмечает последнее
исполнение, зелёная внешняя — выбранный узел. На узком экране схема прокручивается.
Завершённость относится только к собственным тестам узла, не ко всему поддереву.

В браузере проверены начальное состояние, серые keys/protocol на шаге3,
восстановление на шаге5, сохранённый FAIL/key2 PENDING, ручной переход к началу/концу,
шаг назад, выбор узла и Play с автоматической остановкой на шаге7.

## Воспроизведение

Из корня репозитория, Python стандартной библиотеки:

```text
python -B -m unittest tools.research.adaptive_tree.test_engine -v
python -B tools/research/adaptive_tree/run.py --out build/adaptive-tree
python -B tools/research/adaptive_tree/player.py build/adaptive-tree/snapshots.json build/adaptive-tree/player.html
```

Для другого набора: `run.py --fixture <папка>` с facts.json, tree/node.json и
независимо подготовленным expected.json. Код возврата run:0 — совпадение,1 — отличие;
ошибка модели также даёт ненулевое завершение. Отличие не превращается в PASS
через автоматическую перезапись эталона. Штатный host discovery включает модель
через [адаптер тестов](../../../../tests/host/test_adaptive_tree_research.py).

## Вывод и следующий предмет обсуждения

Для конечного последовательного набора модель демонстрирует отсечение ветвей
после каждого теста, продолжение независимых проверок и реактивацию без повторного
исполнения. Полный JSON позволяет проверять не только порядок вызовов, но и причины
решений на промежуточных шагах. Поведение реального оборудования этим не доказано.

Перед дальнейшим развитием согласовать: ERROR в агрегаторах; порядок обхода;
что именно может менять facts; срок актуальности фактов после reset; terminal с
заблокированными узлами и отображение в итоговый отчёт. Восстановление сейчас
явный обычный сценарий независимой ветки, не автоматический retry и не внешний
асинхронный сигнал. Возможные продолжения перечислены в [плане](plan.md).

Linux Docker CI: docs3/3 и host1/1 PASS;112 host-тестов,4 платформенных skips.
Парность RU/EN исследовательских страниц проверена отдельно: базовый main CI
проверяет только docs/ru|en. Сохранённые JSON и HTML воспроизводятся из модели
без отличий. [Сводка проверок и SHA256](../results/checks.json).
