## База и границы

База совместимости — v0.1.0-rc.2, commit
`a0d6547ba83b7c911f8f3028cb064aeedd3e5a36`.
База рабочего дерева указана в [карте исследования](index.md).
Исходные сценарии сохраняются для сравнения; сигнатуры ниже предварительные.

не подменяют класс Target, runner или установленный пакет.

## Кандидаты и проверяемая польза

| Этап | Кандидат | Существующий сценарий и ожидаемая польза |
| --- | --- | --- |
| E1 | `record(name, data)` | [ADC](../../../../tests/firmware/profiles/f411ce/tests/board/test_adc.py), [HAL runtime](../../../../tests/hal-f030/hal_scenarios/peripheral_runtime.py): заменить прямую запись в report публичным контрактом свидетельств |
| E2 | Ограниченный типизированный `read` | Те же сценарии: читать массивы и выбранные поля без повторяющегося value; определить ограничения размера и глубины |
| E3 | `frames` и минимальный `context` | [Sleep/WFI](../../../../tests/firmware/profiles/f411ce/tests/board/test_sleep.py): убрать прямой обход GDB-кадров, сохранить распознавание прерванного контекста |
| E4 | `finish` | [HAL methods](../../../../tests/hal-f030/profile/tests/board/test_hal_methods.py): проверить эффект непосредственно после естественного возврата |
| E5 | Проверка соглашений и свойств API | По каждому разработанному методу сопоставить контракт и результаты с тремя исходными документами; подготовить список соответствий и расхождений |
| E6 | Принятие API и миграция сценариев | После положительного решения по E5 согласовать версию и открытые вопросы, принять API и переработать текущие сценарии |

Для каждого этапа: сначала карточка экспериментального контракта и отрицательные
случаи, затем изолированный прототип и сравнение сценариев, затем отдельный отчёт.
Снимки и события должны быть материализованы, сериализуемы и ограничены по размеру;
живые объекты GDB не должны попадать в результат. Все вызовы GDB — в основном потоке.

- E1: определить повторы имён, порядок записей, недопустимые значения и превышение
  лимита; ошибка записи не должна скрывать исходный FAIL/ERROR.
- E2: отсутствие символа, optimized-out, ошибка памяти, массив/структура,
  выбор полей, лимиты; исключить неявные вызовы функций. Чтение не обещает
  атомарности при работающем DMA. Старый целочисленный value сохраняет семантику.
- E3: конец стека, ограничение глубины, unwind error, безымянные и сигнальные
  кадры, актуальность снимка после продолжения. Неполный стек не означает
  отсутствие вызывающего. Поиск caller и выбор прерванного кадра — техники.
- E4: обычный возврат, void/скаляр, недоступное значение, чужая точка остановки,
  fault, timeout, нехватка аппаратных точек и cleanup. Не обещать неподтверждённые
  ABI/агрегаты. Сохранить fault guards и внешний timeout/recovery.

## Сравнение и критерии

1. Сохранить исходный и экспериментальный вариант, соответствие каждой проверки
   и независимые ожидаемые значения. Сокращение числа проверок не считать улучшением.
2. Сравнивать служебные строки, прямые обращения к GDB/report, диагностические
   данные и отрицательные исходы. Строки прототипа учитывать отдельно от сценария.
3. Проверить контракты host-тестами с управляемыми отказами; такие тесты не
   подтверждают реальные unwind, ABI, breakpoints или MMIO.
4. После возобновления HW сравнить варианты на одном ELF и одинаковых настройках.
   Сначала F411, затем переносимость на F030/F103/F401; F429 — при наличии стенда.
   Фиксировать MCU, GDB, backend, оптимизацию, ABI, хеши ELF/manifest и влияние halt/reset.
5. Для finish отдельно учитывать изменение точки наблюдения: возврат HAL и
   последующий checkpoint приложения проверяют разные свойства. Сохранить оба,
   если исключение одного ослабляет сценарий.

На каждый этап создаётся отдельный RU/EN отчёт `eN.md`; обезличенные JSON —
в `results/`, ссылки на них — в отчёте и реестре. Записывать исходные FAIL/ERROR,
не заменять их удачными повторами. Raw-журналы, ELF и локальные TOML не коммитить.

## Заключительные этапы

### E5: проверка соответствия перед принятием

Основания: [api-evolution.md](../../rc3-gdb-python/ru/api-evolution.md),
[api-proposal.md](../../rc3-gdb-python/ru/api-proposal.md),
[execution-context.md](../../rc3-gdb-python/ru/execution-context.md).
Этап выполняется после E1–E4; обозначения этапов E1–E6 не являются номерами
правил E1–E12 из api-evolution.md.

Для каждого метода и модели данных подготовить следующий список проверок:

- Простота и однозначность назначения; разделение чтения, продолжения, вмешательства.
- Имена, типы, единицы, параметризуемость, keyword-only политики и лимиты, defaults.
- Преемственность относительно rc.2: прежние сценарии, типы, ошибки и поведение;
  классификация additive/behavioral/breaking, обнаружение отсутствующей возможности.
- Материализация, типизация, происхождение и доступность данных; отсутствие живых
  объектов GDB, неизменяемость снимков либо явно согласованная семантика копий.
- Время жизни, run/stop/revision и инвалидация после resume, записи, reset/reconnect;
  различение снимка и ссылки на кадр, границы согласованности состояния MCU.
- Различение неверного входа, неподдержанного случая, FAIL и ERROR; полнота стека
  и недоступные значения без подстановки фиктивного успеха или нуля.
- Отсутствие скрытого resume/call/retry/fallback; главный поток GDB, явные эффекты MMIO.
- Владение ресурсами, пределы памяти/точек, бюджет времени, cleanup и сохранение
  первичной ошибки; поведение при исчерпании и прерывании операции.
- Границы API/техник/шаблонов; поддержка по операции/ABI/MCU/backend/GDB,
  раздельные verified/untested/known failure и подтверждающие отчёты.
- Проверяемость, отрицательные случаи, миграция, документация и трассировка требований.

В отчёте `e5.md` у каждого пункта указать метод, ссылку на конкретный пункт
исходного документа, свидетельство и статус: соответствует / частично / расходится /
не проверено / неприменимо (с причиной). Не считать намерение доказательством.
Отдельно перечислить расхождения, предложения исправлений и вопросы владельцу.
Уже известный вопрос E1: достаточно ли независимых изменяемых копий records для
журнала, если контекст исполнения требует глубоко неизменяемых снимков; не объявлять
эти разные контракты автоматически равнозначными. Объём provenance также проверить.

### E6: принятие и применение

Условие входа — рассмотренные результаты E5 и явное согласование владельцем
состава API, допустимых ограничений и оставшегося долга. План не является принятием.

1. Ответить на открытые вопросы исходного предложения и новые вопросы E5;
   согласовать окончательные сигнатуры, модели данных и ошибки.
2. Согласовать формат и правила версии API, связь с API_VERSION, версией пакета,
   схемами данных и ревизиями ТЗ; определить совместимость и релизную цель.
3. Зафиксировать принятые соглашения и отдельное ТЗ API с перекрёстными ссылками
   на общее ТЗ, не дублируя требования; подготовить миграцию и критерии приёмки.
4. После утверждения переноса реализовать принятый объём в ядре и переработать
   текущие сценарии с сохранением проверок и ожидаемых исходов; обновить API RU/EN,
   CHANGELOG и нормативные документы по правилам проекта.
5. Выполнить регрессию старых вызовов и приёмку переработанных сценариев на
   согласованных конфигурациях, сохранить сравнение и ограничения в `e6.md`.
   Публикация и выпуск — отдельный шаг владельца.

## Отложенные инструменты

Watchpoints, вызовы функций через GDB, произвольная запись PC, универсальный откат
MMIO, RTOS и расширенные ассемблерные операции не входят в E1–E4. Арифметика
счётчиков, диапазоны и MCU-специфичные ожидания остаются техниками потребителя.
Итог исследования — рекомендация по составу API и ограничениям, затем отдельное
согласование соглашений/ТЗ API и переноса в ядро; релизная цель не утверждается автоматически.
