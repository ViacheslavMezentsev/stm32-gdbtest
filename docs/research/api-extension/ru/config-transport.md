## Транспорт

JSON-конверт содержит исходные байты session/target/api/image в base64 и SHA256,
а не JSON-копию разобранного TOML. Получатель проверяет конверт/хеши/набор файлов,
снова разбирает захваченные байты штатным TOML-парсером, применяет валидацию и
defaults, создаёт неизменяемые config/config_props. Исходные пути не открываются.
Отдельный fingerprint defaults отклоняет несовпадающий набор умолчаний вместо
молчаливого изменения поведения на принимающей стороне. Это экспериментальная
схема research-config/1, не новая версия производственного пакета или API.

Проверены дата, локальный/offset datetime, время с микросекундами, integer,
bool, Unicode, вложенные массивы/таблицы, ±Inf, NaN и отрицательный ноль.
Неизвестные поля и исходные хеши сохранены; defaults отсутствуют в props.data.
Указанные float допустимы в неизвестных TOML-данных, но это не расширяет record().
Повреждение base64/хеша, версии, defaults, состава файлов и duplicate JSON keys
отклоняется. Пересчитанный хеш не обходит проверку известного параметра.

Экспериментальный ZIP содержит только config.json. После удаления временного
исходного каталога снимок читается из ZIP без исходных файлов. Это моделирует
недоступность исходных путей, но не является запуском на Orange Pi/по SSH.
Ни новый ZIP, ни base64-конверт не интегрированы в production ddtt-package.

## CMake и совместимость

research_attach вызывает неизменённый stm32_gdbtest_attach. Старый режим создаёт
обычный JSON из восьми полей. Новый выбирает target общим Python-загрузчиком и
создаёт отдельный research-session.json с session_config/profile; конфликт PROFILE
отклоняется. Проверены настоящие CMake configure/generate с Ninja/ARM GCC в Docker.
Зарегистрированные production CTest-команды пока используют старый JSON: новый
descriptor проверяется bridge отдельно. Это не готовая интеграция CTest с config.

Bridge проверяет согласованность выбранного пути target с descriptor, захватывает
новые API-настройки без пересборки и сохраняет предыдущий снимок. Проверка
устаревшего пути target не заменяет ELF/build-manifest проверку при изменении
содержимого target по прежнему пути. Для неё сохраняются штатные проверки ядра.

Реальный старый запуск F030 HW_CI_ADC_UNITS в режиме prepare-only: PASS, contracts
PASS, connection_attempted=false; ELF SHA256 начинается d6bfed5a. Без HW-подключения.
Linux host-регрессия ядра: 114 тестов, 4 платформенных skips, PASS.

## Результаты и сохранённые ошибки

- Windows: 64 теста, 63 PASS и 1 skip CMake (нет cc/ARM GCC в PATH).
- Linux CI: 64/64 PASS, включая CMake old/new/conflict.
- Первый Linux-прогон тоже пропустил CMake: fixture искал только cc. Добавлен
  существующий ARM GCC. Затем получен FAIL «No hardware cases found»: пустой
  тестовый каталог корректно отвергнут production collect. Добавлен собираемый
  фиктивный case, который не исполняется на MCU; после исправления 64/64 PASS.
- Первичные пропуск и FAIL сохранены в реестре; нельзя считать их успешной
  проверкой CMake до исправления fixture.
