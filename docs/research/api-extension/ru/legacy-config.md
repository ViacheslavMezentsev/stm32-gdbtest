# Legacy: config/config_props без session.toml

[Исследование](index.md) · [English](../en/legacy-config.md)

03.10.2026. Изолированный [legacy_config.py](../../../../tests/api-extension/legacy_config.py)
формирует снимок для уже выбранного JSON-дескриптора или распакованного старого
пакета. Это исследование требований общего ТЗ 5.20.10–5.20.11; ядро, CLI и агент
не изменены. Новый загрузчик вызывается явно, production Target этих свойств ещё не имеет.

## Что проверено

| Случай | Результат |
| --- | --- |
| Старый профиль без дополнительных файлов | target из фактического файла; api defaults и props.api=None; image=None в обоих views |
| Соседние session.toml/api.toml | Не обнаруживаются автоматически, даже если session.toml невалиден |
| Выбор image | Явный аргумент выше STM32_GDBTEST_IMAGE_POLICY; невалидный выбранный файл не заменяется запасным |
| Внутреннее image_policy_path | Не становится новым источником выбора: runner формирует его из аргумента/окружения |
| Захват и изменение исходников | Файлы читаются по одному разу; data и SHA256 относятся к исходным байтам, снимок переживает удаление пути |
| Неизменяемость | Вложенные таблицы/списки и свойства оболочки не допускают изменения |
| Старый пакет | Штатные pack/open_package; после переноса исходного каталога reference указывает на фактические распакованные файлы |
| Политика image внутри ZIP | Включение в ZIP не активирует её; путь выбирается явно после распаковки |
| Ошибочные TOML/диапазон/неизвестные поля target и image | Отказ валидации, строгие схемы сохраняются |

Как в текущем runner, относительные пути разрешаются от рабочего каталога процесса,
а не от расположения session.json. Новая семантика путей session.toml не переносится
на старый режим. session_sha256=None: не создаётся фиктивный session.toml.
API defaults не получают выдуманный источник.

## Свидетельства

[Шесть тестов](../../../../tests/api-extension/test_legacy_config.py) используют реальные
валидаторы и штатную упаковку; ELF синтетический, он не выполняется и не считается
успешной проверкой прошивки. Поиск GDB для открытия пакета в тесте подменён; весь
набор дополнительно выполнен внутри настоящего GDB-Python.

- Windows: 79 тестов, 78 PASS / 1 CMake skip (нет компилятора в PATH).
- Linux Docker: 79/79 PASS; документация CI: 4/4 PASS.
- GDB14/Python3.11.4 и GDB16/Python3.13.12: по 6/6 PASS.
- [GDB14](../results/legacy-config-gdb14.json), [GDB16](../results/legacy-config-gdb16.json).
- [Первоначальный FAIL](../results/legacy-config-initial-failure.json): ожидание сравнивало frozen-снимок с обычными списками load_profile. Исправлено ожидание; загрузчик не менялся.

Host: `python -B -m unittest discover -s tests/api-extension -q`.
GDB: импортировать `run_legacy_config` из tests/api-extension и вызвать
`run_legacy_config.run('<result.json>')`; корень репозитория также нужен в sys.path.
Запуск: `-nx -batch -q -iex "set auto-load off"`, без ELF и target remote.

## Границы и следующий шаг

Проверены свойства выбранных файлов и изолированный снимок. Production runner ещё
повторно читает свои файлы; подключение снимка к его prepare/agent и проверка
единого источника при реальном запуске остаются интеграционной работой. Transport
нового режима не изменён: legacy-снимок не передаётся в dumps, ожидающий session.toml.
Старый пакет не получает новый формат или неявный выбор image.

Следующий шаг — собрать итоговую матрицу готовности первого пакета: проверено,
остаётся в прототипе, требуется при интеграции. До переноса остаются согласование
чисел Q6/Q19, публичного импорта/базового класса RecordError и отдельное разрешение
владельца. Ранние M5-сведения о непроверенных legacy views описывают прежний этап;
production-интеграция по-прежнему не выполнена.
