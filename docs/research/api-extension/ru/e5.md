# E5: соответствие соглашениям и готовность к принятию

[Исследование](index.md) · [English](../en/e5.md)

03.10.2026. Проверена реализация на `1e3d25c` и результаты E1–E4.
Это анализ, не утверждение API и не новый аппаратный прогон.
Исходные документы — проекты: [api-evolution](../../rc3-gdb-python/ru/api-evolution.md),
[api-proposal](../../rc3-gdb-python/ru/api-proposal.md),
[execution-context](../../rc3-gdb-python/ru/execution-context.md).
Согласованное уточнение текущего исследования: record — runtime-журнал; экспорт
и адаптеры пока вне объёма. Отличие от прежнего предложения записи в отчёт само
по себе не является дефектом. Остальные отличия нельзя молча объявлять принятыми.

## 1. Свидетельства и критерии оценки

Операции: R — record/records, V — read, C — capture/stack/caller, F — finish.
«Соответствует» относится к проверенной экспериментальной области, не всему
первоначально предложенному API. «Частично» — свойство реализовано не полностью;
«расходится» — наблюдаемая семантика отличается; «не проверено» — доказательств нет.
«Неприменимо» требует причины. Прохождение host-тестов не доказывает HW-контракт.

- R: [E1](e1.md), [парное сравнение](e1-comparison.md), evidence.py/test_record.py,
  test_scenario_variants.py. Проверены снимки, порядок, лимиты, запросы, статистика.
- V: [E2](e2.md), typed_read.py/test_typed_read.py: глобальные RAM-объекты, F411.
- C: [E3](e3.md), stack_context.py/test_stack_context.py: SysTick/WFI, F411.
- F: [E4](e4.md), natural_finish.py/test_natural_finish.py: top frame, void/integer, F411.

Все перечисленные реализации находятся в [tests/api-extension](../../../../tests/api-extension).
Итоговая host-серия — 44/44 PASS; исправленные HW-серии отдельно по 4/4 PASS.
Первичные ERROR E3/E4 и оба восстановления сохранены в реестре. Это не единая
регрессия будущего интегрированного API. Ядро, текущие API RU/EN и общее ТЗ не
изменены относительно базы `b3d19e0`; полный набор старого API заново не прогонялся.

## 2. Список свойств по правилам api-evolution §2

Идентификаторы правил ниже не являются номерами этапов исследования.

| Правило / свойство | R | V | C | F | Основание и оставшийся вопрос |
| --- | --- | --- | --- | --- | --- |
| E1: простота, одно действие, явные эффекты | Соответствует | Соответствует | Частично | Соответствует | R — память, V — чтение, F — явный continue; C объединяет стек/PC/SP и не даёт отдельного frames API |
| E2: имена, типы, параметры, единицы/defaults | Частично | Частично | Частично | Расходится | Лимиты keyword-only есть; разные оболочки вместо Target, C использует stack/revision вместо frames/state_revision, F не имеет frame/timeout_s |
| E3: преемственность | Частично | Частично | Частично | Частично | Старый код не изменён, ADC/HAL-пары проверены; будущая интеграция и полный legacy-набор не проверены |
| E4: доступность новых возможностей, миграция | Не проверено | Не проверено | Не проверено | Не проверено | Нет публичного обнаружения capabilities или согласованной версии; removal/deprecation неприменимы — ничего не удаляется |
| E5: типы, материализация, provenance/availability | Частично | Частично | Частично | Частично | Нет живых GDB-объектов в результатах; общая модель происхождения и доступности отсутствует, подробности §3 |
| E6: различимые ошибки и исходы | Частично | Частично | Частично | Расходится | R объединяет ошибки в RecordError; V смешивает отсутствующее поле с unreadable; C использует общие исключения; F сводит fault/exit к interrupted |
| E7: отсутствие скрытых continue/call/fallback/retry | Соответствует | Частично | Соответствует | Частично | V не вычисляет C, но неоднозначные символы не проверены; F один continue и hardware point, однако multiple locations/ABI не разрешены общей политикой |
| E8: владение, пределы, cleanup, бюджет | Частично | Частично | Частично | Частично | R/V/C имеют лимиты; затраты не измерены. F сохраняет guards, но считает объекты точек, не locations; cleanup имеет отдельные оговорки §3 |
| E9: главный поток и lifetime | Соответствует | Соответствует | Частично | Частично | R не вызывает GDB; V/F работают в главном потоке сценария; C/F не связаны с полной моделью thread/inferior/reset |
| E10: подтверждённая конфигурация | Частично | Частично | Частично | Частично | Отчёты закрепляют F411/GDB14/OpenOCD; программная диагностика поддержки отсутствует, другие сочетания не объявляются проверенными |
| E11: требования, TC, матрица | Частично | Частично | Частично | Частично | Есть экспериментальные контракты/тесты/отчёты, но нет утверждённого отдельного ТЗ API и нормативной трассировки |
| E12: утверждение до переноса | Соответствует | Соответствует | Соответствует | Соответствует | Прототипы разрешены отдельно, ядро не изменено; согласование и итоговая приёмка ещё впереди |

## 3. Сопоставление методов и моделей с двумя другими проектами

| Метод / модель | Источник | Статус | Конкретное отличие / действие |
| --- | --- | --- | --- |
| record/records | api-proposal §3, api-evolution E5/E8 | Частично | Runtime-назначение уточнено владельцем; копии защищают журнал, но сами изменяемы. Нужен явный выбор контракта, не подмена immutable context. Provenance сейчас только имя/sequence внутри экземпляра |
| read / ValueSnapshot | api-proposal §3 и §6 | Частично | Есть тип/размер/value, нет kind/availability/provenance в снимке, frame/local не поддержаны; ширина/знаковость отдельно не описаны. Явно утвердить меньший контракт или дополнить |
| Context | execution-context «Предлагаемая форма» | Расходится | __getitem__ не делает объект полноценным Mapping; нет stop/meta/availability, requested registers, selected_index; stack вместо frames. Удобный ['PC'] подтверждён, остальная схема — нет |
| StackSnapshot/caller | api-proposal §3.1 и §6, execution-context заключение | Частично | Есть кадры/complete/reason, но метаданные только у родительского Context; нет FrameRef, frame/arguments/locals/find_caller. Точная глубина/unknown работают; None-caller требует явной проверки, иначе bool(None) скрывает неопределённость |
| Исторические снимки | execution-context «Актуальность и согласованность», пп. 1–4 | Частично | Иммутабельность и чтение после resume подтверждены; run_id — ID экземпляра, current не сравнивает thread/inferior/image. Возможен ложный current при смене потока без события |
| События/вмешательства | execution-context пп. 2, 6 | Частично | Явный invalidate допускается проектом для raw GDB; но интеграция с Target.set_value/force_return/reset ещё не обеспечена, не все lifecycle-пути проверены |
| Согласованность MCU | execution-context п. 5 | Соответствует | Нет обещания атомарности DMA/MMIO; V принимает явные RAM-диапазоны, C не читает память периферии |
| ReturnResult/StopResult | api-proposal §4, §6 | Расходится | F не возвращает общий StopResult/Context или ValueSnapshot; содержит только номера точек и signal. Потеря соединения/fault не имеют согласованной диагностической модели |
| finish и timeout | api-proposal §4, §7; api-evolution E8 | Частично | Внешний бюджет case сохраняется, отдельного timeout_s и выбранного frame нет; scalar/void HW PASS не доказывает общий finish |

Инспекционные замечания, ещё без отдельной отказной проверки:

- C.close при исключении disconnect может прекратить очистку и подменить исходную
  ошибку из with. Это не закрывается успешной проверкой «0 обработчиков».
- F.cleanup_errors сохраняется в backend, но не включается автоматически в
  ReturnResult/системную диагностику. После внешнего завершения GDB Python finally
  может не выполниться; восстановление обеспечивает host, не этот прототип.
- F использует адрес возврата и SP как свидетельство возврата, не отслеживает
  тождество выбранного вызова для всех рекурсивных/нештатных переходов.
- Ошибка E3 из-за отсутствующей константы и ошибка E4 из-за срока жизни breakpoint
  показывают пробелы исходных host-моделей; добавленные регрессии не заменяют матрицу GDB.

## 4. Решения для обсуждения, а не принятый API

| Кандидат | Рекомендация | До принятия |
| --- | --- | --- |
| record/records | Первый небольшой пакет | Утвердить runtime-only область, копии, лимиты, иерархию ошибок, принадлежность запуску/сценарию; не требовать экспорт сейчас |
| read | Сохранить кандидатом после доработки модели | Утвердить ограниченную RAM/global область либо расширить; связать provenance, availability и удобное извлечение значений |
| frames/context + caller-техника | Сохранить кандидатом после унификации | Mapping/ключи, общий StackSnapshot, thread/inferior/revision, неизвестный конец и caller unknown, cleanup |
| finish | Оставить экспериментальным | Fault/exit/timeout, ABI/capabilities, locations, выбранный frame и интеграция cleanup/контекста; затем новая приёмка |

Первые три пункта не означают готовность немедленно скопировать код в ядро.
Общий вывод: исследовательская полезность подтверждена, соответствие полного
предложения API — нет. Простое уменьшение объёма кода не доказано; основная польза
сейчас — журнал, типизированные данные и отделение механики GDB от техники сценария.

## 5. Открытые вопросы и порядок E6

Q1–Q12 из [конца плана](plan.md) остаются открытыми. Добавлены Q13–Q16:
cleanup при ошибке, полноценная модель контекста, формат результата unknown и версии.
Рекомендации не помечать как согласованные ответы.

По [действующей политике](../../../ru/VERSIONING.md) новые функции до 1.0 относятся
к 0.2.0; имя исследования rc3 не меняет правило. Рекомендация — сохранить SemVer
пакета и независимость API_VERSION/схем/ревизий ТЗ. Номер API_VERSION и критерий
его изменения нужно согласовать отдельно; не увеличивать автоматически вслед за пакетом.

E5 завершён как проверка соответствия, не как успешная приёмка всех методов.
Следующий шаг E6 — решение владельца по первому составу, версиям и вопросам,
затем фиксация контрактов/ТЗ и отдельное разрешение переноса. Пока решения нет,
ядро, старые сценарии и версии остаются прежними. Новых аппаратных запусков E5 нет.

[Продолжение E1–E4 на F0/F1](portability.md): 8/8 HW на каждой плате, ограничения и сохранённый prepare ERROR. [ТЗ API 0.1.0](../../../TECHNICAL_SPECIFICATION_API.md) фиксирует текущий rc.2, без переноса расширений. Следующий этап — разбор Q1–Q16 и согласование E6.
