# E6: первый пакет расширения — проект решения

[Исследование](index.md) · [English](../en/e6-proposal.md)

База: коммит 1e16415, [ТЗ API 0.1.0](../../../TECHNICAL_SPECIFICATION_API.md),
[E5](e5.md) и [F0/F1](portability.md). Документ подготовлен 03.10.2026.
Это предложение для согласования. Контракт 0.1.0 и ядро не изменяются;
разрешение продолжать исследование не принимается за разрешение переноса.

## Принятые решения — 03.10.2026

Владелец согласовал Q1 и Q2 для первого пакета: глубокое копирование на записи
и чтении с изменяемыми независимыми результатами; обычные значения/словари без
прямого приёма Snapshot и автоматических преобразований. Эти вопросы закрыты.
По Q5 согласована история журнала: continue/reset внутри сценария её сохраняют,
новый сценарий начинает пустой журнал. Актуальность context/read остаётся открытой.
Остальные положения ниже — предложения. Это не разрешение реализации в ядре;
спецификация 0.1.0 продолжает описывать текущий rc.2.

## 1. Состав

Предлагается принять первым пакетом только `Target.record` и `Target.records`.
Их польза — накопление наблюдений, запросы и статистика в одном сценарии;
сокращение количества строк парное сравнение не показало. API не должен
подменять обычную локальную переменную, если журнал не нужен.

`read`, context/stack/caller и `finish` остаются кандидатами. Проверки F0/F1
расширили свидетельства, но не устранили вопросы lifetime, availability,
неполного стека, ABI, timeout и cleanup. RTOS и долг первого исследования
остаются на паузе.

## 2. Предлагаемый контракт журнала

| ID | Условие / операция | Предлагаемое поведение |
| --- | --- | --- |
| J1 | `record(name, data) -> None` | Добавить независимую глубокую копию после полной проверки; одинаковые имена допустимы |
| J2 | `records(name=None) -> list[dict]` | Вернуть независимые глубокие копии в порядке добавления; строка фильтрует по точному имени; отсутствие совпадений даёт `[]` |
| J3 | Структура записи | Ровно `sequence`, `name`, `data`; sequence начинается с 1 и сквозной внутри журнала, при фильтрации не перенумеровывается |
| J4 | name / фильтр | Только точный встроенный str, непустой; None допустим только как отсутствие фильтра |
| J5 | data | Только точные встроенные None/bool/int/конечный float/str/list/dict со строковыми ключами; подклассы, tuple, bytes, GDB-объекты и циклы отклоняются |
| J6 | Ошибка записи | Нет частичной записи, расхода логического бюджета и пропуска sequence; существующие записи неизменны |
| J7 | Владение | Один журнал на вызов сценария, новый вызов начинает с пустого; не разделяется между cases, платами и процессами |
| J8 | Время жизни | Resume/reset внутри того же сценария не очищают историю. `clear()` сохраняет прежний смысл очистки точек и не очищает журнал. Конец сценария освобождает владение журналом; уже полученные копии обычные Python-данные |
| J9 | Эффекты | Только память Python; нет GDB-вызовов, чтения MCU, continue, файлового ввода-вывода, автоматической записи в report или изменения PASS/FAIL |
| J10 | Происхождение | sequence означает порядок записи автором, а не номер остановки MCU. Нет автоматических PC, времени, image/thread/run ID или обещания атомарного аппаратного снимка |
| J11 | Запросы | Фильтрация/срезы/any/all/mean/stdev средствами Python; отдельный язык запросов не вводится. `all([])` истинно: непустоту проверяет сценарий |
| J12 | Ресурсы | Решение владельца 03.10.2026: лимиты — параметры сценария с внешней конфигурацией; итоговая конфигурация запуска доступна сценарию только на чтение. Общий контракт согласуется в Q20 |

J7–J9 требуют проверки после интеграции: исследовательская оболочка не является
доказательством поведения будущего Target. Экспорт/адаптеры, общая неизменяемая
модель Context и очистка журнала отдельной операцией не входят в пакет.

Предлагаемые значения по умолчанию на один журнал (числа ещё не утверждены): 128 записей, 4096 узлов, 65536 UTF-8 байт текста;
глубина data не более 8 (корень имеет глубину 0), int.bit_length не более 256.
Узел — каждое посещённое значение, включая контейнеры, ключи dict и имя записи;
текст — имя, ключи и строковые значения. Служебные поля обёртки не учитываются.
Повторная ссылка на один объект копируется и учитывается заново; Unicode с
непарными суррогатами отклоняется. Проверка лимитов относится к входу/журналу,
не является точной верхней оценкой RSS процесса: копии `records()` занимают
дополнительную память, удерживаемую вызывающим кодом.

Прежняя рекомендация фиксированных лимитов отклонена владельцем 03.10.2026.
Настройка входит в первый пакет через общий механизм конфигурации (Q20),
а не через доступ к внутреннему Journal. Состав пакета теперь включает этот механизм.

## 3. Ошибки и наблюдаемость

Предлагается публичный `RecordError(ValueError)` с машинно-читаемым `code`:
`invalid_name`, `unsupported_type`, `invalid_text`, `non_finite`, `cycle`,
`limit_exceeded`. Для последнего — `limit` со значением `records`, `nodes`,
`depth`, `text_bytes` или `integer_bits`. Текст сообщения не используется как код.
Если нарушено несколько условий, гарантируется отказ без записи; приоритет
диагностик не фиксируется. Это **доработка**, не уже проверенный контракт E1.

Ошибка входа в records также даёт invalid_name. Ошибки среды, включая MemoryError,
не маскируются под отказ проверки данных. Необработанные исключения дают системный
ERROR; несовпадение ожидания через check — FAIL. В будущей интеграции RecordError
предлагается экспортировать из stm32_gdbtest для явного перехвата.

Доступность проверяется по наличию обеих вызываемых операций до первого
действия нового сценария. Отсутствие — явный ERROR с требованием версии,
без тихого пропуска или fallback. API_VERSION пока не служит реестром методов.

## 4. Ревизии и версии — предложение

| Величина | Предложение |
| --- | --- |
| ТЗ API 0.1.0 | Неизменная база описания действующего rc.2 |
| PATCH документа: 0.1.1 | Уточнение/исправление контракта без изменения совместимого поведения; новое измерение платы само по себе не требует ревизии |
| MINOR документа: 0.2.0 | Принятые новые совместимые операции, например record/records |
| Несовместимость | Отдельное решение и миграция; после 1.0 — MAJOR, до 1.0 — MINOR с явным признаком breaking; никогда не скрывать в PATCH |
| Пакет | По действующей VERSIONING: расширение планировать на 0.2.0, точный prerelease выбрать при подготовке выпуска |
| API_VERSION | Предлагается сохранить 1 при совместимом добавлении; существующие операции/соглашение case не меняются. Изменение смысла этого номера — отдельное решение |
| Схемы JSON/TOML | Не менять ради runtime-журнала, который не экспортируется |

Ревизия документа и версия пакета независимы, даже если оба номера окажутся
0.2.0. Сначала согласуется контракт, затем отдельно разрешается реализация.
Новая ревизия описывает принятые требования; статус реализации и проверки
фиксируется отдельно. Само повышение номера не означает выпуск или HW PASS.


Статусы и принятые решения Q1–Q20 ведутся в [реестре плана](plan.md).
Рекомендации этого документа сами по себе не закрывают вопросы.

## 6. Приёмка после разрешения реализации

Идентификаторы A1–A6 локальны этому предложению, не являются TC утверждённого ТЗ.

| Проверка | Критерий |
| --- | --- |
| A1: перенос контракта | Новые номера ТЗ API и TC, таблица J → требование → проверка; старые восемь операций неизменны |

## Q20: session.toml и связанные файлы

Принято владельцем 03.10.2026: внешний session.toml связывает конфигурации
текущей сессии сценария. api.toml — отдельный файл особенностей и настроек API;
предложение объединить их в scenario.toml отменено. Сценарию доступна конфигурация
запуска на чтение. Конкретный интерфейс чтения ещё обсуждается.

```toml
# session.toml
[config]
api = "api.toml"
target = "target.toml"
image = "full_image.toml"
```

Это TOML-запись принятых config.api/config.target/config.image.

| Файл | Ответственность | Статус |
| --- | --- | --- |
| session.toml | Выбор связанных файлов конфигурации сессии | Принято, не реализовано |
| api.toml | Настройки используемого в сессии API, включая лимиты журнала | Выделение принято; схема содержимого открыта |
| target.toml | MCU и ограничения аппаратного профиля | Существующая схема 1 |
| full_image.toml | Политика образа: область, fill и CRC | Существующая схема [image], выбранное имя файла |

Имена выбираются ссылками: существующие full-image.toml не переименовываются.
Проверено по коду 470d90c: profile.load_profile строго проверяет target;
full_image.load_policy читает [image], проверяет по target и возвращает таблицу
с SHA256 файла. Runner передаёт profile/full_image_policy агенту через run.json,
но Target получает только внутренний изменяемый profile. Публичного общего
интерфейса чтения конфигураций пока нет.

Существующий session.json — сгенерированный служебный артефакт запуска, который
сейчас принимает --session. Новый session.toml — предлагаемая пользовательская
точка входа конфигурации; он не заменяет JSON автоматически. Загрузка TOML,
его связь с CMake/CLI/JSON и сохранение старого пути запуска требуют контракта.

Предложение интерфейса (не утверждено): ключи совпадают с именами config.*,
содержимое сохраняет структуру соответствующего TOML:

```python
mcu = t.config["target"]["mcu"]
image_end = t.config["image"]["image"]["end"]
limit = t.config["api"]["journal"]["max_records"]
```

Двойное image здесь означает выбранный документ и его существующую таблицу
[image]. Можно обсудить более удобную форму, не меняя сам файл.

Пункты 1–3 приняты владельцем 03.10.2026; пункты 4–5 остаются предложениями:

1. Относительные пути config.* разрешать относительно session.toml, а не cwd.
   Не искать одноимённый файл автоматически в соседних каталогах.
2. Загружать/проверять выбранные файлы до подключения к MCU; передавать сценарию
   неизменяемый снимок содержимого, а не перечитывать пути в GDB. Изменение исходного
   файла после подготовки не меняет текущий запуск; удалённому стенду не требуются
   исходные пути компьютера пользователя.
3. config.target обязательна. config.api необязательна: без ссылки используются
   документированные настройки API по умолчанию. config.image необязательна:
   без ссылки сохраняется проверка загружаемых ELF-секций. Если ссылка указана,
   отсутствие или некорректность файла даёт ERROR до подключения к MCU;
   другой файл или defaults вместо ошибочного файла не подставляются.
   Численные defaults и допустимость пропущенных полей внутри api.toml ещё обсуждаются.
4. Отдельно определить место параметров самого тестового скрипта: решение об
   api.toml не означает автоматического размещения в нём порогов/ожиданий платы.
5. Определить метаданные источников/hash, доступ к конфигурации стенда и сохранение
   для воспроизведения. Подставленные defaults отличать от содержимого файла.

Q20 остаётся открытым с принятым составом/связями файлов. Общая схема приоритетов
декоратора и overrides не принята. Системное ТЗ владеет загрузкой/проверкой/передачей,
ТЗ API — публичным чтением и применением лимитов. Ядро и ТЗ API 0.1.0 не меняются.
Q6/Q19 остаются открытыми. Приёмка: выбранный файл против соседнего, отсутствующая
ссылка против ошибочного пути, изменение оригинала после снимка, удалённый запуск,
запрет вложенной мутации и проверка конфигурации до подключения.

### Следующее предложение: содержимое api.toml

Не согласовано; числа взяты из исследовательского прототипа:

```toml
schema = 1

[journal]
max_records = 128
max_nodes = 4096
max_text_bytes = 65536
max_depth = 8
max_integer_bits = 256
```

Предлагается: schema обязательна при наличии файла; journal и отдельные его поля
можно опускать с применением документированных defaults. Неизвестные поля,
неподдержанная схема и неверные значения дают ERROR до подключения. Лимиты —
положительные целые, bool не принимается. Верхние допустимые границы требуют
оценки Q6/Q19; произвольные величины не объявляются проверенными.
Номер схемы файла не является версией спецификации API или API_VERSION.
Параметры/пороги самих тестов сюда пока не включаются: их размещение — оставшаяся
часть Q20. Принятие структуры не означает согласования численных defaults.

### Как сейчас появляется session.json

stm32_gdbtest_attach в STM32GDBTest.cmake использует file(GENERATE) на стадии
генерации CMake и записывает build/<конфигурация>/hwtest/session.json.
Поля: elf, gdb, tests, root, out, stand, profile, build_manifest. Это ссылки на
артефакты и каталоги, а не содержимое target.toml и не результат тестирования.
stand может быть пустым; его можно выбрать при запуске. Сам ELF и build-manifest
появляются при сборке: manifest создаётся POST_BUILD, не генерацией session.json.
CLI читает JSON, выбирает case по --test и передаёт данные runner. Runner загружает
конфигурации и создаёт отдельный run.json для GDB-агента; результаты пишутся отдельно.
image policy сейчас выбирается через --image-policy или переменную окружения,
восемь полей CMake session.json её не содержат. Схема файла внутренняя, без обещания
стабильного пользовательского формата; вручную штатный сгенерированный файл не правят.
