## Оставшиеся решения первого пакета

| Решение | Рекомендация | Статус |
| --- | --- | --- |
| Q6/Q19, API 10.2.4 | defaults/max: records 128/1024, nodes 4096/32768, text_bytes 65536/524288, depth 8/32, integer_bits 256/1024 | Согласовано 03.10.2026 |
| Критерий затрат | Повторить набор на интеграции; расследовать ухудшение медианы более чем вдвое в сопоставимой среде; не обещать RSS/latency | Согласовано 03.10.2026 |
| API 10.2.5 | `from stm32_gdbtest import RecordError`; наследник ValueError, импорт доступен и без GDB | Согласовано 03.10.2026 |
| Перенос | Только принятый первый пакет, отдельным этапом с обновлением документации и регрессией | Разрешение не получено |

Импорт из корня пакета позволяет сценариям не зависеть от внутренних модулей.
Класс ошибки не нуждается в GDB; это сохраняет возможность host-проверок.
ValueError соответствует ошибке входных данных и уже используется прототипом;
для точного перехвата сценарий использует RecordError.code/limit.

Пример предлагаемого публичного использования, пока не работающий в ядре rc.2:

```python
from stm32_gdbtest import RecordError

try:
    t.record('sample', measurement)
except RecordError as error:
    if error.code == 'limit_exceeded':
        raise RuntimeError(f'record budget exceeded: {error.limit}') from error
    raise
```

Это явная политика сценария: пример не скрывает неполную серию измерений и не
пытается записать ещё одну запись в уже заполненный журнал.

Общая политика будущих breaking-изменений (API 10.2.2) остаётся открытой, но
конкретное совместимое добавление и версии первого пакета уже приняты.
Q3–Q5, Q7–Q15 относятся преимущественно к отложенным read/context/caller/finish.
Их не закрываем и не включаем автоматически. Требование сохранять первичную
ошибку при интеграции проверяется отдельно от общей будущей модели cleanup Q13.

## Порядок после решений

1. Записать согласованные числа и импорт новой ревизией ТЗ API; обновить его
   таблицу расхождений с учётом поздних исследований. Старые отчёты сохранить.
2. После отдельного разрешения переноса реализовать первый пакет: общий снимок
   конфигурации, транспорт/валидация, Target и ошибки, CMake/CLI/legacy.
3. Провести интеграционные положительные/отказные проверки из матрицы, регрессию
   прежних сценариев, парное сравнение на согласованных платах и повтор замеров.
4. Оформить отчёт приёмки; точный prerelease, слияние и публикация — отдельные шаги.

Следующий разговор — два решения о контракте: численные ограничения/критерий и
публичный импорт/базовый класс. Их принятие само по себе не разрешает перенос.

## Адаптация сценариев: до и после интеграции

Предлагаемый порядок (разъяснение следующего этапа, не разрешение переноса):

1. **До ядра:** довести изолированные настройки до согласованных границ; выбрать
   2–3 представительных сценария (серия VDDA/температуры, HAL/ADC с несколькими
   наблюдениями, конфигурируемый сценарий). Создать парные варианты через оболочку.
   Старые сценарии сохранить как контроль; ранее созданные варианты E1 использовать
   как основу. Ожидания и число проверок не ослаблять.
2. Проверить конфигурацию/подготовку и затем парные прогоны на согласованном стенде.
   Сравнивать смысл проверок и исходы, не равенство температуры между прогонами.
   При недоступном стенде явно оставить аппаратную часть непроверенной.
3. **После отдельного разрешения:** перенести API в ядро и переключить опытные
   сценарии с оболочки на настоящий Target. Повторить host/prepare и аппаратную
   приёмку, включая baseline/restore и отказные исходы.
4. **После успешной приёмки:** адаптировать остальной подходящий набор там, где
   журнал или конфигурация полезны. Простые проверки без накопления данных сохраняют
   прежние value/check; необязательно переписывать каждый сценарий.

Следующий практический шаг — проверка принятых верхних границ в прототипе, затем
выбор и подготовка парных сценариев. Это позволяет оценить API до его переноса,
а совместимость настоящего ядра подтвердить после него.
