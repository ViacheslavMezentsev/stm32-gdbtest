# Q20: переход к session.toml

[Исследование](index.md) · [English](../en/session-migration.md)

03.10.2026. Проект внедрения на базе 74cc842. Состав файлов и интерфейсы
config/config_props приняты; M1 принят владельцем: явный SESSION_CONFIG, сохранение JSON/старого режима и
отказы при конфликтующих источниках. Детали реализации далее остаются проектом. Изменений ядра и аппаратных запусков нет.

## Текущее поведение

STM32GDBTest.cmake выбирает PROFILE либо PROFILE_DIR/target.toml, создаёт
session.json с восемью полями и регистрирует CTest с --session <JSON>.
CLI читает JSON непосредственно; runner отдельно выбирает image policy из
--image-policy/STM32_GDBTEST_IMAGE_POLICY. Поэтому простого добавления ссылки
на TOML в сценарий недостаточно: проверка образа и сам сценарий должны видеть
одни и те же настройки. package.py сейчас явно собирает ELF, target, сценарии
и manifest; новые файлы автоматически в пакет не попадут.

## 1. Пользовательская конфигурация и описание сборки

Предлагается сохранить служебный session.json, но в новом режиме сделать
session.toml единственным источником выбора api/target/image:

```toml
# profile/session.toml
[config]
api = "api.toml"
target = "target.toml"
image = "full_image.toml"
```

В CMake добавить явно выбираемый параметр SESSION_CONFIG:

```cmake
# Предлагаемый синтаксис, пока не реализован
stm32_gdbtest_attach(firmware
    PROFILE_DIR "${CMAKE_CURRENT_SOURCE_DIR}/profile"
    SESSION_CONFIG "${CMAKE_CURRENT_SOURCE_DIR}/profile/session.toml")
```

PROFILE_DIR сохраняет роль каталога сценариев/requirements/contracts; имя
не превращает его в ещё один источник target. Одновременные SESSION_CONFIG и
PROFILE предлагается запрещать: в новом режиме target выбирает config.target.
Без SESSION_CONFIG сохраняется прежний путь запуска, включая PROFILE и все
прежние приоритеты. Автоматического обнаружения session.toml нет.

session.json получает ссылку session_config; ELF/GDB/tests/root/out/stand и manifest
остаются данными интеграции со сборкой. Поле profile можно сохранить для совместимости
внутренних потребителей, но оно вычисляется из config.target и сверяется с ним:
не два независимых источника. Менять восемь старых полей вручную не требуется.
Обычная команда run --session <сгенерированный JSON> не меняется. Прямой запуск
--session session.toml пока не предлагается: в этом TOML нет ELF/GDB/tests/out.

## 2. Один механизм загрузки

1. Общий host-загрузчик читает session.toml и связанные файлы, разрешает ссылки
   относительно каталога TOML, проверяет известные настройки, сохраняет неизвестные
   поля api.toml. CMake получает выбор target через этот же Python-механизм,
   без второй реализации разбора TOML в CMake.
2. Во время подготовки конкретного запуска runner получает единый снимок байтов,
   разобранных данных и defaults. Проверка образа использует именно его image/target,
   GDB-агент получает те же config/config_props. Повторного чтения исходных файлов
   внутри GDB нет. Проверки согласованности ELF/manifest остаются обязательными.
3. Чтение при configure и при запуске — разные фазы, не обещание вечного кэша.
   В пределах одного запуска хеш и данные каждого файла получаются из одного
   чтения. Изменение после создания снимка не меняет этот запуск.
4. CMake отслеживает session.toml и выбранный target; изменение выбора target
   требует обновления генерации/manifest. При обнаружении устаревшего выбора runner
   отказывает до подключения, а не запускает собранный образ с другим профилем.
   Настройки api/image — отдельные входы запуска; изменение лимита журнала само
   по себе не должно требовать перекомпиляции firmware.

## 3. Конфликты и отсутствие настроек

Предлагается: в новом режиме CLI/окружение не подменяют config.api/target/image.
Если переданы --image-policy или STM32_GDBTEST_IMAGE_POLICY, выдавать ERROR до
подключения с указанием конфликта. Для другого образа выбирать другой session.toml.
Даже одинаковую вторую ссылку не считать вторым разрешённым источником.
Без config.image действует принятое правило ELF-секций; переменная окружения
не должна незаметно включать другую политику.

--stand, --timeout и --identity-policy пока сохраняют прежнюю роль: для них
не вводились соответствующие ключи в новом TOML. Область config остаётся
конфигурациями api/target/image, не обещает описание всех параметров процесса.
Если позже потребуется доступ к стенду/таймауту, это отдельное расширение схемы.

В старом режиме существующие CLI/окружение работают по прежним правилам.
Указанный session.toml или связанный файл с ошибкой не вызывает fallback на старый режим.

## 4. Перенос на стенд и совместимость

pack/--package и удалённый запуск должны переносить снимки содержимого, а не
полагаться на исходные абсолютные пути. reference сохраняет исходную ссылку
для диагностики; фактический путь извлечения не подменяет её смысл.
Проверяется целостность исходных байтов и соответствие разобранным данным;
типам TOML вроде дат/времени нужно явное переносимое представление. Не превращать
их в строки молча и не удалять неизвестные поля ради JSON.

Влияние на manifest пакета и отчёты оценить отдельно; новую версию схемы не
назначать автоматически. Старые пакеты и старый путь session.json входят в регрессию.
Для старого режима интерфейс config/config_props требует явного описания:
target можно получить из profile, API — defaults, image — из фактически выбранной
политики. Источник помечается правдиво; не выдумывается отсутствующий session.toml.
Форма таких метаданных — оставшаяся часть Q20, не уже принятый контракт.

### Принято: перенос TOML и совместимость defaults — 03.10.2026

Решение владельца: передавать исходные байты выбранных TOML в base64 внутри
служебного JSON вместе с SHA256. Получатель проверяет хеши и разбирает переданные
данные, не открывает исходные пути. Типы TOML и неизвестные поля сохраняются;
для сценария это обычные неизменяемые config/config_props, base64 не является
публичным форматом значений API.

Набор defaults при подготовке и запуске должен совпадать. Несовпадение — ERROR
до подключения, без автоматической подстановки настроек принимающей стороны.
Для исправления нужна совместимая версия инструмента либо повторная подготовка
пакета. Fingerprint набора defaults проверен в M4; алгоритм/версия переносимого
конверта будут зафиксированы при интеграции. Совпадение defaults само по себе
не доказывает совместимость всех остальных контрактов версий.

Эта часть Q20 принята; остаются config_props старого режима, границы/конфликты
имён и детали интеграции. Нормативный API 0.1.0 и ядро не меняются.
