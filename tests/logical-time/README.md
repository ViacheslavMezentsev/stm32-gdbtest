# Автомат с логическим временем

[Техника TECH-022](../../docs/ru/TESTING_TECHNIQUES.md#tech-022) · [English](README.en.md)

Нейтральная учебная нагрузка: один C++-модуль для host и Cortex-M3 в Renode.
Это пример вызова реальных функций через API 3, без ядра модуля, плат, DMA и RTOS.

## Условия и независимые ожидания

`start(now, delay)` переводит IDLE/DONE/FAILED в WAITING; `poll(now)` переводит
WAITING в DONE при прошедших `delay` тиках. `fail()` переводит только WAITING в FAILED.
Повторные `poll`/`fail` не увеличивают счётчики завершения. Новый start после отказа
начинает новую эпоху без reset объекта. Активный автомат и delay вне 1..2^31−1
отклоняют start без изменения каких-либо байтов объекта.

Время — uint32_t. Вызывающий обеспечивает монотонное логическое время по модулю 2^32
и опрос до полного оборота от старта. Произвольное движение назад и пропуск целого
оборота неразличимы по одному uint32_t и не входят в контракт модели.
Половина диапазона — выбранное ограничение задержки, не средство обнаружить пропущенный оборот.

| Сценарий | Входы | Ожидание фаз |
| --- | --- | --- |
| TIME_THRESHOLD | start(100,10), poll 109/110/111 | WAITING/DONE/DONE; один успех |
| TIME_WRAP | start(0xfffffff8,10), poll 0xffffffff/1/2/3 | WAITING/WAITING/DONE/DONE |
| TIME_RETRY | start, fail дважды, poll; start(1000,10), poll 1009/1010/1011 | FAILED устойчив; WAITING/DONE/DONE новой эпохи |
| TIME_REJECT | delay 0/0x80000000/0xffffffff; start во время WAITING | отказ и побайтовая неизменность |

Дополнительно: опрос сразу после пропущенного порога, новый start после DONE,
счётчики попыток/успехов/отказов и защитные слова. Числа ожиданий выписаны в сценарии,
не получены вызовом той же формулы реализации.

## Дефекты и повтор

`DEFECT=1`: `>` вместо `>=` — порог срабатывает поздно (три сценария FAIL).
`DEFECT=2`: сравнение с абсолютным deadline — раннее завершение при wrap (один FAIL).
`DEFECT=3`: старое started после FAILED — преждевременный успех следующей попытки (один FAIL).
`DEFECT=0`: исправление. Renode выполняет четыре сценария для 1,2,3,0,0: 20 исходов,
из них ровно пять намеренных FAIL. Кампания требует конкретных имён упавших проверок,
сохранённого records, полного восстановления POD по размеру из ELF и cleanup VERIFIED.
Первичный FAIL остаётся FAIL; PASS кампании означает соответствие ожидаемой матрице.

## Запуск

```powershell
python tests/logical-time/run.py --host-only
python tests/logical-time/run.py --toolchain "$HOME/xpack-arm-none-eabi-gcc-14.2.1-1.1" --renode "C:/Program Files/Renode/renode.exe"
```

```sh
python3 tests/logical-time/run.py --toolchain /opt/xpack-arm-none-eabi-gcc-14.2.1-1.1 --renode /opt/renode-1.17.0/renode
```

Нужны g++ для host, ARM GCC/GDB-Python, Python 3.11+, Renode 1.17. Пути выбирайте
по установленным инструментам. Логи, входы, SHA-256 и summary — `build/logical-time/<id>`.
Linux на Windows: исходники и сборки в Docker volume, как в [локальном CI](../../docs/guides/ru/local-ci.md).

## Правильно и неправильно: API

- Правильно: `result = t.call("poll", 110, timeout=2)`, проверить `outcome` и
  `return_state`, затем `result["return_value"]`. В async-сценарии нужен `await`.
  Неправильно: сравнивать `t.call(...)` с числом — это словарь описания операции.
- Правильно: время передавать числом; `record` до `check`; сохранить POD через
  `symbol`/`memory` и проверить восстановление в finally, в том числе после FAIL.
  Неправильно: `t.read("poll(110)")` (скрытый вызов), reset между отказом и retry
  (скрывает дефект), повторять вызов ради получения того же значения (новый эффект).
- Возврат 0 функции start — отказ приложения, проверяется `check`; `refused`
  предназначен для ожидаемого отказа API, а не для числа, возвращённого прошивкой.
- `timeout=2` — бюджет вызова в секундах хоста, а 110 — логические тики модели.
  sleep ПК и await wait не продвигают этот источник времени.

Логическая проверка не измеряет физическую задержку и не доказывает корректность
IRQ/DMA, планировщика, watchdog или восстановления MCU. Снимок покрывает только POD
без указателей и внешних ресурсов; память стекового контекста обслуживается GDB.

## Проверенный объём

27.10.2026: host Windows/Linux — четыре варианта с точными ожидаемыми отказами;
Renode 1.17 Windows/Linux — по 20/20 ожидаемых исходов (15 PASS, 5 FAIL), включая
два прогона исправления. ARM GCC 14.2.1 / GDB 15.2.90. Capture и восстановление
POD проверены для всех исходов. Первая авторская ошибка сравнения словаря call
с числом обнаружена в Renode, сохранена отдельно и не засчитана как дефект модели.
Аппаратные свойства этим примером не подтверждаются.
