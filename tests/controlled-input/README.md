# Имитируемый вход: write и ret

[English](README.en.md) · [TECH-004](../../docs/ru/TESTING_TECHNIQUES.md#tech-004)

A5.1, выпуск 0.6.0. Один нейтральный C++-модуль собирается для host и Cortex-M3
в Renode. Ядро библиотеки не меняется; платы, GPIO, DMA, RTOS и приборы не участвуют.
Checkpoint-функции принадлежат только учебной нагрузке: добавлять такие hooks в
прошивку потребителя не требуется. В рабочем ELF выбирают существующие точки.

## Что доказывает опыт

Маршрут: предусловия → применение → потребление → ветка приложения → следующий
вход → восстановление. `write` подтверждает значение SRAM, `ret` — подставленный
возврат; ни один результат сам по себе не доказывает использование значения кодом.

| Сценарий | Независимое ожидание первого прохода | Исход |
| --- | --- | --- |
| HW_INPUT_BASELINE | Без воздействия consumed=0, active=0, reads=1 | PASS |
| HW_INPUT_SRAM | После refresh записано 1: consumed=1, active=1, reads=1 | PASS |
| HW_INPUT_RET_HIGH | Источник 0, ret(1): consumed=1, active=1, reads=0 | PASS |
| HW_INPUT_RET_LOW | Источник 1, ret(0): consumed=0, active=0, reads=0 | PASS |
| HW_INPUT_TOO_EARLY | До refresh записано 1, после него consumed=0; ожидание потребления 1 неверно | намеренный FAIL |
| HW_INPUT_EXCEPTION | Изменение SRAM, затем заданное Python-исключение до потребления | намеренный ERROR |

Успешные воздействия дополнены следующим штатным входом 0 и проверкой счётчиков.
`reads=0` при ret показывает пропуск тела; исходный источник имеет противоположное
значение. После ret приложение ещё не обработало возврат: проверка выполняется
только после продолжения до after_processing. Ret не требует await, навигация в
async def требует. При другом ELF необходимо повторно проверить точку остановки:
встраивание, LTO и оптимизация могут изменить доступность кадра и уже выполненные эффекты.

Все изменяемые данные — POD `input_state` (32 байта), включая счётчики и защитные
слова. Размер/адрес берутся из ELF, полный снимок и обратная сверка выполняются
в finally также при FAIL/ERROR. Журнал сохраняет SHA-256 до/после. Это восстановление
данных, не возврат PC/стека во времени; backend отдельно завершает сеанс. Оно не
покрывает потерю процесса GDB, питание, параллельные DMA/IRQ и внешние ресурсы.

## Запуск

```powershell
python tests/controlled-input/run.py --host-only
python tests/controlled-input/run.py --toolchain <каталог-GCC> --renode <путь-к-Renode>
```

На Linux те же параметры. Нужны host g++, ARM GCC/GDB с Python и Renode 1.17.
Host исполняет ту же обработку и модель пропуска sample_input, но не проверяет GDB ret.
Настоящие write/ret проходят штатный runner в Renode; каждый сценарий получает свежий
ELF-сеанс, вся шестёрка повторяется дважды: 8 PASS, 2 ожидаемых FAIL, 2 ожидаемых ERROR.

Артефакты: build/controlled-input/<UTC>/ — копии входов/хеши, ELF, версии инструментов,
логи сборки, result.json и records.json каждого прогона, summary.json кампании.
Анализ использует общие читатели result/records, проверяет целостность, полноту,
конкретные ошибки, численные ожидания и восстановление. Исходные FAIL/ERROR остаются
такими же. PASS кампании означает совпадение с ожидаемой матрицей, а не 12 PASS сценариев.
Отсутствующие/усечённые данные, другая ошибка или неверное восстановление отклоняются.

## Границы DDTT

Свидетельство относится к software-input: реакции обработчика на подготовленное
значение. Оно не квалифицирует проводку, кнопку, регистр GPIO или путь сбора данных.
Не называйте программную запись физическим нажатием. Время здесь не измеряется.
Отдельное поле observation фиксирует метод, значение, consumed/active/reads/cycles
и исключённые слои. Это соглашение примера, не новая схема runner.
