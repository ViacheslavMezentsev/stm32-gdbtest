# Буфер и повторное потребление

[English](README.en.md) · [TECH-004](../../docs/ru/TESTING_TECHNIQUES.md#tech-004)

A5.3, выпуск 0.6.0. Один нейтральный C++-модуль собирается для host и Cortex-M3
в Renode. Ядро библиотеки не меняется; платы, UART, DMA, прерывания, RTOS и приборы
не участвуют. Checkpoint-функции принадлежат только учебной нагрузке.

## Что доказывает опыт

Подготовленный пакет кладётся в буфер `inject_buf`, принадлежащий опыту, и обработчик
`handle_packet` вызывается явно через `Pointer("inject_buf", count=N)` с точной длиной
и сигнатурой. Штатный путь приложения (`receive` → `handle_packet(rx_buf, …)`) остаётся
соседним: после воздействия он обязан обработать следующий пакет как обычно.

| Сценарий | Независимое ожидание | Исход |
| --- | --- | --- |
| HW_BUFFER_BASELINE | Без воздействия один штатный пакет: accepted=1, sequence=1, тип 0x10 | PASS |
| HW_BUFFER_PACKETS | Два пакета опыта по порядку (0x21, затем 0x22), затем штатный: sequence=3 | PASS |
| HW_BUFFER_REJECT | Искажённая сумма отвергнута без изменения результата; следующий пакет принят | PASS |
| HW_BUFFER_REENTRY | Вложенный вызов во время штатной обработки отвергнут; текущий пакет обработан | PASS |
| HW_BUFFER_BOUNDS | Pointer на 17 элементов массива из 16 отклонён до вызова: entries=0 | PASS |
| HW_BUFFER_UNCONSUMED | Пакет записан в буфер без вызова; ожидание его потребления неверно | намеренный FAIL |
| HW_BUFFER_EXCEPTION | Запись в буфер, затем заданное Python-исключение до вызова | намеренный ERROR |

Успешный вызов дополнен проверкой возврата, счётчиков, защитных слов вокруг буфера,
неизменности буфера опыта штатным путём и следующего штатного пакета. Вложенный вызов
выполняется на остановке внутри штатной обработки (`inside_handler`): это проверка
защиты от повторного входа, а не воспроизведение прерывания.

Все изменяемые данные лежат подряд в секции `.experiment` (76 байт): защитные слова,
буфер опыта, штатный буфер, длина и состояние обработчика. Сценарий сначала проверяет
отсутствие промежутков по адресам и размерам из ELF, затем снимает секцию целиком и
возвращает её в finally также при FAIL/ERROR; журнал сохраняет SHA-256 до и после.
Это восстановление данных, не возврат PC/стека во времени.

## Запуск

```powershell
python tests/buffer-consumption/run.py --host-only
python tests/buffer-consumption/run.py --toolchain <каталог-GCC> --renode <путь-к-Renode>
```

На Linux те же параметры. Host исполняет ту же обработку пакетов и модель флага
повторного входа, но не проверяет GDB call и Pointer. Настоящие memory/call проходят
штатный runner в Renode; каждый сценарий получает свежий ELF-сеанс, семёрка повторяется
дважды: 10 PASS, 2 ожидаемых FAIL, 2 ожидаемых ERROR. Артефакты — build/buffer-consumption/<UTC>/.

Анализ использует общие читатели result/records и проверяет целостность, полноту, ранний
отказ Pointer, порядок пакетов, возвраты, счётчики и восстановление. Исходные FAIL/ERROR
не переписываются; PASS кампании означает совпадение с ожидаемой матрицей.

## Границы DDTT

Свидетельство относится к software-buffer: реакции обработчика на подготовленные данные.
DMA не участвовал, поэтому работа DMA, передача владения буфером и остановка потока не
проверены. Прерывание, приём периферией и физический сигнал тоже исключены. Активный DMA
требует отдельного порядка: остановить поток, забрать буфер, подготовить данные, вернуть
владение и восстановить состояние. Поле observation фиксирует метод, пакеты, возвраты,
счётчики и исключённые слои; это соглашение примера, не новая схема runner.
