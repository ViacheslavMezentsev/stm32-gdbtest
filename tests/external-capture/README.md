# Совместный захват с подставным внешним источником

[TECH-026](../../docs/ru/TESTING_TECHNIQUES.md#tech-026) · [English](README.en.md)

Автономный host-пример протокола захвата и анализа, без MCU, GDB, Renode и изменений
ядра. Сценарий здесь — явно заданная host-модель, не выполненный @case модуля.
Отдельный Python-процесс источника получает только run/revision и выдаёт свой
предзаданный поток. Он не читает результаты сценария. Оба потока синтетические:
это проверка связи/доставки, а не независимой точности датчика.

## Маршрут

1. Создать новый каталог, идентичность опыта и копию входных исходников с SHA-256.
2. Запустить собственный источник, дождаться READY (до 3 с).
3. Только после READY открыть окно; записать результат host-модели сценария.
4. Прочитать внешний поток до EOF, дождаться процесса (до 2 с на фазу захвата).
5. При зависании завершить только свой процесс; дождаться выхода и reader, сохранить
   исходные байты, stderr, exit code и состояние очистки. Источник не создаёт потомков.
6. Прочитать сохранённые файлы отдельным анализатором: полнота → идентичность →
   временная применимость → согласованность значений. Исходный сценарий не изменять.

`capture.status=COMPLETE` означает успешное завершение транспорта до EOF, а не
полноту прикладного журнала: даже exit code 0 требует end-маркера, точного состава
каналов, номеров и количества. Смерть процесса и повреждённый JSON сохраняются.
При отсутствии READY сценарий NOT_RUN; при потере записи после окна сценарий может
остаться PASS, а анализ даст UNKNOWN. Очистка проверяется отдельно.

## Данные и время

Ожидаются три записи channel=signal, unit=unit, seq=0/1/2; значения 10/20/30.
Host-модель хранит тики 10/20/30. Источник хранит 1010/1020/1030.
Две **заданные моделью** временные опоры (0↔1000, 40↔1040) задают offset=1000;
неопределённость ±1 модельный тик, допуск сопоставления ±2 тика. Это не измеренная
синхронизация часов устройств и не привязка source_tick к perf_counter_ns.
Монотонные часы ПК подтверждают только READY ≤ начало окна ≤ закрытие захвата.

Временное утверждение PASS, если весь интервал неопределённости помещается в допуск;
FAIL — если интервал целиком вне допуска; пересечение границы даёт UNKNOWN.
Неизвестные опоры/слишком большая неопределённость дают UNKNOWN до сравнения значений.
В реальном адаптере нужны подтверждённые опоры, дрейф, единицы, эпоха и разрешение часов.
Предзаданный offset этого примера нельзя выдавать за калибровку реального стенда.

## Независимые исходы

| Случай | Сценарий | Анализ |
| --- | --- | --- |
| Полная согласованная запись и повтор после отказных случаев | PASS | PASS |
| Пропуск, дубль, перестановка, нет end, повреждение JSON | PASS | UNKNOWN |
| Другой run/revision/канал/единицы | PASS | UNKNOWN |
| Непригодные часы или пересечение временной границы | PASS | UNKNOWN |
| Полная запись с неверным значением | PASS | FAIL |
| Полная запись с временем заведомо вне допуска | PASS | FAIL |
| Нет READY | NOT_RUN | UNKNOWN |
| Таймаут после READY | PASS | UNKNOWN |
| Отказ host-модели сценария | FAIL | UNKNOWN |

Матрица содержит 19 опытов: два PASS, два FAIL и 15 UNKNOWN **анализа**. Кампания
успешна, только если совпали и вердикты, и причины, сценарий сохранён и cleanup VERIFIED.
Это не означает 19 успешных прикладных проверок. Исходные отрицательные данные остаются.
Границы и ожидания заданы до запуска; неверное значение не исправляется анализатором.

## Запуск и повторный анализ

```sh
python tests/external-capture/run.py
python tests/external-capture/analysis.py build/external-capture/<campaign>/normal
```

Только Python 3.11+, без сторонних библиотек. `--output <новая-папка>` задаёт каталог
кампании; существующий каталог не перезаписывается. По умолчанию build/external-capture.
Анализатор: exit 0=PASS, 1=FAIL, 2=UNKNOWN; run.py: 0=совпала вся матрица, 1=расхождение.

Для каждого опыта: manifest.json, scenario.json, capture.json, external.jsonl,
source.stderr, analysis.json, sha256.json. Это **локальные учебные форматы**, не
новая публичная схема result/records. analysis.py повторно читает артефакты и проверяет
их хеши, если sha256.json присутствует; хеши обнаруживают изменение, но не подписывают
происхождение и не защищают от одновременной подмены данных и перечня хешей.
Сырые файлы и статус сценария не переписываются. run.py сохраняет также входы и summary.

## Перенос в проект и API

- Координатор запускается на host вне главного потока GDB. Не вставляйте ожидание pipe
  или subprocess в тело async-сценария: оно блокирует обработку событий GDB.
- Перед resume(sync=False) приёмник должен быть готов; await wait()/halt() управляют
  целью, но сами не подтверждают полноту внешнего захвата. После окна нужен drain/EOF.
- record сохраняет связь с внешней записью (идентичность, канал, хеш, эпоха), а не
  автоматически импортирует её. Для штатного сохранения records нужен capture=true.
- Отсутствующие данные — UNKNOWN анализа, не нулевое измерение и не skip вместо FAIL.
  При блокировке DDTT затрагиваются только утверждения, зависящие от этих свидетельств.
- Не подгоняйте часы по ожидаемому результату; подтверждайте погрешность отдельно.
- ROS/rosbag, MCAP Android и радиоимитатор пока не подключены. Их адаптеры должны
  привести реальные данные к явному контракту каналов/времени/происхождения.

Этот пример не подтверждает восстановление MCU, пригодность физической лаборатории,
работу GDB live-окна или реальных форматов захвата. Это следующий отдельный этап.

## Проверка

27.10.2026: Windows/Linux — 19/19 ожидаемых исходов, повтор после отказных случаев,
cleanup VERIFIED. Host-регрессии проверяют полный интервал погрешности, готовность,
неизменность исходных файлов и обнаружение подмены по хешам. Сценарная host-модель
действительно сравнивает три результата масштабирования с заданными ожиданиями;
её отдельный отказ сохраняется и блокирует анализ, а не выдаётся за аппаратный FAIL.
