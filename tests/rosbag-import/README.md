# Офлайн-импорт ROS1 bag v2 (A6)

[TECH-026](../../docs/ru/TESTING_TECHNIQUES.md#tech-026) · [English](README.en.md)

Первый реальный адаптер внешних свидетельств: сохранённая запись ROS1 bag v2
переводится в нейтральный набор каналов и выборок, а отдельный анализ решает,
можно ли связать её со снимком отладчика. Новый захват, MCU, GDB и Renode не нужны;
модуль `stm32_gdbtest` не изменяется. Только Python 3.11+, без сторонних библиотек.

## Состав

| Файл | Роль |
| --- | --- |
| `rosbag1.py` | Строгий читатель bag v2: несжатые и bz2-чанки, сверка с индексом, std_msgs |
| `importer.py` | Адаптер формата: топик → канал с объявленными единицами, время записи с явным источником |
| `analysis.py` | Отдельный вердикт: полнота → идентичность → часы → каналы → опоры → момент GDB → значения |
| `fixture.py` | Синтетическая bag v2 для CI и её повреждённые копии |
| `run.py` | Синтетическая кампания или локальный импорт реальной записи |

Читатель не возвращает частичных данных: обрыв файла, `index_pos=0` (запись не
закрыта), расхождение chunk info/index data с сообщениями, неизвестное сжатие
(в том числе lz4) или лишние байты сообщения дают `import_invalid` с причиной.
Тип расшифровывается только при точном совпадении имени и md5 определения;
иначе канал остаётся нерасшифрованным, и сравнение с ним невозможно.

## Время

`ros1_record_time` — время приёма сообщения хостом записи (unix, нс). Это не часы МК и
не момент чтения GDB; часы хоста записи и ПК со сценарием могут быть разными.
Опоры строятся анализом по каналу-счётчику МК (например, uptime в секундах,
тот же источник тиков, что и снимок отладчика). Переход k−1 → k даёт интервал
(последний приём k−1, первый приём k). Момент снимка с тиком T, k = ⌊T/1000⌋, лежит в
`[последний приём k − задержка, первый приём k+1]`. Без обоих переходов в одном
сегменте — `moment_outside_anchors`; убывание счётчика (сброс) начинает новый
сегмент, совпадение в нескольких сегментах — `moment_ambiguous`.

Задержка доставки должна быть ограничена: `basis=measured` для реальной записи,
`fixture` только для синтетики. Предположенная задержка (`assumed`) даёт `clock_assumed`
даже при совпадении значений. Последовательные выборки rostopic в records не считаются
одновременными между собой или совпадающими с bag и в анализе не используются.

## Значения

Канал согласован, если все выборки, принятые в интервале возможного момента
(плюс задержка), совпадают со снимком в допуске; все вне допуска — FAIL; смешанно —
`time_boundary`. Повторяющееся постоянное значение не считается дублем.
ROS и GDB читают одно состояние прошивки: согласие двух транспортов — проверка
доставки и времени, а не независимое измерение (`independence=same_firmware_state`).

## Синтетическая кампания

```sh
python tests/rosbag-import/run.py
python tests/rosbag-import/analysis.py build/rosbag-import/<campaign>/normal
```

23 опыта, ожидания заданы до запуска: три PASS (несжатая, bz2, повтор), один FAIL
(значение вне допуска при полной временной определённости) и 19 UNKNOWN анализа.

| Причина | Опыты |
| --- | --- |
| `import_invalid` | обрыв файла, без индекса, расхождение индекса, lz4 |
| `channel_contract` | другой тип, чужая md5, переименованный топик, другие единицы |
| `nonfinite_value` | NaN в сравниваемом канале |
| `identity` | другой опыт в метаданных, другое число сообщений |
| `clock_shift` | время bag вне окна record |
| `clock_unqualified`, `clock_assumed` | нет счётчика МК; задержка не измерена |
| `moment_outside_anchors` | остановка отладчиком, затем сброс: перехода k+1 нет |
| `moment_ambiguous` | сброс: тот же тик в двух сегментах |
| `time_boundary` | значение меняется внутри интервала |
| `snapshot_missing`, `scenario_not_pass` | нет снимка; сценарий не PASS |

Каждый опыт сохраняет `source.bag`, `manifest.json`, `import.json`, `samples.jsonl`,
`capture.json`, `scenario.json`, `records.json`, `analysis.json` и `sha256.json`.
Повторный анализ читает только файлы и проверяет хеши. Анализатор: exit 0=PASS,
1=FAIL, 2=UNKNOWN; run.py: 0, если совпала вся матрица.

## Реальная запись

```sh
python tests/rosbag-import/run.py --bag <rec>.bag --capture <rec>.json \
  --result <ddtt>/result.json --records <ddtt>/records.json --contract <local-contract>.json
```

Контракт (каналы, единицы, допуски, опора и ожидаемый исход) и сами данные остаются
локальными; из метаданных в `capture.json` переносятся только опыт, окно record и
сводка bag, без порта и серийных номеров. Исходные файлы только читаются.

Проверено 28.10.2026 на записи телеметрии F411 (Windows и Linux): 63 канала и
13 776 сообщений импортированы полностью, сводка совпала с метаданными. Найдены два
сегмента (сброс при завершении сеанса) и пауза 13,8 с — цель остановлена отладчиком.
Снимок GDB взят на тике 27 044 мс, после последнего перехода 26 с; перехода 27 → 28
до сброса нет, поэтому итог `UNKNOWN moment_outside_anchors`. Это ожидаемая граница:
без публикаций после чтения момент снимка не привязан к времени bag, а задержка
доставки не измерялась. Числа «отладчик минус ROS» в records этим анализом не подтверждаются.

## Границы

MCAP Android и радиоимитатор — следующие источники; нейтральный формат каналов и
выборок рассчитан на их подключение, но адаптеры не реализованы. Физическая
синхронизация часов, измерение задержки и пригодность DDTT по реальной записи требуют
отдельного опыта. Учебные JSON — локальный формат примера, не публичная схема result.
