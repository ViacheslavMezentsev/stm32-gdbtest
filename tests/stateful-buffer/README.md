# Остаточное состояние и порядок событий в кольце

[Документация](../../docs/ru/index.md) · [English](README.en.md)

Нейтральный пример TECH-021 для **0.5.x / API 3**, без платы и периферийных моделей.
Один C++-модуль используется на host и Cortex-M3 в Renode. Инициализированный POD-объект
не содержит указателей; Python вызывает реальные функции через `Target.call`, сохраняет
его по размеру ELF и восстанавливает полным обратным чтением даже после FAIL.
Это учебная прошивка, не добавление тестовых hooks в приложение потребителя.

## Что проверяется

| Сценарий | Действие и независимое ожидание |
| --- | --- |
| HW_EMU_NEXT_COMPLETE | Пакет длины 3, затем длины 2 без reset: две публикации, точные байты второго |
| HW_EMU_NEXT_TIMEOUT | Частичный пакет, expire, новый пакет: одна публикация без старого хвоста |
| HW_EMU_RING_ORDER | Переход кольца через границу, RX-ошибка при TX, kick до/после complete, повтор complete: точный выход без дублей; новый enqueue не расширяет уже начатый сегмент |

Host дополнительно проверяет отказ при заполненной очереди. Таймаут — событие expire,
а не измерение длительности; complete — явное событие, не реальный IRQ/DMA.
Эта последовательность не доказывает отсутствие всех гонок, барьеры памяти или RTOS-безопасность.
Кольцо рассчитано на одного владельца; физическая передача и CRC здесь не моделируются.

## Воспроизводимый маршрут

Из корня репозитория (g++ должен быть в PATH):

```powershell
python tests/stateful-buffer/run.py --host-only
python tests/stateful-buffer/run.py --toolchain "$HOME/xpack-arm-none-eabi-gcc-14.2.1-1.1" --renode "C:/Program Files/Renode/renode.exe"
```

Linux, с установленными теми же инструментами:

```bash
python3 tests/stateful-buffer/run.py --toolchain /opt/xpack-arm-none-eabi-gcc-14.2.1-1.1 --renode /opt/renode-1.17.0/renode
```

`--host-cxx` выбирает host-компилятор. Нужны Python 3.11+, GDB с Python, ARM GCC и Renode 1.17.
Windows Docker: снимок исходников и сборки в одном volume по [локальному CI](../../docs/guides/ru/local-ci.md).
Runner использует выделенный Renode, не подключается к имеющемуся endpoint; ограничение
слушающего GDB-порта Renode описано в [backend](../../docs/guides/ru/RENODE.md).

## Красный контроль, исправление, повтор

`DEFECT=1` оставляет used после полного пакета/expire; `DEFECT=2` разрешает kick менять
уже начатый сегмент. `DEFECT=0` — исправленный алгоритм. Host запускает все три варианта.
Renode запускает одинаковые три сценария на вариантах 1, 2, 0, 0: **12 ожидаемых исходов**,
из них 3 намеренных FAIL. Кампания успешна только при точном составе сценариев, ожидаемом
имени упавшей проверки, сохранённом capture, восстановлении и cleanup VERIFIED.
Намеренный FAIL не переписывается в PASS; PASS summary означает совпадение с матрицей.

В `build/stateful-buffer/<id>` сохраняются исходные входы и SHA-256, журналы сборки/версий,
ELF, result/records каждого сценария и summary.json. Команда возвращает 0 при совпадении
всей матрицы; иначе 1 с сохранённым ERROR/FAIL. Прерванную кампанию нельзя считать PASS.
Повтор исправленного варианта проверяет повторяемость и освобождение своих процессов.
Восстановление относится только к объекту модели; уничтожение эмулятора не доказывает recovery MCU.

## Перенос в проект

Замените учебные ожидания требованиями проекта, подтвердите владение объектом, callbacks
и буферами. Добавьте реальные регистры только через MMIO/SVD и отдельный допуск стенда.
Сначала подтвердите исходный FAIL, затем исправление и соседние случаи тем же сценарием.
[Техника](../../docs/ru/TESTING_TECHNIQUES.md#tech-021), [DDTT](../../docs/ru/DDTT.md#consumer-feedback).

Проверено 27.10.2026: host Windows/Linux, Renode 1.17 Windows/Linux с xPack GCC/GDB 14.2.1 / 15.2.90. На каждой ОС — 12/12 ожидаемых исходов, 3 намеренных FAIL, сохранённый capture и восстановление объекта. Это не аппаратная проверка.
