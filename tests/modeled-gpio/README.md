# Моделируемый GPIO: воздействие и границы override

[English](README.en.md) · [MMIO](../../docs/ru/api/mmio.md)

Нейтральный исполняемый пример A5.2 для API 3. Ядро модуля и платы не меняются.
Это диагностический GDB probe, а не новый API инъекции и не штатный сценарий `@case`.
Все обращения GDB выполняются в главном потоке. Используется проверенная внешняя
обвязка `tools/renode_probe.py`: штатный backend Renode намеренно не загружает
произвольные PythonPeripheral из платформы.

## Маршрут свидетельства

Внешний источник → вход учебной модели GPIO → volatile-чтение IDR прошивкой →
публикация raw/active/neighbour/samples → независимый анализ.

Внешний файл `stimulus.json` не отображён в память MCU. Он обновляется атомарно
при остановленном ядре; модель применяет новое поколение на следующем обращении.
Это дискретная модель двух входов, **не модель STM32 GPIO**, не электрический
сигнал, не доказательство времени реакции, дребезга, EXTI, DMA или подтяжек.
Физическое воздействие и конкретный MCU требуют отдельного аппаратного опыта.

## Проверки

| Воздействие | Независимое ожидание |
| --- | --- |
| IDR read-only, в том числе с reason | write_denied, ноль callbacks модели |
| override без reason | отказ, ноль callbacks |
| override с read-write и reason | один W callback, ACK, verified=false; модель игнорирует запись |
| Ложное утверждение «override поднял вход» | отдельный исходный FAIL: ожидание 1, потреблено 0 |
| Внешние уровни 2, 3, 3, 2, 3, 2 | шесть чтений прошивкой, active 0/1/1/0/1/0, соседний бит всегда 1 |
| Штатное завершение и исключение до resume | весь POD 16 байт и входы возвращены, проверено чтением |

IDR этой модели безопасен для повторного чтения. Не переносите этот приём
на read-to-clear/FIFO без анализа эффектов. `override` заменяет описание доступа,
но не права и физику устройства. ACK и совпадение readback не доказывают потребление.
Поколение стимула монотонно растёт; восстановление означает возврат уровней, а не
откат истории внешнего источника.

## Запуск

```powershell
python -m unittest discover -s tests/host -p test_modeled_gpio.py
python tests/modeled-gpio/run.py --toolchain <toolchain-root> --renode <renode-executable>
```

Linux: те же команды с `python3`; пример Renode 1.17.0 —
`--toolchain /opt/xpack-arm-none-eabi-gcc-14.2.1-1.1 --renode /opt/renode-1.17.0/renode`.
Нужны ARM GCC/GDB с Python, Renode 1.17 и host g++ для проверки общего C++ обработчика.
Для Docker соблюдайте [локальный CI](../../docs/ru/local-ci.md): исходники и сборки в volume.

В `build/modeled-gpio/<run>/`: входы и SHA-256, ELF, версии GCC/GDB, команда сборки,
`accesses.jsonl` независимой модели, лог Renode с версией, GDB log;
в `runs/probe-*/` — observations, checks, result, negative-control и штатный capture
с `records.json`. Читатель capture проверяется при сохранении.
`result.status=PASS` означает совпадение **анализа** с ожиданиями, включая отдельный
`negative-control.status=FAIL`; не превращайте его в успешную проверку ложного утверждения.
Launcher ограничивает время и завершает только свой процесс Renode; процессная очистка
фиксируется отдельно от восстановления ресурсов модели.

Host проверяет общий C++ обработчик, модель, отказные входы и анализ неполных/ложных
свидетельств. Только Renode проверяет настоящий GDB/RSP и чтение MCU-моделью.
Первичный ERROR при отсутствии UTF-8 coding header у PythonPeripheral сохранён локально;
модель содержит явный header для IronPython. Повторять опыт увеличением таймаутов не требуется.
