# Правила для агентов и разработчиков

- Сначала читать README.md, docs/API.md, docs/TEST_AUTHORING.md и TODO.md.
- Это ядро инфраструктуры. MCU/плата/ожидания, приборы и тесты приложения — в проекте
  потребителя. Fixtures не являются рабочими HW-профилями и доказательствами HAL.
- Не добавлять тестовые hooks в firmware. -g3 не сохраняет неиспользуемые функции.
- GDB API вызывать только из основного потока; сохранять внешний timeout и recovery.
- Сборка/host PASS не означают HW PASS. Фиксировать точные MCU/HAL/GDB/backend,
  ELF/manifest, влияние halt/reset и границы доказательства.
- Перед HW запуском назвать плату, отладчик, backend и соединения; смена стенда
  требует подтверждения владельца. Не выводить разводку из USB enumeration.
- Не включать mass erase, option bytes, firmware update отладчика, shared mode
  или Flash breakpoints автоматически. Восстановить оговорённую прошивку/состояние.
- Не запускать сторонний сервер параллельно на том же отладчике. Mutex координирует
  только участвующие runner одной Windows-сессии; после crash проверить orphan processes.
- Все изменения/temp/логи внутри текущего разрешённого workspace. Подмодули,
  установленные библиотеки и инструменты читать/запускать, не менять без задачи.
- Не коммитить local TOML/serial, абсолютные персональные пути, ELF/build/cache.
- Развивать host-тесты для отказов до аппаратного доступа. Базовая проверка:
  python -B -m unittest discover -s Tests/host -v; пример собирать через presets,
  ctest --preset offline. Полный ctest примера прошивает MCU — запускать осознанно.
- Меняя интерфейс, обновлять docs/API.md, CHANGELOG.md, TODO.md и миграцию.
  Источник версии — stm32_gdbtest/__init__.py; правила в docs/VERSIONING.md.
- Ветки codex/...; локальные коммиты допустимы. Push/release/tag публикацию выполняет
  владелец по согласованному этапу. Не считать создание remote/release разрешённым
  только потому, что это упомянуто в дорожной карте.
- В русских текстах использовать «отладчик». Не скрывать ERROR и причины отказов.
