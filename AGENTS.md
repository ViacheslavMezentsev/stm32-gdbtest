# AGENTS.md

Инструкция для ИИ-агентов и новых участников проекта **stm32-gdbtest**.
Instructions for AI agents and new contributors ([English](docs/en/maintenance.md#working-with-the-project)).

Порядок ознакомления, рабочий цикл, правила веток, коммитов, ТЗ и двуязычной
документации описаны в [docs/ru/maintenance.md → «Порядок работы с проектом»](docs/ru/maintenance.md#порядок-работы-с-проектом).
Начните с него. При проблеме с git, стендом, отладчиком или Docker сначала загляните
в [памятку](docs/ru/HOWTO.md) ([English](docs/en/HOWTO.md)) и только потом ищите новое решение.

Кратко:

1. Прочитайте [README](README.md), затем раздел «Текущее состояние» и «Ближайшие шаги» в [TODO.md](TODO.md).
   Последние изменения — раздел `[Unreleased]` и последний выпуск в [CHANGELOG](CHANGELOG.md).
2. Метод, который реализует модуль, — [спецификация DDTT](docs/ru/DDTT.md) ([English](docs/en/DDTT.md)).
   Требования — два ТЗ, только на русском: [общее](docs/TECHNICAL_SPECIFICATION.md) (runner, стенды,
   образы, CMake, CI) и [ТЗ API сценариев](docs/TECHNICAL_SPECIFICATION_API.md) (методы `Target`).
   В каждом смотрите реквизиты (текущая ревизия), блок изменений последней ревизии и раздел вопросов
   и решений владельца. Копии ТЗ вне репозитория не ведутся.
3. Сценарии пишутся по API 0.3.0: [справочник методов](docs/ru/api/index.md) и
   [каталог техник со стилем сценариев](docs/ru/TESTING_TECHNIQUES.md). Стиль проверяет тест
   `tests/host/test_scenario_style.py`; образцы — `tests/firmware/common/tests` (девять сценариев-примеров)
   и `tests/firmware/profiles/*/tests`. Что и на каких стендах принято — [API_ACCEPTANCE](docs/ru/API_ACCEPTANCE.md).
   Навыки для агентов проектов-потребителей — [skills](skills/README.md); правило сценариев меняется сначала
   в каталоге техник и тесте стиля, затем в навыке.
4. Работайте в ветке `<агент>/<задача>` от актуального main; префикс — имя
   создающего ветку агента или участника (`claude/`, `codex/`, `gemini/`, `dev/`, …).
   PR не используются: проверенная ветка сливается в main перемоткой (`git land`,
   [памятка](docs/ru/HOWTO.md#git-рабочий-цикл-без-pr)), после чего удаляется.
5. Изменение поведения или интерфейса — с host-регрессией, обновлением docs/ru/API.md и docs/en/API.md,
   карточки справочника `docs/*/api` и миграции, записью в CHANGELOG (RU и EN) и новой ревизией ТЗ
   (общего или ТЗ API — по месту требования). Проверки до
   GDB-сервера — по [единому руководству локального CI](docs/ru/local-ci.md): прочитайте его
   до запуска. На Windows исходники и сборки размещайте в одном Docker volume; bind mount
   используйте только для передачи архива. Выберите docs/host/матрицу по изменению,
   сохраняйте exit code и отчёты даже при ошибке; не увеличивайте таймауты вместо исправления I/O.
   Агент готовит ветку и подписанные коммиты, владелец пушит каждую ветку; после проверки CI
   последнего SHA владелец выполняет `git land`. Агент не сливает и не удаляет ветки без
   отдельного явного поручения на эти действия; локальный PASS не заменяет GitHub CI.
6. Коммиты — Conventional Commits на английском, подписанные ключом GitHub
   Signing Key, без ссылок на сессии агентов. Push, теги и релизы — владелец.
7. Документация ведётся на русском и английском, обе версии обновляются в одном
   коммите; ТЗ ведётся только на русском и не переводится.
8. Сборка и host PASS не означают HW PASS. Аппаратный запуск — только на
   согласованном стенде, без mass erase, option bytes и shared mode; ERROR не скрывать.
   Схемы запуска и их приёмка — [RUN_LAYOUTS](docs/ru/RUN_LAYOUTS.md) и [API_ACCEPTANCE](docs/ru/API_ACCEPTANCE.md).
9. MCU, платы, ожидания и тесты приложения — в проекте потребителя; тестовые
   hooks в прошивку не добавлять; GDB API — только из основного потока GDB.
10. Не коммитить локальные TOML стендов, серийные номера, персональные пути,
    ELF, build и кэши.
11. Новое решение частой проблемы (команда git, настройка стенда, окно J-Link и т. п.)
    записывается в памятку `docs/ru|en/HOWTO.md` в том же коммите.

12. Перед исследованием прочитайте раздел [«Проведение исследований»](#проведение-исследований)
    ниже; он определяет порядок ознакомления, хранения материалов и фиксации результатов.

Собственные новые каталоги — lowercase; профили/примеры — `tests`. Имена стороннего кода сохранять. Локальные удалённые стенды — `<profile>-<backend>.remote.toml` (gitignored); подробности и совместимость — в maintenance.

## Проведение исследований

1. До планирования или продолжения опытов прочитайте локальный `docs/research/README.md`
   (English: `README.en.md` в той же папке), затем план, сводку и последний отчёт нужного
   исследования. Последовательность результатов и ссылки на отчёты — в локальном
   `docs/research/HISTORY.md` (English: `HISTORY.en.md`); новые записи сверху.
   Если локальных материалов нет, явно укажите пробел; не считайте прежние результаты проверенными.
2. Материалы храните только локально в `docs/research/<research-id>/`: минимум `ru/`, `en/`,
   `results/`. Прототипы — в исключённых `tests/dev-*`. Проверяйте `.gitignore`; не используйте
   принудительное добавление в Git. Названия новых каталогов — lowercase-kebab-case.
   Правила песочницы кода — раздел 2.1 локального README: явные команды запуска, связь с отчётами,
   снимки проверенных исходников перед изменением; без автоматического включения в штатные тесты/CI.
3. Для новых исследований используйте `plan.md`, `verification.md`, `results.md` в обеих
   локализациях; для этапа — `<stage>-plan.md` и `<stage>-results.md`. Вопросы и отложенное —
   `questions.md` и `technical-debt.md`. Сохраняйте исторические имена и указывайте их в карте документов.
4. До запуска фиксируйте ожидаемые исходы и условия; после — фактические результаты, версии,
   хеши прототипов/входов, логи и ограничения. Не перезаписывайте исходные FAIL/ERROR после исправлений.
   Host PASS не заменяет HW PASS; аппаратные опыты и восстановление — по правилам проекта.
5. После каждого этапа обновляйте обе локализации отчёта, сводку, матрицу, вопросы и локальный
   историю исследований: дата, краткое изменение и ссылки на выходные артефакты, без версии кода.
   Сообщайте результат и следующий шаг. Наблюдение, предложение и принятое решение
   различайте явно. Перенос экспериментального API в ядро требует отдельного согласования.
6. В публичных документах оставляйте принятые результаты без ссылок на локальные материалы.
   Пути выше — соглашение о локальном хранении, не ссылки на поставляемые документы.
   В выпускной ветке обязательна проверка `docs.public` через `python ci/run_checks.py docs`.
