# Нейтральный пример допуска DDTT

[English](README.en.md) · [Контракт](../../docs/ru/DDTT_QUALIFICATION.md)

```powershell
python examples/ddtt-qualification/run.py --out build/qualification-demo
```

Используйте новый каталог. Откройте index.html: десять синтетических случаев, сырой
исход и применимость. Каждый случай содержит map.json, snapshot.json, result.json,
admission.json (кроме missing), view/ddtt-evidence.json и lcov.info.

Это host-модель: ELF-хеш — явно синтетическая метка, частота не измерялась, никакая
плата не квалифицирована. 16 вместо 25 МГц даёт UNKNOWN для зависимого утверждения;
независимая ready остаётся CONFIRMED. raw-fail при верных условиях остаётся FAILED.
Потеря питания, конфликт, устаревание, другой экземпляр и декларация вместо измерения
не дают зелёной отметки. optional-absent показывает доказанную неприменимость опции.

fixture() показывает формат измерений и карты. bind() вызывается внешним организатором
после попытки; оригинальный результат не меняется. Для настоящего проекта нужны реальные
records/capture, измерительная цепочка, корректный inputs_sha256 и сохранённые входы.

## Renode: независимый журнал приёмника

`run_renode.py` собирает один нейтральный ELF и запускает штатный runner:
предварительный и основной прогоны для нормы, потери второго слова и повторной нормы.
Прошивка сообщает три отправки; PythonPeripheral независимо регистрирует принятые
слова. Сценарий читает только RAM отправителя, не журнал и не состояние приёмника.

```powershell
python examples/ddtt-qualification/run_renode.py `
  --cxx <toolchain>/bin/arm-none-eabi-g++.exe `
  --gdb <toolchain>/bin/arm-none-eabi-gdb-py3.exe `
  --renode <renode>/renode.exe --out build/qualification-renode/run-01
```

На Linux используются те же аргументы с Linux-путями без `.exe`. Выходной каталог
должен быть новым. Нужен Renode 1.17, ARM GCC и GDB с Python. Самодостаточный REPL
содержит скрипт модели; внешние файлы периферии backend не загружает.

Ожидание: исходный PASS во всех трёх случаях. При двух принятых словах зависимая
точка становится UNKNOWN/VIOLATED; инициализация остаётся CONFIRMED. Повторная норма
возвращает CONFIRMED. Это демонстрация **условия применимости**: проверка счётчика
отправок сама по себе не доказывает доставку. Карта явно добавляет требование к приёмнику.

В каждом каталоге сохраняются `preflight-receiver.jsonl`, `snapshot.json`, основной
`receiver.jsonl`, неизменённые `result.json`, `records.json`, `admission.json`, карта и
`view/lcov.info`, `view/ddtt-evidence.json`; общая сводка — `summary.json`. В ней
`result_unchanged` проверяется хешем до/после экспорта. Логи Renode фиксируют версию.

Снимок получен до основной попытки и действует 120 секунд. Это ограниченная гарантия
фиксированной детерминированной модели: после попытки журнал и хеши входов сверяются
повторно. Неизвестный/повреждённый журнал или изменившаяся модель останавливают опыт,
не создавая допуска. Эмулятор не измеряет реальный кварц, напряжение или доставку
по физическому проводу; прошивка приёмника, IRQ и DMA здесь не моделируются.
Это не непрерывный монитор физических условий и не аппаратная квалификация.


## Проектный маршрут records / [data]

Та же команда теперь выполняет четыре пары preflight/main: норма, потеря слова,
повторная норма и намеренный FAIL. Первые три main дают PASS; четвёртый сохраняет
FAIL, зависимую FAILED и независимую CONFIRMED. check() прекращает сценарий на FAIL,
поэтому независимая проверка и записи выполняются до отрицательного контроля.

Порядок: журнал preflight → snapshot.json → qualification.toml → session.toml
с `[data] qualification = "qualification.toml"` → t.profile.data → records.json →
проверка связи → admission.json → экспорт. Захват `[results] capture = true` обязателен.
Новый session.toml генерируется рядом с данными; относительный путь отсчитывается от него.

`snapshot_data.py` — код примера проекта, не новая функция Target. Он хранит в TOML
schema=1, snapshot_sha256 и snapshot_json (канонический JSON как строка). Это позволяет
без потерь передать null, вложенные таблицы и числа, сохраняя формат снимка schema 1.
Файл создаётся без перезаписи. Сценарий читает захваченную копию через
`t.profile.data['qualification']`, сверяет хеш JSON и записывает `qualification_input`:
полный снимок, snapshot_sha256 и SHA-256 TOML из `t.profile.files['data.qualification']`.
Это квитанция о получении условий, а не новое независимое измерение.

Организатор перед bind проверяет capture=saved, run_id, case_id, ровно одну запись,
полное совпадение снимка и обоих хешей. Отсутствие, чужая запись или конфликт прерывают
проектный маршрут до создания допуска. Сырые result.json и records.json не редактируются;
оба хеша сверяются после экспорта, фиксируются в summary.json. Недопустимое условие
не меняет PASS сценария; намеренный FAIL при допустимых условиях остаётся FAILED.

Это дополнительная проектная проверка: отдельный вызов экспортёра не запускает
verify_records автоматически. Хеши обеспечивают согласованность, не защиту от
намеренной подделки всех материалов. JSON внутри TOML — соглашение этого примера,
не новая обязательная схема [data] для всех проектов. Физическая квалификация остаётся
отдельным этапом; MCU, датчики и платы в этом опыте не проверялись.
